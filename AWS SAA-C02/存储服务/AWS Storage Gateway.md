# AWS Storage Gateway - 混合云存储网关

> **AWS Storage Gateway** 是混合云存储服务，通过部署在本地的网关设备，让本地应用像访问本地存储一样**持续、实时**地访问 AWS 云存储，同时提供本地缓存以获得低延迟访问。与一次性迁移的 [[AWS Snowball]]、批量同步的 [[AWS DataSync]] 不同，Storage Gateway 面向的是**长期在线**的混合云集成场景。
>
> 相关文档：[[AWS DataSync]] | [[AWS Snowball]] | [[S3 - Object Storage]] | [[块储存 - EBS]] | [[S3 Glacier Archive]]

---

## 核心概念

### 混合云集成的定位（考试要点）

| 方案 | 访问模式 | 是否持续在线 | 适用场景 |
|------|---------|------------|---------|
| **AWS Storage Gateway** | 本地应用**持续、实时**读写，通过网关透明访问云存储 | **是**，长期运行的网关服务 | 本地应用无需改造即可使用云存储，且需要本地低延迟缓存 |
| [[AWS DataSync]] | 批量/计划任务的数据**传输** | 按计划任务运行，非持续在线服务 | 有网络带宽，需要定期/持续同步文件到云端 |
| [[AWS Snowball]] | 物理设备**一次性**运输 | 否 | 数据量巨大、网络不可用或成本过高的一次性迁移 |

> **考试陷阱**：题目描述"本地应用需要**像访问本地磁盘/文件共享一样**持续访问云存储，且不希望改造应用逻辑"→ **Storage Gateway**；若题目描述"定期把文件**同步**到云端"（一次性/批量任务而非持续在线的存储接口）→ **DataSync**。

### 核心价值

- **无需改造应用**：本地应用继续使用熟悉的协议（iSCSI、NFS、SMB、VTL）访问网关，网关在背后透明地与 AWS 存储服务交互
- **本地缓存加速**：网关在本地保留**热数据缓存**，最近访问的数据可本地低延迟读取，冷数据存储在云端降低本地存储成本
- **无缝扩展云存储的弹性和持久性**：本地存储容量不再是瓶颈，数据实际持久化在 AWS（S3、EBS、Glacier 等）

## 三种网关模式（考试高频）

| 网关类型 | 协议 | 云端存储 | 典型场景 |
|---------|------|---------|---------|
| **文件网关（File Gateway）** | NFS / SMB | [[S3 - Object Storage]]（对象直接以文件形式存取） | 需要通过文件协议访问 S3 中的对象，如内容仓库、数据湖前端 |
| **卷网关（Volume Gateway）** | iSCSI | [[块储存 - EBS]] 快照（存储在 S3，以 EBS 快照格式管理） | 本地服务器需要块存储卷，同时希望云端保留备份/快照 |
| **磁带网关（Tape Gateway）** | iSCSI-VTL（虚拟磁带库） | [[S3 Glacier Archive]] | 替代物理磁带备份，兼容现有备份软件（NetBackup、Veeam 等） |

### 卷网关的两种子模式

| 子模式 | 数据存放位置 | 特点 |
|--------|------------|------|
| **缓存卷（Cached Volumes）** | 主数据存储在 S3，本地只保留**热数据缓存** | 本地存储需求小，适合本地存储空间有限但数据总量大的场景 |
| **存储卷（Stored Volumes）** | 主数据存储在**本地**，异步**备份快照**到 S3 | 本地需要完整数据副本以获得最低延迟，云端仅作为灾备 |

> **考试陷阱**：**缓存卷**关注"节省本地存储空间，主数据在云端"；**存储卷**关注"本地保留全量数据，云端只是异步备份"——两者极易在场景题中被调换考察，需要根据"本地存储容量是否充足"这一关键描述来判断。

## 部署方式

- **虚拟机镜像**：VMware ESXi、Microsoft Hyper-V、KVM，部署在本地数据中心
- **硬件设备**：Storage Gateway Hardware Appliance，适合没有虚拟化环境的本地站点
- **EC2 实例**：也可部署在 AWS 云端（如作为跨区域/跨账户的存储代理），并非只能部署在本地

## 安全性

| 机制 | 说明 |
|------|------|
| **传输加密** | 网关与 AWS 之间的数据传输使用 **SSL/TLS** 加密 |
| **静态加密** | 数据在 S3/EBS/Glacier 落地后使用 **SSE**（默认 AES-256），可选 [[KMS]] 管理密钥 |
| **IAM 权限控制** | 通过 IAM 角色控制网关对 S3/EBS 等资源的访问权限 |
| **本地访问控制** | 卷网关/磁带网关可配置 CHAP 身份验证，限制哪些本地发起方（Initiator）可连接 iSCSI 目标 |

## 典型应用场景

| 场景 | 推荐网关类型 |
|------|------------|
| **本地应用需要通过文件协议访问 S3 中的对象** | 文件网关 |
| **本地服务器需要块存储卷，且本地空间有限** | 卷网关（缓存卷模式） |
| **本地需要完整数据副本，云端仅做灾备** | 卷网关（存储卷模式） |
| **替代物理磁带库做长期归档备份** | 磁带网关 |
| **数据湖前端需要文件系统接口写入 S3** | 文件网关 |
| **持续增量同步文件到云端（非持续在线访问）** | 改用 [[AWS DataSync]]，而非 Storage Gateway |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：让本地应用持续、透明地访问云存储，而非一次性迁移或批量同步
2. **三种网关类型**：文件网关（NFS/SMB→S3）、卷网关（iSCSI→EBS 快照）、磁带网关（VTL→Glacier）
3. **卷网关两种子模式**：缓存卷（主数据在云端，本地缓存热数据）vs 存储卷（主数据在本地，云端异步备份）
4. **Storage Gateway vs DataSync**：持续在线的存储接口用 Storage Gateway；批量/计划任务的文件同步用 DataSync
5. **Storage Gateway vs Snowball**：长期混合云集成用 Storage Gateway；一次性大规模迁移用 Snowball
6. **磁带网关是物理磁带库的云端替代**：兼容主流备份软件，无需更换现有备份流程
7. **本地无需改造应用**：网关对应用透明，应用仍使用标准的 NFS/SMB/iSCSI 协议
8. **部署位置灵活**：不仅可部署在本地（VM/硬件设备），也可部署在 EC2
9. **传输和静态数据均加密**：SSL/TLS 传输 + S3/EBS 端的 SSE 静态加密
10. **文件网关落地对象仍是标准 S3 对象**：可被其他 AWS 服务（如 CloudFront、Lambda 事件）直接访问和处理

### 场景题解题思路

```
场景分析 → 选择 Storage Gateway 类型
├── "本地应用需通过 NFS/SMB 持续访问 S3 中的文件" → 文件网关
├── "本地服务器需要块存储卷，本地空间有限" → 卷网关（缓存卷）
├── "本地需要完整数据副本，云端仅备份" → 卷网关（存储卷）
├── "需要替代物理磁带库做长期归档" → 磁带网关
├── "只是定期同步文件到云端，不需要持续在线的存储接口" → 改用 AWS DataSync
├── "数据量巨大或网络不可用，需要一次性迁移" → 改用 AWS Snowball
└── "本地无虚拟化环境，需要专用硬件" → Storage Gateway 硬件设备
```

## 最佳实践

1. **按访问协议选择网关类型**：文件类工作负载用文件网关，块存储用卷网关，磁带备份场景用磁带网关
2. **本地存储有限时优先缓存卷模式**：让云端承担主数据存储压力
3. **对延迟极敏感的场景使用存储卷模式**：本地保留全量数据，云端仅作异步灾备
4. **持续在线访问用 Storage Gateway，批量同步任务用 DataSync**：不要混用两者的适用场景
5. **启用 CHAP 身份验证**：限制卷网关/磁带网关的 iSCSI 连接来源
6. **静态数据启用 KMS 加密**：涉及敏感数据的网关应使用自定义 KMS 密钥而非默认 SSE-S3
7. **磁带网关迁移前评估备份软件兼容性**：确认现有备份软件支持 VTL 接口
