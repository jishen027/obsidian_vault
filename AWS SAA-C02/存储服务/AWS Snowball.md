# AWS Snowball - 物理数据迁移

> **AWS Snowball** 是 AWS Snow 家族的核心成员，通过**物理存储设备**在本地环境与 AWS 之间安全地迁移大规模（TB 到 PB 级）数据，专为网络带宽受限或成本过高的场景设计。
>
> 相关文档：[[存储服务 - Storage Service]] | [[AWS DataSync]] | [[AWS Storage Gateway]] | [[S3 - Object Storage]] | [[块储存 - EBS]] | [[文件储存 - AWS EFS]] | [[KMS]]

---

## 核心概念

### 为什么需要物理迁移

- 网络传输大规模数据存在**时间和成本瓶颈**：以 10 MB/s 的可用带宽计算，上传 1 TB 数据约需 10 天以上；数据量越大，网络传输越不经济
- **判断依据（考试要点）**：AWS 官方建议，当预估的网络传输时间**超过约一周**时，物理设备迁移通常比网络传输更快、更经济——这也是 SAA-C02 场景题中判断"该用网络传输还是 Snowball"的核心计算逻辑
- 核心价值：将"传输数据"变成"运输硬件"，用物流速度替代网络带宽的限制

### Snow 家族总览（考试要点）

| 产品 | 定位 | 容量/算力 | 典型场景 |
|------|------|----------|---------|
| **Snowcone / Snowcone SE** | 最小型边缘设备 | 8 TB（HDD）/ 14 TB（SSD），可带计算 | 空间受限的边缘位置、小规模数据采集 |
| **Snowball Edge - Storage Optimized** | 存储优化型 | 约 80 TB 可用存储 + 轻量计算 | 大规模数据迁移、本地存储扩容 |
| **Snowball Edge - Compute Optimized** | 计算优化型 | 更强 CPU/GPU + 存储 | 边缘机器学习推理、视频分析、需要较强本地计算的场景 |
| **Snowmobile** | 超大规模迁移的集装箱卡车 | 单台最高 **100 PB** | Exabyte 级别的数据中心整体迁移 |

> **考试陷阱**：**Snowball（经典款）已被 Snowball Edge 取代**，现在的 AWS 文档和考试中提到的"Snowball"通常指 **Snowball Edge**（自带计算能力，可在设备本地运行 [[Lambda]] 函数或 EC2 实例进行边缘处理），不要将其误认为只是一个"纯存储运输盒子"。

## Snowball Edge 工作流程

1. 在 AWS 控制台创建**导入/导出任务（Job）**，指定目标区域和 S3 Bucket
2. AWS 将 Snowball Edge 设备**物理寄送**到指定地址
3. 通过 **AWS OpsHub**（图形化管理工具）或命令行工具在本地网络中连接设备，将数据拷贝至设备
4. 将设备**寄回 AWS**（设备上的电子墨水屏会自动更新运单地址）
5. AWS 将设备中的数据自动导入指定的 **S3 存储桶**
6. 数据确认导入完成后，AWS 会对设备存储介质执行**符合 NIST 800-88 标准的擦除**

> **考试要点**：Snowball Edge 同样支持**反向流程（导出）**——即把 S3 中的数据导出到设备上，寄送到本地，用于数据中心退役、灾备副本获取等场景。

## 安全性

| 机制 | 说明 |
|------|------|
| **静态加密** | 设备内置 **256 位 AES 加密**，数据在写入设备的过程中自动加密 |
| **密钥管理** | 加密密钥永远不会与设备一同物理运输，需通过 AWS 管理控制台单独获取，即使设备丢失也无法直接解密数据 |
| **物理坚固性** | 设备外壳防震防摔，专为运输环境设计 |
| **数据擦除** | 数据成功导入 AWS 后，设备存储介质会按照 **NIST 800-88** 标准进行安全擦除 |
| **电子墨水屏（E Ink）+ 自动寻址** | 设备通过内置屏幕自动显示寄回地址，无需用户手动打印运单，降低误寄风险 |

## Snowball Edge 的本地计算能力

- Snowball Edge 内置计算资源，可在设备上运行 **[[Lambda]] 函数**或 **EC2 兼容实例**，实现"边处理边迁移"
- **典型用途**：
  - 在断网/弱网的边缘环境（如工厂、船舶、油田）预处理数据后再批量传回 AWS
  - 数据迁移前先做过滤、压缩、格式转换，减少后续处理负担
  - 作为临时的本地计算/存储节点，弥补远程站点缺乏稳定网络连接的问题
- 多台 Snowball Edge 设备可**集群化（Clustering）**部署，提供本地高可用存储，适合作为长期边缘存储方案而非仅一次性迁移工具

## Snow 家族 vs 其他迁移方案

| 方案                      | 迁移方式        | 适用场景                                                                                  |
| ----------------------- | ----------- | ------------------------------------------------------------------------------------- |
| **Snowball Edge**       | 物理设备运输      | 数据量大（TB 到几十 TB 级）、网络带宽不足或不可用                                                          |
| **Snowmobile**          | 集装箱卡车运输     | 单次迁移达 **Exabyte** 级别的超大规模数据中心迁移                                                       |
| [[AWS DataSync]]        | 网络自动化传输     | 有可用网络带宽，需要持续/增量同步本地与 [[S3 - Object Storage]]/[[文件储存 - AWS EFS]]/[[文件储存 - AWS FSx]] 数据 |
| [[AWS Storage Gateway]] | 混合云网关（持续在线） | 长期、持续的本地与云存储集成，而非一次性迁移                                                                |
| **AWS Direct Connect**  | 专线网络连接      | 需要长期稳定、低延迟的本地到 AWS 专线，带宽充足时的更优选择                                                      |

> **考试陷阱**：**一次性大规模迁移用 Snowball/Snowmobile；持续/增量同步用 DataSync**；题目若强调"每天/每周持续同步本地文件系统改动到云端"，答案通常是 **DataSync** 而非 Snowball（Snowball 是一次性物理搬运，不适合持续同步场景）。

## 典型应用场景

| 场景 | 推荐方案 |
|------|---------|
| **大规模一次性数据迁移（TB-PB 级，网络不可用/不经济）** | Snowball Edge（Storage Optimized） |
| **数据中心整体退役/迁移（Exabyte 级）** | Snowmobile |
| **边缘位置需要本地计算 + 数据采集** | Snowball Edge（Compute Optimized）或 Snowcone |
| **空间受限、只需小规模数据采集** | Snowcone / Snowcone SE |
| **持续增量同步本地文件到 S3/EFS/FSx** | AWS DataSync（非 Snowball） |
| **长期混合云存储集成** | [[AWS Storage Gateway]]（非 Snowball） |
| **灾难恢复场景下需要快速导出云上数据到本地** | Snowball Edge 导出任务 |

## 考试重点总结

### SAA-C02 高频考点

1. **判断依据**：网络传输预估耗时**超过约一周**时，优先考虑 Snowball 而非网络传输
2. **Snowball = Snowball Edge**：现代考试语境下的"Snowball"默认指带本地计算能力的 Snowball Edge
3. **两种 Edge 类型**：Storage Optimized（偏存储）vs Compute Optimized（偏算力，含 GPU 选项）
4. **Snowmobile 用于 Exabyte 级**：单台最高 100 PB，适合整个数据中心搬迁
5. **加密密钥与设备分离运输**：即使设备在运输途中丢失，没有密钥也无法解密数据
6. **数据导入后自动擦除**：符合 NIST 800-88 标准，无需担心归还设备后的数据残留
7. **支持导出（Import 和 Export 均可）**：不仅能把本地数据搬上云，也能把云上数据导出到本地
8. **本地计算能力**：可运行 Lambda/EC2，实现边缘预处理，减少后续云端处理负担
9. **一次性 vs 持续同步**：Snowball 解决一次性大规模迁移；DataSync 解决持续/增量同步
10. **可集群化部署**：多台 Snowball Edge 可组成本地高可用存储集群，不只是"搬完就还"的一次性工具

### 场景题解题思路

```
场景分析 → 选择迁移方案
├── "本地数据量巨大（TB 到几十 TB），网络传输预估超过一周" → Snowball Edge
├── "整个数据中心迁移，数据量达 Exabyte 级" → Snowmobile
├── "边缘位置需要就地计算 + 有限数据采集，空间受限" → Snowcone
├── "边缘位置需要较强本地计算/GPU 推理" → Snowball Edge (Compute Optimized)
├── "需要每天/持续同步本地文件到 S3/EFS/FSx" → [[AWS DataSync]]（非 Snowball）
├── "需要长期、持续的本地与云存储混合集成" → [[AWS Storage Gateway]]（非 Snowball）
├── "需要把云上数据快速导出到本地" → Snowball Edge 导出任务
└── "网络带宽充足且需长期低延迟专线" → AWS Direct Connect（非 Snowball）
```

## 最佳实践

1. **迁移前用公式估算**：数据量 ÷ 可用带宽 与运输+处理时间对比，超过约一周优先选 Snowball
2. **善用本地计算能力**：迁移前用 Snowball Edge 上的 Lambda/EC2 做预处理，减少数据量和后续云端处理成本
3. **大规模迁移优先 Storage Optimized，需要边缘算力时选 Compute Optimized**
4. **牢记密钥与设备分离**：加密密钥通过控制台单独获取，不要依赖设备本身的安全性
5. **持续同步场景改用 DataSync**：不要把 Snowball 当作日常增量同步工具使用
6. **多站点/超大规模场景评估集群化部署**：Snowball Edge 集群可作为长期边缘存储节点而非一次性工具
7. **迁移完成后确认擦除记录**：留存 AWS 提供的数据擦除证明，满足合规审计需求
