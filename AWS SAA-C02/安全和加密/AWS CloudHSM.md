# AWS CloudHSM - 专用硬件安全模块

> **AWS CloudHSM** 提供**专用（Dedicated）、单租户**的硬件安全模块（HSM）设备，运行在客户自己的 [[VPC]] 内，密钥材料的生成、存储和密码学运算**完全由客户控制**——AWS 对密钥内容**没有任何访问权限或可见性**，满足最严格的合规要求（如需要证明密钥"仅由客户掌控"的行业监管场景）。
>
> 相关文档：[[KMS]] | [[AWS Certificate Manager (ACM)]] | [[VPC]] | [[IAM]] | [[RDS]] | [[EC2]]

## 核心概念

### 为什么需要 CloudHSM

- **[[KMS]] 的局限**：KMS 是**多租户共享**的托管加密服务——密钥材料存储在 AWS 运营的 HSM 中，AWS 负责底层硬件运维，这对绝大多数场景已经足够安全，但部分行业监管（金融、政府、医疗等）要求密钥必须存储在**客户独占控制**的专用硬件中，共享基础设施无法满足这类合规要求
- **CloudHSM 的核心价值**：提供**单租户专属**的 HSM 集群，客户拥有对密钥材料的**完全控制权**，包括密钥的生成、导入、导出、销毁，AWS 仅负责硬件的物理安全和基础维护，**无法访问密钥内容本身**

### CloudHSM vs KMS（考试高频）

| 维度        | AWS KMS                           | AWS CloudHSM                                       |
| --------- | --------------------------------- | -------------------------------------------------- |
| **租户模型**  | 多租户共享 HSM 基础设施                    | **单租户专属**集群                                        |
| **密钥控制权** | AWS 管理底层 HSM，密钥材料托管在 AWS 运营的基础设施中 | **客户完全控制**，AWS 无法访问密钥内容                            |
| **合规认证**  | FIPS 140-3 Level 3 验证（截至 2025 年）  | FIPS 140-2/140-3 **Level 3** 验证，专为**专用硬件**场景设计     |
| **易用性**   | 与几乎所有 AWS 服务深度集成，开箱即用             | 需要客户自行管理集群、安装客户端、通过标准 API（PKCS#11、JCE、CNG/KSP）编程访问 |
| **成本**    | 按密钥数量 + API 调用量计费，成本较低            | 按 HSM 实例数量和运行时长计费，**成本显著更高**                       |
| **典型场景**  | 绝大多数需要静态加密的 AWS 服务集成场景            | Oracle TDE、需要直接操作 HSM 的自定义应用、严格合规要求的密钥管理           |

> **考试陷阱**：**两者的 FIPS 认证级别差距已随 KMS 升级而缩小，判断依据应回归"是否需要单租户专属硬件控制权"而非单纯比较 FIPS 等级**——题目描述"需要专用、单租户的硬件安全模块，且密钥必须完全由客户掌控，AWS 不能有任何访问权限" → **CloudHSM**；题目描述"只需要静态加密，希望与 AWS 服务无缝集成、无需自行运维 HSM" → **KMS** 已经足够，无需承担 CloudHSM 的额外复杂度和成本。

## 集群架构

### HSM 集群（Cluster）

- CloudHSM 以**集群**形式部署，集群内可包含多个 HSM 实例，**跨多个可用区**分布以实现高可用
- 集群内的 HSM **自动同步密钥材料**，客户端可通过集群端点连接到任意可用的 HSM，实现负载均衡和故障转移
- 可随时向集群**添加或移除 HSM** 实例，灵活应对性能和容量需求变化

### 客户端-服务器模型

- 应用通过安装在 [[EC2]] 实例上的 **CloudHSM 客户端软件**与 HSM 集群通信，客户端与 HSM 之间通过 **mTLS（双向 TLS）**加密通信
- 支持标准密码学 API：**PKCS#11**、**Java Cryptography Extension (JCE)**、**Microsoft CNG/KSP**，便于现有应用（如 Oracle 数据库的透明数据加密 TDE）直接对接，无需大幅改造代码

## 硬件与合规

| 项目 | 说明 |
|------|------|
| **FIPS 140-2/140-3 Level 3 验证** | 专用硬件设计天然满足最高级别的密码学模块合规认证要求 |
| **hsm2m.medium（新一代实例）** | 支持 **FIPS 140-3 Level 3**，可运行于**非 FIPS 模式**（更灵活的合规适配）、单集群最多支持约 **16,666 个密钥**的存储容量、支持客户端与 HSM 间的 **mTLS** |
| **hsm1 实例类型退役** | 旧一代 **hsm1** 实例已于 **2025 年 12 月 1 日**停止服务，新部署应使用 hsm2m.medium |
| **区域可用性** | 并非所有 AWS 区域都提供 CloudHSM，部分区域（南美、非洲、部分亚太区域）暂不支持，依赖 CloudHSM 的 KMS 自定义密钥库在这些区域同样不可用 |

## 与 KMS 自定义密钥库的集成（考试要点）

- **[[KMS]] Custom Key Store（自定义密钥库）**允许在 KMS 中创建密钥时，将实际的密钥材料和密码学运算**委托给客户自己的 CloudHSM 集群**执行，而非使用 AWS 运营的共享 HSM
- 这种组合让用户同时获得**KMS 的便捷管理界面和 AWS 服务集成能力**，以及**CloudHSM 的专属硬件控制权**——是"既要合规、又要易用性"场景的折中方案
- 详见 [[KMS]] 笔记中"自定义密钥库"章节

---

## 备份与灾难恢复（考试陷阱）

- CloudHSM 支持**集群备份**，可将加密的备份数据存储在 AWS 管理的存储中，用于恢复集群或创建新集群
- **关键责任划分**：AWS 负责 HSM 硬件的物理安全，但**密钥材料的备份和灾难恢复完全是客户的责任**——若客户未妥善备份且集群内所有 HSM 同时丢失，**AWS 无法以任何方式恢复密钥材料**（因为 AWS 从未拥有过密钥的可见性），加密数据将永久不可解密

> **考试陷阱**：**这是 CloudHSM"客户完全控制"带来的双刃剑**——题目描述"CloudHSM 集群意外丢失且未备份，能否请求 AWS 恢复密钥" → **不能**，AWS 无法访问或恢复客户在 CloudHSM 中的密钥材料，这与 KMS（AWS 托管，有更完善的内部灾难恢复机制）形成鲜明对比，也是选择 CloudHSM 前必须权衡的运维责任。

## 管理与身份验证

- CloudHSM 使用**基于配额（Quorum）的身份验证**机制管理高权限操作（如集群配置变更），需要多个管理员共同授权才能执行敏感操作，防止单点权限滥用
- 与 [[IAM]] 的关系：IAM 控制**谁能管理 CloudHSM 集群资源本身**（创建/删除集群、添加 HSM），但**集群内部的密钥访问和密码学操作权限由 CloudHSM 自身的用户体系管理**，与 IAM 是两套独立的权限模型

## 安全性

| 机制 | 说明 |
|------|------|
| **[[VPC]] 私有部署** | HSM 集群部署在客户 VPC 内的私有子网，每个可用区一个网络接口（ENI） |
| **mTLS 通信** | 客户端与 HSM 之间的通信使用双向 TLS 加密和身份验证 |
| **Quorum 身份验证** | 高权限操作需要多个管理员共同确认，防止单点滥用 |
| **AWS 零可见性** | AWS 运维人员无法访问客户存储在 HSM 中的密钥材料和密码学运算内容 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **严格合规要求密钥必须由客户完全掌控** | AWS CloudHSM 专属集群 |
| **Oracle 数据库透明数据加密（TDE）** | CloudHSM + PKCS#11/JCE 标准接口对接 |
| **需要 KMS 的易用性 + CloudHSM 的硬件控制权** | KMS 自定义密钥库（Custom Key Store）+ CloudHSM |
| **自定义应用需要直接调用 HSM 做密码学运算** | CloudHSM 客户端 + PKCS#11/JCE/CNG API |
| **仅需静态加密，无需专属硬件** | 改用 [[KMS]]（而非 CloudHSM，成本更低、无需自行运维） |
| **需要为集群提供高可用和容灾** | 跨多可用区部署 HSM + 妥善管理集群备份 |
| **新部署 CloudHSM 集群** | 使用 hsm2m.medium 实例类型（hsm1 已退役） |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：单租户专属硬件安全模块，密钥完全由客户控制，AWS 无访问权限
2. **判断依据**：需要"专属硬件、客户完全掌控密钥"选 CloudHSM；只需"静态加密、易用集成"选 KMS
3. **集群架构支持高可用**：跨可用区部署多个 HSM，客户端连接集群端点实现负载均衡和故障转移
4. **标准密码学 API 对接**：PKCS#11、JCE、CNG/KSP，便于现有应用（如 Oracle TDE）直接集成
5. **成本显著高于 KMS**：按 HSM 实例计费，是"高合规但也高成本"的专属方案
6. **可作为 KMS 自定义密钥库的底层**：兼顾 KMS 易用性和 CloudHSM 硬件控制权
7. **密钥备份是客户的责任**：集群丢失且未备份，AWS 无法恢复密钥，加密数据永久不可解密
8. **Quorum 身份验证管理高权限操作**：多管理员共同授权，防止单点滥用
9. **hsm2m.medium 是新一代实例**：支持 FIPS 140-3 Level 3、更大存储容量、mTLS，hsm1 已于 2025 年底退役
10. **IAM 管集群资源，CloudHSM 自身管密钥访问权限**：两套独立的权限模型，不可混淆

### 场景题解题思路

```
场景分析 → 判断是否用 CloudHSM
├── "密钥必须由客户完全掌控，AWS 不能有任何访问权限" → AWS CloudHSM
├── "Oracle 数据库需要透明数据加密（TDE）" → CloudHSM + 标准密码学 API
├── "希望兼顾 KMS 易用性和专属硬件控制权" → KMS 自定义密钥库 + CloudHSM
├── "只需静态加密，无需专属硬件，控制成本" → 改用 KMS（而非 CloudHSM）
├── "CloudHSM 集群意外丢失且未备份，能否恢复密钥" → 不能，AWS 无法访问/恢复客户密钥
├── "需要为 HSM 集群提供高可用" → 跨多可用区部署 + 妥善管理备份
└── "新部署 CloudHSM，应选择哪种实例类型" → hsm2m.medium（hsm1 已退役）
```

## 最佳实践

1. **仅在真正需要专属硬件合规时选择 CloudHSM**：绝大多数场景 KMS 已能满足需求，避免不必要的运维和成本负担
2. **集群跨多可用区部署**：保证 HSM 硬件故障不影响整体可用性
3. **务必妥善管理集群备份**：这是客户不可推卸的责任，定期验证备份可用性，避免因备份缺失导致密钥永久丢失
4. **新部署统一使用 hsm2m.medium**：获得更好的 FIPS 认证、存储容量和 mTLS 支持
5. **需要 AWS 服务集成时优先评估 KMS 自定义密钥库**：而非完全脱离 KMS 生态直接对接 CloudHSM
6. **高权限操作善用 Quorum 身份验证**：避免单一管理员账户被攻破导致整个集群失控
7. **提前确认目标区域是否支持 CloudHSM**：并非所有区域都提供该服务，尤其在规划依赖 KMS 自定义密钥库的架构时需一并确认
8. **应用集成优先选用标准密码学 API**：PKCS#11/JCE/CNG 已有成熟生态支持，减少自定义集成的开发成本
