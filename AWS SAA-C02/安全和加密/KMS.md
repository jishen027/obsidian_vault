# AWS KMS - 密钥管理服务

> **AWS Key Management Service (KMS)** 是集中管理加密密钥的核心托管服务，负责密钥的创建、轮换、禁用、删除全生命周期管理，并与几乎所有 AWS 存储/数据库服务深度集成，为静态数据提供透明的加密保护，是 AWS 安全体系中"数据加密"这一维度的基础设施。
>
> 相关文档：[[S3]] | [[S3 Security]] | [[EBS]] | [[AWS EFS]] | [[RDS]] | [[DynamoDB]] | [[IAM]] | [[CloudTrail]] | [[AWS Secrets Manager]] | [[AWS CloudHSM]]

---

## 核心概念

### 密钥类型（考试高频）

| 类型 | 控制权 | 轮换 | 典型场景 |
|------|--------|------|---------|
| **AWS 拥有的密钥（AWS Owned Keys）** | 完全由 AWS 管理，用户不可见、不可控 | AWS 自行处理 | 多个账户共享底层密钥的默认加密（如 S3 默认的 SSE-S3） |
| **AWS 托管密钥（AWS Managed Keys）** | 由 AWS 自动创建（如 `aws/s3`、`aws/rds`），在用户账户的 KMS 控制台可见 | **自动每年轮换**，用户无法更改周期 | 用户希望使用 KMS 加密但不想自行管理密钥的默认选项 |
| **客户管理密钥（Customer Managed Key, CMK）** | 用户拥有**完全控制权**——自定义密钥策略、轮换周期、手动禁用/删除 | 可选自动轮换（默认关闭，开启后每年）或完全手动 | 需要精细审计、自定义密钥策略、跨账户共享等场景 |

> **考试陷阱**：**三种密钥类型的核心区别是控制粒度**——题目强调"需要自定义密钥策略、控制谁能使用/禁用密钥、精细审计" → **客户管理密钥（CMK）**；只是"希望数据加密，不关心密钥细节" → AWS 托管密钥已足够，无需额外创建 CMK。

### 对称密钥 vs 非对称密钥

| 类型 | 说明 |
|------|------|
| **对称密钥（Symmetric）** | 加解密使用同一把密钥，**密钥明文永远不会离开 KMS**，是绝大多数 AWS 服务集成（S3/EBS/RDS 等）默认使用的类型 |
| **非对称密钥（Asymmetric）** | 公钥/私钥对，适合需要在 **KMS 之外**完成加密（只分发公钥）或需要数字签名验证的场景，性能通常低于对称密钥 |

## 信封加密（Envelope Encryption，考试要点）

- KMS 加密大数据量时**不会直接用主密钥加密整份数据**，而是采用**信封加密**机制：
  1. 调用 `GenerateDataKey` API，KMS 返回一份**明文数据密钥（Plaintext Data Key）**和该密钥的**加密版本（Encrypted Data Key）**
  2. 应用在本地用明文数据密钥加密实际数据，随后**立即从内存中清除明文密钥**
  3. 加密后的数据与加密版本的数据密钥一并存储
  4. 解密时，先调用 KMS `Decrypt` 用主密钥解出明文数据密钥，再用它在本地解密数据
- **核心价值**：数据加解密在**本地**完成，无需每次都把大量数据传输给 KMS 做加密运算，兼顾了性能和主密钥不出域的安全性——这是 AWS SDK 客户端加密库和多个 AWS 服务底层加密机制的通用模式

## 密钥轮换（考试陷阱高发区）

| 轮换方式 | 适用范围 | 说明 |
|---------|---------|------|
| **自动轮换（Automatic Rotation）** | 仅对称的**客户管理密钥**可选启用 | 每年自动生成新的密钥材料，**旧密钥材料仍保留**用于解密此前用旧材料加密的数据，对使用方完全透明，无需重新加密历史数据 |
| **按需轮换（On-Demand Rotation）** | 客户管理密钥 | 可随时手动触发一次轮换，不受自动轮换周期限制 |
| **非对称密钥/导入密钥材料的密钥** | **不支持自动轮换** | 使用外部导入密钥材料（BYOK）或非对称密钥时，需要通过创建新密钥并手动切换来实现"轮换" |

> **考试要点**：**轮换只是生成新的密钥材料，密钥的逻辑标识（Key ID/ARN）不变**——应用无需修改任何引用密钥 ID 的代码或配置，旧数据依然可用同一个 Key ID 正常解密，这是 KMS 轮换"对使用方透明"的关键设计。

## 授权机制（考试高频）

### 密钥策略（Key Policy）

- KMS **必须通过密钥策略**进行授权——密钥策略是附加在密钥资源本身的**资源策略**，是密钥访问控制的**主入口**（区别于普通 AWS 资源默认依赖 IAM 身份策略）
- 默认密钥策略授予**账户 Root 用户完全权限**，并允许通过 IAM 策略进一步委派权限给账户内的用户/角色
- 典型划分**密钥管理员（Key Administrators，可管理密钥但不能用其加解密）**和**密钥用户（Key Users，可用密钥加解密但不能删除/修改策略）**两类角色，贯彻最小特权原则

### 授权（Grants）

- **授权（Grant）**是一种**临时性、程序化**的权限委派机制，常由 AWS 服务在需要短期访问某个 CMK 时动态创建（如 EBS 卷加解密时临时获得对应密钥的使用权），无需修改静态的密钥策略
- 相比修改密钥策略，Grant 更适合**自动化、短生命周期**的授权场景

### 跨账户访问

- 密钥策略中显式允许其他账户的主体，**同时**目标账户内该主体的 IAM 策略也需要授予相应权限——与 IAM 跨账户访问"双向都要允许"的逻辑一致

---

## 多区域密钥（Multi-Region Keys）

- 支持创建**密钥材料相同**的主密钥副本并分发到多个区域，应用可在不同区域用各自的区域密钥加解密**同一份数据**，无需跨区域调用 KMS API
- **典型场景**：[[DynamoDB]] 全球表（Global Tables）、Aurora 全球数据库等跨区域复制架构的静态加密需求，以及跨区域灾难恢复场景下避免"数据在异地却无法解密"的问题
- 多区域密钥仍是**独立的 KMS 资源**（各区域各自计费和管理），只是共享密钥材料，而非单一的全局密钥

---

## 导入密钥材料（BYOK）与自定义密钥库

| 能力 | 说明 |
|------|------|
| **导入密钥材料（Import Key Material）** | 允许客户使用自己生成的密钥材料创建 KMS 密钥，而非由 AWS 生成；**不支持自动轮换**，需要客户自行管理密钥材料的生命周期 |
| **自定义密钥库（Custom Key Store）** | 基于 **[[AWS CloudHSM]]** 集群支撑的 KMS 密钥库，密钥材料实际存储在客户专属的 HSM 集群中，满足"密钥必须存储在客户完全控制的专用硬件"这类严格合规要求，详见 [[AWS CloudHSM]] 独立笔记 |

---

## 密钥删除保护

- KMS 密钥**不能立即删除**——发起删除请求后进入**待删除窗口期（Pending Deletion）**，可配置 **7 到 30 天**的等待期，期间可随时取消删除
- **设计目的**：防止误删密钥导致所有用该密钥加密的数据永久无法解密（密钥一旦真正删除，加密数据将**永久不可恢复**）

---

## 服务集成与数据保护

- **落盘数据加密（Encryption at Rest）**：KMS 广泛集成 AWS 核心存储/数据库服务，为 [[S3]]（SSE-KMS）、[[EBS]]、[[AWS EFS]]、[[RDS]]、[[DynamoDB]] 等提供透明的静态加密保护，详见 [[S3 Security]] 中 SSE-KMS 的具体实现和 **S3 Bucket Keys** 优化
- **开发工具安全**：如 CodeCommit 存储库也会使用 KMS 管理的密钥对静态代码自动加密
- **合规和审计**：KMS 与 [[CloudTrail]] 深度集成，每一次密钥使用行为（加密、解密、生成数据密钥等）都会被记录，为企业提供完整的审计追踪

> **考试要点**：**高频访问小对象的 SSE-KMS 加密可能触及 KMS 每秒请求配额限流**——如 S3 中海量小文件的频繁 GET/PUT 都会各自调用 KMS API；缓解方式是启用 **S3 Bucket Keys**，在 Bucket 级别生成信封密钥的数据密钥，大幅减少实际调用 KMS 的次数（详见 [[S3 Security]]）。

## 在安全性工具链中的定位

| 服务 | 定位 | 与 KMS 的关系 |
|------|------|--------------|
| **KMS** | 通用的托管加密**密钥**服务 | —— |
| **[[AWS CloudHSM]]** | 专用的第三方验证硬件安全模块（HSM），面向需要**专用硬件、单租户控制**的高合规工作负载 | 可作为 KMS 自定义密钥库的底层存储 |
| **[[AWS Secrets Manager]]** | 专注于管理**凭证**（数据库密码、API 密钥等），而非加密密钥本身 | 存储凭证时**底层调用 KMS** 对凭证内容做加密 |

> **考试陷阱**：**KMS 管密钥，Secrets Manager 管凭证，两者不可互换**——题目描述"需要集中管理和自动轮换数据库密码" → [[AWS Secrets Manager]]；描述"需要为 S3/EBS/RDS 等提供静态加密的密钥管理" → KMS；描述"需要专用第三方验证硬件、单租户 HSM 满足严格合规要求" → [[AWS CloudHSM]]（而非普通 KMS 密钥）。

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **为 S3/EBS/RDS 等提供静态数据加密** | AWS 托管密钥（默认）或客户管理密钥（需要精细控制时） |
| **需要自定义密钥策略、跨账户共享密钥** | 客户管理密钥（CMK）+ 密钥策略 |
| **加密大量数据且要求高性能** | 信封加密（GenerateDataKey + 本地加密） |
| **跨区域复制数据且需两端都能解密** | 多区域密钥（Multi-Region Keys） |
| **密钥必须存储在客户专属硬件中满足合规** | 自定义密钥库（Custom Key Store，基于 [[AWS CloudHSM]]） |
| **AWS 服务需要临时、程序化获得密钥使用权** | 授权（Grants） |
| **S3 海量小对象加密触及 KMS 请求限流** | S3 Bucket Keys（减少 KMS API 调用次数） |
| **需要审计每一次密钥使用行为** | KMS + CloudTrail 集成 |
| **需要专用硬件安全模块、单租户控制** | 改用 [[AWS CloudHSM]]（而非普通 KMS） |
| **需要集中管理和轮换数据库密码等凭证** | 改用 [[AWS Secrets Manager]]（底层仍调用 KMS 加密） |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：集中管理加密密钥的托管服务，为 AWS 服务提供透明的静态加密
2. **三种密钥类型**：AWS 拥有（不可见不可控）、AWS 托管（可见、自动年度轮换）、客户管理（完全控制）
3. **信封加密机制**：GenerateDataKey 返回明文+加密数据密钥，数据在本地加密，主密钥明文不出域
4. **自动轮换只针对对称 CMK**：每年轮换，旧密钥材料保留用于解密历史数据，Key ID 不变、应用无感知
5. **密钥策略是授权的主入口**：资源策略优先于/独立于 IAM 身份策略，两者可协同委派权限
6. **Grants 用于临时程序化授权**：无需修改静态密钥策略，适合自动化短期场景
7. **跨账户访问需要双向授权**：密钥策略允许 + 目标主体的 IAM 策略也需允许
8. **多区域密钥共享密钥材料**：跨区域灾备/全球表场景避免"数据在异地无法解密"
9. **密钥删除有 7-30 天等待期**：防止误删导致数据永久不可恢复
10. **KMS vs [[AWS CloudHSM]] vs [[AWS Secrets Manager]]**：通用托管密钥服务 vs 专用单租户硬件 vs 凭证管理（底层用 KMS 加密）

### 场景题解题思路

```
场景分析 → 判断使用 KMS 的哪个能力
├── "需要为 S3/EBS/RDS 等提供静态加密，无需精细控制密钥" → AWS 托管密钥
├── "需要自定义密钥策略、精细控制谁能使用/禁用密钥" → 客户管理密钥（CMK）
├── "需要加密大量数据且要求高性能" → 信封加密（GenerateDataKey）
├── "需要跨区域复制数据并在两端都能解密" → 多区域密钥
├── "密钥必须存储在客户专属硬件模块中" → 自定义密钥库（[[AWS CloudHSM]] 支撑）
├── "AWS 服务需要临时获得密钥使用权限" → 授权（Grants）
├── "S3 海量小对象的 SSE-KMS 加密触及请求限流" → 启用 S3 Bucket Keys
├── "需要审计每次密钥使用行为" → KMS + CloudTrail 集成
├── "需要专用第三方验证硬件、单租户控制的高合规场景" → 改用 [[AWS CloudHSM]]（而非 KMS）
└── "需要集中管理和自动轮换数据库密码" → 改用 [[AWS Secrets Manager]]（而非 KMS 本身）
```

## 最佳实践

1. **默认使用 AWS 托管密钥，仅在需要精细控制时创建 CMK**：避免不必要的密钥管理开销
2. **善用密钥策略实现管理员/使用者角色分离**：贯彻最小特权原则，管理员不应默认拥有加解密权限
3. **自动化/短期场景优先使用 Grants 而非频繁修改密钥策略**：减少静态策略变更带来的管理负担
4. **海量小对象加密启用 S3 Bucket Keys**：显著降低 KMS API 调用量和成本，规避请求限流
5. **跨区域架构评估多区域密钥**：避免因区域间无法共享密钥材料导致的解密失败
6. **高合规场景评估 [[AWS CloudHSM]] 或自定义密钥库**：普通 KMS 密钥无法满足"专用单租户硬件"这类严格要求
7. **密钥删除前充分评估影响**：利用 7-30 天等待期窗口确认没有遗漏的依赖数据
8. **敏感操作结合 CloudTrail 审计密钥使用记录**：满足合规审计对"谁在何时使用了密钥"的追溯要求
9. **凭证类数据使用 [[AWS Secrets Manager]] 而非直接用 KMS 加密后自行存储**：复用其自动轮换和凭证生命周期管理能力
