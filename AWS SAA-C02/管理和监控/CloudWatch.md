# Amazon CloudWatch - 监控与可观测性中枢

> **Amazon CloudWatch** 是 AWS 管理和监控体系的**性能中枢**，负责收集指标（Metrics）和日志（Logs）、回答"资源当前运行得怎么样"，并基于阈值触发自动化响应（告警、通知、弹性伸缩）。与专注"谁做了什么"的 [[CloudTrail]]、专注"资源配置长什么样"的 [[AWS Config]] 共同构成 AWS 管理和监控三件套。
>
> 相关文档：[[CloudTrail]] | [[AWS Config]] | [[Auto Scaling]] | [[EC2]] | [[SNS]] | [[AWS Lambda]] | [[VPC]] | [[Amazon Kinesis]] | [[KMS]]

---

## 核心概念

### CloudWatch 在管理监控体系中的定位（考试要点）

| 服务 | 核心问题 | 数据类型 | 典型场景 |
|------|---------|---------|---------|
| **CloudWatch** | 资源运行得怎么样？ | 指标（Metrics）、日志（Logs） | 性能监控、告警、自动化响应 |
| [[CloudTrail]] | 谁在什么时候做了什么？ | API 调用事件日志 | 审计、安全取证、合规追溯 |
| [[AWS Config]] | 资源配置长什么样、如何变化？ | 配置项（Configuration Item）快照 | 配置合规、变更管理、关系分析 |

> **考试陷阱**：三者经常在选项中同时出现，判断依据是题目问的是**性能表现**（CloudWatch）、**操作行为**（CloudTrail）还是**配置状态**（AWS Config）；三者可以组合使用形成完整的可观测性闭环——CloudTrail 记录操作 → CloudWatch Logs 聚合并触发告警 → AWS Config 追溯配置变更的最终结果。

## 指标（Metrics）

### 核心概念

- **命名空间（Namespace）**：指标的顶层容器，用于隔离不同服务/应用的指标（如 `AWS/EC2`、自定义命名空间）
- **维度（Dimension）**：唯一标识一个指标的名称/值对（如 `InstanceId=i-xxx`），同一指标名在不同维度下是不同的数据流
- **标准指标 vs 自定义指标**：AWS 服务自动发布的指标为标准指标（如 EC2 的 CPU 利用率）；应用自行上报的业务指标（如订单数）为自定义指标，通过 `PutMetricData` API 或 CloudWatch 统一代理上报

### 监控精度

| 类型 | 采集间隔 | 说明 |
|------|---------|------|
| **基本监控（Basic）** | 5 分钟 | EC2 等资源的默认免费监控粒度 |
| **详细监控（Detailed）** | 1 分钟 | 需要显式开启，通常产生额外费用 |
| **高分辨率自定义指标** | 最高 1 秒 | 自定义指标可配置到秒级精度，用于对延迟极度敏感的监控场景 |

> **考试陷阱**：**EC2 默认的基本监控不包含内存、磁盘使用率等操作系统层面的指标**——CPU、网络、磁盘 I/O 等 Hypervisor 层面可见的指标默认可用，但内存利用率、磁盘空间等需要在实例内安装 **CloudWatch 统一代理（Unified Agent）**主动上报为自定义指标；题目问"如何监控 EC2 实例的内存使用率"，答案是安装 CloudWatch Agent，而非误以为是默认指标。

### 数据保留期

- 指标数据按精度分级保留：**1 分钟精度数据保留 15 天**，**5 分钟精度保留 63 天**，**1 小时精度保留 15 个月**——数据会随时间自动降低精度（Roll-up），而非直接删除

### 异常检测（Anomaly Detection）

- 基于机器学习为指标建立正常范围的"预期带（Band）"，自动适应趋势和季节性波动（如工作日 vs 周末的流量差异），偏离预期带时触发告警，相比固定静态阈值更适合波动性强的业务指标

## CloudWatch Logs

### 核心概念

- **日志组（Log Group）/ 日志流（Log Stream）**：日志组是逻辑容器（通常对应一个应用/资源），日志流是其中来自单一来源的连续日志序列
- **日志来源**：[[EC2]] 实例（需 CloudWatch Agent）、[[AWS Lambda]]（自动集成）、[[VPC]] 流日志（Flow Logs）、[[CloudTrail]] 事件、API Gateway 访问日志等
- **保留期**：可按日志组配置保留期（1 天到永久），默认永久保留，需主动配置以控制存储成本

### 指标筛选器（Metric Filters）

- 定义模式匹配规则，从日志流中提取特定文本（如 `"ERROR"`、HTTP 5xx 状态码）并转化为可分析、可告警的**数值指标**
- 是"从非结构化日志中提炼可监控信号"的标准手段，无需修改应用代码即可对日志内容设置告警

### CloudWatch Logs Insights

- 交互式查询语言，用于对日志组中的海量日志做**即席查询和分析**（聚合、过滤、排序），无需预先定义指标筛选器
- 适合排查问题时的探索性分析，区别于指标筛选器面向的"持续监控固定模式"场景

### 订阅过滤器（Subscription Filters）

- 将日志**实时流式传输**到 [[AWS Lambda]]、[[Amazon Kinesis]] Data Streams/Firehose 等下游服务，用于实时日志处理、跨账户日志集中收集等场景
- 与指标筛选器的区别：订阅过滤器传输**原始日志数据**用于下游处理，指标筛选器只提取**聚合后的数值**用于告警

## CloudWatch 告警（Alarms）

### 告警状态与工作机制

| 状态 | 说明 |
|------|------|
| **OK** | 指标在正常阈值范围内 |
| **ALARM** | 指标触发了配置的阈值条件 |
| **INSUFFICIENT_DATA** | 数据不足以判断状态（如指标刚启用、无数据点） |

- 告警基于指标在**评估周期（Evaluation Period）**内的统计数据（如平均值、最大值）与阈值比较，可配置连续多少个周期越界才真正触发，避免瞬时抖动导致误报

### 告警动作

| 动作类型 | 说明 |
|---------|------|
| **[[SNS]] 通知** | 触发告警时发送消息到 SNS 主题，进而通知邮件/短信/Lambda 等订阅端 |
| **[[Auto Scaling]] 扩缩容** | 驱动 Auto Scaling 组根据指标自动增减实例数量 |
| **EC2 自动恢复（Recover）** | 检测到底层硬件故障等状态检查失败时，自动恢复实例（保留实例 ID、私有 IP 等元数据）|
| **EC2 自动重启/停止/终止** | 基于告警状态对实例执行相应的生命周期操作 |

### 复合告警（Composite Alarms）

- 将多个独立告警通过逻辑运算符（AND/OR）组合成一个复合告警，减少告警噪音（避免单个指标抖动就发出通知），只在多个条件同时满足时才真正触发

## CloudWatch Dashboards

- 可视化仪表盘，跨多个服务/区域/账户聚合展示关键指标图表，构建统一的运维监控视图
- 支持**跨账户、跨区域**聚合展示，适合集中监控多账户/多区域架构下的整体健康状况

---

## CloudWatch Synthetics（金丝雀监控）

- 使用可编程的"金丝雀（Canary）"脚本，模拟用户行为定期访问应用端点（如 API、网页），主动检测可用性和延迟问题
- 与被动等待告警触发不同，Synthetics 是**主动探测**，能在真实用户受影响前发现问题

---

## 与 Amazon EventBridge 的关系（考试提示）

- **CloudWatch Events** 是 **Amazon EventBridge** 的前身/子集——EventBridge 在 CloudWatch Events 的基础上扩展了更丰富的事件总线、第三方 SaaS 事件源集成等能力
- 基于**事件（Event）**的响应式规则（如"某个 EC2 状态变化时触发 Lambda"）现由 EventBridge 承接，而 CloudWatch 告警仍专注于**基于指标阈值**的监控响应
- **考试要点**：题目描述"基于 AWS 服务状态变化事件触发自动化工作流"通常指向 EventBridge（或历史上的 CloudWatch Events）；题目描述"基于指标数值越过阈值触发响应"是 CloudWatch Alarms 的经典场景，两者机制不同但常被放在一起比较

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以发布指标、创建告警、读取日志 |
| **静态加密** | CloudWatch Logs 可使用 [[KMS]] 客户管理密钥加密日志组数据 |
| **传输加密** | API 调用默认通过 HTTPS/TLS |
| **VPC Endpoint** | 支持通过接口终端节点在 VPC 内私有访问 CloudWatch API，无需经过公网 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **监控 EC2 CPU/网络等基础设施指标** | 默认标准指标 + 基本/详细监控 |
| **监控 EC2 内存/磁盘等操作系统层面指标** | 安装 CloudWatch 统一代理上报自定义指标 |
| **从日志中提取特定错误模式并告警** | CloudWatch Logs 指标筛选器 |
| **排查问题时对海量日志做探索性查询** | CloudWatch Logs Insights |
| **将日志实时转发给 Lambda/Kinesis 做进一步处理** | 订阅过滤器（Subscription Filters） |
| **指标越过阈值时自动扩缩容/通知/恢复实例** | CloudWatch Alarms + Auto Scaling/SNS/EC2 恢复 |
| **减少多指标抖动导致的告警噪音** | 复合告警（Composite Alarms） |
| **主动探测应用端点的可用性和延迟** | CloudWatch Synthetics 金丝雀 |
| **跨账户/跨区域集中展示运维指标** | CloudWatch Dashboards |
| **业务指标存在明显趋势/季节性波动** | 异常检测（Anomaly Detection）而非静态阈值 |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：性能监控中枢，回答"资源运行得怎么样"，区别于 CloudTrail（谁做了什么）和 AWS Config（配置长什么样）
2. **EC2 默认指标不含内存/磁盘**：需安装 CloudWatch Agent 才能采集操作系统层面的自定义指标
3. **基本监控 5 分钟 vs 详细监控 1 分钟**：详细监控需显式开启，自定义指标最高可达秒级精度
4. **指标筛选器 vs 订阅过滤器**：前者从日志提取数值用于告警，后者实时转发原始日志给下游服务处理
5. **Logs Insights 用于探索性查询**：区别于指标筛选器面向的持续监控固定模式场景
6. **告警三种典型动作**：SNS 通知、Auto Scaling 扩缩容、EC2 自动恢复
7. **复合告警减少噪音**：多个条件通过 AND/OR 组合，避免单指标抖动导致的误报
8. **CloudWatch Events 与 EventBridge**：基于事件的自动化响应现由 EventBridge 承接，与基于指标阈值的 CloudWatch Alarms 机制不同
9. **Synthetics 是主动探测**：金丝雀脚本模拟用户访问，先于真实用户发现可用性问题
10. **数据保留期随精度分级**：1 分钟精度 15 天、5 分钟精度 63 天、1 小时精度 15 个月

### 场景题解题思路

```
场景分析 → 判断使用 CloudWatch 的哪个能力
├── "需要监控 EC2 实例的内存/磁盘使用率" → 安装 CloudWatch Agent 上报自定义指标
├── "需要从日志中识别特定错误并触发告警" → 指标筛选器（Metric Filter）
├── "需要对海量日志做临时性排查分析" → CloudWatch Logs Insights
├── "需要将日志实时转发给 Lambda/Kinesis 处理" → 订阅过滤器（Subscription Filter）
├── "指标越过阈值需要自动扩容/通知/恢复实例" → CloudWatch Alarms + 对应动作
├── "多个指标同时异常才需要真正告警，减少噪音" → 复合告警（Composite Alarm）
├── "需要主动探测应用端点是否可用" → CloudWatch Synthetics
├── "业务指标随时间/季节呈现明显波动模式" → 异常检测（Anomaly Detection）
├── "需要基于 AWS 服务状态变化事件触发工作流" → Amazon EventBridge（而非 CloudWatch Alarms）
└── "需要判断这个问题该看 CloudWatch/CloudTrail/Config 哪个" → 性能选 CloudWatch，操作行为选 CloudTrail，配置状态选 Config
```

## 最佳实践

1. **需要操作系统层面指标时主动安装 CloudWatch Agent**：不要假设内存/磁盘等指标默认可用
2. **善用指标筛选器把日志转化为可告警的信号**：无需修改应用代码即可对已有日志内容建立监控
3. **探索性排查用 Logs Insights，持续监控用指标筛选器**：按场景选择合适的日志分析方式
4. **合理配置日志组保留期**：避免默认永久保留导致存储成本失控
5. **多指标关联场景使用复合告警**：降低告警噪音，让告警更贴近真实的故障场景
6. **对波动性强的业务指标启用异常检测**：比固定静态阈值更能适应趋势和季节性变化
7. **关键用户旅程配置 Synthetics 金丝雀**：主动发现可用性问题，而非被动等待用户投诉或告警触发
8. **基于事件的自动化响应场景评估 EventBridge**：CloudWatch Alarms 面向指标阈值，事件驱动的复杂路由逻辑更适合用 EventBridge
9. **敏感日志数据启用 KMS 加密**：涉及合规要求的日志组应配置客户管理密钥加密
