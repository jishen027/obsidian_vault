# AWS Config - 配置追踪与合规审计

> **AWS Config** 在 AWS 的管理和监控体系中扮演"资源时间机器"的角色，持续发现、记录 AWS 资源的**配置状态**及其变化历史，并通过**规则（Rule）**自动评估配置是否符合预定义基准，回答"**资源配置长什么样、如何随时间变化**"。与专注"资源运行得怎么样"的 [[CloudWatch]]、专注"谁做了什么"的 [[CloudTrail]] 共同构成 AWS 管理和监控三件套。
>
> 相关文档：[[CloudTrail]] | [[CloudWatch]] | [[SNS]] | [[IAM]] | [[S3]] | [[AWS CloudFormation]] | [[AWS Organizations]]

---

## 核心概念

### AWS Config 在管理监控体系中的定位（考试要点）

| 服务 | 核心问题 | 数据类型 | 典型场景 |
|------|---------|---------|---------|
| **AWS Config** | 资源配置长什么样、如何变化？ | 配置项（Configuration Item）快照 | 配置合规、变更管理、关系分析 |
| [[CloudTrail]] | 谁在什么时候做了什么？ | API 调用事件日志 | 审计、安全取证、合规追溯 |
| [[CloudWatch]] | 资源运行得怎么样？ | 指标（Metrics）、日志（Logs） | 性能监控、告警、自动化响应 |

> **考试陷阱**：三者常在选项中一起出现——题目问"这个安全组上周的配置是什么样、什么时候被修改成现在这样"选 **AWS Config**；问"谁执行了这次修改"选 CloudTrail；问"这个资源当前运行状态如何"选 CloudWatch。CloudTrail 记录**操作行为**，AWS Config 记录这些操作**导致的最终配置状态**，两者结合可提供完整的操作与状态溯源。

## 状态追踪：资源时间机器

### 配置项（Configuration Item）与配置历史

- AWS Config 会**自动发现**账户内支持的资源，记录其详细配置设置，并**持续监控**后续的任何变动
- 每次资源配置发生变化，都会生成一份**配置项（Configuration Item）**——包含该时间点的详细设置、元数据以及与其他资源的关系
- 这些配置项按时间顺序汇编成**配置历史（Configuration History）**，让用户能够**追溯资源在过去任意时刻的真实配置状态**，而不仅仅是当前状态

### 关系分析（Relationship Mapping）

- AWS Config 能自动识别并展示资源之间的关联关系（如某个**安全组**关联了哪些 EC2 实例、某个 VPC 包含哪些子网）
- **典型用途**：修改一个安全组规则前，先查看它关联了哪些资源，评估变更的影响范围，这对变更管理和故障排查至关重要

## 合规性与规则（Rules，考试高频）

### AWS Config 规则

- 通过 **AWS Config 规则**定义理想的配置基准（如"确保所有 EBS 卷都已加密"、"CloudTrail 必须已启用"），可使用 **AWS 托管规则**（数百个预置的常见合规检查）或自定义规则（基于 Lambda 实现自定义评估逻辑）
- 当资源配置**偏离基准**时，系统自动将其标记为**非合规（NON_COMPLIANT）**，并可通过 [[SNS]] 发送通知，帮助满足审计和监管要求

### 检测型规则 vs 主动型规则

| 规则类型 | 评估时机 | 行为 |
|---------|---------|------|
| **检测型规则（Detective）** | 资源**部署后**评估 | 持续评估已存在资源的配置是否合规，发现偏离基准的情况 |
| **主动型规则（Proactive）** | 资源**部署前**评估 | 在资源实际创建前评估其配置（如结合 [[AWS CloudFormation]] 部署前检查），判定合规/非合规，但**不会阻止资源部署**，仍需配合其他机制（如 CloudFormation Hooks）才能真正拦截 |

> **考试陷阱**：**主动型规则不会自动阻止不合规资源的创建**——它只是提前给出合规判定结果；若题目要求"在资源创建前就拦截不合规的部署"，还需要额外的强制执行机制（如 CloudFormation Hooks 或 [[AWS Organizations]] 的服务控制策略 SCP），而不能仅依赖 Config 主动型规则本身。

### 合规修复（Remediation）

- 检测到非合规资源后，可通过 **AWS Systems Manager Automation 文档**触发**自动修复（Auto Remediation）**，无需人工干预即可将资源修正为合规状态
- 也可配置为**手动修复**——生成修复操作建议，但等待人工审批后才执行，适合对自动变更较谨慎的关键资源
- 检测（Config）+ 修复（SSM Automation）的组合是构建"自愈式（Self-Healing）"合规基础设施的标准模式

### 合规包（Conformance Packs）

- 将一组 Config 规则和修复操作**打包**成单一实体，可一次性部署到单个账户/区域，或通过 **[[AWS Organizations]]** 部署到整个组织
- 简化多账户环境下的合规治理——无需在每个账户/区域重复配置相同的规则集合

---

## 多账户多区域聚合（Aggregator）

- **聚合器（Aggregator）**是 AWS Config 的资源，用于将**多个账户、多个区域**的配置和合规信息**集中汇总**到单一账户查看
- 适合中心化的云治理团队统一监控整个企业内多个 AWS 账户的合规状态，无需登录每个账户分别查看
- 结合合规包的组织级部署，可实现"组织级统一定义规则 + 组织级统一查看合规状态"的完整治理闭环

## 与其他服务的协同

### 与 [[CloudTrail]] 的互补关系

- **CloudTrail** 记录"谁在什么时候做了什么"（操作行为的事件日志）；**AWS Config** 记录这些动作产生的"最终配置状态变化"，两者结合可提供完整的**操作与状态溯源**——先用 CloudTrail 找到"是谁做的"，再用 Config 确认"改成了什么样"

### 与 [[CloudWatch]] 的互补关系

- **CloudWatch** 关注资源运行得**好不好**（性能指标、日志）；**AWS Config** 关注资源**长什么样**（配置细节及其历史），两者是完全不同的观测维度，不可互相替代

### 与 [[AWS CloudFormation]] 的关系

- Config 的主动型规则可结合 CloudFormation 部署流程，在资源实际创建前先做合规评估，是"预防式治理（Shift-Left Governance）"实践的一环

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以查看配置历史、管理规则和聚合器 |
| **S3 存储配置快照** | 配置历史可交付到 [[S3]]，可结合 Bucket 权限和加密进一步保护 |
| **SNS 通知** | 非合规事件可通过 SNS 通知相关团队，也可与告警/工单系统集成 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **追溯资源在过去某个时间点的配置状态** | 配置历史（Configuration History） |
| **评估修改某资源会影响哪些关联资源** | 关系分析（Relationship Mapping） |
| **持续检测资源配置是否符合安全基准** | 检测型 Config 规则（托管规则/自定义规则） |
| **在资源创建前评估其合规性** | 主动型 Config 规则（仍需额外机制才能真正拦截） |
| **发现非合规资源后自动修复** | Config 规则 + SSM Automation 自动修复 |
| **多账户组织统一部署相同的合规规则集** | Conformance Packs + [[AWS Organizations]] 组织级部署 |
| **中心化查看多账户多区域的合规状态** | 聚合器（Aggregator） |
| **需要证明某次变更是谁做的、改成了什么样** | AWS Config（配置状态）+ CloudTrail（操作记录）组合 |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：追踪资源配置状态及其历史变化，回答"配置长什么样、如何变化"，区别于 CloudTrail（谁做的）和 CloudWatch（运行得怎么样）
2. **配置项 + 配置历史**：每次配置变化生成配置项，汇编成可追溯任意历史时刻状态的配置历史
3. **关系分析辅助变更影响评估**：修改前先查看资源关联关系，评估变更的影响范围
4. **检测型规则 vs 主动型规则**：前者评估已部署资源，后者评估部署前的资源，但**主动型规则本身不阻止部署**
5. **合规修复需结合 SSM Automation**：Config 负责检测，Systems Manager Automation 负责执行修复，二者组合实现自愈式治理
6. **自动修复 vs 手动修复**：自动修复无需人工干预，手动修复生成建议但需人工审批
7. **合规包（Conformance Packs）简化多账户治理**：规则和修复操作打包后可一次性部署到整个组织
8. **聚合器实现多账户多区域集中查看**：无需登录每个账户即可统一监控合规状态
9. **AWS Config vs CloudTrail 组合溯源**：CloudTrail 找到"谁做的"，Config 确认"改成了什么样"，两者互补而非替代
10. **托管规则覆盖数百种常见合规检查**：无需自行用 Lambda 实现，可直接复用 AWS 提供的预置规则

### 场景题解题思路

```
场景分析 → 判断使用 AWS Config 的哪个能力
├── "需要追溯资源过去某个时间点的配置状态" → 配置历史
├── "需要评估修改某资源会影响哪些关联资源" → 关系分析
├── "需要持续检测资源是否符合安全/合规基准" → 检测型 Config 规则
├── "需要在资源创建前评估合规性" → 主动型 Config 规则（+ CloudFormation Hooks 等强制拦截机制）
├── "发现非合规资源后希望自动修复" → Config 规则 + SSM Automation 自动修复
├── "多账户组织需要统一部署相同的合规规则集" → Conformance Packs + [[AWS Organizations]]
├── "需要中心化查看多账户多区域的合规状态" → 聚合器（Aggregator）
└── "需要确认某次配置变更是谁做的、改成了什么样" → CloudTrail（操作）+ AWS Config（状态）组合
```

## 最佳实践

1. **优先复用 AWS 托管规则**：覆盖数百种常见合规检查场景，减少自定义 Lambda 规则的开发和维护成本
2. **关键安全基线配置自动修复**：如"S3 Bucket 禁止公开访问"等高风险项，结合 SSM Automation 实现自动纠正
3. **对影响面大的资源采用手动修复**：涉及生产关键资源的修复操作应保留人工审批环节，避免自动化误修复造成故障
4. **多账户环境使用 Conformance Packs + [[AWS Organizations]]**：统一治理策略，避免各账户配置基准不一致
5. **搭配聚合器实现集中式合规视图**：中心治理团队无需逐个账户排查，提升治理效率
6. **变更前善用关系分析评估影响范围**：尤其是安全组、IAM 角色等被广泛引用的核心资源
7. **主动型规则不能替代真正的部署拦截机制**：需要强制阻止不合规部署时，应结合 CloudFormation Hooks 或 [[AWS Organizations]] SCP 等机制
8. **结合 CloudTrail 构建完整的变更溯源链路**：仅有配置状态历史不足以确定责任人，需要 CloudTrail 的操作记录补全"谁做的"这一环
