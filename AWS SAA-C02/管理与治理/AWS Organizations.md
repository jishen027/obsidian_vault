# AWS Organizations - 多账户治理与管控

> **AWS Organizations** 是多账户治理服务，让企业能够将多个 AWS 账户集中管理——统一账单（Consolidated Billing）、通过**服务控制策略（SCP）**和**资源控制策略（RCP）**设置权限护栏、批量管理合规和配置策略，是构建"多账户架构"这一 AWS 最佳实践的核心基础设施。
>
> 相关文档：[[IAM]] | [[AWS Config]] | [[CloudTrail]] | [[AWS CloudFormation]] | [[KMS]]

---

## 核心概念

### 为什么需要多账户架构

- **单账户的局限**：所有资源、团队、环境（开发/测试/生产）挤在同一个账户中，权限边界模糊、爆炸半径大（一个账户被攻破影响全部）、账单难以按团队/项目拆分
- **多账户架构的价值**：按业务单元/环境/合规要求拆分成独立账户，天然获得**账户级别的隔离边界**（账户本身就是最强的安全边界），同时通过 Organizations 集中管理这些账户，避免各自为政
- **Organizations 的核心价值**：在保留账户隔离优势的同时，提供**集中化的账单、权限护栏和策略管理**，让治理团队无需登录每个账户即可实施统一的安全和合规标准

### 核心概念

| 概念 | 说明 |
|------|------|
| **管理账户（Management Account）** | 创建组织的账户，拥有管理组织的最高权限，**原名 Master Account** |
| **成员账户（Member Account）** | 加入组织的其他账户，受组织策略约束 |
| **组织单元（OU, Organizational Unit）** | 用于分组账户的容器，可嵌套形成树状层级（如按环境分 Prod/Dev OU，或按部门分） |
| **根（Root）** | 组织树的顶层容器，包含所有 OU 和账户 |

> **考试要点**：**策略沿 OU 树自上而下继承**——附加在 Root 或父 OU 上的 SCP 会自动应用到其下所有 OU 和账户；因此可以在顶层设置组织级的基线护栏，再在特定 OU 上叠加更严格的限制，实现分层治理。

## 账单管理

| 模式 | 说明 |
|------|------|
| **合并账单（Consolidated Billing）** | 组织内所有账户的费用汇总到管理账户统一支付一份账单，并能享受**批量折扣**（如 Reserved Instance/Savings Plans 可在账户间共享，达到更高的批量定价层级） |
| **完整功能模式（All Features）** | 在合并账单基础上，进一步启用 **SCP**、**RCP**、标签策略、备份策略等完整的治理能力，是绝大多数生产组织的推荐模式 |

## 服务控制策略（SCP，考试高频）

### 核心机制

- SCP 是组织级的**权限护栏（Guardrail）**，定义 IAM 用户和角色的**权限上限**——**SCP 本身不授予任何权限**，只能进一步收窄成员账户内 IAM 策略已授予的权限
- **最终有效权限 = IAM 权限 ∩ SCP 允许的权限**——即使 IAM 策略授予了某个操作的权限，若 SCP 未允许（或显式拒绝）该操作，用户依然无法执行
- 默认提供隐式的 `FullAWSAccess` 策略（允许所有操作），管理员可替换为白名单式策略实现更严格的默认拒绝基线

### 关键限制与规则

| 项目 | 说明 |
|------|------|
| **策略大小上限** | 单个 SCP 最大 **10,240 字符**（2026 年 5 月从 5,120 字符翻倍） |
| **每节点策略数量** | 单个 Root/OU/账户最多可附加 **10 个** SCP（此前为 5 个） |
| **语法支持** | 支持完整的 IAM 策略语言，包括条件（Condition）、具体资源 ARN、`NotAction` 与 `Allow` 组合、Action 字符串开头/中间的通配符 |
| **不影响管理账户** | SCP **不会限制管理账户本身**的权限，仅约束成员账户 |

> **考试陷阱**：**SCP 是权限的"天花板"而非"授权来源"**——题目描述"某用户的 IAM 策略明明授予了权限，但依然无法执行该操作"，根本原因很可能是**组织的 SCP 限制了该权限**；SCP 不能用来"额外授予"权限，只能限制。

## 资源控制策略（RCP，新特性，考试提示）

- **RCP（Resource Control Policies）**于 2024 年底推出，与 SCP 的方向**互补而非重复**——SCP 限制**身份（用户/角色）**能做什么，RCP 限制**资源**能把权限授予给谁（包括账户外部的主体，如跨账户访问、公开访问）
- **典型价值**：即使某个 S3 Bucket Policy 意外授予了外部账户或公网访问权限，RCP 仍可作为组织级护栏统一收紧，防止单个资源策略配置失误导致数据泄露
- **支持的服务**（持续扩展中）：S3、STS、KMS、SQS、Secrets Manager、ECR、OpenSearch Serverless 等

> **考试要点**：**SCP 管身份、RCP 管资源**——题目强调"防止某个身份执行危险操作"用 SCP；题目强调"防止某个资源被过度授权给外部主体（如意外公开的 S3 Bucket）"更适合用 RCP，两者可以组合使用形成双重防护。

## 声明式策略（Declarative Policies）

- 用于**集中声明并强制执行**某个 AWS 服务在整个组织范围内的**期望配置状态**（如"所有账户的 EC2 实例必须禁止公网 IP"、"所有 VPC 必须启用 Flow Logs"）
- **核心优势**：配置一旦声明即**持续生效**——即使该服务后续新增了功能或 API，声明式策略仍会自动维持既定的配置期望，无需手动追加新规则
- 目前主要覆盖 EC2、EBS、VPC 等基础设施类服务的配置基线

---

## 标签策略与备份策略

| 策略类型 | 说明 |
|---------|------|
| **标签策略（Tag Policies）** | 标准化组织内资源标签的键值命名规范，防止各账户标签格式混乱，便于统一的成本分摊和资源管理 |
| **备份策略（Backup Policies）** | 通过 AWS Backup 在组织级别集中定义和强制执行备份计划，确保成员账户的关键资源按统一标准备份 |
| **AI 服务选择退出策略** | 控制组织内账户是否允许 AI 相关服务使用客户数据用于服务改进等目的 |

---

## 委派管理员（Delegated Administrator）

- 允许将特定 AWS 服务（如 [[AWS Config]]、GuardDuty、[[CloudTrail]]）的组织级管理权限**委派给指定的成员账户**，而非必须使用管理账户操作
- **价值**：管理账户通常应仅用于账单和组织本身的治理，日常的安全/合规服务管理可下放给专门的安全账户，遵循**最小权限和职责分离**原则

## 与其他服务的集成（考试高频）

| 集成服务 | 说明 |
|---------|------|
| **[[CloudTrail]] Organization Trail** | 在管理账户创建后自动应用到所有成员账户，实现组织级强制审计 |
| **[[AWS Config]] Conformance Packs** | 可通过 Organizations 一次性部署规则集到整个组织的所有账户 |
| **[[AWS CloudFormation]] StackSets** | 结合 Organizations 可将同一套 CloudFormation 模板批量部署到组织内多个账户/区域 |
| **AWS Control Tower** | 构建在 Organizations 之上的"着陆区（Landing Zone）"自动化服务，进一步简化多账户环境的初始搭建和护栏配置 |

## 安全性

| 机制 | 说明 |
|------|------|
| **[[IAM]] 与 SCP 协同** | SCP 设定权限上限，IAM 策略在此范围内做具体授权，两层机制共同决定最终有效权限 |
| **RCP 防止资源侧过度授权** | 作为身份侧 SCP 的补充，从资源侧限制权限授予范围 |
| **管理账户特殊保护** | 管理账户不受 SCP 约束，应严格限制其日常使用，仅用于组织治理 |
| **加密** | 组织策略本身的元数据由 AWS 管理，跨服务集成（如 Config、CloudTrail）的数据加密遵循各自服务的 [[KMS]] 集成机制 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **企业需要集中管理多个 AWS 账户的账单** | Consolidated Billing，共享 RI/Savings Plans 折扣 |
| **需要为整个组织设置权限护栏（禁止某些高危操作）** | Service Control Policies（SCP） |
| **防止资源策略意外授予外部账户/公网访问权限** | Resource Control Policies（RCP） |
| **需要在组织范围内持续强制某服务的配置基线** | 声明式策略（Declarative Policies） |
| **多账户组织需要统一部署合规检测规则** | AWS Config Conformance Packs + Organizations |
| **需要标准化组织内的资源标签规范** | 标签策略（Tag Policies） |
| **需要将安全服务管理权下放到专用安全账户** | 委派管理员（Delegated Administrator） |
| **需要批量在多账户/区域部署同一套基础设施模板** | CloudFormation StackSets + Organizations |
| **希望快速搭建符合最佳实践的多账户环境** | AWS Control Tower（构建在 Organizations 之上） |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：多账户治理服务，提供合并账单、权限护栏（SCP/RCP）、策略集中管理
2. **组织结构**：管理账户 + 成员账户，通过 OU 分组，策略沿树形结构自上而下继承
3. **SCP 不授予权限，只设定上限**：最终有效权限 = IAM 权限 ∩ SCP 允许范围，两者缺一不可
4. **SCP 不影响管理账户**：只约束成员账户
5. **SCP vs RCP**：SCP 限制身份能做什么，RCP 限制资源能把权限授予给谁，两者互补
6. **声明式策略持续生效**：配置期望即使服务新增功能/API 也会自动维持，无需手动追加规则
7. **合并账单支持折扣共享**：RI/Savings Plans 等批量折扣可在组织内账户间共享
8. **Conformance Packs/Organization Trail 依赖 Organizations**：多账户统一合规检测和审计跟踪的组织级部署基础
9. **委派管理员实现职责分离**：安全/合规服务的组织级管理可下放到专用账户，而非依赖管理账户
10. **Control Tower 构建在 Organizations 之上**：提供开箱即用的着陆区自动化，而非替代 Organizations 本身

### 场景题解题思路

```
场景分析 → 判断使用 Organizations 的哪个能力
├── "需要为多个账户提供统一账单和批量折扣" → Consolidated Billing
├── "需要禁止组织内所有账户执行某类高危操作" → Service Control Policies（SCP）
├── "需要防止某资源被意外授权给外部账户/公网" → Resource Control Policies（RCP）
├── "IAM 策略授权了但用户依然无法执行操作" → 检查是否被组织 SCP 限制
├── "需要在组织范围内持续强制某服务的配置基线" → 声明式策略（Declarative Policies）
├── "需要标准化组织内的资源标签命名" → 标签策略（Tag Policies）
├── "需要把安全服务的管理权委派给专用账户" → 委派管理员（Delegated Administrator）
├── "需要批量在多账户部署相同的基础设施模板" → CloudFormation StackSets + Organizations
└── "需要快速搭建符合最佳实践的多账户环境" → AWS Control Tower
```

## 最佳实践

1. **管理账户仅用于组织治理，不部署业务资源**：降低管理账户被攻破的影响面，也避免管理账户权限不受 SCP 约束带来的风险
2. **默认拒绝、白名单授权的 SCP 策略优于事后拉黑**：从组织顶层设定严格基线，比逐个排查违规操作更可靠
3. **按环境/业务单元设计 OU 层级结构**：让策略继承关系清晰反映实际的组织治理需求
4. **SCP 与 RCP 组合使用形成双重防护**：身份侧和资源侧同时设限，降低单点配置失误的风险
5. **安全/合规类服务的日常管理下放给委派管理员账户**：遵循最小权限和职责分离，减少管理账户的日常操作
6. **善用声明式策略维护基础设施配置基线**：避免服务新增功能后护栏"失效"，需要持续手动补丁维护
7. **多账户批量部署优先使用 StackSets 而非逐账户手动操作**：结合 Organizations 目标选择，减少人工操作和配置漂移
8. **新建多账户环境优先评估 Control Tower**：相比从零手动搭建 Organizations 治理框架，能更快获得符合最佳实践的基线配置
