# AWS Trusted Advisor - 最佳实践自动检查

> **AWS Trusted Advisor** 是**自动化的最佳实践检查**服务，持续扫描账户内的资源配置，对照 AWS 预定义的检查项，在**六大类别**（成本优化、性能、安全性、容错、服务配额、卓越运营）下给出**红/黄/绿**三色状态提示和具体改进建议。它与需要**人工逐项回答问题**的 **[[AWS Well-Architected Framework]] 工具**互补——前者是**自动化、持续扫描实际资源状态**的"体检报告"，后者是**结构化、人工参与的架构自评估**，两者常被同时提及但解决的问题层次不同。
>
> 相关文档：[[AWS Well-Architected Framework]] | [[AWS Config]] | [[Amazon GuardDuty]] | [[Cost Explorer]] | [[IAM]] | [[CloudWatch]]

## 核心概念

### 六大检查类别（考试提示：并非五大类别）

| 类别 | 检查内容示例 |
|------|-------------|
| **成本优化（Cost Optimization）** | 闲置/低利用率的 EC2、未关联的 Elastic IP、可购买 Reserved/Savings Plans 的负载 |
| **性能（Performance）** | 服务限制接近上限、EBS 卷配置不合理、CloudFront 未优化的分发配置 |
| **安全性（Security）** | 根账户未启用 MFA、安全组开放高危端口（如 22/3389 对所有来源开放）、S3 存储桶权限过于宽松 |
| **容错（Fault Tolerance）** | 未启用 Multi-AZ 的关键数据库、未配置自动扩展、EBS 快照缺失 |
| **服务配额（Service Quotas，原"服务限制"）** | 各服务用量是否接近账户配额上限，提前预警避免触及硬性限制 |
| **卓越运营（Operational Excellence）** | 资源缺少标签、未使用推荐的日志/监控配置等运维规范性检查 |

> **考试陷阱**：**Trusted Advisor 目前是六大类别，"卓越运营"是后续新增的类别**——较早的资料或题目若只提及"五大类别"，属于过时表述；作答时应以**当前六大类别**为准，尤其注意"卓越运营"类别检查的是标签规范、日志配置等运维卫生问题，而非成本/安全/容错等传统类别。

### 检查状态（红/黄/绿）

- **绿色**：未发现问题
- **黄色**：建议调查
- **红色**：建议立即处理

### 访问范围随支持计划分级（考试高频）

| 支持计划 | 可用检查范围 |
|---------|-------------|
| **Basic / Developer** | 仅可使用**一小部分核心检查**（主要集中在安全性和服务配额，如根账户 MFA、开放的高危端口） |
| **Business / Enterprise** | 解锁**全部六大类别的完整检查项**，并支持通过 **AWS Support API** 程序化访问、结合 [[CloudWatch]]/EventBridge 对检查状态变化做自动化响应 |

> **考试要点**：**题目描述"账户支持计划为 Basic，却期望看到完整的成本优化检查结果" → 不满足**，完整检查需要 **Business 或 Enterprise 支持计划**；这是"为什么 Trusted Advisor 检查项看起来比预期少"这类问题的标准排查方向。

### 排除项（Exclusions）

- 对于**已人工评估并确认符合预期**的资源（如故意开放的安全组），可将其从特定检查中**排除**，避免持续产生噪音告警，而无需真正修改资源配置

## AWS Trusted Advisor vs AWS Well-Architected Tool（考试高频对比）

| 维度 | Trusted Advisor | Well-Architected Tool |
|------|-------------------|---------------------------|
| **运作方式** | **自动化**持续扫描账户实际资源配置 | **人工**针对具体工作负载逐一回答标准化问题 |
| **检查项来源** | AWS 预定义的固定检查项，**不可自定义** | 六大支柱下的结构化问题清单，评估**架构设计决策** |
| **输出形式** | 红/黄/绿状态 + 具体资源级别的整改建议 | 高风险问题（HRIs）清单 + 改进计划 |
| **典型场景** | "我的账户里有没有明显违反最佳实践的资源配置" | "我们的整体架构设计相对最佳实践还有哪些差距" |

> **考试陷阱**：**两者常被误认为是同一个工具的不同名字**——题目描述"需要自动、持续地扫描账户资源，发现具体的配置问题（如开放的危险端口）" → **Trusted Advisor**；题目描述"需要对某个具体工作负载的整体架构设计做结构化评估，产出改进计划" → **[[AWS Well-Architected Framework]] 工具**，完整框架内容见 [[AWS Well-Architected Framework]] 独立笔记。

---

## AWS Trusted Advisor vs AWS Config（考试高频对比）

| 维度 | Trusted Advisor | [[AWS Config]] |
|------|-------------------|-------------------|
| **规则来源** | AWS **预定义**的固定检查项菜单 | 用户**自定义/选用**的规则（Managed 或 Custom Rules） |
| **历史追溯** | 只反映**当前**状态 | 记录**完整的配置变更历史**，可查看任意时间点的配置快照 |
| **自动修复** | 不提供 | 可结合 Systems Manager Automation 实现**自动修复** |
| **典型场景** | 快速体检、发现常见的最佳实践偏差 | 需要自定义合规规则、追溯配置变更历史、自动修复的场景 |

> **考试要点**：**题目描述"需要自定义合规规则并追溯资源配置的历史变化" → [[AWS Config]]**；描述"只是想快速看看账户有没有明显违反 AWS 通用最佳实践的地方" → **Trusted Advisor**，两者可以互补使用而非二选一。

## AWS Trusted Advisor vs Amazon GuardDuty（考试提示）

- **Trusted Advisor 的安全类别**做的是**静态配置检查**（如"根账户是否开启 MFA"、"安全组是否对全网开放高危端口"），检查的是**配置是否符合最佳实践**
- **[[Amazon GuardDuty]]** 做的是**持续的威胁行为检测**（如"是否存在与已知恶意 IP 的通信"、"是否有异常 API 调用模式"），检测的是**是否正在发生攻击**
- **考试陷阱**：**题目描述"检查根账户是否启用了 MFA" → Trusted Advisor**；描述"检测账户是否存在被入侵、异常登录等攻击行为" → **[[Amazon GuardDuty]]**，完整边界见 [[Amazon GuardDuty]] 独立笔记。

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **快速体检账户是否存在明显的成本浪费/安全隐患/容错缺陷** | AWS Trusted Advisor |
| **需要完整的六大类别检查结果** | 升级到 Business/Enterprise 支持计划 |
| **已人工确认某资源的"违规"配置是有意为之** | 将该资源从对应检查项中排除 |
| **需要对整体架构做结构化的自评估和改进规划** | 改用 [[AWS Well-Architected Framework]] 工具 |
| **需要自定义合规规则并追溯配置历史** | 改用 [[AWS Config]] |
| **需要检测正在发生的攻击行为，而非静态配置问题** | 改用 [[Amazon GuardDuty]] |
| **需要根据检查状态变化自动触发响应** | Business/Enterprise 支持计划 + CloudWatch/EventBridge 集成 |

## 考试重点总结

### SAA-C02 高频考点

1. **Trusted Advisor 是自动化的预定义最佳实践检查，六大类别**：成本优化、性能、安全性、容错、服务配额、卓越运营（卓越运营为后续新增）
2. **检查状态为红/黄/绿三色**：分别代表无问题、建议调查、建议立即处理
3. **Basic/Developer 支持计划只能看到少量核心检查**：完整六大类别需要 Business/Enterprise 支持计划
4. **可对已确认无误的资源设置排除项**：避免持续产生无意义的告警噪音
5. **与 Well-Architected Tool 的区别是"自动扫描现状" vs "人工评估架构设计"**：两者互补而非同一工具
6. **与 AWS Config 的区别是"固定检查菜单" vs "自定义规则+历史追溯"**：Config 支持自动修复，Trusted Advisor 不支持
7. **与 GuardDuty 的区别是"静态配置检查" vs "持续威胁行为检测"**：前者查配置是否合规，后者查是否正在被攻击
8. **成本优化只是六大类别之一**：不要把 Trusted Advisor 等同于专门的成本分析工具（真正的成本分析用 Cost Explorer/Budgets/CUR）
9. **Business/Enterprise 支持计划解锁 Support API 程序化访问**：可结合 CloudWatch/EventBridge 做自动化响应
10. **Trusted Advisor 不提供自动修复能力**：只给出建议，实际整改仍需人工或结合其他自动化工具执行

### 场景题解题思路

```
场景分析 → 判断 Trusted Advisor 相关配置
├── "快速体检账户是否存在明显的最佳实践违规" → Trusted Advisor
├── "检查结果比预期少，怀疑权限或配置问题" → 检查当前支持计划是否为 Basic/Developer
├── "某资源的检查结果是有意为之的配置" → 设置排除项
├── "需要对整体架构做结构化自评估" → 改用 Well-Architected Tool
├── "需要自定义合规规则并追溯配置历史" → 改用 AWS Config
├── "需要检测正在发生的攻击行为" → 改用 Amazon GuardDuty
└── "需要专门的成本趋势分析而非泛化检查" → 改用 Cost Explorer/Budgets/CUR
```

## 最佳实践

1. **将 Trusted Advisor 检查纳入常规运维巡检流程**：而非仅在出问题后才被动查看
2. **升级到 Business/Enterprise 支持计划以获得完整检查覆盖**：Basic/Developer 计划下的检查范围远不足以支撑生产环境治理
3. **对已评估确认的"违规"配置及时设置排除项**：保持检查结果的信噪比，避免团队对告警产生疲劳
4. **将 Trusted Advisor 与 Config、GuardDuty、Well-Architected Tool 组合使用**：分别覆盖"快速体检"、"自定义合规追溯"、"威胁检测"、"架构结构化评估"四个互补维度
5. **结合 CloudWatch/EventBridge 对红色状态的检查项做自动化通知**：避免依赖人工定期登录控制台查看
6. **不要把 Trusted Advisor 当作专门的成本分析工具**：深入的成本趋势分析和预算告警应使用 Cost Explorer/Budgets/CUR
