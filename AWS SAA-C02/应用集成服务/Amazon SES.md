# Amazon SES - Simple Email Service

> **Amazon SES（Simple Email Service）**是可大规模发送和接收电子邮件的**全功能邮件平台**，面向**事务性邮件**（订单确认、密码重置、验证码）、**营销邮件**和**批量邮件**场景，提供发送 API/SMTP 接口、域名身份验证、送达率监控（退信/投诉率）、事件跟踪等完整能力。它与 [[SNS]] 的 **Email 订阅端点**有本质区别——SNS 的 Email 端点只是把系统事件通知**少量固定订阅者**（人工确认订阅后接收），而 SES 是面向**大规模、可编程发送给任意收件人**的邮件基础设施，两者解决的是完全不同量级和场景的问题。
>

## 核心概念

### 发送与接收邮件（考试提示）

- **发送**：应用可通过 **SES API** 或标准 **SMTP 接口**发送邮件，适配几乎所有现有邮件发送代码库
- **接收**：SES 也能为**已验证的域名**接收邮件，并通过**接收规则（Receipt Rules）**将收到的邮件路由到 **[[S3]]**（归档存储）、**[[SNS]]**（触发通知）或 **[[AWS Lambda]]**（自定义处理逻辑，如自动解析、分类、转发）
- **考试陷阱**：**"SES 只能发邮件"是常见的误解**——题目描述"需要自动化处理客户回复的邮件内容（如解析工单、自动分类）" → SES 的**接收**能力 + 接收规则触发 Lambda，而不是假设需要额外部署自建邮件服务器。

### 身份验证（考试高频）

| 验证方式 | 说明 |
|---------|------|
| **单个邮箱地址验证** | 只允许从该**具体地址**发送邮件，适合测试或极少量固定发件地址的场景 |
| **域名验证** | 通过在 DNS 中添加 **TXT 记录**证明域名所有权后，可从该域名下**任意地址**发送邮件（如 `no-reply@example.com`、`support@example.com`），无需逐个验证 |
| **DKIM 签名** | 为域名配置 DKIM（DomainKeys Identified Mail），在邮件头中加入加密签名，证明邮件确实来自声明的域名，显著提升送达率、降低被判定为垃圾邮件的概率 |

> **考试要点**：**大规模/多发件地址场景应验证整个域名，而非逐个验证邮箱地址**——题目描述"需要从同一域名下的多个不同地址（如订单、客服、营销）发送邮件" → 验证**域名**一次即可覆盖该域名下所有地址；配合 **DKIM**、**SPF**、**DMARC** 记录进一步提升送达率和防伪造能力，避免邮件被主流邮箱服务商标记为垃圾邮件或直接拒收。

### 沙盒环境（Sandbox，考试最高频考点）

- **新创建的 SES 账户默认处于沙盒环境**，具备两大限制：
  1. **只能发送邮件给已验证的收件人地址/域名**——无法发送给任意未验证的真实客户
  2. **发送速率和每日发送配额都被严格限制**（通常为每秒极低速率、每 24 小时几百封）
- 需要提交**生产访问权限申请（Request Production Access）**，说明使用场景和退信/投诉处理机制，审核通过后才能移出沙盒，向任意收件人发送邮件并获得更高配额

> **考试陷阱**：**"SES 配置正确但邮件发不出去/收件人收不到"，最常见的原因是账户仍处于沙盒环境**——题目描述"应用集成 SES 后可以发给自己的测试邮箱，但发给真实客户就失败" → 检查账户是否仍在**沙盒模式**，需要申请移出沙盒，而不是排查代码逻辑或 IAM 权限。

### 发送配额与速率

- **每秒最大发送速率（Send Rate）**和**24 小时最大发送配额（Sending Quota）**是两个独立限制，账户的发送信誉良好且用量增长后配额会**逐步自动提升**，也可主动申请提升
- 超出速率限制的请求会被**限流（Throttle）**，应用层应实现指数退避重试

### 送达率管理：退信与投诉（考试高频）

- SES 持续监控账户的**退信率（Bounce Rate）**和**投诉率（Complaint Rate）**
- 若这两项指标**超过阈值**，AWS 可能**暂停账户的发送能力**，以保护 SES 整体发送域的信誉不被滥用者拖累
- **考试要点**：**必须妥善处理退信和投诉事件**（如立即将永久退信的地址从发送列表中移除），而不是持续向同一批无效地址反复发送——可通过**配置集（Configuration Set）**将退信/投诉事件推送到 [[SNS]] 或 [[AWS Lambda]]，实现自动化的列表清理。

### 配置集（Configuration Set）与事件跟踪

- 为一组邮件应用统一的**跟踪和事件路由规则**，可将发送、送达、打开、点击、退信、投诉等事件推送到 **[[SNS]]**、Kinesis Data Firehose 或 **[[CloudWatch]]**，用于构建发送效果的监控和分析仪表盘
- 是量化邮件送达质量、及时发现异常（如某批次退信率骤增）的标准手段

### 专用 IP 地址（Dedicated IP）

- 高发送量客户可申请**专用 IP 地址**（或专用 IP 池），发送信誉与其他 SES 客户共享的默认 IP 池**相互隔离**
- **考试要点**：题目描述"担心与其他 SES 客户共用 IP 导致自身发送信誉被他人的不良发送行为拖累" → 使用**专用 IP**，而不是默认共享 IP 池。

## SES vs SNS Email 端点（考试高频对比）

| 维度 | Amazon SES | SNS Email 订阅端点 |
|------|-----------|---------------------|
| **定位** | 全功能邮件发送/接收平台 | 事件通知的一种订阅端点类型 |
| **收件人规模** | 面向**任意数量**的外部收件人（客户、用户） | 面向**少量固定**的内部订阅者（如运维团队邮箱） |
| **收件人确认** | 无需收件人手动确认（发送方需验证发件身份） | 收件人需**手动确认订阅**才能开始接收 |
| **内容形式** | 支持模板化、个性化正文、附件、HTML 富文本 | 固定的通知文本格式 |
| **典型场景** | 订单确认、密码重置、营销邮件、批量通知 | 系统告警通知运维人员 |

> **考试陷阱**：**题目描述"需要向大量客户发送个性化的订单确认邮件" → SES**；题目描述"CloudWatch 告警触发后需要给运维团队几个固定邮箱发通知" → **SNS Email 端点**已经足够，无需引入 SES；混淆两者是这一知识点最常见的失分点，完整的 SNS 订阅端点类型见 [[SNS]] 独立笔记。

> **现状提示**：**[[Amazon Pinpoint (Deprecated)]]**（面向细分受众的营销编排服务）历史上其 Email 渠道底层就是复用 SES 的发送能力；随着 Pinpoint 营销功能于 2026-10-30 终止支持，需要"细分 + 自动化编排 + 邮件发送"的场景应改为**直接使用 SES 处理发送，另评估 Amazon Connect 承担细分/编排逻辑**，完整现状说明见 [[Amazon Pinpoint (Deprecated)]] 独立笔记。

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以调用 SES API 发送邮件 |
| **传输加密** | API/SMTP 调用默认通过 TLS 加密传输 |
| **DKIM 域名签名** | 证明邮件确实来自声明的域名，防止伪造 |
| **[[KMS]] 集成** | 接收邮件存储到 S3 时，可使用 KMS 密钥对邮件内容加密 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **应用需要发送订单确认、密码重置等事务性邮件** | Amazon SES API/SMTP 发送 |
| **需要从同一域名的多个地址发送邮件** | 验证整个域名，而非逐个验证邮箱地址 |
| **邮件发送后收件人收不到，但测试邮箱正常** | 检查账户是否仍处于沙盒环境，申请生产访问权限 |
| **需要提升邮件送达率，避免被判定为垃圾邮件** | 配置 DKIM/SPF/DMARC |
| **需要自动清理无效收件地址** | 配置集将退信/投诉事件推送到 SNS/Lambda 自动化处理 |
| **需要监控邮件打开率、点击率等发送效果** | 配置集 + 事件推送到 CloudWatch/Kinesis Data Firehose |
| **高发送量场景担心与其他客户共用 IP 影响信誉** | 申请专用 IP 地址 |
| **需要自动化处理客户回复的邮件内容** | SES 接收规则 + 触发 Lambda/投递到 S3 |
| **只需通知少量内部运维人员** | 改用 SNS Email 订阅端点，无需引入 SES |

## 考试重点总结

### SAA-C02 高频考点

1. **SES 是全功能邮件发送/接收平台，不只是发送工具**：接收邮件可路由到 S3/SNS/Lambda
2. **域名验证优于逐个邮箱验证**：大规模/多发件地址场景应验证整个域名
3. **新账户默认处于沙盒环境**：只能发给已验证收件人，且配额极低，需申请生产访问权限
4. **"邮件发不出去"的首要排查点是沙盒限制**：而非代码逻辑或权限配置
5. **退信率/投诉率超标会导致账户被暂停发送能力**：必须自动化清理无效地址
6. **配置集用于统一的事件跟踪和路由**：发送/退信/投诉等事件可推送到 SNS/CloudWatch/Kinesis Data Firehose
7. **DKIM/SPF/DMARC 提升送达率、防止伪造**：尤其对大规模发送场景至关重要
8. **专用 IP 地址隔离发送信誉**：避免被其他 SES 客户的不良行为拖累
9. **SES 与 SNS Email 端点定位完全不同**：前者面向大规模外部收件人的可编程发送，后者是少量固定内部订阅者的通知渠道
10. **发送速率和 24 小时配额是两个独立限制**：均可随信誉提升或申请而增长

### 场景题解题思路

```
场景分析 → 判断 Amazon SES 相关配置
├── "需要向大量客户发送个性化事务性/营销邮件" → Amazon SES
├── "只需通知少量固定的内部运维邮箱" → 改用 SNS Email 端点
├── "同一域名下多个地址都要发信" → 验证域名而非逐个邮箱
├── "邮件发不出去，但测试邮箱正常" → 检查是否仍处于沙盒环境
├── "担心邮件被判定为垃圾邮件" → 配置 DKIM/SPF/DMARC
├── "需要自动清理无效收件地址" → 配置集 + SNS/Lambda 处理退信投诉
├── "高发送量需要独立的发送信誉" → 申请专用 IP
└── "需要自动处理客户的回信内容" → SES 接收规则 + Lambda/S3
```

## 最佳实践

1. **上线前提前申请移出沙盒环境**：避免生产发布当天才发现无法给真实客户发信
2. **大规模/多地址发送场景优先验证域名而非单个邮箱**：减少重复验证的运维成本
3. **务必配置 DKIM/SPF/DMARC**：显著提升送达率，降低被主流邮箱服务商拒收的概率
4. **通过配置集自动化处理退信和投诉**：及时清理无效地址，保护账户发送信誉不被暂停
5. **高发送量场景评估专用 IP**：避免与其他客户共享 IP 池带来的信誉风险
6. **明确 SES 与 SNS Email 端点的适用边界**：内部少量通知用 SNS，外部大规模可编程发送用 SES
7. **敏感邮件内容的接收存储启用 KMS 加密**：尤其是包含用户隐私信息的收件内容
8. **持续监控发送效果指标**：结合配置集事件数据及时发现异常批次，而非等账户被暂停才排查
