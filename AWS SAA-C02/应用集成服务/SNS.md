# Amazon SNS - Simple Notification Service

> **Amazon SNS（Simple Notification Service）** 是全托管的**发布/订阅（Pub/Sub）消息服务**，允许一个发布者将消息**一对多**地推送给多个订阅端点，实现事件通知与系统间的扇出（Fan-out）架构。
>
> 相关文档：[[SQS]] | [[Lambda]] | [[CloudWatch]] | [[Amazon Kinesis]] | [[KMS]]

---

## 核心概念

### 发布/订阅模型

- **Topic（主题）**：消息发布的逻辑通道，发布者只需将消息发送到 Topic，无需关心有哪些订阅者
- **发布者（Publisher/Producer）**：向 Topic 发送消息的应用、服务或 AWS 事件源（如 CloudWatch Alarm、S3 事件）
- **订阅者（Subscriber）**：注册到 Topic 上的接收端点，Topic 收到消息后会**自动推送（Push）**给所有已订阅的端点
- 与 SQS 的拉取（Pull）模型不同，SNS 是**推送**模型——消息产生后立即主动投递，不支持消费者按自己的节奏拉取或重放历史消息

### SNS 定位（考试要点）

| 服务 | 模型 | 消费方式 | 典型场景 |
|------|------|---------|---------|
| **SNS** | 发布/订阅（Pub/Sub），推送 | 一条消息广播给**所有**订阅端点 | 事件通知、多系统扇出、告警分发 |
| [[SQS]] | 点对点，拉取 | 一条消息通常只被**一个**消费者取走并删除 | 异步任务队列、削峰填谷 |
| [[Amazon Kinesis]] | 流式，拉取 | 多消费者可独立、重复读取同一数据流 | 实时数据流分析、日志/点击流处理 |

> **考试陷阱**：题目描述"一条事件需要同时触发多个独立系统的处理逻辑"（如订单创建后需要同时触发发货、计费、通知三个系统）→ 首选 **SNS**（或 SNS + SQS 扇出）；若只是"多个 Worker 分担同一批任务"→ 用 **SQS**，让多个消费者共享一个队列即可，不需要 SNS。

## 订阅端点类型

| 端点类型 | 说明 | 典型场景 |
|---------|------|---------|
| **[[SQS]]** | 消息投递到 SQS 队列 | Fan-out 扇出模式，各下游系统独立异步消费 |
| **[[Lambda]]** | 直接触发 Lambda 函数执行 | 事件驱动的实时处理逻辑 |
| **HTTP/HTTPS** | 推送到任意 Web 端点 | Webhook 集成第三方系统 |
| **Email / Email-JSON** | 发送邮件通知 | 人工告警、运营通知 |
| **SMS** | 发送短信 | 紧急告警、验证码类通知 |
| **移动推送（Mobile Push）** | 通过 APNs/FCM 等平台端点推送到移动 App | App 消息推送 |

> **考试要点**：HTTP/HTTPS、Email、SMS 端点需要**用户手动确认订阅（Confirm Subscription）**后才能开始接收消息；SQS 和 Lambda 订阅通过资源策略自动授权，无需人工确认。

---

## Fan-out（扇出）架构模式

- **场景**：一个事件需要被多个独立系统各自完整处理（例如订单事件需要同时触发库存扣减、发货通知、数据分析三条流水线）
- **实现**：SNS Topic 同时订阅多个 [[SQS]] 队列，发布者只需发一次消息到 Topic，SNS 自动将消息复制并投递到每个订阅队列
- **优势**：
  - 相比让多个消费者共享同一个 SQS 队列（消息只会被其中一个取走），扇出模式确保**每个下游队列都能收到完整副本**
  - 每条下游流水线独立异步处理，互不阻塞，某一路故障不影响其他路
  - 新增下游系统只需新增一个订阅，无需改动发布者代码

```
发布者 → SNS Topic → SQS 队列 A（库存服务）
                    → SQS 队列 B（发货服务）
                    → SQS 队列 C（数据分析）
```

## 消息过滤（Message Filtering）

- 默认情况下，Topic 的所有订阅者都会收到**全部**消息
- 可为每个订阅配置**过滤策略（Filter Policy）**，基于消息属性（Message Attributes）只接收满足条件的消息子集
- **优势**：避免"所有订阅者收到全部消息后自行判断是否处理"的浪费，减少不必要的调用和成本

> **考试陷阱**：题目描述"多个订阅者只关心特定类型/区域/优先级的消息子集"→ 使用 **SNS Message Filtering**，而不是在每个订阅者内部编写过滤逻辑。

## FIFO 主题

| 特性 | 标准主题（Standard） | FIFO 主题 |
|------|---------------------|-----------|
| **消息顺序** | 尽力而为，不保证顺序 | 严格先进先出，按 `MessageGroupId` 分组保序 |
| **消息交付** | 至少一次，可能重复 | 恰好一次处理，支持去重 |
| **订阅端点** | SQS、Lambda、HTTP/S、Email、SMS、移动推送 | **仅支持 SQS 订阅**（且必须是 FIFO 队列） |
| **主题命名** | 任意名称 | 必须以 **`.fifo`** 结尾 |

> **考试陷阱**：FIFO 主题**只能订阅 FIFO 类型的 SQS 队列**，不能直接订阅 Lambda、HTTP 端点或标准 SQS 队列。

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以 `Publish`/`Subscribe` 到 Topic |
| **SNS 访问策略（Topic Policy）** | 附加在 Topic 上的资源策略，类似 S3 Bucket Policy，可授权其他账户发布/订阅 |
| **传输加密** | 所有 API 调用默认通过 HTTPS |
| **静态加密（SSE）** | 可选启用，使用 [[KMS]] 管理的密钥对 Topic 中的消息内容加密 |

## 与其他服务集成（考试高频）

### CloudWatch Alarm + SNS

- [[CloudWatch]] 告警触发时，可直接发布消息到 SNS Topic，再由 Topic 分发给 Email（通知运维人员）、Lambda（自动化修复）、SQS（记录审计）等多个订阅者
- 是"资源异常时同时通知人工并触发自动化响应"的标准解法

### S3 事件通知 + SNS

- S3 对象事件（如 `PUT`、`DELETE`）可直接发布到 SNS Topic，再扇出到多个下游处理系统

### SNS + SQS 扇出 + Lambda

- Topic 同时订阅多个 SQS 队列，每个队列再各自通过 Lambda 事件源映射触发独立的处理函数，兼具"广播"与"异步缓冲解耦"的双重优势

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **一对多事件广播** | SNS + 多个 SQS 订阅（Fan-out） |
| **系统异常告警** | CloudWatch Alarm → SNS → Email/SMS + Lambda 自动化响应 |
| **只关心特定子集消息的多订阅者** | SNS Message Filtering |
| **强顺序 + 防重复的多下游分发** | SNS FIFO 主题 + FIFO SQS 订阅 |
| **移动 App 推送通知** | SNS 移动推送端点（APNs/FCM） |
| **第三方系统 Webhook 集成** | SNS HTTP/HTTPS 订阅 |

## 考试重点总结

### SAA-C02 高频考点

1. **核心模型**：发布/订阅（Pub/Sub），消息推送给**所有**订阅端点，与 SQS 的点对点拉取模型相反
2. **Fan-out 扇出模式**：SNS + 多个 SQS 订阅是"一条事件触发多个独立系统"的标准架构
3. **订阅确认机制**：HTTP/HTTPS、Email、SMS 需手动确认订阅；SQS、Lambda 通过策略自动授权
4. **Message Filtering**：订阅者只想接收消息子集时用过滤策略，而非在消费端自行过滤
5. **FIFO 主题限制**：FIFO 主题只能订阅 FIFO SQS 队列，不支持 Lambda/HTTP/Email 等其他端点类型
6. **CloudWatch Alarm 标准搭档**：告警 → SNS → 多渠道通知（Email/SMS）+ 自动化响应（Lambda）
7. **SNS 不持久化消息**：未订阅或订阅端点故障期间产生的消息不会被保留或重放（区别于 Kinesis）
8. **SNS vs SQS 选型**：广播多个独立系统用 SNS；多个 Worker 分担同一批任务用 SQS
9. **静态加密**：涉及敏感数据的 Topic 应通过 KMS 启用 SSE
10. **跨账户发布/订阅**：通过 Topic Policy（资源策略）授权，而非仅依赖 IAM 策略

### 场景题解题思路

```
场景分析 → 选择 SNS 配置
├── "一条事件需要同时触发多个独立系统处理" → SNS + 多个 SQS 订阅（Fan-out）
├── "资源异常需要同时通知运维人员并自动化响应" → CloudWatch Alarm → SNS → Email/SMS + Lambda
├── "订阅者只关心某类/某区域的消息子集" → SNS Message Filtering
├── "多下游分发场景下要求严格顺序、不能重复" → SNS FIFO 主题 + FIFO SQS 订阅
├── "需要给移动 App 用户推送通知" → SNS 移动推送端点
├── "需要把事件推给第三方 Webhook" → SNS HTTP/HTTPS 订阅
└── "多个 Worker 分摊同一批任务，无需广播" → 改用 SQS，而非 SNS
```

## 最佳实践

1. **多系统需要感知同一事件时优先用 Fan-out**：SNS + SQS 组合优于让发布者直接调用每个下游系统
2. **善用 Message Filtering**：减少订阅者的无效调用和处理成本
3. **告警场景搭配多渠道订阅**：Email/SMS 保证人工可见，Lambda/SQS 实现自动化联动
4. **强顺序广播场景使用 FIFO 主题**，并确保下游订阅的是 FIFO SQS 队列
5. **HTTP/HTTPS 端点及时确认订阅**：未确认的订阅不会收到消息，需在集成测试中验证
6. **静态数据启用 SSE 加密**：涉及敏感信息的通知内容应通过 KMS 加密
7. **跨账户场景显式配置 Topic Policy**：明确允许哪些账户可以发布或订阅
