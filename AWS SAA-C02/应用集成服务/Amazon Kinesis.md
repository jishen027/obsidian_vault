# Amazon Kinesis - 实时流数据处理

> **Amazon Kinesis** 是一组用于收集、处理、存储和交付**实时流数据**的全托管服务集合，能够每秒从数千个源摄入千兆字节级数据，适合日志、遥测、点击流、音频和视频等场景。
>
> 相关文档：[[SQS]] | [[SNS]] | [[Lambda]] | [[S3 - Object Storage]] | [[数据仓库服务 - Redshift]] | [[DynamoDB - NoSQL]]

---

## 核心概念

### Kinesis 家族总览

| 服务 | 定位 | 典型场景 |
|------|------|---------|
| **Kinesis Data Streams (KDS)** | 自定义实时消费的流数据管道 | 需要自己写消费者程序做实时处理的场景 |
| **Kinesis Data Firehose** | 全托管的流数据交付服务 | 无需自定义消费者，直接近实时落地到 S3/Redshift 等目标 |
| **Kinesis Data Analytics** | 对流数据做实时 SQL/Apache Flink 分析 | 实时聚合、异常检测、实时仪表盘 |
| **Kinesis Video Streams** | 时间索引的视频流摄入与存储 | 安全摄像头、机器视觉、音视频分析 |

### Kinesis vs SQS/SNS（考试要点）

| 服务 | 模型 | 消息保留/重放 | 消费方式 |
|------|------|--------------|---------|
| **Kinesis Data Streams** | 拉取（Pull），流式 | 默认 24 小时，最长 **365 天**，支持**多消费者独立重放**同一数据 | 多个消费者可各自从任意位置读取，互不影响 |
| [[SQS]] | 拉取（Pull），点对点 | 消息被消费后即删除，不支持重放 | 一条消息通常只被一个消费者取走并删除 |
| [[SNS]] | 推送（Push），发布/订阅 | 不持久化，未订阅即丢失 | 消息广播给所有订阅端点 |

> **考试陷阱**：题目强调"需要保留历史数据、支持多个应用各自独立重复读取同一份流数据"→ **Kinesis Data Streams**；只需要"一次性异步解耦"或"一对多广播"，用 SQS/SNS 即可，不必上 Kinesis（Kinesis 更复杂、需要管理分片）。

## Kinesis Data Streams（数据流）

### 核心组件

- **生产者-消费者模型**：生产者（Producer）通过 API/KPL（Kinesis Producer Library）写入数据，消费者（Consumer）通过 API/KCL（Kinesis Client Library）读取数据
- **分片（Shard）**：数据流的基本吞吐单位
  - 每个分片：写入 **1 MB/s 或 1,000 条记录/秒**，读取 **2 MB/s**
  - 流的总吞吐量 = 分片数量 × 单分片吞吐量，需要更高吞吐时**增加分片数（Resharding）**
- **分区键（Partition Key）**：决定记录被写入哪个分片，相同分区键的数据会被路由到同一分片，从而保证**同一分区键内的顺序性**
- **序列号（Sequence Number）**：分片内记录的唯一递增标识，消费者据此追踪读取位置

### 容量模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **预置模式（Provisioned）** | 手动指定分片数量，按分片数付费 | 吞吐量可预估、需要精细控制成本的场景 |
| **按需模式（On-Demand）** | 自动根据流量弹性伸缩吞吐量，无需管理分片 | 流量不可预测或不想手动管理分片的场景 |

### 消费模式：共享吞吐 vs 增强扇出

| 消费模式 | 吞吐量 | 延迟 | 说明 |
|---------|--------|------|------|
| **标准消费者（共享吞吐）** | 每个分片 **2 MB/s 由所有消费者共享** | 约 200ms 起 | 消费者越多，平均每个消费者可用带宽越低 |
| **增强扇出（Enhanced Fan-Out, EFO）** | 每个消费者独享每个分片 **2 MB/s** | 约 70ms | 每个注册的 EFO 消费者都有专属吞吐通道，多消费者互不争抢带宽 |

> **考试陷阱**：题目描述"多个消费者应用同时读取同一数据流，出现读取吞吐量不足或消费延迟增加"→ 应启用 **Enhanced Fan-Out**，而不是单纯增加分片数量。

### 保留期

- 默认保留 **24 小时**，可延长至 **365 天**（Extended Data Retention）
- 保留期内数据可被任意消费者多次、独立地重放（Replay）

## Kinesis Data Firehose（交付流）

- **定位**：全托管的**交付**服务，专注于将流数据近实时地加载到目标存储/分析服务，**没有"消费者订阅"概念**，数据由 Firehose 自动投递
- **数据转换**：交付前可调用 **[[Lambda]]** 函数对数据做格式转换（如 JSON 转 Parquet/ORC）或轻量处理
- **缓冲机制**：数据先按**缓冲大小（Buffer Size，最小 1 MB）**或**缓冲时间（Buffer Interval，最小 60 秒）**中先满足者触发投递，因此是**近实时（Near Real-Time）**而非真正的亚秒级实时
- **目的地**：[[S3 - Object Storage]]、[[数据仓库服务 - Redshift]]、Amazon OpenSearch Service、Splunk、HTTP 端点、第三方服务商
- **自动缩放**：无需管理分片，吞吐量随数据量自动伸缩

> **考试陷阱**：Firehose **不支持自定义消费者程序**，也**不支持消息重放**；若题目要求"多个自定义应用需要各自独立处理同一份流数据"，答案应是 Data Streams 而非 Firehose。

---

## Kinesis Data Analytics（实时分析）

- 对 Kinesis Data Streams 或 Firehose 中的流数据执行**实时 SQL 查询**或基于 **Apache Flink** 的应用逻辑
- 典型用途：实时聚合指标、滑动窗口计算、异常检测、实时仪表盘数据源
- 输入源可以是 Kinesis Data Streams/Firehose，处理结果可再输出到 Firehose（进而落地 S3/Redshift）、Lambda 或另一个 Data Stream

> **考试要点**：题目描述"需要对流数据做实时 SQL 聚合/窗口计算，而不是简单地落地存储"→ **Kinesis Data Analytics**。

---

## Kinesis Video Streams（视频流）

- 专门用于传输和存储**时间索引**的视频及音频数据
- **应用场景**：安全摄像头、智能手机视频上传、机器视觉、结合 Amazon Rekognition Video 做实时视频分析
- **保留期**：默认 24 小时，最长可配置至 **7 天**
- 每个生产者（如一台摄像头）对应一个独立的流，支持批量设备并发写入

---

## Data Streams vs Firehose 核心对比

| 特性 | Kinesis Data Streams | Kinesis Data Firehose |
|------|----------------------|------------------------|
| **数据处理方式** | 需自定义消费者程序（KCL/Lambda）处理 | 自动投递到 AWS 目标，可选 Lambda 轻量转换 |
| **延迟** | 亚秒级（实时） | 60 秒或以上（近实时，取决于缓冲配置） |
| **数据保留/重放** | 支持，最长 365 天，多消费者独立重放 | 不支持，无持久化订阅概念 |
| **扩展方式** | 需管理分片数量（或使用按需模式） | 完全托管，自动缩放，无需管理分片 |
| **典型场景** | 需要多个自定义应用实时处理同一数据流 | 只需把数据近实时落地到 S3/Redshift 等存储 |

## 考试重点总结

### SAA-C02 高频考点

1. **Kinesis 定位**：专为实时/近实时流数据设计，区别于 SQS（异步任务队列）和 SNS（一次性广播）
2. **分片吞吐限制**：写入 1 MB/s（或 1,000 条/秒），读取 2 MB/s，超出需增加分片
3. **保留期与重放**：Data Streams 默认 24 小时最长 365 天，支持多消费者独立重放；Firehose 不支持重放
4. **Enhanced Fan-Out**：多消费者读取吞吐不足时，用 EFO 让每个消费者独享 2 MB/s，而非单纯扩分片
5. **Firehose 无消费者概念**：数据直接投递到目的地，靠缓冲大小/时间控制延迟，是近实时而非真正实时
6. **数据转换靠 Lambda**：Firehose 交付前可用 Lambda 做格式转换（JSON → Parquet 等）
7. **Data Analytics 用于实时聚合**：需要流数据实时 SQL/窗口计算时选它，而非仅落地存储
8. **按需模式简化容量管理**：流量不可预测时优先用 On-Demand，避免手动管理分片
9. **分区键决定顺序性**：同一分区键的数据保证进入同一分片、保持顺序，跨分区键不保证全局顺序
10. **视频流独立于其他三种**：Kinesis Video Streams 专注音视频，不与 Data Streams/Firehose 共享分片机制

### 场景题解题思路

```
场景分析 → 选择 Kinesis 服务
├── "需要自定义程序实时处理流数据，且要求可重放历史数据" → Kinesis Data Streams
├── "只需把流数据近实时导入 S3/Redshift，无需自己写消费者" → Kinesis Data Firehose
├── "需要在数据落地前用 Lambda 做格式转换" → Firehose + Lambda 转换
├── "需要对流数据做实时 SQL 聚合/窗口分析" → Kinesis Data Analytics
├── "多个消费者应用共享同一数据流，吞吐/延迟不达标" → 启用 Enhanced Fan-Out
├── "写入吞吐量不足，出现 ProvisionedThroughputExceeded" → 增加分片数量（Resharding）或改用按需模式
├── "需要传输/存储摄像头视频数据" → Kinesis Video Streams
└── "只需要一次性异步解耦或一对多广播，无需保留/重放" → 改用 SQS/SNS，而非 Kinesis
```

## 最佳实践

1. **流量不可预测时使用按需模式**：避免手动预置分片导致吞吐不足或浪费
2. **多消费者场景优先评估 Enhanced Fan-Out**：避免多个应用共享 2 MB/s 导致延迟上升
3. **合理设计分区键**：避免热点分片（Hot Shard），分区键应有足够的基数以均匀分布负载
4. **仅需落地存储时选择 Firehose**：比自建 Data Streams 消费者更简单、运维成本更低
5. **需要重放或多路独立处理时选择 Data Streams**：Firehose 无法满足重放和多消费者独立处理的需求
6. **按需延长保留期**：需要长时间窗口回溯分析时，将 Data Streams 保留期延长至 365 天
7. **Firehose 缓冲参数按延迟要求调优**：对延迟敏感的场景调小 Buffer Size/Interval，但会增加请求次数和成本
