# Amazon Pinpoint - 多渠道客户互动服务

> ⚠️ **重要现状提示（截至 2026-09）**：AWS 已宣布 Amazon Pinpoint 于 **2026 年 10 月 30 日终止支持**，**新客户自 2025 年 5 月起已无法开通**，其**营销分析层**（活动 Campaign、旅程 Journey、细分 Segment、模板、分析仪表盘）将被**彻底下线**；但**事务性发送能力**（SMS、推送、语音）已于 2024 年**更名为 AWS End User Messaging** 并持续提供，API 基本不变、无需大规模改造。AWS 官方迁移建议：活动/旅程 → **Amazon Connect Outbound Campaigns**；细分/终端节点 → **Amazon Connect Customer Profiles**；邮件发送 → **[[Amazon SES]]**。以下内容按 SAA-C02 传统考点整理 Pinpoint 的核心概念，但**在真实生产环境和最新考纲中应以上述迁移路径为准**，不应再新建基于 Pinpoint 营销功能的架构。
>
> **Amazon Pinpoint** 传统上是**多渠道、有针对性的客户互动服务**——在 [[Amazon SES]]（邮件发送）、SMS/推送等基础发送能力之上，叠加**用户细分（Segment）**、**自动化多步骤旅程（Journey）**和**参与度分析**，实现"给正确的人、在正确的渠道、发送正确的消息"，区别于 [[SNS]]/SES 只负责"把消息送达"而不管**该给谁发、什么时候发**。
>
> 相关文档：[[Amazon SES]] | [[SNS]] | [[AWS Lambda]] | [[Amazon Kinesis]] | [[S3]]

## 核心概念（传统架构，考试历史考点）

### 终端节点（Endpoint）

- 代表一个可投递消息的**具体目标**——一台设备的推送令牌、一个邮箱地址、一个手机号码
- 每个终端节点可以关联**用户属性**（Attributes）和**行为数据**，作为后续细分和个性化的依据

### 细分（Segment）

- 基于终端节点的属性或行为，定义一组**目标受众**——如"过去 7 天未打开 App 的用户"、"来自特定地区的高价值用户"
- 支持**动态细分**（条件持续生效，成员自动进出）和**静态细分**（导入固定名单）

### 活动（Campaign）

- 面向某个**细分**、在**指定渠道**（推送/短信/邮件/语音/应用内消息）、按**计划或触发条件**发送的一次性或周期性消息投放

### 旅程（Journey）

- **多步骤、多渠道、带分支逻辑**的自动化用户互动流程（类似"drip campaign"）——例如"用户注册后立即发欢迎邮件 → 3 天未激活则推送提醒 → 7 天仍未激活则发短信优惠券"
- 是 Pinpoint 相较单次 Campaign **更复杂的编排能力**，支持基于用户行为动态分支

### 支持的渠道

| 渠道 | 说明 |
|------|------|
| **推送通知（Push）** | 通过 APNs/FCM 等平台推送到移动 App |
| **短信（SMS）** | 文本消息，含验证码、营销短信等 |
| **邮件（Email）** | 底层复用 **[[Amazon SES]]** 的发送能力 |
| **语音（Voice）** | 自动语音呼叫 |
| **应用内消息（In-App）** | 用户打开 App 时在界面内展示的消息 |
| **自定义渠道** | 通过 **[[AWS Lambda]]** 对接第三方渠道（如 Webhook、第三方推送平台） |

## Pinpoint vs SNS vs SES（考试高频对比，历史考点）

| 维度 | [[SNS]] | [[Amazon SES]] | Amazon Pinpoint |
|------|---------|-----------------|------------------|
| **核心定位** | 通用发布/订阅通知广播 | 邮件发送/接收基础设施 | 面向细分受众的**多渠道营销/互动编排** |
| **是否支持用户细分** | 不支持 | 不支持 | **支持**（Segment） |
| **是否支持多步骤自动化流程** | 不支持 | 不支持 | **支持**（Journey） |
| **是否内置参与度分析** | 不支持 | 基础发送统计 | **完整的分析仪表盘**（打开率、转化漏斗等） |
| **典型场景** | 系统事件广播、告警 | 事务性/批量邮件发送 | 基于用户行为的个性化多渠道营销 |

> **考试陷阱（历史考点）**：**题目描述"需要基于用户行为触发多步骤、跨渠道的个性化营销流程，并跟踪参与度"** → 传统答案是 **Pinpoint**；但结合当前现状，**新架构应评估 Amazon Connect Outbound Campaigns（活动/旅程）+ SES（邮件发送）的组合**，而非继续基于即将下线的 Pinpoint 营销功能设计。若题目只是"广播系统事件通知"或"发送事务性邮件"，则 Pinpoint 并非必要——**SNS/SES 已经足够**，Pinpoint 的价值仅在于**细分 + 编排 + 分析**这一层。

## 与 AWS End User Messaging 的关系（现状核心）

- 2024 年起，Pinpoint 的**事务性发送能力**（SMS、推送、语音）被**重新品牌化**为 **AWS End User Messaging**，作为独立产品线继续演进，**不受 Pinpoint 营销层下线影响**
- 换言之：**"发短信/推送本身"这件事继续存在（改名为 AWS End User Messaging）；"基于细分做营销活动编排和分析"这件事正在被移除**，需要迁移到 Amazon Connect 相关能力
- **考试要点**：若题目/资料中出现 **AWS End User Messaging**，应理解为 Pinpoint 事务性发送能力的延续，而非全新概念；若题目涉及**营销活动、旅程编排、用户细分**，应认识到这部分已不再由 Pinpoint 承载。

## 典型应用场景（含现状标注）

| 场景 | 传统方案（历史考点） | 当前推荐方案 |
|------|---------------------|-------------|
| **基于用户行为的多步骤营销自动化** | Pinpoint Journey | Amazon Connect Outbound Campaigns |
| **精准用户细分定向发送** | Pinpoint Segment | Amazon Connect Customer Profiles |
| **纯粹的事务性 SMS/推送/语音发送** | Pinpoint | **AWS End User Messaging**（无需迁移，仅更名） |
| **大规模事务性/营销邮件发送** | Pinpoint（底层调用 SES） | 直接使用 **[[Amazon SES]]** |
| **系统事件广播给内部固定订阅者** | 不适用 Pinpoint | **[[SNS]]** |
| **参与度分析和转化漏斗跟踪** | Pinpoint 分析仪表盘 | 需评估替代分析方案（Pinpoint 分析仪表盘将随下线一并移除） |

## 考试重点总结

### SAA-C02 高频考点（含现状提示）

1. **Pinpoint 传统定位是"细分 + 编排 + 分析"，而非单纯的发送通道**：这是与 SNS/SES 的核心区别
2. **Segment（细分）驱动"发给谁"，Campaign（活动）驱动"发一次"，Journey（旅程）驱动"多步骤自动化流程"**：三者是递进关系
3. **Email 渠道底层复用 Amazon SES**：Pinpoint 不是独立的邮件发送引擎
4. **⚠️ Pinpoint 已宣布 2026-10-30 终止支持，新客户自 2025-05 起无法开通**：营销层（Campaign/Journey/Segment/分析）被下线
5. **事务性发送能力（SMS/推送/语音）已更名为 AWS End User Messaging 并持续提供**：API 基本不变，不受下线影响
6. **迁移路径**：活动/旅程 → Amazon Connect Outbound Campaigns；细分 → Customer Profiles；邮件 → SES
7. **不要在新场景题/新架构设计中把 Pinpoint 当作面向未来的推荐答案**：应结合上述迁移路径判断
8. **Pinpoint vs SNS**：广播通知无需细分/编排用 SNS，需要精准定向和多步骤流程（历史上）用 Pinpoint
9. **Pinpoint vs SES**：纯发送邮件无需细分/编排用 SES，需要叠加受众定向和自动化流程（历史上）用 Pinpoint
10. **考试资料若仍以 Pinpoint 作为标准答案，属于滞后于现状的历史内容**：应理解其考察的"能力层次"（细分/编排/分析），而非拘泥于产品名称本身是否仍在服务

### 场景题解题思路

```
场景分析 → 判断 Amazon Pinpoint 相关知识点（含现状意识）
├── "基于用户行为的多步骤跨渠道营销自动化"（历史考法） → Pinpoint Journey（现状：迁移至 Amazon Connect Outbound Campaigns）
├── "精准用户细分定向推送"（历史考法） → Pinpoint Segment（现状：迁移至 Customer Profiles）
├── "纯粹发送事务性 SMS/推送/语音，不涉及细分编排" → AWS End User Messaging（原 Pinpoint 发送能力）
├── "大规模邮件发送，不涉及细分编排" → 直接用 Amazon SES
├── "系统事件广播给固定内部订阅者" → SNS
└── "题目强调参与度分析/转化漏斗" → 历史答案是 Pinpoint 分析仪表盘，现状需评估替代方案
```

## 最佳实践

1. **新项目不应基于 Pinpoint 的营销功能（Campaign/Journey/Segment）设计架构**：已进入下线倒计时，应直接采用 Amazon Connect 相关能力
2. **正在使用 Pinpoint 营销功能的现有系统应尽快规划迁移**：终止支持后将无法访问 Pinpoint 控制台和相关资源
3. **纯发送场景（SMS/推送/语音）继续使用 AWS End User Messaging，无需因为"Pinpoint 下线"而恐慌迁移**：这部分能力只是更名，功能延续
4. **邮件发送场景直接对接 Amazon SES**：不必再通过 Pinpoint 这一层间接调用
5. **备考时理解 Pinpoint 题目背后考察的"细分 + 编排 + 分析"能力层次**：即使产品本身即将下线，这一分层理解仍有助于判断新服务（如 Amazon Connect Outbound Campaigns）的定位
6. **关注 AWS 官方迁移指南的最新时间节点**：2026-10-30 是当前已知的终止支持日期，实际收到的账户通知应以官方为准
