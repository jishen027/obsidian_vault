# Amazon SQS - Simple Queue Service

> **Amazon SQS（Simple Queue Service）** 是全托管的消息队列服务，用于在分布式系统和微服务组件之间传递消息，实现应用间的**解耦（Decoupling）**与**削峰填谷（Buffering）**。
>
> 相关文档：[[SNS]] | [[Lambda]] | [[Auto Scaling]] | [[Amazon Kinesis]] | [[Amazon API Gateway]] | [[DynamoDB - NoSQL]]

---

## 核心概念

### 解耦（Decoupling）的价值

- **传统架构**：组件 A 直接调用组件 B。若 B 宕机或处理变慢，请求会失败或阻塞，A 的故障会直接传导给 B（及反之）
- **SQS 架构**：组件 A（生产者）将任务发送到队列，组件 B（消费者）按自己的节奏取出处理。即使 B 暂时不可用或处理速度较慢，消息仍安全地留在队列中，两端的可用性和伸缩性互不影响
- **削峰填谷**：当流量突发（如秒杀、批量上传）时，队列充当缓冲区，避免下游服务被瞬时流量压垮，配合 [[Auto Scaling]] 按队列深度动态伸缩消费者数量

### SQS 定位（考试要点）

| 服务 | 模型 | 消息保留/重放 | 典型场景 |
|------|------|--------------|---------|
| **SQS** | 拉取（Pull），点对点 | 消息被消费后即删除，不支持重放 | 任务队列、异步解耦、削峰填谷 |
| [[SNS]] | 推送（Push），发布/订阅 | 不持久化，未订阅即丢失 | 一对多广播、事件通知、扇出（Fan-out） |
| [[Amazon Kinesis]] | 拉取（Pull），流式 | 数据可保留 24 小时-365 天，支持多消费者重放 | 实时数据流分析、日志/点击流处理 |

> **考试陷阱**：SQS 是**一对一**消费模型（一条消息通常只被一个消费者处理并删除）；若需要"一条消息广播给多个独立系统"，应使用 **SNS + SQS 扇出（Fan-out）模式**，而不是让多个消费者共享同一个 SQS 队列。

## 两种队列类型

| 特性 | 标准队列（Standard） | FIFO 队列 |
|------|---------------------|-----------|
| **吞吐量** | 近乎无限 | 有限：不启用批处理约 300 TPS，启用高吞吐模式后最高 3,000 TPS |
| **消息顺序** | 尽力而为（Best-effort），不保证顺序 | 严格**先进先出**，按 `MessageGroupId` 分组保序 |
| **消息交付** | **至少一次（At-least-once）**，可能重复 | **恰好一次处理（Exactly-once processing）**，通过去重机制避免重复 |
| **队列命名** | 任意名称 | 名称必须以 **`.fifo`** 结尾 |
| **典型场景** | 通用异步任务、日志缓冲、无顺序依赖的工作队列 | 订单处理、金融交易、库存扣减等强顺序/防重复场景 |

### FIFO 去重机制

- **基于内容去重（Content-Based Deduplication）**：SQS 对消息体做 SHA-256 哈希作为去重 ID，5 分钟去重窗口内相同内容视为重复
- **显式去重 ID（`MessageDeduplicationId`）**：生产者手动指定，适用于内容相同但业务上应视为不同消息的场景
- **`MessageGroupId`**：同一 Group ID 内的消息严格保序且同一时间只能被一个消费者处理；不同 Group ID 之间可并行消费，是 FIFO 队列突破单线程限制、提升吞吐的关键设计

> **考试陷阱**：题目强调"消息不能重复、顺序不能乱"（如银行转账、订单状态流转）→ 首选 **FIFO 队列**；题目只强调"吞吐量优先，顺序和重复可以容忍"→ **标准队列**。

## 关键工作机制

### 核心参数一览

| 参数                            | 默认值      | 范围/说明                                                                                                  |
| ----------------------------- | -------- | ------------------------------------------------------------------------------------------------------ |
| **消息大小**                      | -        | 最高 **256 KB**；更大的负载需配合 **SQS Extended Client Library**，将消息体存入 [[S3 - Object Storage]]，队列中只存指针（最大 2 GB） |
| **可见性超时（Visibility Timeout）** | 30 秒     | 0 秒-12 小时，消费者应在此时间内处理完并删除消息                                                                            |
| **消息保留期（Retention Period）**   | 4 天      | 1 分钟-14 天                                                                                              |
| **延迟队列（Delay Seconds）**       | 0 秒      | 0-15 分钟，消息发布后延迟一段时间才对消费者可见                                                                             |
| **长轮询等待时间**                   | 0 秒（短轮询） | 最高 20 秒                                                                                                |

### 可见性超时（Visibility Timeout）

- 消费者取走消息后，该消息进入"不可见"状态，防止其他消费者重复处理同一条消息
- 若消费者在超时时间内**未删除**该消息（处理失败或超时），消息会重新变为可见，被重新投递
- **考试陷阱**：若消费者的实际处理时间经常超过可见性超时，会导致同一条消息被多个消费者重复处理——应通过 `ChangeMessageVisibility` API **动态延长**超时时间，而不是一味调大默认值

### 短轮询 vs 长轮询

| 方式 | 行为 | 影响 |
|------|------|------|
| **短轮询（Short Polling）** | 立即返回结果，即使队列为空 | 空响应多，API 调用成本高，可能因分区采样而漏读部分消息 |
| **长轮询（Long Polling）** | 队列为空时等待最多 20 秒，直到有消息到达或超时 | 大幅减少空响应次数，降低成本，且能查询所有分区，减少消息漏读 |

> **最佳实践**：生产环境应始终启用长轮询（设置 `ReceiveMessageWaitTimeSeconds` 为 1-20 秒）。

## 故障处理：死信队列（Dead-Letter Queue, DLQ）

- 通过 **Redrive Policy** 配置 `maxReceiveCount`：消息被消费者接收次数超过该阈值仍未被删除时，自动转移到 DLQ
- 防止"毒丸消息"（格式错误、逻辑异常导致反复处理失败的消息）无限重试，堵塞整个队列的处理进度
- **DLQ 本身也是一个普通 SQS 队列**，需要单独创建并监控（如配合 CloudWatch 告警 `ApproximateNumberOfMessagesVisible`），供后续人工排查或重新处理

> **考试陷阱**：**标准队列的 DLQ 必须也是标准队列，FIFO 队列的 DLQ 必须也是 FIFO 队列**，两者不能混用；且 DLQ 应与源队列在**同一区域**。

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以对队列执行 `SendMessage`/`ReceiveMessage`/`DeleteMessage` 等 API |
| **SQS 访问策略（Access Policy）** | 附加在队列上的资源策略，类似 S3 Bucket Policy，支持跨账户授权其他账户直接向队列发送消息 |
| **传输加密** | 所有 API 调用默认通过 HTTPS |
| **静态加密（SSE）** | 可选启用，使用 [[KMS]] 管理的密钥对队列中的消息内容加密 |
| **VPC Endpoint（接口终端节点）** | 让 VPC 内资源通过私有网络访问 SQS，无需经过公网/NAT 网关 |

## 与其他服务集成（考试高频）

### SQS + Lambda

- [[Lambda]] 可通过**事件源映射（Event Source Mapping）**轮询 SQS 队列，自动触发函数处理消息，无需手动管理消费者
- 可配置**批处理大小（Batch Size）**，一次调用处理多条消息，提升吞吐、降低调用成本
- FIFO 队列作为 Lambda 触发源时，同一 `MessageGroupId` 内的消息仍保证顺序处理

### SQS + Auto Scaling

- 基于 CloudWatch 指标 `ApproximateNumberOfMessagesVisible`（队列中可见消息数）设置告警，驱动 [[Auto Scaling]] **动态增减消费者（EC2/ECS）数量**
- 是"按队列积压程度弹性伸缩后端处理能力"的标准解法

### [[SNS]] + SQS 扇出模式（Fan-out）

- SNS 主题发布一条消息，可同时推送到**多个订阅的 SQS 队列**，每个队列对应一个独立的下游系统，各自异步、独立地消费
- 相比让多个消费者共享同一 SQS 队列（消息只会被其中一个取走），扇出模式确保**每个下游系统都能收到完整的消息副本**

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **异步任务解耦** | Web 层生产任务 → SQS 标准队列 → 后端 Worker（EC2/Lambda/ECS）消费 |
| **削峰填谷** | 突发流量写入 SQS 缓冲 → 消费者按自身处理能力匀速消费，避免下游过载 |
| **强顺序业务（订单/交易）** | FIFO 队列 + `MessageGroupId` 按业务键分组 |
| **一对多事件广播** | SNS + SQS 扇出模式 |
| **大文件消息传递** | SQS Extended Client Library + S3 存储实际负载 |
| **按负载弹性伸缩消费者** | SQS + CloudWatch（队列深度指标）+ Auto Scaling |

## 考试重点总结

### SAA-C02 高频考点

1. **核心价值**：解耦生产者与消费者，提升系统容错性和可伸缩性
2. **标准 vs FIFO**：吞吐量优先选标准队列；顺序 + 防重复选 FIFO 队列（队列名必须以 `.fifo` 结尾）
3. **消息大小上限 256 KB**：更大负载需用 Extended Client Library + S3
4. **可见性超时**：处理失败/超时未删除的消息会重新可见，需警惕重复处理；处理时间长时应主动延长超时
5. **长轮询降低成本**：应始终优先使用长轮询而非短轮询
6. **消息保留期最长 14 天**：默认 4 天，超期未消费的消息会被自动删除
7. **死信队列（DLQ）类型必须匹配**：标准队列配标准 DLQ，FIFO 队列配 FIFO DLQ
8. **SQS 是拉取模型、点对点**：广播场景需要 SNS + SQS 扇出，而非多消费者共享同一队列
9. **SQS + Auto Scaling**：按 `ApproximateNumberOfMessagesVisible` 指标弹性伸缩消费者
10. **SQS vs Kinesis**：SQS 消费后即删除、不支持重放；Kinesis 支持数据保留和多消费者重放同一数据流

### 场景题解题思路

```
场景分析 → 选择 SQS 配置
├── "需要异步解耦生产者和消费者" → SQS 标准队列
├── "订单/交易类业务，顺序不能乱，不能重复处理" → SQS FIFO 队列
├── "消息体积超过 256 KB" → SQS + Extended Client Library + S3
├── "同一条消息需要广播给多个独立下游系统" → SNS + SQS 扇出模式
├── "消费者处理失败的消息反复重试，阻塞队列" → 配置死信队列（DLQ）+ maxReceiveCount
├── "希望降低轮询产生的 API 调用成本" → 启用长轮询
├── "消息经常被重复处理" → 检查/延长可见性超时，确保处理时间 < 超时时间
├── "希望根据积压消息量自动扩缩容后端 Worker" → CloudWatch 指标 + Auto Scaling
└── "需要保留数据流并支持多消费者重放" → 改用 Amazon Kinesis 而非 SQS
```

## 最佳实践

1. **优先启用长轮询**：减少空响应，降低 API 调用成本
2. **合理设置可见性超时**：略大于消费者实际平均处理时间，处理时间不确定时用 `ChangeMessageVisibility` 动态延长
3. **为生产队列配置死信队列**：避免坏消息无限重试拖垮整个处理管道，并对 DLQ 设置监控告警
4. **强顺序/防重复场景选择 FIFO**，其余场景优先标准队列以获得更高吞吐
5. **大负载走 S3 + Extended Client Library**：不要试图把超过 256 KB 的数据硬塞进消息体
6. **按队列深度驱动 Auto Scaling**：让消费者数量随积压量弹性伸缩，而非固定容量
7. **广播场景使用 SNS + SQS 扇出**：不要让多个系统争抢同一个队列里的消息
8. **静态加密启用 SSE**：涉及敏感数据的队列应通过 KMS 加密消息内容
