# Amazon EventBridge - 无服务器事件总线

> **Amazon EventBridge** 是无服务器的**事件总线（Event Bus）**服务，用于构建**事件驱动架构（Event-Driven Architecture）**——接收来自 AWS 服务、自建应用、SaaS 合作伙伴的事件，基于**事件模式（Event Pattern）**匹配规则并路由到多个目标（Lambda、Step Functions、SQS 等），实现应用组件之间的松耦合集成。**前身为 CloudWatch Events**，在其基础上扩展了自定义事件总线、Schema Registry、第三方 SaaS 集成等能力。
>
> 相关文档：[[CloudWatch]] | [[AWS Lambda]] | [[SQS]] | [[SNS]] | [[AWS Step Functions]] | [[Amazon Kinesis]] | [[Amazon MSK]] | [[IAM]]

## 核心概念

### 为什么需要 EventBridge

- **传统轮询/紧耦合集成的痛点**：应用组件之间若靠定时轮询检查状态变化，或直接调用彼此的 API，会产生延迟、资源浪费和紧耦合的依赖关系
- **EventBridge 的核心价值**：**发布/订阅式的事件路由**——事件生产者只需把事件发布到总线，无需知道谁在消费；消费者通过定义**规则（Rule）**声明"对什么样的事件感兴趣"，EventBridge 自动匹配并路由，生产者和消费者完全解耦
- **与 CloudWatch Events 的关系**：EventBridge 是 CloudWatch Events 的演进版本，两者共享同一套底层规则引擎，但 EventBridge 新增了**自定义事件总线**、**合作伙伴事件源**、**Schema Registry** 等企业级事件驱动架构所需的能力

### EventBridge 在应用集成服务中的定位（考试要点）

| 服务 | 模型 | 路由方式 | 典型场景 |
|------|------|---------|---------|
| **EventBridge** | 事件路由/总线 | 基于事件内容的**模式匹配**，一对多路由到不同目标 | AWS 服务状态变化响应、SaaS 事件集成、事件驱动架构 |
| [[SNS]] | 发布/订阅 | 基于**主题订阅**，广播给所有订阅端点 | 简单的一对多消息广播，无需复杂内容路由 |
| [[SQS]] | 点对点队列 | 无路由概念，消费者主动拉取 | 异步任务队列、解耦生产消费速率 |
| [[AWS Step Functions]] | 工作流编排 | 按状态机定义的顺序执行多步骤 | 需要编排的复杂业务流程，而非单纯的事件路由 |

> **考试陷阱**：题目描述**"需要根据事件内容的不同字段将事件路由到不同的目标服务"** → 答案是 **EventBridge**（基于事件模式的精细化路由）；若只需要"一条消息广播给所有订阅者，无需按内容路由"→ **SNS** 更简单；若强调"需要按预定义步骤顺序编排多个服务的调用" → **Step Functions**（EventBridge 常作为 Step Functions 工作流的**触发器**，而非替代编排能力）。

## 事件总线（Event Bus）

| 类型 | 说明 |
|------|------|
| **默认事件总线（Default Event Bus）** | 自动接收账户内 **AWS 服务发出的事件**（如 EC2 状态变化、S3 对象创建），每个账户自带一个 |
| **自定义事件总线（Custom Event Bus）** | 供**自建应用**发布自定义业务事件，需要显式创建，与默认总线相互隔离 |
| **合作伙伴事件总线（Partner Event Bus）** | 接收来自第三方 SaaS 合作伙伴（如 Zendesk、Datadog、Salesforce 等）的事件，无需自行开发集成 |

- **跨账户/跨区域事件共享**：可通过**资源策略（Resource Policy）**授权其他账户向本账户的事件总线发布事件，实现跨账户事件聚合（如安全事件集中到审计账户）

## 规则（Rules）与事件模式

### 两种规则类型

| 规则类型 | 触发条件 | 典型场景 |
|---------|---------|---------|
| **事件模式规则（Event Pattern Rule）** | 事件内容匹配预定义的 JSON 模式 | "当某个 EC2 实例状态变为 terminated 时触发" |
| **计划规则（Schedule Rule）** | 基于 Cron 表达式或固定速率（Rate）定时触发 | "每天凌晨 2 点触发一次批处理任务" |

### 事件模式匹配能力

- 支持精确匹配、**数值范围匹配**、**前缀匹配**、**排除匹配（anything-but）**、**字段存在性判断（exists）**等丰富的内容过滤能力
- 只有匹配规则的事件才会被路由到对应目标，未匹配的事件被丢弃（除非配置了归档）

---

## 目标（Targets）

- 单条规则可配置**多个目标**，匹配的事件会**并行**发送给所有配置的目标
- **支持超过 200 个 AWS 服务**作为目标，包括 [[AWS Lambda]]、[[AWS Step Functions]]、[[SQS]]、[[SNS]]、Kinesis、ECS 任务等
- **API 目标（API Destinations）**：可将事件发送到 **AWS 之外的 HTTP 端点**（如第三方 SaaS 的 Webhook），并支持连接凭证的安全管理
- **死信队列（DLQ）**：目标交付失败时，可配置将事件发送到 [[SQS]] 死信队列，配合可自定义的**重试策略**，避免事件静默丢失

---

## EventBridge Schema Registry

- 自动**发现**流经事件总线的事件结构，并将其**schema 存入注册表**，供团队查阅和复用，无需手动编写 schema 定义
- 支持基于 schema **生成代码绑定（Code Binding）**，为 Java、Python、TypeScript 等语言自动生成强类型的事件处理代码，减少手动解析事件 JSON 的样板代码

---

## EventBridge Pipes（点对点集成）

- 面向**点对点集成**场景的无服务器资源——将一个源（如 [[SQS]]、Kinesis、DynamoDB Streams、[[Amazon MSK]]）与一个目标直接连接
- 内置**过滤（Filter）**、**数据增强（Enrichment）**、**转换（Transform）**能力，可在数据从源流向目标的过程中做轻量处理，减少专门为"胶水逻辑"编写 Lambda 函数的需求

> **考试要点**：**Pipes 面向"一个源到一个目标"的简单直连集成**，而 EventBridge 规则面向"一个事件可能路由到多个目标"的**广播式**路由——两者互补而非替代，题目强调"简化流式数据源到目标的直接对接、内置过滤转换" → Pipes；强调"基于事件内容动态路由到不同下游" → 常规的 Rules + Targets。

---

## EventBridge Scheduler

- 独立于常规 Rules 的**大规模定时任务调度**服务，支持**一次性**、**周期性（Cron/Rate）**任务，可靠调度多达**数百万**个任务，并能调用超过 200 个 AWS 服务作为目标
- 相比在事件总线上创建大量计划规则，Scheduler 专为**海量、细粒度定时任务**场景设计（如为每个租户单独安排任务），扩展性更强

---

## 归档与重放（Archive & Replay）

- **归档（Archive）**：可对匹配特定模式的事件持续归档保存，用于审计、历史分析
- **重放（Replay）**：可将归档中的历史事件按原始时间顺序重新发送到事件总线，常用于**故障恢复**（下游服务故障期间丢失的事件重新处理）或**测试**（用真实历史事件验证新的处理逻辑）

---

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以发布事件、创建规则、管理事件总线 |
| **资源策略（Resource Policy）** | 用于授权跨账户发布事件到指定事件总线 |
| **静态加密** | 事件数据默认加密存储 |
| **传输加密** | API 调用默认通过 HTTPS/TLS |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **AWS 资源状态变化时自动触发响应**（如 EC2 状态变化通知运维） | 默认事件总线 + 事件模式规则 + Lambda/SNS 目标 |
| **多个下游系统需要按不同条件消费同一类业务事件** | 自定义事件总线 + 多条事件模式规则路由到不同目标 |
| **集成第三方 SaaS 事件（如 Zendesk 工单创建）** | 合作伙伴事件总线 |
| **简化单一数据源到单一目标的过滤/转换集成** | EventBridge Pipes |
| **海量、细粒度的定时任务调度（按租户/按用户）** | EventBridge Scheduler |
| **故障恢复期间重新处理丢失的事件** | Archive & Replay |
| **触发 Step Functions 工作流的启动条件** | EventBridge 规则 + Step Functions 目标 |
| **跨账户集中收集安全/审计相关事件** | 资源策略授权跨账户发布到中心事件总线 |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：无服务器事件总线，基于事件内容做模式匹配和一对多路由，前身为 CloudWatch Events
2. **判断依据**：需要"按内容精细路由到不同目标"选 EventBridge；只需"广播给所有订阅者"选 SNS；需要"编排多步骤顺序流程"选 Step Functions（EventBridge 常作为其触发器）
3. **三种事件总线**：默认（AWS 服务事件）、自定义（应用事件）、合作伙伴（第三方 SaaS）
4. **两种规则类型**：事件模式规则（内容匹配）、计划规则（Cron/Rate 定时）
5. **单规则多目标并行路由**：一条规则匹配后可同时发送给多个不同目标
6. **支持 200+ AWS 服务 + API 目标**：API Destinations 可将事件发送到 AWS 之外的 HTTP 端点
7. **目标交付失败配置 DLQ**：避免事件因下游故障静默丢失
8. **Pipes 面向点对点集成**：一个源到一个目标，内置过滤/增强/转换，区别于 Rules 的广播式路由
9. **Scheduler 面向海量定时任务**：可靠调度数百万级任务，比常规计划规则扩展性更强
10. **Archive & Replay 用于故障恢复和测试**：归档事件可按原始顺序重新发送

### 场景题解题思路

```
场景分析 → 判断是否用 EventBridge
├── "AWS 资源状态变化需要触发自动化响应" → EventBridge 默认事件总线 + 事件模式规则
├── "自建应用需要发布业务事件供多个下游系统按需消费" → EventBridge 自定义事件总线
├── "需要集成第三方 SaaS 平台的事件通知" → EventBridge 合作伙伴事件总线
├── "只需将消息广播给所有订阅者，无需按内容路由" → 改用 SNS（而非 EventBridge）
├── "需要简化单一流数据源到单一目标的过滤转换" → EventBridge Pipes
├── "需要可靠调度数百万级的细粒度定时任务" → EventBridge Scheduler（而非常规计划规则）
├── "目标服务故障导致事件丢失" → 配置死信队列（DLQ）+ 重试策略
├── "需要恢复故障期间丢失的事件或用历史事件测试" → Archive & Replay
└── "需要按预定义步骤顺序编排多个服务调用" → 改用 Step Functions（EventBridge 作为触发器）
```

## 最佳实践

1. **应用自定义事件使用独立的自定义事件总线**：与 AWS 服务的默认事件总线隔离，便于权限管理和事件治理
2. **善用事件模式的高级匹配能力**：数值范围、前缀、排除匹配等，减少下游 Lambda 中的重复过滤逻辑
3. **关键目标配置死信队列**：确保交付失败的事件不会静默丢失，便于后续排查和重放
4. **简单点对点集成优先评估 Pipes**：避免为简单的过滤转换场景编写和维护额外的 Lambda 胶水代码
5. **海量定时任务场景使用 Scheduler 而非大量计划规则**：获得更好的扩展性和管理体验
6. **启用 Schema Registry 和代码绑定生成**：减少团队手动维护事件结构定义和解析代码的成本
7. **重要事件流启用归档**：为故障恢复、合规审计、离线分析预留可重放的历史事件数据
8. **跨账户事件聚合使用资源策略**：而非在每个账户重复搭建独立的事件处理逻辑
