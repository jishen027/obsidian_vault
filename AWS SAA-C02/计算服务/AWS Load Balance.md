# Elastic Load Balancing (ELB)

> **Elastic Load Balancing (ELB)** 是 AWS 的托管负载均衡服务，充当流量的"指挥官"，将请求分发到健康的后端资源，并与 [[Auto Scaling]] 紧密集成实现弹性扩展。
>
> 相关文档：[[Auto Scaling]] | [[EC2]] | [[Security Group]] | [[VPC]] | [[AWS Certificate Manager (ACM)]]

---

## 核心概念

### 核心职责

| 职责 | 说明 |
|------|------|
| **流量分发** | 将请求引导至健康的后端服务器，实现负载均衡 |
| **健康检查** | 定期测试后端资源的运行状况，故障实例自动摘除，恢复后自动加回 |
| **与 Auto Scaling 集成** | 新实例启动后自动注册到目标组，无需人工介入 |
| **单一访问入口** | 客户端只需访问负载均衡器的固定 DNS 名称，无需感知后端实例变化 |

### 四种负载均衡器类型（考试重点）

| 类型 | OSI 层级 | 处理协议 | 核心定位 |
|------|---------|---------|---------|
| **ALB (Application LB)** | 第 7 层（应用层） | HTTP / HTTPS / gRPC | 智能内容路由，微服务/容器场景 |
| **NLB (Network LB)** | 第 4 层（传输层） | TCP / UDP / TLS | 超高性能、低延迟、突发流量 |
| **GWLB (Gateway LB)** | 第 3 层（网络层） | IP（GENEVE 封装） | 部署第三方虚拟设备（防火墙、IDS/IPS） |
| **CLB (Classic LB)** | 第 4/7 层 | HTTP/HTTPS/TCP | 已过时，仅用于遗留系统，AWS 不再推荐 |

---

## ALB (Application Load Balancer)

运行在 OSI 模型的第 7 层（应用层），**专门处理 HTTP 和 HTTPS 流量**，支持基于内容的高级路由规则。

### 核心特性

| 特性 | 说明 |
|------|------|
| **高级路由功能** | 依据**主机名、路径、HTTP 头、HTTP 方法、查询字符串、源 IP** 等多种条件将流量路由到不同目标组（详见下方[[#基于内容的路由规则：ALB 依据什么将流量路由到不同目标组]]章节） |
| **粘性会话 (Sticky Sessions)** | 通过 **Cookie** 实现会话亲和性，确保同一用户的连续请求路由到同一后端服务器，适合需要本地缓存或状态的应用（详见下方[[#粘性会话 (Sticky Sessions)]]章节） |
| **深入健康检查** | 针对目标组执行 HTTP 健康检查，可检查特定响应代码（通常 200-499），未通过检查的实例自动停止接收流量 |
| **深度集成 Auto Scaling** | Auto Scaling 启动新实例时自动注册到 ALB 目标组 |
| **容器化支持** | 原生支持 [[ECS]] 等容器化应用，可灵活管理**动态端口映射** |
| **SSL/TLS 卸载** | 在 ALB 上集中管理加密证书（通过 **[[AWS Certificate Manager (ACM)]]**），减轻后端服务器计算负担（详见[[#SSL/TLS 与 SNI (Server Name Indication)]]） |
| **多证书支持 (SNI)** | 通过 **SNI (Server Name Indication)** 在同一监听器上托管多个域名证书，无需多个 ALB |

### 目标组支持类型：ALB 目标组可以注册哪些类型的目标

ALB 的**目标组 (Target Group)** 在创建时需要指定**目标类型 (Target Type)**，同一目标组内的所有目标必须是同一类型。共支持 **4 种**注册目标：

| 目标类型 | 说明 |
|---------|------|
| **Instance** | 通过 **EC2 实例 ID** 注册目标 |
| **IP** | 通过 **IP 地址** 注册目标 |
| **Lambda** | 注册 **Lambda 函数**，将 HTTP 请求路由给函数处理 |
| **Application Load Balancer** | 将另一个 **ALB** 作为目标（多层 ALB 场景，2023 年新增） |

#### 1. Instance（实例 ID）

- 通过 **EC2 实例 ID** 注册，流量路由到实例的**主私有 IP**（也可指定其他 ENI）
- 与 [[Auto Scaling]] 深度集成：ASG 扩缩容时**自动注册/注销**实例到目标组，无需人工操作
- 实例必须处于 **running** 状态才能被正常路由流量；**stopped/terminated** 的实例会被判定为不健康
- 目标组的**端口**可以与实例安全组开放的端口不同（只要安全组放行来自 ALB 的流量即可）

#### 2. IP（IP 地址）

- 直接通过 **IP 地址**注册目标，更灵活，适用于**没有固定实例 ID**或**跨网络**的场景
- 可注册的 IP 范围包括：
  - **本 VPC 内**的资源（EC2 实例私有 IP、ENI）
  - **对等 (Peered) VPC** 中的资源
  - 通过 **Direct Connect / Site-to-Site VPN** 连接的**本地数据中心 (on-premises)** 服务器 IP，实现**混合云负载均衡**
  - **容器化应用**（如 [[ECS]] 任务的私有 IP，尤其是 `awsvpc` 网络模式下每个任务拥有独立 IP）
- 不能注册以下类型 IP：EC2 实例的公有 IP、部分 AWS 托管服务的 IP 段

#### 3. Lambda（无服务器函数）

- 将 **Lambda 函数**直接注册为目标，**仅 ALB 支持**（NLB/GWLB/CLB 均不支持）
- ALB 将 HTTP(S) 请求**同步调用**为 Lambda 事件，把请求方法、路径、请求头、查询字符串、Body 等封装为 **JSON 事件**传给函数，函数返回的 JSON 也会被 ALB 转换回标准 HTTP 响应
- 一个目标组通常只注册**一个 Lambda 函数**（可结合函数别名/版本做灰度）
- 健康检查通过**调用函数**（可选择跳过）判断，而非传统的 TCP/HTTP 探测
- 典型场景：希望通过统一的 ALB 入口，将部分路径（如 `/webhook`）路由给无服务器函数处理，其余路径仍路由给 EC2/容器

#### 4. Application Load Balancer（ALB 作为目标）

- 可以将另一个 **ALB** 注册为目标组中的目标，用于构建**多层/嵌套 ALB** 架构
- 典型场景：需要跨账户、跨 VPC 转发流量，或在共享服务架构中统一入口后二次分发

### 目标组的其他要点

- **同一目标可注册到多个目标组**，也可以配置**权重 (Weighted Target Groups)** 实现多目标组间的加权流量分配（例如蓝绿部署、灰度发布）
- 每个目标组独立配置**协议、端口、健康检查**参数，互不影响
- 目标组是 ALB 与 [[Auto Scaling]] 之间的**桥梁**：ASG 只需要知道目标组，无需感知负载均衡器本身

### 基于内容的路由规则：ALB 依据什么将流量路由到不同目标组

ALB 的核心能力是根据**监听器规则 (Listener Rules)** 检查请求内容，将流量分发到不同的**目标组 (Target Group)**。每条规则由**条件 (Condition)** + **动作 (Action)** 组成，ALB 支持以下几类路由条件（可单独使用，也可组合使用）：

| 路由依据 | 说明 | 示例 |
|---------|------|------|
| **主机名 (Host-based / Host Header)** | 根据请求的 `Host` 头（域名）路由，支持通配符 | `api.example.com` → API 服务目标组，`www.example.com` → Web 服务目标组 |
| **路径 (Path-based)** | 根据 URL 路径路由，支持通配符 `*` 和 `?` | `/api/*` → API 目标组，`/images/*` → 静态资源目标组 |
| **HTTP 请求头 (HTTP Header)** | 根据自定义或标准请求头的值路由 | `User-Agent` 头包含 `Mobile` → 移动端目标组 |
| **HTTP 请求方法 (HTTP Method)** | 根据 `GET`、`POST`、`PUT`、`DELETE` 等方法路由 | `POST /orders` → 写服务目标组，`GET /orders` → 读服务目标组 |
| **查询字符串 (Query String)** | 根据 URL 查询参数的键值路由 | `?version=beta` → 灰度/测试目标组 |
| **源 IP 地址 (Source IP / CIDR)** | 根据客户端源 IP（或经过的 CIDR 段）路由 | 内部办公网段 IP → 内部管理目标组 |

> 以上条件可以**组合**在同一条规则中（例如"主机名为 `api.example.com` **且** 路径为 `/v2/*`"才路由到某目标组），实现更精细的流量控制。

### 路由规则的评估机制

- 每个监听器可配置**多条规则**，每条规则有一个**优先级数字**（数字越小优先级越高）
- ALB 按**优先级从高到低**依次评估规则，**第一条匹配成功的规则**决定流量走向，后续规则不再评估
- 若所有规则都不匹配，则执行监听器的**默认规则（Default Action）**，通常指向一个默认目标组
- 每条规则的动作（Action）不仅可以是 `forward`（转发到目标组），也可以是 `redirect`（重定向，如 HTTP → HTTPS）或 `fixed-response`（返回固定响应，如自定义 403/404 页面）

### 核心应用场景

如果需要构建**微服务架构**，或根据 URL 内容灵活分发流量的复杂 Web 应用，ALB 是最佳选择。

## 粘性会话 (Sticky Sessions)

**粘性会话**（也称**会话亲和性 Session Affinity**）确保同一客户端的所有请求在会话期间都被路由到**同一个后端目标**，而不是被负载均衡算法分散到不同实例。

### 为什么需要粘性会话

大多数负载均衡器默认按**轮询**或最小负载等算法分发请求，同一用户的连续请求可能落在不同后端实例上。如果应用**在实例本地保存会话状态**（如登录态、购物车、本地缓存），请求被路由到不同实例就会导致状态丢失或不一致。粘性会话通过让同一用户始终命中同一实例来规避这个问题。

> **最佳实践**：更推荐将会话状态外置到 [[ElastiCache]] 或 [[DynamoDB]] 等共享存储，实现真正的无状态应用架构，而不是依赖粘性会话。粘性会话是一种**过渡/权宜方案**，不能替代无状态设计。

### 实现方式：负载均衡器生成的 Cookie (Duration-Based)

ELB 通过 **Cookie** 实现粘性会话。最常用、也是最简单的方式是**负载均衡器生成的 Cookie**：

| 属性 | 说明 |
|------|------|
| **Cookie 名称** | `AWSALB`（ALB）/ `AWSELB`（CLB） |
| **生成方** | 负载均衡器自动生成，无需修改后端应用代码 |
| **工作原理** | 客户端首次请求后，ELB 在响应中种下该 Cookie；后续请求携带此 Cookie 时，ELB 将其固定路由到**同一目标实例** |
| **过期控制** | 由 ELB 完全控制 Cookie 的生命周期（配置的 Stickiness 过期时间） |

> **提示**：ALB 还支持**应用生成的 Cookie（Application-Based，`AWSALBAPP`）**，即跟随后端应用自定义的 Cookie 实现粘性，但需要修改应用逻辑。若无特殊需求，优先使用更简单的负载均衡器生成 Cookie 方式。

### 支持范围

| 负载均衡器类型 | 粘性会话支持 | 说明 |
|--------------|------------|------|
| **ALB** | ✅ 支持 | 在**目标组**级别配置，基于 Cookie |
| **CLB** | ✅ 支持 | 同样基于 Cookie（`AWSELB`） |
| **NLB** | ❌ 原生不支持 Cookie 粘性 | 工作在第 4 层无法读取 HTTP Cookie；可通过**客户端 IP 哈希**实现类似效果，但不是真正的会话粘性 |

### 配置要点

- 在 ALB 中，粘性会话是**目标组属性**，需要显式开启（`Enable stickiness`）
- 可设置 **Cookie 过期时间**（1 秒 ~ 7 天），超时后重新按负载均衡算法分配目标
- 使用负载均衡器生成的 Cookie 无需修改应用代码，是最简单、最推荐的启用方式

### 潜在问题（考试易考点）

- **负载不均衡**：开启粘性会话后，如果某些用户请求量远高于其他用户，可能导致流量集中在少数实例上，破坏负载均衡的初衷
- **实例故障影响**：绑定的目标实例被移除或不健康时，该用户的会话会被重新分配到新实例，本地会话状态仍会丢失
- 因此粘性会话适合**短期、轻量级**的会话保持需求，长期有状态架构应优先考虑外部会话存储

### 与跨可用区负载均衡的关系

粘性会话与 [[#跨可用区负载均衡 (Cross-Zone Load Balancing)]] 是两个独立但会相互影响的机制：

- 粘性会话决定**同一用户的请求固定到哪个目标实例**；跨可用区负载均衡决定**流量是否均匀分发到所有 AZ 的实例**，二者可以同时启用
- 若开启粘性会话后用户分布不均（例如大量用户被绑定到少数实例），即使开启了跨可用区负载均衡，也无法解决**因粘性策略本身**导致的负载倾斜——跨可用区负载均衡解决的是"按 AZ 均分"，不是"按粘性会话均分"
- 因此评估负载是否均衡时，需要同时考虑两者：**跨可用区负载均衡**解决 AZ 间的均衡问题，**粘性会话的负载不均**则需要通过控制 Cookie 过期时间或迁移到外部会话存储来缓解

### 核心应用场景

- 应用**未做无状态改造**，用户会话数据（如购物车、登录态）保存在实例本地内存中
- 需要保证同一用户请求命中同一实例以利用**本地缓存**，减少重复计算或数据库查询

## NLB (Network Load Balancer)

运行在第 4 层（传输层），**处理 TCP、UDP 和 TLS 协议**，专为极致性能、低延迟和应对突发流量（每秒数百万请求）而设计。

### 核心特性

| 特性 | 说明 |
|------|------|
| **超高性能** | 每秒可处理**数百万请求**，延迟可低至个位数毫秒 |
| **静态 IP / 弹性 IP** | 每个可用区可分配**一个静态 IP**，也可绑定 **Elastic IP**，适合需要白名单固定 IP 的场景 |
| **保留源 IP** | 与 ALB 不同，NLB **原生保留客户端源 IP**，无需依赖 `X-Forwarded-For` 头 |
| **TLS 卸载** | 支持在 NLB 层终止 TLS 连接，也可选择 **TCP 直通**保留端到端加密（详见[[#SSL/TLS 与 SNI (Server Name Indication)]]） |
| **健康检查** | 支持 TCP、HTTP、HTTPS 健康检查 |

### 核心应用场景

- 需要**极致性能**和低延迟的场景（游戏服务器、金融交易系统）
- 需要**固定 IP 地址**对接第三方白名单
- 处理 **TCP/UDP** 非 HTTP 协议流量

---

## GWLB (Gateway Load Balancer)

运行在第 3 层（网络层），**将透明网络网关与负载均衡功能合二为一**，专为部署**第三方虚拟安全设备**（防火墙、入侵检测/防御系统 IDS/IPS、深度包检测）而设计。

### 核心特性

| 特性 | 说明 |
|------|------|
| **透明流量拦截** | 流量在到达目的地前先经过虚拟设备检测，设备处理后再转发，客户端无感知 |
| **GENEVE 协议** | 使用 **GENEVE (端口 6081)** 协议封装转发流量到虚拟设备实例 |
| **Gateway Load Balancer Endpoint (GWLBE)** | 通过 [[VPC]] Endpoint 将流量路由到 GWLB，实现跨 VPC 的流量检测 |
| **弹性扩展** | 结合 [[Auto Scaling]] 自动扩展第三方虚拟设备集群 |

### 核心应用场景

- 部署第三方**防火墙 / IDS / IPS** 虚拟设备集群
- 需要对**所有进出 VPC 的流量**进行统一安全检测

---

## Classic Load Balancer (CLB)

较旧的负载均衡器版本，同时支持第 4 层和第 7 层，现已基本被 **ALB** 和 **NLB** 取代。

- **不推荐用于新架构**：功能有限，不支持基于内容的高级路由
- 仅用于**遗留系统兼容**场景，AWS 官方建议迁移到 ALB/NLB

## 四类负载均衡器对比（考试高频考点）

| 特性 | ALB | NLB | GWLB | CLB |
|------|-----|-----|------|-----|
| **OSI 层级** | 第 7 层 | 第 4 层 | 第 3 层 | 第 4/7 层 |
| **协议** | HTTP/HTTPS/gRPC | TCP/UDP/TLS | IP (GENEVE) | HTTP/HTTPS/TCP |
| **内容路由** | ✅ 支持（路径/主机名） | ❌ 不支持 | ❌ 不支持 | ❌ 不支持 |
| **静态/弹性 IP** | ❌ 不支持 | ✅ 支持 | - | ❌ 不支持 |
| **保留源 IP** | 需 X-Forwarded-For | ✅ 原生保留 | - | 需 X-Forwarded-For |
| **SNI 多证书** | ✅ 支持 | ✅ 支持 | 不适用 | ❌ 不支持（一 CLB 一证书） |
| **性能** | 高 | 极高（百万级请求/秒） | 高 | 中 |
| **典型场景** | 微服务、容器、Web 应用 | 游戏、金融、固定 IP 需求 | 第三方防火墙/IDS/IPS | 遗留系统 |

## 健康检查

- 负载均衡器定期向后端目标发送健康检查请求（HTTP/HTTPS/TCP）
- 连续失败达到阈值后，目标被标记为 **unhealthy**，负载均衡器停止向其转发流量
- 恢复正常响应后自动重新加入可用目标池
- 与 [[Auto Scaling]] 集成时，ASG 可使用 ELB 健康检查判断实例是否需要被替换（相比 EC2 健康检查更准确，能反映应用层真实状态）

---

## 跨可用区负载均衡 (Cross-Zone Load Balancing)

| 负载均衡器类型 | 默认状态 | 说明 |
|--------------|---------|------|
| **ALB** | 默认**开启**，且**免费** | 请求会均匀分发到所有已注册 AZ 的全部实例 |
| **NLB** | 默认**关闭** | 开启后会产生**跨 AZ 数据传输费用** |
| **CLB** | 默认关闭，可手动开启 | 视配置而定 |

> **考试要点**：若关闭跨可用区负载均衡，流量只会均匀分发到**同一可用区内**的实例，可能导致各 AZ 实例数量不均时负载失衡。

---

## 连接排空 (Connection Draining / Deregistration Delay)

- 当实例被标记为**注销中**（如 Auto Scaling 缩容、手动移除）时，负载均衡器**不会立即切断**现有连接
- 会在**注销延迟时间**（默认 300 秒，可调整）内让实例完成正在处理的请求，之后才真正停止转发流量
- 目的：避免正在处理请求的用户遭遇连接中断

## SSL/TLS 与 SNI (Server Name Indication)

### SSL/TLS 卸载 (SSL/TLS Termination)

**SSL/TLS 卸载**指负载均衡器代替后端实例**终止（解密）客户端的 HTTPS/TLS 连接**，将证书管理和加解密运算集中在负载均衡器层，从而减轻后端服务器的计算负担。

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **SSL Offload（卸载/终止）** | 客户端 ↔ LB 之间为 HTTPS，LB ↔ 后端实例之间为**明文 HTTP** | 后端在私有子网内、且不要求端到端加密的常规 Web 应用；LB 需要读取明文内容做**七层路由**（如 ALB 的路径/主机名路由） |
| **SSL Bridging（端到端加密 / Re-encryption）** | LB 终止客户端连接后，用**自己的证书**与后端建立**新的 TLS 连接**重新加密转发 | 合规要求端到端加密，同时又需要 LB 读取解密内容做智能路由 |
| **TLS Pass-through（直通）** | LB **不终止 TLS**，仅转发原始加密的 TCP 流量给后端，由后端实例自行解密 | 需要**真正端到端加密**（LB 完全不接触明文）、或需要在后端实现 **mTLS（双向 TLS）** 校验客户端证书；仅 **NLB** 支持此模式 |

### 各负载均衡器的 TLS 支持

| 负载均衡器 | 监听器类型 | 终止位置 | 说明 |
|-----------|-----------|---------|------|
| **ALB** | HTTPS 监听器 | 第 7 层，必须终止 TLS | 只有解密后才能读取 HTTP Host/Path 等信息用于高级路由 |
| **NLB** | TLS 监听器 | 第 4 层，可终止 TLS，也可选择 **TCP 直通** 保留端到端加密 | 唯一支持 TLS Pass-through 的负载均衡器 |
| **CLB** | HTTPS/SSL 监听器 | 第 4/7 层，终止 TLS | 功能有限，已过时 |
| **GWLB** | 不适用（第 3 层，IP/GENEVE 封装） | 不处理/不终止 TLS | 只做透明流量转发，不涉及证书 |

### SNI (Server Name Indication)

**背景问题**：在 TLS 握手阶段，服务器需要先出示证书，但此时 **HTTP 请求还未发送**，服务器/负载均衡器并不知道客户端要访问哪个域名。传统上这意味着**一个 IP/端口只能绑定一张证书**，要托管多个域名的 HTTPS 站点就需要多个负载均衡器或多个 IP。

**SNI 的作用**：SNI 是 TLS 协议的一项扩展，客户端在 **ClientHello** 阶段就携带其请求的目标主机名，使服务器/负载均衡器能够**在握手完成前根据主机名选择正确的证书**，从而实现**一个监听器托管多个域名证书**。

| 负载均衡器 | SNI 支持 | 说明 |
|-----------|---------|------|
| **ALB** | ✅ 支持 | 可在**同一 HTTPS 监听器**上添加多张证书，ALB 依据 SNI 自动匹配对应证书；未匹配到时使用**默认证书**兜底 |
| **NLB** | ✅ 支持 | TLS 监听器同样支持多证书 + SNI |
| **CLB** | ❌ 不支持 | **每个 CLB 只能绑定一张证书**，要托管多个域名必须创建**多个 CLB**（考试高频差异点） |
| **GWLB** | 不适用 | 不涉及 TLS |

> **考试要点**：题目描述"需要在**同一个**负载均衡器上托管多个域名的 SSL/TLS 证书，且不想创建多个负载均衡器" → 答案是 **ALB 或 NLB**（利用 SNI），**不是 CLB**。

### 证书管理：[[AWS Certificate Manager (ACM)]]

- 负载均衡器的证书通过 **[[AWS Certificate Manager (ACM)]]** 集中签发、部署和**自动续期**，无需手动管理证书生命周期，完整的证书类型、验证方式等见 [[AWS Certificate Manager (ACM)]] 独立笔记
- ACM 颁发的公有证书**免费**，可直接绑定到 ALB/NLB/CLB 的 HTTPS/TLS 监听器
- 也支持**导入第三方证书**（如自购的商业证书）到 ACM 后再绑定到负载均衡器
- 证书集中托管在负载均衡器层，后端实例无需处理加解密运算，也无需分发/更新证书

## 场景题解题思路

```
场景分析 → 选择负载均衡器类型
├── "HTTP/HTTPS + 基于路径/主机名/HTTP 头/方法/查询字符串/源 IP 路由" → ALB
├── "微服务架构 / 容器化应用（ECS）" → ALB
├── "需要将请求路由到 Lambda" → ALB（目标组类型选 Lambda）
├── "需要负载均衡跨对等 VPC / 本地数据中心（Direct Connect/VPN）的服务器" → ALB（目标组类型选 IP）
├── "极致性能 + 百万级请求/秒" → NLB
├── "需要固定/静态 IP 对接白名单" → NLB
├── "需要保留客户端真实源 IP" → NLB
├── "应用在实例本地保存会话状态，需保持用户请求命中同一实例" → 开启粘性会话 (Sticky Sessions)，长期方案考虑外置会话存储
├── "部署第三方防火墙/IDS/IPS" → GWLB
├── "同一负载均衡器需托管多个域名的 SSL 证书" → ALB 或 NLB（利用 SNI），不是 CLB
├── "需要端到端加密 / 后端要做 mTLS 校验客户端证书" → NLB 的 TLS 直通（Pass-through）
├── "遗留系统，无特殊路由需求" → CLB（不推荐新架构使用）
├── "流量在 AZ 间分布不均" → 检查是否开启跨可用区负载均衡
└── "缩容时避免中断正在处理的请求" → 配置合理的注销延迟（Connection Draining）
```

## 考试重点总结

1. **ALB vs NLB vs GWLB**：按 OSI 层级和协议类型区分核心场景
2. **ALB 高级路由**：可依据**主机名、路径、HTTP 头、HTTP 方法、查询字符串、源 IP**（可组合）智能分发到不同目标组，按规则**优先级**从高到低匹配，第一条命中即生效，全不匹配则走默认规则
3. **NLB 静态 IP**：唯一支持每 AZ 固定 IP / Elastic IP 的负载均衡器
4. **GWLB 用途**：专为第三方虚拟安全设备设计，使用 GENEVE 协议
5. **跨可用区负载均衡**：ALB 默认开启且免费，NLB 默认关闭且开启后收费
6. **粘性会话**：基于 Cookie 实现（负载均衡器生成的 `AWSALB`/`AWSELB` 或应用生成的 `AWSALBAPP`），ALB/CLB 支持，NLB 不原生支持；适合有状态应用，但可能导致负载不均，长期应优先考虑无状态架构
7. **健康检查**：故障实例自动摘除，恢复后自动加回
8. **连接排空**：缩容/注销时给正在处理的请求预留完成时间
9. **SSL/TLS 卸载**：证书集中在负载均衡器层管理，减轻后端负担；ALB 必须终止 TLS（需读取明文做七层路由），NLB 可终止也可 **TCP 直通**保留端到端加密
10. **SNI**：让一个监听器托管多张证书（按域名匹配），**ALB/NLB 支持，CLB 不支持**（CLB 一个负载均衡器只能绑一张证书）
11. **ALB 目标组类型**：可注册 **Instance（实例 ID）、IP（含跨 VPC/本地数据中心）、Lambda、另一个 ALB** 四种目标，其中 **Lambda 作为目标仅 ALB 支持**
12. **CLB 已过时**：新架构应优先选择 ALB 或 NLB

---

## 最佳实践

1. **HTTP/HTTPS 场景优先选 ALB**：利用其高级路由和容器集成能力
2. **高性能/固定 IP 场景选 NLB**：满足极致性能和白名单需求
3. **安全检测场景引入 GWLB**：统一部署和扩展第三方安全设备
4. **开启跨可用区负载均衡**：避免因 AZ 实例数量不均导致负载倾斜（注意 NLB 的额外费用）
5. **合理配置健康检查阈值**：避免过于敏感（误判）或过于迟钝（故障恢复慢）
6. **设置合理的注销延迟**：确保缩容/部署更新时不中断用户请求
7. **集中管理证书**：使用 [[AWS Certificate Manager (ACM)]] 简化证书轮换和多域名支持；多域名场景优先用 ALB/NLB 的 SNI，而非拆分多个负载均衡器
8. **淘汰 CLB**：将遗留的 Classic Load Balancer 迁移到 ALB/NLB
