# AWS Lambda - Serverless 计算

> **AWS Lambda** 是无服务器（Serverless）计算的核心服务，让用户无需预置或管理任何服务器，只需上传代码，函数即可在事件触发时自动运行，并按实际执行时间计费。
>
> 相关文档：[[ECS]] | [[EKS]] | [[AWS Fargate]] | [[EC2]] | [[Amazon API Gateway]] | [[SQS]] | [[SNS]] | [[DynamoDB]] | [[IAM]] | [[CloudWatch]] | [[Amazon EventBridge]]

---

## 核心概念

### 无服务器架构的定义

- **高度抽象化**：用户只需部署代码（函数），无需配置、打补丁或扩容任何底层服务器
- **事件驱动（Event-Driven）**：代码只在被事件触发时运行，空闲时不产生任何计算资源占用
- **自动管理生命周期**：函数执行完毕后，AWS 自动回收计算资源；无请求时资源规模可**缩容至零**

### Lambda 定位（考试要点）

| 服务 | 管理粒度 | 执行时长上限 | 典型场景 |
|------|---------|------------|---------|
| **Lambda** | 无需管理，事件驱动 | **最长 15 分钟** | 短时函数、事件处理、API 后端、自动化任务 |
| [[AWS Fargate]] | 无需管理服务器，但需定义容器 | 无固定上限（长期运行） | 长期运行的容器化应用/微服务 |
| [[EC2]] | 完全自管理 | 无限制 | 需要完全控制底层环境的长期运行应用 |

> **考试陷阱**：SAA-C02 题目中若同时出现**"自动扩展"、"无需维护服务器"、"针对间歇性/突发任务优化成本"**这三个关键词，正确答案通常是 **Lambda**；但若任务**执行时长可能超过 15 分钟**或是**长期持续运行的服务**，应改用 Fargate/ECS/EC2，而非勉强拆分成多个 Lambda 调用。

## 运行机制

### 执行环境与限制

| 项目 | 限制/说明 |
|------|---------|
| **最长执行时长** | **15 分钟**（900 秒），超过需拆分任务或改用容器/EC2 |
| **内存配置** | 128 MB - 10,240 MB，**CPU 算力随内存线性分配**（增加内存也会增加可用 CPU） |
| **临时存储（`/tmp`）** | 默认 512 MB，最高可配置至 10,240 MB |
| **部署包大小** | 压缩包 50 MB（直接上传），解压后 250 MB；容器镜像最大 **10 GB** |
| **并发执行数** | 账户级别默认限制（可申请提升），单函数可配置**预留并发**上限 |

> **考试要点**：Lambda **没有独立的 CPU 配置项**——CPU 算力由内存大小自动决定，题目中"函数执行缓慢，怀疑 CPU 不足"的排查方向通常是**调高内存分配**，而非寻找单独的 CPU 设置。

### 冷启动（Cold Start）

- 函数长时间未被调用后首次触发，Lambda 需要重新初始化执行环境（下载代码、启动运行时），产生额外延迟
- **缓解手段**：
  - **预置并发（Provisioned Concurrency）**：预先初始化指定数量的执行环境，消除冷启动延迟，适合对延迟敏感的 API 场景，但需按预置的时长付费
  - 减小部署包体积、精简依赖、避免在处理函数体外做重量级初始化

### 并发控制

| 概念 | 说明 |
|------|------|
| **预留并发（Reserved Concurrency）** | 为函数保留固定数量的并发执行额度，既是**上限**也是**保证**（不会被其他函数挤占） |
| **预置并发（Provisioned Concurrency）** | 预先初始化好的"热"执行环境数量，用于消除冷启动，与预留并发是两个不同维度的概念 |
| **突发并发限制** | 账户/区域级别的并发上限，超出会触发限流（Throttling） |

> **考试陷阱**：**预留并发（控制配额/隔离资源）** 与 **预置并发（消除冷启动延迟）** 是**两个完全不同的机制**，容易在场景题中混淆——题目问"如何保证某函数不被其他函数抢占并发资源"选预留并发；问"如何降低 API 首次调用延迟"选预置并发。

## 触发方式（事件源）

| 触发类型                            | 说明                                            | 典型服务                                             |
| ------------------------------- | --------------------------------------------- | ------------------------------------------------ |
| **同步调用**                        | 调用方等待函数返回结果                                   | [[Amazon API Gateway]]、Application Load Balancer |
| **异步调用**                        | 调用方不等待结果，Lambda 内部排队处理，失败可配置重试和**死信队列/失败目的地** | [[S3]] 事件通知、[[SNS]]             |
| **事件源映射（Event Source Mapping）** | Lambda 主动轮询/订阅流式或队列服务，批量拉取记录触发函数              | [[SQS]]、[[Amazon Kinesis]]、DynamoDB Streams      |

- **失败处理（异步调用）**：可配置 **On-Failure Destination**（SQS/SNS/[[Amazon EventBridge]]/另一个 Lambda）接收失败事件，避免静默丢失
- **事件源映射的批处理**：从 SQS/Kinesis/DynamoDB Streams 拉取时可配置批处理大小（Batch Size），一次调用处理多条记录，提升吞吐并降低调用次数

## 执行权限与网络

### IAM 执行角色（Execution Role）

- 每个 Lambda 函数关联一个**执行角色**，授予函数运行时可调用的其他 AWS 服务 API 权限（如读写 S3、写入 DynamoDB）
- 遵循**最小权限原则**：仅授予函数实际需要访问的资源和操作

### VPC 集成

- Lambda 默认运行在 AWS 托管的网络环境中，可直接访问公网服务和大多数 AWS 服务
- 若函数需要访问 [[VPC]] 内的私有资源（如 RDS 私有子网中的数据库），需将 Lambda **配置进 VPC**（指定子网和安全组）
- **考试陷阱**：Lambda 配置进 VPC 私有子网后，若还需要访问公网/其他 AWS 服务，必须通过 **NAT Gateway** 或对应的 **VPC Endpoint**，否则会因缺少出网路径而调用超时

## 代码组织与部署

| 特性 | 说明 |
|------|------|
| **Lambda Layers（层）** | 将公共依赖库、运行时扩展打包成独立层，供多个函数共享引用，减小每个函数自身的部署包体积 |
| **版本（Versions）** | 每次发布代码会生成不可变的版本快照，用于回滚和追溯 |
| **别名（Aliases）** | 指向特定版本的可变指针（如 `PROD`、`STAGING`），客户端调用别名而非具体版本号，便于灰度发布 |
| **加权别名 + 流量迁移** | 通过别名配置流量权重（如 90% 指向旧版本、10% 指向新版本），结合 CodeDeploy 实现**金丝雀/线性发布**，异常时自动回滚 |
| **容器镜像支持** | 除 ZIP 部署包外，也支持将函数打包为符合 Lambda 运行时接口的 **Docker 容器镜像**（最大 10 GB），便于复用现有容器化工具链 |

## 可靠性与性能

- **原生高可用**：Lambda 自动跨多个可用区运行，无需用户配置任何高可用架构
- **极小的资源占用**：不预置闲置容量，函数不运行时不产生计算成本
- **按需付费**：仅按**调用次数**和**实际执行时长（按毫秒计费）**收费，无请求时几乎零成本

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **从后端数据库检索数据** | Lambda + [[Amazon API Gateway]] 构建 REST API |
| **解析实时数据流** | Lambda + [[SQS]]/[[Amazon Kinesis]] 事件源映射 |
| **轻量级事务处理** | Lambda + [[DynamoDB]] |
| **自动化运维任务** | Lambda + [[Amazon EventBridge]] 定时触发 |
| **图片/文件处理流水线** | S3 事件通知 → Lambda（缩略图生成、格式转换） |
| **对延迟敏感的高频 API** | Lambda + 预置并发 |
| **长期运行/执行时间可能超 15 分钟的任务** | 改用 [[AWS Fargate]]/[[ECS]]，而非 Lambda |

## 考试重点总结

### SAA-C02 高频考点

1. **三大关键词识别 Lambda**：自动扩展、无需维护服务器、间歇性任务成本优化 → 首选 Lambda
2. **执行时长上限 15 分钟**：超过需拆分任务或改用容器/EC2
3. **CPU 算力由内存决定**：无独立 CPU 配置项，性能不足时应调高内存
4. **预留并发 vs 预置并发**：前者保证/限制并发配额，后者消除冷启动延迟，二者机制不同
5. **三种触发模式**：同步（API Gateway）、异步（S3/SNS，可配置失败目的地）、事件源映射（SQS/Kinesis/DynamoDB Streams，支持批处理）
6. **VPC 内资源访问需显式配置**：进入私有子网后仍需 NAT Gateway/VPC Endpoint 才能访问公网或其他 AWS 服务
7. **执行角色遵循最小权限**：函数通过 IAM 执行角色获得访问其他服务的权限，而非硬编码密钥
8. **版本 + 别名实现灰度发布**：结合 CodeDeploy 加权别名做金丝雀/线性部署
9. **支持容器镜像部署**：最大 10 GB，兼容现有 Docker 工具链
10. **按调用次数 + 执行时长计费**：空闲无成本，是"间歇性负载成本优化"的核心原因

### 场景题解题思路

```
场景分析 → 判断是否用 Lambda
├── "自动扩展 + 无需管理服务器 + 间歇性任务成本优化" → Lambda
├── "任务执行时间可能超过 15 分钟" → 改用 Fargate/ECS/EC2（而非 Lambda）
├── "函数执行缓慢，怀疑计算资源不足" → 调高内存分配（CPU 随内存线性增加）
├── "需要保证某函数不被其他函数抢占并发资源" → 预留并发（Reserved Concurrency）
├── "需要降低高频 API 的首次调用延迟（冷启动）" → 预置并发（Provisioned Concurrency）
├── "需要处理 SQS/Kinesis/DynamoDB Streams 中的流式数据" → 事件源映射 + 批处理
├── "异步调用失败后不想丢失事件" → 配置 On-Failure Destination（SQS/SNS/[[Amazon EventBridge]]）
├── "需要访问 VPC 私有子网中的 RDS，同时还要访问公网 API" → Lambda 进 VPC + NAT Gateway
└── "需要平滑上线新版本、可快速回滚" → 版本 + 别名 + CodeDeploy 加权流量迁移
```

## 最佳实践

1. **三大关键词场景优先选 Lambda**：自动扩展、无服务器、间歇性任务，比自建 EC2/容器更省心省钱
2. **执行时间接近或超过 15 分钟时提前迁移**：改用 Fargate/ECS/[[AWS Step Functions]] 编排长任务
3. **性能不足先调内存而非猜测其他原因**：内存与 CPU 算力线性绑定
4. **区分预留并发与预置并发的使用场景**：不要用预留并发去解决冷启动问题，也不要用预置并发去做并发配额隔离
5. **异步调用务必配置失败目的地**：避免失败事件被静默丢弃
6. **执行角色最小权限**：按函数实际需要的资源和操作精确授权，避免使用过宽的通配策略
7. **公共依赖抽取为 Layer**：减小单个函数部署包体积，多个函数共享复用
8. **生产环境使用别名 + 灰度发布**：降低新版本上线的风险，出现异常可快速回滚
9. **进入 VPC 前评估是否真的需要**：非必要不要把 Lambda 放入 VPC，会增加冷启动延迟和网络配置复杂度
