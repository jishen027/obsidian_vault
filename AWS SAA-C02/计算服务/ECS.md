# Amazon ECS - Elastic Container Service

> **Amazon ECS (Elastic Container Service)** 是一种高度可扩展、高性能的容器管理服务，允许您在 AWS 上轻松运行、停止和管理 Docker 容器。
>
> 相关文档：[[EC2]] | [[AWS Fargate]] | [[EKS]] | [[Auto Scaling]] | [[AWS Load Balance]]

---

## 核心概念

### ECS 定位

| 服务              | 类型            | 场景       | 特点        |
| --------------- | ------------- | -------- | --------- |
| **ECS**         | AWS 专有容器编排    | 微服务部署    | 容器编排、任务管理 |
| [[EKS]]         | 标准 Kubernetes 编排 | 已有 K8s 经验/跨云场景 | 标准 K8s 兼容，学习曲线更高 |
| [[AWS Fargate]] | Serverless 计算层 | 无服务器容器   | ECS/EKS 均可选用，无需管理集群 |
| [[EC2]]     | 虚拟机           | 传统应用托管   | 完全控制服务器   |
| [[AWS Lambda]]      | Serverless 计算 | 事件驱动函数执行 | 无需管理服务器   |

### ECS 核心组件

| 组件 | 描述 |
|------|------|
| **任务定义 (Task Definition)** | JSON 格式的蓝图，描述容器的配置（镜像、内存、CPU、端口等） |
| **任务 (Task)** | 任务定义的运行实例 |
| **服务 (Service)** | 维护预定数量的任务副本，与负载均衡器集成 |
| **集群 (Cluster)** | 逻辑分组，用于管理任务和服务的计算资源 |

## 两种运行模式（考试重点）

### Fargate vs EC2 模式对比

| 特性 | Fargate（无服务器） | EC2 模式 |
|------|-------------------|---------|
| **基础设施管理** | 无需管理 | 自行管理 EC2 实例 |
| **成本模型** | 按容器资源使用计费 | 按 EC2 实例计费 |
| **启动速度** | 快（几秒钟） | 慢（需要启动 EC2） |
| **成本控制** | 较高 | 可优化（Spot 实例、预留实例） |
| **适用场景** | 微服务、突发负载 | 长期稳定负载、GPU 需求 |
| **推荐程度** | **现代应用推荐** | 特定需求时使用 |

### 选择指南

```
选择运行模式
├── "追求极简、不想管服务器" → Fargate
├── "需要 GPU" → EC2 模式
├── "优化成本、长期使用" → EC2 模式（Spot 实例）
├── "特定底层硬件需求" → EC2 模式
└── "微服务、突发负载" → Fargate
```

## 架构详解

### 组件关系

```
集群 (Cluster)
├── 服务 (Service)
│   ├── 任务 (Task) → 容器 (Container)
│   └── 任务 (Task) → 容器 (Container)
└── 任务 (Task) → 容器 (Container)
```

### 任务定义 (Task Definition)

| 配置项 | 说明 |
|--------|------|
| **容器镜像** | Docker 镜像地址（通常来自 ECR） |
| **内存限制** | 容器可用的内存（MB/GB） |
| **CPU 限制** | 容器可用的 vCPU 数量 |
| **端口映射** | 容器端口到主机端口的映射 |
| **IAM 角色** | 任务级别的权限 |
| **日志配置** | CloudWatch Logs 集成 |

### 服务 (Service)

| 功能 | 说明 |
|------|------|
| **任务副本管理** | 维护预定数量的任务运行中 |
| **负载均衡集成** | 与 [[AWS Load Balance]] (ALB/NLB) 集成处理流量 |
| **健康检查** | 自动替换不健康的任务 |
| **滚动更新** | 支持任务定义的滚动更新 |

### 网络模式（Network Mode）

| 模式 | 说明 | 适用运行模式 |
|------|------|------------|
| **awsvpc** | 每个任务获得独立的 **弹性网络接口（ENI）和私有 IP**，可直接绑定安全组 | Fargate **强制使用**；EC2 模式可选 |
| **bridge** | 容器共享宿主机网络命名空间，通过 Docker 内置 NAT 转发端口 | 仅 EC2 模式 |
| **host** | 容器直接使用宿主机网络接口，无端口映射开销 | 仅 EC2 模式 |

> **考试要点**：`awsvpc` 模式下每个任务像一台独立的"微型 EC2"一样拥有自己的 ENI，可以在任务级别而非实例级别配置**安全组**，实现更细粒度的网络隔离——这是 Fargate 任务安全性的基础。

### 部署类型（Deployment Type）

| 类型 | 说明 |
|------|------|
| **滚动更新（Rolling Update）** | 默认方式，逐步用新任务替换旧任务，可配置最小健康百分比和最大百分比控制替换节奏 |
| **蓝/绿部署（Blue/Green）** | 通过 **AWS CodeDeploy** 集成，创建全新的任务集并切换流量，支持自动回滚，风险更低但需要额外配置 |

## 容量提供程序（Capacity Providers）

- 决定任务实际运行在**哪种底层计算资源**上，一个集群可同时关联多个容量提供程序，并按权重（Weight）分配任务

| 容量提供程序 | 说明 | 适用场景 |
|-------------|------|---------|
| **FARGATE** | 按需 Fargate | 稳定负载，需要 SLA 保障 |
| **FARGATE_SPOT** | 使用闲置容量，价格最高降低 **70%** | 可容忍中断的批处理、无状态任务 |
| **EC2 Auto Scaling Group（ASG）容量提供程序** | 关联一个 [[Auto Scaling]] 组，ECS 根据任务需求自动伸缩 ASG 实例数量 | EC2 模式下希望集群容量随任务负载自动增减 |

> **考试陷阱**：**FARGATE_SPOT 与 EC2 Spot 实例是两个不同层面的成本优化手段**——前者是 Fargate 任务级别的竞价容量，后者是 EC2 实例级别的竞价容量；题目问"Fargate 模式下如何进一步降低成本"时，答案是 FARGATE_SPOT，而非"使用 Spot 实例"（Spot 实例概念只存在于 EC2 模式）。

## 任务放置策略（Task Placement Strategies，仅 EC2 模式）

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **装箱（Binpack）** | 尽量将任务集中部署到少数实例上，减少碎片化闲置资源 | 追求成本优化、提高资源利用率 |
| **分散（Spread）** | 将任务均匀分布到多个实例或可用区 | 追求高可用性，避免单点故障影响过多任务 |
| **随机（Random）** | 随机选择实例放置任务 | 对放置无特殊要求的简单场景 |

> **考试要点**：任务放置策略**仅适用于 EC2 模式**——Fargate 由 AWS 完全托管底层资源分配，用户无需（也无法）配置放置策略。

## ECS 优势

### 核心优势

| 优势 | 说明 |
|------|------|
| **快速启动** | 容器几秒钟内启动，比 EC2 快数分钟 |
| **资源利用率高** | "装箱"技术，单实例部署多个微服务 |
| **深度集成** | 与 ECR、IAM、CloudWatch 集成 |
| **可扩展性** | 自动扩展任务数量 |
| **安全性** | IAM 角色为每个任务分配精细权限 |

### 与 ECR 集成

- **ECR (Elastic Container Registry)**：AWS 专用的容器镜像注册表
- 安全存储和拉取容器镜像
- 与 ECS 无缝集成
- 支持镜像扫描和漏洞检测

### 与 IAM 集成

- 任务级别的 IAM 角色
- 精细权限控制
- 无需在容器内硬编码访问密钥

## 与相关服务对比

### ECS vs Fargate vs Lambda

| 特性 | ECS | Fargate | Lambda |
|------|-----|---------|--------|
| **服务器管理** | 可选（EC2 模式） | 无需管理 | 无需管理 |
| **执行时间** | 无限制 | 最长 14 天 | 最长 15 分钟 |
| **冷启动** | 快（秒级） | 快（秒级） | 可能有冷启动延迟 |
| **成本** | 按 EC2 + 资源 | 按资源使用 | 按请求 + 执行时间 |
| **适用场景** | 长期运行的容器 | 短期任务、微服务 | 事件驱动函数 |

### ECS vs [[EKS]]

| 特性 | ECS | [[EKS]] |
|------|-----|-----|
| **编排器** | AWS 专有管理 | 标准 Kubernetes |
| **学习曲线** | 低 | 高（需要 K8s 知识） |
| **兼容性** | 仅 Docker，AWS 专有 | 标准 K8s 兼容，可跨云迁移 |
| **控制平面费用** | 免费 | 按小时收费 |
| **适用场景** | 简单容器管理、新项目 | 已有 K8s 经验、需要跨云可移植性 |

## 考试重点总结

### SAA-C02 高频考点

1. **ECS 定位**：容器编排服务，管理 Docker 容器
2. **Fargate vs EC2**：无服务器 vs 自管理，现代应用推荐 Fargate
3. **核心组件**：任务定义、任务、服务、集群
4. **与 ECR 集成**：安全存储和拉取容器镜像
5. **与 IAM 集成**：任务级别权限控制
6. **快速启动**：容器秒级启动，比 EC2 快
7. **资源利用**：装箱技术，提高硬件利用率
8. **负载均衡集成**：与 ALB/NLB 集成处理流量
9. **ECS 免费**：服务本身免费
10. **ECS vs Fargate**：ECS 是编排器，Fargate 是计算驱动方式
11. **awsvpc 网络模式**：每个任务独立 ENI + 私有 IP，可配置任务级安全组，Fargate 强制使用该模式
12. **FARGATE_SPOT ≠ EC2 Spot 实例**：分别是 Fargate 任务级和 EC2 实例级的两种独立竞价容量优化手段
13. **任务放置策略仅适用于 EC2 模式**：Binpack（省成本）、Spread（高可用）、Random，Fargate 无需配置
14. **蓝/绿部署需 CodeDeploy**：滚动更新是默认方式，蓝/绿部署风险更低但需额外集成

### 场景题解题思路

```
场景分析 → 选择容器方案
├── "微服务、不想管服务器" → ECS + Fargate
├── "GPU 需求" → ECS + EC2 模式
├── "优化成本、长期负载" → ECS + EC2（Spot 实例）
├── "事件驱动函数" → Lambda
├── "K8s 兼容性" → [[EKS]]
├── "Fargate 模式下进一步降低成本，可容忍中断" → FARGATE_SPOT 容量提供程序
├── "EC2 模式下希望任务集中部署、减少碎片" → Binpack 任务放置策略
├── "EC2 模式下希望任务分散、避免单点故障" → Spread 任务放置策略
├── "希望降低部署风险、支持自动回滚" → 蓝/绿部署（CodeDeploy）
└── "容器镜像存储" → ECR
```

### 常见考试场景分析

**场景：公司需要部署微服务架构，追求极简管理，不想管服务器，最佳方案？**

| 选项 | 是否正确 | 原因 |
|------|---------|------|
| **ECS + Fargate** | ✅ 正确 | 无服务器容器，无需管理基础设施 |
| ECS + EC2 模式 | ❌ 错误 | 需要管理 EC2 实例，增加运维负担 |
| EC2 | ❌ 错误 | 需要自行管理容器编排 |
| Lambda | ❌ 错误 | 适合事件驱动函数，不适合长期运行的微服务 |

**关键总结：**
- **"微服务、不想管服务器"** → ECS + Fargate
- **"GPU 需求"** → ECS + EC2 模式
- **"事件驱动函数"** → Lambda
- **"容器镜像存储"** → ECR
