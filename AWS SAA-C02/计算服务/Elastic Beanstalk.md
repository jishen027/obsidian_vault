# AWS Elastic Beanstalk - 应用部署平台 (PaaS)

> **AWS Elastic Beanstalk** 是一种面向应用的 PaaS（平台即服务），开发者只需上传代码，Beanstalk 会自动完成底层基础设施（[[EC2]]、[[AWS Load Balance]]、[[Auto Scaling]]、[[CloudWatch]] 等）的配置、部署和管理。
>
> 相关文档：[[EC2]] | [[ECS]] | [[Lambda]] | [[Auto Scaling]] | [[AWS CloudFormation]]

---

## 核心概念

### Elastic Beanstalk 定位

| 服务 | 类型 | 场景 | 特点 |
|------|------|------|------|
| **Elastic Beanstalk** | PaaS | 传统 Web 应用快速部署 | 只需管理代码，基础设施持续运行 |
| [[EC2]] | IaaS | 完全自定义的服务器托管 | 手动管理底层架构，控制力最强 |
| [[ECS]] | 容器编排 | 微服务架构 | 更适合容器化、松耦合的微服务 |
| [[Lambda]] | Serverless 计算 | 事件驱动函数 | 无基础设施、按调用计费、可缩容至零 |

### 核心特性

- **基础设施抽象化**：开发者只需管理代码，Beanstalk 自动处理容量配置、负载均衡、自动扩展和健康监控
- **持续运行模式**：Beanstalk 启动的基础设施（EC2、ELB 等）会**持续运行**，不会像 Lambda 一样缩容至零，本质上仍是常驻的 IaaS 资源，只是管理方式被自动化
- **服务本身免费**：Elastic Beanstalk 编排能力本身不收费，只需支付底层实际使用的 EC2、ELB、RDS 等资源费用

## 架构组成

### 环境层级结构

```
应用 (Application)
└── 环境 (Environment)
    ├── 环境层：Web 服务器环境 / 工作进程环境
    ├── 底层资源：EC2 / Auto Scaling / ELB / RDS（可选）
    └── 应用版本 (Application Version) → 存储于 S3
```

| 概念 | 说明 |
|------|------|
| **应用 (Application)** | 逻辑容器，包含多个环境和应用版本 |
| **环境 (Environment)** | 运行应用某个版本的一整套 AWS 资源集合 |
| **应用版本 (Application Version)** | 部署包的一个版本，存储在 S3，支持随时回滚 |
| **保存的配置 (Saved Configuration)** | 环境配置模板，可在多个环境间复用 |

### 环境层类型（Environment Tier）

| 类型 | 说明 | 典型场景 |
|------|------|---------|
| **Web 服务器环境** | 前端挂载 ELB，接收 HTTP(S) 请求 | 标准 Web 应用、API 服务 |
| **工作进程环境（Worker）** | 后台从 **SQS 队列**拉取消息并处理，无需直接对外暴露 | 异步任务处理、批处理作业 |

- Java、.NET、PHP、Node.js、Python、Ruby、Go 等主流语言运行时
- 支持 **Docker**（单容器或多容器），也可通过自定义平台运行任意语言/运行时

## 部署策略（考试重点）

| 策略 | 说明 | 停机时间 | 回滚速度 | 额外资源成本 |
|------|------|:---:|:---:|:---:|
| **全部一次性（All at Once）** | 同时更新所有实例 | 有 | 慢（需重新部署旧版本） | 无 |
| **滚动（Rolling）** | 分批替换实例，逐批更新 | 无 | 中 | 无 |
| **滚动 + 额外批次（Rolling with additional batch）** | 先增加一批新实例再滚动更新，容量始终不减少 | 无 | 中 | 有（临时） |
| **不可变部署（Immutable）** | 创建一套全新实例部署新版本，验证通过后才替换旧实例 | 无 | 快（直接终止新实例） | 有（临时，风险最低） |
| **蓝绿部署（Blue/Green）** | 在全新环境部署新版本，通过 **CNAME 交换**切换流量 | 无 | 快（换回 CNAME 即可） | 有（需维护两套环境） |
| **流量分配（Traffic Splitting）** | 将一部分流量导向新版本，用于金丝雀发布 | 无 | 快 | 有（临时） |

> **考试要点**：**Immutable** 部署风险最低（新旧环境完全隔离，出问题直接丢弃新实例），**Blue/Green** 需要手动交换 CNAME，Beanstalk 本身不直接内置蓝绿部署按钮，需人工创建新环境并切换。

## 环境类型

| 类型 | 说明 | 适用场景 |
|------|------|---------|
| **单实例环境** | 仅一台 EC2 实例，无负载均衡 | 开发、测试环境，成本最低 |
| **负载均衡 + 自动扩展环境** | 挂载 ELB，配合 Auto Scaling 水平扩展 | 生产环境，需要高可用 |

## 配置和自定义

- 通过项目中的 **`.ebextensions`** 配置文件（YAML/JSON）自定义底层资源，如安装额外软件包、设置环境变量、修改实例配置
- 支持挂载已有的 **RDS** 数据库，或在环境内直接创建一个与环境生命周期绑定的 RDS 实例（不推荐用于生产，因为环境删除会连带删除数据库）
- 底层实际由 **AWS CloudFormation** 驱动资源编排，因此本质上是 CloudFormation 之上的一层易用性封装

## 监控和健康检查

| 工具 | 说明 |
|------|------|
| **基本健康报告** | 简单的健康状态（正常/告警/严重） |
| **增强型健康报告（Enhanced Health Reporting）** | 提供更细粒度的实例级、请求级健康指标 |
| **CloudWatch 集成** | 监控 CPU、延迟、请求数等底层资源指标 |

## 架构局限性

- Beanstalk 面向**传统单体或简单多层应用**的快速部署，构建**微服务架构**时不如 [[ECS]] 灵活（缺乏细粒度的服务发现、任务编排能力）
- 基础设施持续运行，无法像 [[Lambda]] 一样在无流量时自动缩容至零，成本模型更接近传统 EC2

## 考试重点总结

### SAA-C02 高频考点

1. **定位**：PaaS，只需管理代码，基础设施由 Beanstalk 自动配置和管理
2. **免费服务**：Beanstalk 本身免费，仅收取底层资源费用
3. **部署策略选择**：追求零风险选 Immutable，追求快速切换选 Blue/Green，追求平滑过渡选 Rolling
4. **环境层类型**：Web 服务器环境处理 HTTP 请求，工作进程环境处理 SQS 异步任务
5. **持续运行**：与 Lambda 的按需/缩容至零模式不同，Beanstalk 资源持续运行
6. **微服务局限**：复杂微服务架构应优先考虑 ECS/Fargate 而非 Beanstalk
7. **本质是 CloudFormation 封装**：底层通过 CloudFormation 编排资源

### 场景题解题思路

```
场景分析 → 选择计算方案
├── "快速部署 Web 应用，不想管基础设施细节" → Elastic Beanstalk
├── "需要异步处理 SQS 队列中的任务" → Elastic Beanstalk 工作进程环境
├── "部署新版本要求零风险、可快速丢弃" → Immutable 部署
├── "需要即时切换新旧版本流量" → Blue/Green（CNAME 交换）
├── "构建复杂微服务架构" → ECS / Fargate（优于 Beanstalk）
├── "完全无服务器、事件驱动、按需付费" → Lambda
└── "需要完全掌控底层服务器" → 直接使用 EC2
```

## 最佳实践

1. **生产环境使用负载均衡 + 自动扩展环境**：避免单实例环境的单点故障
2. **数据库与环境解耦**：使用独立创建的 RDS 实例，而非环境内置数据库，避免环境删除连带丢失数据
3. **优先选择 Immutable 部署**：将部署风险降到最低，出现问题可直接丢弃新实例
4. **使用 `.ebextensions` 管理配置**：将环境配置代码化，便于版本控制和复用
5. **保留历史应用版本**：便于快速回滚到已知正常的版本
6. **微服务场景转向 ECS/Fargate**：Beanstalk 更适合单体或简单多层应用
7. **启用增强型健康报告**：获得更细粒度的问题定位能力
