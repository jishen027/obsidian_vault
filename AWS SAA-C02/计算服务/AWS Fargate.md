# AWS Fargate - 无服务器容器引擎

> **AWS Fargate** 是专为容器设计的**无服务器（Serverless）计算引擎**，是 [[ECS]] 和 [[EKS]] 共用的两种运行模式之一，让用户无需管理任何底层服务器即可直接运行容器。
>
> 相关文档：[[ECS]] | [[EKS]] | [[EC2]] | [[Auto Scaling]] | [[AWS Lambda]]

---

## 核心概念

### 无服务器容器化的价值

- 传统容器运行模式（[[ECS]] EC2 模式）需要用户自行管理底层 [[EC2]] 实例：打补丁、扩缩容、管理操作系统
- Fargate 的核心价值：用户只需打包应用镜像，在**任务定义（Task Definition）**中声明所需的 **CPU 和内存**，AWS 自动处理底层计算基础设施的分配、伸缩和维护
- 本质是把"容器编排"和"底层服务器管理"两件事解耦——编排逻辑仍由 [[ECS]]/[[EKS]] 负责，服务器管理完全交给 Fargate

### Fargate 定位（考试要点）

| 服务 | 类型 | 管理粒度 | 典型场景 |
|------|------|---------|---------|
| **Fargate** | 无服务器容器计算引擎 | 只需定义容器 CPU/内存需求 | 微服务、突发负载、追求零运维 |
| [[ECS]] EC2 模式 | 容器编排 + 自管理实例 | 需管理 EC2 实例（打补丁、扩容） | 需要 GPU、特定内核、长期稳定负载的成本优化 |
| [[AWS Lambda]] | Serverless 函数计算 | 无需管理，但受限于单次执行时长 | 事件驱动的短时函数（最长 15 分钟） |

> **考试陷阱**：Fargate 本身**不是一个独立的容器编排服务**，而是 ECS 或 EKS 的一种**运行模式（计算层）**；题目中若要求"编排容器"，正确答案是 [[ECS]]/[[EKS]]，"Fargate"只是二者之下的一个可选执行方式。

---

## 与 ECS 结合的工作逻辑

- 在任务定义（Task Definition）的 JSON 中通过 `requiresCompatibilities: ["FARGATE"]` 指定该任务运行在 Fargate 上
- 必须显式声明任务级别的 **CPU（如 0.25 vCPU）**和**内存（如 0.5 GB）**，AWS 按声明值分配资源并计费
- **强制使用 `awsvpc` 网络模式**：每个 Fargate 任务拥有独立的弹性网络接口（ENI）和私有 IP，可绑定任务级安全组，实现细粒度网络隔离
- 配合 [[Auto Scaling]]（ECS Service Auto Scaling），可根据 CPU/内存利用率或自定义 CloudWatch 指标秒级启动新任务，响应突发负载

## Fargate 的显著优势

| 优势 | 说明 |
|------|------|
| **管理负担极低** | 无需打补丁、扩容集群、管理实例操作系统等运维工作 |
| **资源利用率高** | 采用"装箱"技术，在受管基础设施上紧密调度多个任务负载 |
| **安全性增强** | 每个任务运行在独立的内核隔离计算环境中，任务间不共享内存或 CPU，安全边界优于共享 EC2 实例的容器 |
| **按需付费** | 仅按声明的 CPU/内存资源和实际运行时间计费，无闲置实例浪费 |
| **秒级启动** | 无需等待 EC2 实例启动，容器可在几秒内就绪 |

## 成本优化

| 手段 | 说明 |
|------|------|
| **Fargate Spot（容量提供程序）** | 使用 AWS 闲置容量运行 Fargate 任务，价格最高可降低 **70%**，适合可容忍中断的批处理/无状态任务 |
| **Compute Savings Plans** | 承诺 1-3 年的使用量，可比按需价格最高节省 **66%**，适合长期稳定运行的 Fargate 负载 |

> **考试陷阱**：**Fargate Spot 与 EC2 Spot 实例是两套独立的竞价容量机制**——Fargate Spot 作用于 Fargate 任务层面，EC2 Spot 实例作用于 ECS EC2 模式下的底层实例层面，两者不能混用概念。

---

## 什么时候该选 Fargate 而不是 EC2 模式

| 选择 | 适用条件 |
|------|---------|
| **选 Fargate** | 追求极致简便、想减少运维开销、处理突发性不规律负载、无特殊硬件需求 |
| **选 [[EC2]] 模式** | 需要完全控制底层实例（如特定内核调优）、需要 **GPU** 硬件、有极大规模且稳定的负载希望用预留实例/Spot 实例做极致成本优化 |

---

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **微服务架构，追求零运维** | [[ECS]]/[[EKS]] + Fargate |
| **可容忍中断的批处理任务** | ECS + Fargate Spot |
| **长期稳定运行的容器负载** | ECS + Fargate + Compute Savings Plans |
| **需要 GPU 或特定内核参数** | ECS + EC2 模式（非 Fargate） |
| **短时事件驱动函数** | 改用 [[AWS Lambda]]，而非 Fargate |

## 考试重点总结

### SAA-C02 高频考点

1. **Fargate 是运行模式，不是编排器**：真正的容器编排仍由 [[ECS]]/[[EKS]] 负责
2. **只需声明 CPU/内存**：无需管理底层 EC2 实例，AWS 自动分配计算资源
3. **强制 awsvpc 网络模式**：每个任务独立 ENI + 私有 IP，可配置任务级安全组
4. **Fargate Spot 降本最高 70%**：适合可容忍中断的场景，与 EC2 Spot 实例是不同层面的概念
5. **Compute Savings Plans 降本最高 66%**：适合长期稳定负载的成本优化
6. **需要 GPU/特定内核时选 EC2 模式**：Fargate 不支持底层硬件的深度定制
7. **秒级启动**：容器几秒内就绪，远快于等待 EC2 实例启动
8. **安全隔离优于共享实例**：每个任务独立内核隔离环境，不共享内存/CPU
9. **按声明资源计费**：成本与任务定义中的 CPU/内存声明值直接挂钩
10. **事件驱动短函数不是 Fargate 的强项**：执行时长较短且事件驱动的场景应优先考虑 Lambda

### 场景题解题思路

```
场景分析 → 选择计算方式
├── "微服务、追求零运维、不想管服务器" → Fargate
├── "需要 GPU 或特定内核调优" → [[ECS]]/[[EKS]] + EC2 模式（非 Fargate）
├── "可容忍中断的批处理任务，希望进一步降本" → Fargate Spot
├── "长期稳定运行的容器负载，追求成本优化" → Fargate + Compute Savings Plans
├── "需要极大规模、稳定负载下用预留/Spot 实例压价" → ECS + EC2 模式
├── "短时、事件驱动的函数执行（分钟级）" → 改用 Lambda
└── "任务需要独立网络隔离和安全组" → Fargate（awsvpc 模式原生支持）
```

## 最佳实践

1. **追求零运维的微服务优先选 Fargate**：减少底层实例管理的运维负担
2. **可容忍中断的负载使用 Fargate Spot**：批处理、无状态任务优先评估以降低成本
3. **长期稳定负载评估 Compute Savings Plans**：相比按需价格可节省最高 66%
4. **合理声明 CPU/内存**：过度声明会浪费成本，声明不足会导致任务被限流或 OOM
5. **需要 GPU/特定硬件时不要勉强用 Fargate**：应改用 [[ECS]]/[[EKS]] 的 EC2 模式
6. **善用任务级安全组**：借助 awsvpc 模式为不同任务配置差异化的网络访问策略
7. **短时事件驱动场景优先评估 Lambda**：避免为极短生命周期的任务引入容器管理开销
