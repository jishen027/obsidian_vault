# AWS Batch - 批处理计算服务

> **AWS Batch**是全托管的**批处理计算**服务，专为**运行到完成即结束**的计算密集型任务设计（科学模拟、金融风险建模、基因组分析、媒体转码、机器学习训练/批量推理等），而非长期运行的在线服务。它根据**作业队列中排队的任务量和资源需求**，自动计算并**动态调配**最优数量和类型的计算资源（[[EC2]] On-Demand/Spot 或 [[AWS Fargate]]），免去了手动搭建和管理批处理计算集群的重复劳动。
>
> 相关文档：[[EC2]] | [[ECS]] | [[AWS Fargate]] | [[AWS Lambda]] | [[AWS Step Functions]] | [[Auto Scaling]] | [[IAM]]

## 核心概念

### 四大核心组件

| 组件 | 作用 |
|------|------|
| **作业（Job）** | 提交给 AWS Batch 的一个具体工作单元，本质上是一次**容器运行**（镶嵌在作业定义中的容器镶像 + 命令） |
| **作业定义（Job Definition）** | 描述作业**如何运行**的模板——容器镶像、所需 vCPU/内存、[[IAM]] 角色、重试策略、环境变量，与 [[ECS]] 任务定义的理念一致 |
| **作业队列（Job Queue）** | 作业提交后进入的队列，具备**优先级**，并关联一个或多个**计算环境** |
| **计算环境（Compute Environment）** | 定义实际承载作业运行的计算资源——可以是 [[EC2]]（On-Demand/Spot）或 **[[AWS Fargate]]/Fargate Spot** |

### 托管 vs 非托管计算环境

| 类型 | 说明 |
|------|------|
| **托管（Managed）** | AWS Batch **自动**为你创建、扩缩容并终止底层 [[ECS]] 集群的容量，队列空闲时可**缩容到零**，无需人工干预 |
| **非托管（Unmanaged）** | 客户自行创建和管理 [[ECS]] 集群，AWS Batch 只负责作业调度，适合需要对底层集群做特殊定制的场景 |

> **考试要点**：**绝大多数场景应优先选择托管计算环境**——它能在队列没有作业时自动缩容到零，避免为闲置容量付费；只有在需要对集群做高度定制化配置时才考虑非托管模式。

### 调度与作业依赖

- AWS Batch 的调度器根据**优先级、资源需求和依赖关系**决定队列中的作业**何时、在哪个计算资源上**运行
- **数组作业（Array Jobs）**：从**同一份作业定义**批量派生出大量相似作业（如对 1000 个参数组合分别跑一次模拟），便于批量提交和跟踪，而不必逐个单独提交
- **作业依赖（Job Dependencies）**：可声明某作业必须等待其他作业**完成后**才能开始，构建有依赖关系的处理流水线（如"数据预处理作业完成后才能启动分析作业"）
- **多节点并行作业（Multi-Node Parallel Jobs）**：面向**紧耦合的高性能计算（HPC）**场景（如 MPI 分布式计算），跨**多个 EC2 实例**协同运行同一个作业，要求低延迟的实例间网络——**仅支持 EC2 计算环境，不支持 Fargate**

> **考试陷阱**：**题目描述"需要跨多个实例运行紧耦合的 MPI 分布式计算任务"** → 必须使用 **EC2 计算环境的多节点并行作业**，Fargate 计算环境**不支持**这种跨实例紧耦合通信模式；Fargate 更适合**相互独立、无需实例间通信**的常规批处理作业。

## 计算资源选型：EC2 vs Fargate（考试高频）

| 维度 | EC2 计算环境 | Fargate 计算环境 |
|------|-------------|-------------------|
| **底层管理** | 需要指定实例类型范围，AWS Batch 负责伸缩 | 完全无服务器，无需关心实例类型 |
| **GPU/特殊实例支持** | **支持**（如需要 GPU 做机器学习训练） | **不支持**指定 GPU 等特殊硬件 |
| **Spot 折价** | 支持 EC2 Spot，容错批处理任务可享最高 90% 折扣 | 支持 Fargate Spot，同样有折扣 |
| **多节点并行作业** | **支持** | **不支持** |
| **启动速度** | 相对较慢（需拉起实例） | 更快，无需等待实例启动 |
| **适用场景** | 需要 GPU、特殊实例规格、或多节点紧耦合计算 | 常规、独立、无特殊硬件需求的批处理作业，追求更简单的运维 |

> **考试要点**：**题目描述"批处理任务需要 GPU 进行机器学习训练"或"任务需要跨实例的紧耦合并行计算"** → 必须选择 **EC2 计算环境**；题目描述"大量相互独立、无特殊硬件需求的批处理作业，希望进一步简化运维"** → **Fargate 计算环境**更合适。

## 与相关计算/编排服务的边界（考试高频）

| 服务 | 定位 | 与 AWS Batch 的关系 |
|------|------|----------------------|
| **[[AWS Lambda]]** | 短时、事件驱动函数 | Lambda 执行时长上限 **15 分钟**，不适合长时间运行或需要 GPU 的批处理任务；这类场景应改用 AWS Batch，完整边界见 [[AWS Lambda]] 独立笔记 |
| **[[ECS]] / [[AWS Fargate]]** | 容器编排/无服务器容器运行时 | AWS Batch **底层构建在 ECS 之上**，在其上叠加了**作业队列、优先级调度、依赖关系管理**这一层专为"运行到完成"的批处理任务设计的能力，而非面向长期在线服务 |
| **[[Auto Scaling]]** | 面向**长期运行**的服务器/容器集群的弹性伸缩 | Auto Scaling 维持一组持续在线的实例；AWS Batch 面向**离散的、有限的作业队列**，队列清空后可缩容到零，两者的伸缩目标对象不同 |
| **[[AWS Step Functions]]** | 跨多个 AWS 服务的工作流编排（状态机） | 可以把一个或多个 AWS Batch 作业作为 Step Functions 状态机中的**一个步骤**，用 Step Functions 编排"提交批处理作业 → 等待完成 → 触发下一步"的完整数据管道，两者常**组合使用**而非互相替代 |

> **考试陷阱**：**题目描述"运行时间较长、可能需要 GPU 的批量计算任务，且执行时长不可预测" → AWS Batch**，而不是勉强用 Lambda（15 分钟上限）硬撑或直接裸用 ECS/Fargate（缺少作业队列、优先级调度和依赖管理能力）；题目描述"需要编排包含批处理作业的多步骤数据管道" → **AWS Step Functions + AWS Batch** 组合，而非把所有编排逻辑塞进单一批处理作业。

## 定价（考试提示）

- **AWS Batch 服务本身不收取额外费用**，只需为作业实际消耗的底层计算资源（EC2 On-Demand/Spot 或 Fargate）付费
- 容错性高的批处理作业应优先使用 **EC2 Spot 或 Fargate Spot**，可节省最高 90% 的计算成本，与 [[EC2]] 笔记中"Spot 适合批处理"这一考点一致

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **大规模、可容忍中断的批处理计算任务** | AWS Batch + EC2/Fargate Spot 计算环境 |
| **需要 GPU 加速的机器学习批量训练/推理** | AWS Batch + EC2 计算环境（指定 GPU 实例类型） |
| **跨多实例的紧耦合 MPI/HPC 计算** | AWS Batch 多节点并行作业（仅 EC2 计算环境） |
| **大量相互独立、无特殊硬件需求的批处理作业** | AWS Batch + Fargate 计算环境，简化运维 |
| **对同一份作业定义批量派生大量相似任务（参数扫描）** | AWS Batch 数组作业（Array Jobs） |
| **多步骤、有先后依赖的批处理流水线** | AWS Batch 作业依赖（Job Dependencies），或结合 [[AWS Step Functions]] 编排 |
| **任务执行时间可能远超 15 分钟，且计算量较大** | 改用 AWS Batch（而非勉强拆分成多个 Lambda 调用） |

## 考试重点总结

### SAA-C02 高频考点

1. **官方名称是 AWS Batch，不是 Amazon Batch**：面向"运行到完成"的批处理计算任务，而非长期在线服务
2. **四大组件**：作业、作业定义、作业队列（带优先级）、计算环境
3. **托管计算环境可自动缩容到零**：队列空闲时不产生计算资源费用，绝大多数场景应优先选择
4. **EC2 计算环境支持 GPU 和多节点并行作业，Fargate 不支持**：需要 GPU 或跨实例紧耦合计算时必须选 EC2
5. **多节点并行作业面向紧耦合 HPC/MPI 场景，仅支持 EC2**：Fargate 更适合相互独立的常规批处理作业
6. **数组作业用于从同一作业定义批量派生大量相似任务**：避免逐个单独提交
7. **AWS Batch 底层构建在 ECS 之上**：额外叠加了作业队列、优先级调度、依赖管理能力
8. **Lambda 有 15 分钟执行时长上限，不适合长时间/GPU 批处理**：应改用 AWS Batch
9. **AWS Batch 本身不收费，只为底层计算资源付费**：容错任务应优先用 Spot 降低成本
10. **常与 AWS Step Functions 组合使用**：Step Functions 编排多步骤管道，AWS Batch 承担其中的计算密集型步骤

### 场景题解题思路

```
场景分析 → 判断 AWS Batch 相关配置
├── "大规模、容错性高的批处理计算任务" → AWS Batch + Spot 计算环境
├── "批处理需要 GPU 加速" → AWS Batch + EC2 计算环境（GPU 实例类型）
├── "跨多实例的紧耦合 MPI/HPC 计算" → AWS Batch 多节点并行作业（仅 EC2）
├── "大量独立、无特殊硬件需求的批处理作业" → AWS Batch + Fargate 计算环境
├── "同一作业定义需批量派生大量相似任务" → 数组作业（Array Jobs）
├── "多步骤有依赖关系的批处理流水线" → 作业依赖，或 + Step Functions 编排
├── "任务执行时间可能超过 15 分钟，计算量较大" → 改用 AWS Batch（而非 Lambda）
└── "只是需要长期运行的服务器/容器集群弹性伸缩" → 改用 Auto Scaling（而非 Batch）
```

## 最佳实践

1. **默认使用托管计算环境**：让 AWS Batch 自动处理容量伸缩和缩容到零，避免手动管理集群
2. **容错性高的批处理任务优先使用 Spot 计算环境**：显著降低计算成本，仅在任务不能容忍中断时才用 On-Demand
3. **需要 GPU 或多节点紧耦合计算时明确选择 EC2 计算环境**：不要误以为 Fargate 能覆盖所有场景
4. **大批量相似任务使用数组作业而非逐个提交**：简化管理和跟踪
5. **多步骤数据管道优先结合 AWS Step Functions 编排**：让 AWS Batch 专注于计算密集型作业本身，编排逻辑交给 Step Functions
6. **任务执行时间接近或可能超过 Lambda 的 15 分钟上限时及早迁移到 AWS Batch**：避免勉强拆分成多个 Lambda 调用增加架构复杂度
7. **合理设置作业重试策略和超时时间**：避免瞬时故障导致整批作业失败，同时防止异常作业无限占用计算资源
