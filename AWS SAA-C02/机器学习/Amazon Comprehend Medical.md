# Amazon Comprehend Medical - 医疗自然语言处理服务

> **Amazon Comprehend Medical** 是 [[Amazon Comprehend]] 的**医疗专用变体**，使用针对医学文本训练的机器学习模型，从临床笔记、出院小结、医患对话记录等非结构化医疗文本中提取医学实体（诊断、药物、剂量、检验结果等）、识别**受保护健康信息（PHI）**，并可关联到标准医学编码体系（**ICD-10-CM、RxNorm、SNOMED CT**），无需自行训练医学 NLP 模型。
>
> 相关文档：[[Amazon Comprehend]] | [[Amazon Transcribe]] | [[S3]] | [[AWS Lambda]] | [[IAM]] | [[KMS]]

---

## 核心概念

### 为什么需要专用的医疗 NLP 服务

- **通用 NLP 模型的局限**：医疗文本包含大量专业术语、缩写、剂量表达和临床上下文关系（如"药物-剂量-频率"的关联），通用的 [[Amazon Comprehend]] 模型未针对这类结构化医学语义做优化
- **Comprehend Medical 的核心价值**：基于**专门的医学语料训练**，能准确识别医学实体及其属性（如药物名称、剂量、给药途径、检验数值、诊断），并自动关联到行业标准编码体系，大幅减少病历结构化和医学编码的人工工作量
- **在 AWS AI 服务栈中的定位**：与 [[Amazon Comprehend]] 之于通用文本、Amazon Transcribe Medical 之于医疗语音的关系一致——是**面向医疗/生命科学垂直领域的专用化服务**，而非通用能力的简单复用

### Comprehend Medical 在 SAA-C02 考试中的定位（考试要点）

| 服务 | 领域 | 核心能力 | 典型场景 |
|------|------|---------|---------|
| **Comprehend Medical** | 医疗文本专用 | 医学实体识别、PHI 检测、医学编码关联 | 临床笔记结构化、医疗合规脱敏、医学编码辅助 |
| [[Amazon Comprehend]] | 通用文本 | 情感分析、通用实体识别、PII 检测 | 客户评论、通用文档的语义分析，**未针对医学术语优化** |
| Amazon Transcribe Medical | 医疗语音专用 | 医患对话转录 | 通常是 Comprehend Medical 的**上游**，先转录医患对话再做医学实体提取 |

> **考试陷阱**：题目描述**"需要从临床文本/病历中提取诊断、药物、剂量等医学实体，并满足医疗合规要求"** → 答案是 **Comprehend Medical**，而非通用的 **Comprehend**——通用 Comprehend 的 PII 检测覆盖姓名、电话等常见个人信息，但**不理解医学术语，也不识别 PHI（受保护健康信息）这一医疗合规特定范畴**；医疗场景应优先选择专用变体。

## 核心能力

| 能力 | 说明 |
|------|------|
| **医学实体与关系提取（NERe）** | 识别医学实体（如诊断、症状、治疗、检验结果、解剖部位）及实体间的关系（如"药物-剂量-频率"的关联结构） |
| **PHI 检测（Protected Health Information）** | 识别符合 **HIPAA Safe Harbor** 标准的 **18 类受保护健康信息**（姓名、日期、地址、病历号等），用于合规脱敏 |
| **ICD-10-CM 编码关联（InferICD10CM）** | 检测文本中的疾病/诊断相关实体，并关联到标准的 **ICD-10-CM** 疾病分类编码，按置信度排序返回匹配结果 |
| **RxNorm 编码关联（InferRxNorm）** | 检测文本中的药物名称，并关联到美国国立医学图书馆的 **RxNorm** 标准化药物概念标识符 |
| **SNOMED CT 编码关联（InferSNOMEDCT）** | 检测医学概念（病症、解剖部位、检查、治疗程序），并关联到 **SNOMED CT** 医学术语本体编码 |

> **考试要点**：三种**本体关联（Ontology Linking）**能力分别对应不同的标准医学编码体系——**ICD-10-CM 面向诊断/疾病编码**（常用于医保理赔），**RxNorm 面向药物标准化**（常用于用药安全核查），**SNOMED CT 面向更广泛的临床术语标准化**；题目提到具体的编码体系名称时，应对应到相应的 Infer API，而非笼统地选择"医学实体识别"。

## PHI 检测与合规

- PHI（受保护健康信息）是 **HIPAA（美国健康保险流通与责任法案）**下需要特殊保护的个人健康数据范畴，检测范围覆盖姓名、地址、电话、邮箱、社保号、病历号、日期等 **18 类字段**
- **典型用途**：在将医疗文本用于分析、共享或存储到数据湖之前，先用 PHI 检测识别并脱敏敏感字段，降低合规风险
- 与通用 [[Amazon Comprehend]] 的 **PII 检测**概念相似，但 PHI 检测专门针对医疗行业的合规框架（HIPAA），覆盖字段和判定标准均按医疗场景定制

## 处理模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **实时分析（Synchronous）** | 单条临床文本同步调用 API，立即返回结果 | 临床工作流中的实时辅助（如医生录入病历时的即时编码建议） |
| **批量分析（Asynchronous Batch）** | 提交存储在 [[S3]] 中的大批量医疗文档，异步处理 | 历史病历库的批量结构化、大规模医学编码回溯 |

## 架构与集成

| 集成方式 | 说明 |
|---------|------|
| **Amazon Transcribe Medical + Comprehend Medical** | 医患对话语音先转录为文本，再提取医学实体和 PHI，构成"医疗语音 → 文本 → 结构化医学信息"的完整管道 |
| **S3 触发批量分析** | 病历文档上传到 [[S3]] 后，通过事件通知触发 [[AWS Lambda]] 调用批量分析 |
| **医疗合规数据管道** | Comprehend Medical PHI 检测作为病历数据入湖/共享前的标准预处理步骤，自动脱敏后再供下游分析使用 |
| **医保理赔/编码辅助系统** | 结合 ICD-10-CM/RxNorm 编码关联结果，辅助医疗编码人员提升编码效率和准确性 |

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以调用 Comprehend Medical API |
| **静态加密** | 分析结果和批量处理输出可使用客户管理的 [[KMS]] 密钥加密 |

| **VPC Endpoint** | 支持通过接口终端节点在 VPC 内私有调用 API |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：Comprehend 的医疗专用变体，针对医学文本训练，提取医学实体并关联标准编码体系
2. **判断依据**：处理临床文本/病历、需要医学术语理解或 HIPAA 合规时选 Comprehend Medical；通用文本用普通 Comprehend
3. **三种本体关联能力**：ICD-10-CM（诊断编码）、RxNorm（药物标准化）、SNOMED CT（广泛临床术语标准化），分别对应不同场景
4. **PHI 检测 vs PII 检测**：PHI 是医疗行业 HIPAA 合规框架下的特定概念（18 类字段），区别于通用 Comprehend 的 PII 检测
5. **常与 Transcribe Medical 组合**：医患对话语音转录 + 医学实体提取，构成医疗语音处理的标准管道
6. **属于 HIPAA 合规资格服务**：可处理受 HIPAA 监管的健康数据，需配合 AWS BAA 协议使用
7. **实时 vs 批量分析**：临床工作流实时辅助用同步 API；历史病历库批量处理用异步分析
8. **医学实体关系提取（NERe）**：不仅识别实体，还能识别实体间关系（如药物-剂量-频率）
9. **不应用通用 Comprehend 替代医疗场景**：通用模型未针对医学术语训练，准确率和合规覆盖范围均不足
10. **常用于医保编码辅助和用药安全核查**：ICD-10-CM/RxNorm 编码关联是这两类场景的核心支撑能力

### 场景题解题思路

```
场景分析 → 判断是否用 Comprehend Medical
├── "需要从临床笔记/病历中提取诊断、药物、检验结果等医学实体" → Amazon Comprehend Medical
├── "医疗文本处理需要满足 HIPAA 合规要求" → Comprehend Medical（HIPAA 合规资格服务）
├── "需要将诊断信息关联到标准疾病编码" → InferICD10CM
├── "需要将药物名称标准化以便跨系统核查" → InferRxNorm
├── "需要将临床术语关联到广泛的医学本体编码" → InferSNOMEDCT
├── "医患对话录音需要提取结构化医学信息" → Transcribe Medical + Comprehend Medical 组合
├── "病历数据入湖前需要脱敏受保护健康信息" → Comprehend Medical PHI 检测
└── "处理的是通用（非医疗）文本" → 改用 Amazon Comprehend（而非 Medical 变体）
```

## 最佳实践

1. **医疗场景优先选择 Comprehend Medical 而非通用 Comprehend**：专用模型对医学术语和 PHI 的识别准确率更高，且满足合规要求
2. **按需求选择对应的本体关联 API**：明确场景需要诊断编码（ICD-10-CM）、药物标准化（RxNorm）还是通用临床术语（SNOMED CT），避免混用
3. **病历数据入湖前统一走 PHI 脱敏流程**：作为标准化的合规预处理步骤，而非事后补救
4. **医患对话场景搭建标准管道**：Transcribe Medical（转录）→ Comprehend Medical（实体提取），避免自建医学 NLP 逻辑
5. **确认已签署 AWS BAA 协议**：处理受 HIPAA 监管的健康数据前，确保完成必要的合规协议签署
6. **临床工作流实时辅助场景用同步 API**：保证医生/护士录入病历时获得即时反馈
7. **历史病历批量结构化用异步批量分析**：避免同步调用处理大批量文档导致超时
8. **医学编码结果仍需人工复核**：自动关联的 ICD-10-CM/RxNorm/SNOMED CT 编码作为辅助建议，关键医保/临床决策场景应保留人工审核环节
