# Amazon RDS Proxy - 数据库连接代理

> **Amazon RDS Proxy** 是一种完全托管的高可用数据库连接代理，位于应用与 [[RDS]] / [[Aurora]] 之间，负责连接池化与复用，减轻数据库的连接压力并缩短故障转移感知时间。
>
> 相关文档：[[RDS]] | [[Aurora]] | [[AWS Secrets Manager]] | [[IAM]] | [[AWS Lambda]]

---

## 核心概念

### RDS Proxy 定位

| 服务 | 类型 | 场景 | 特点 |
|------|------|------|------|
| **RDS Proxy** | 连接代理层 | 连接池化、故障转移加速 | 应用无需修改代码，透明接入 |
| [[RDS]] / [[Aurora]] | 数据库 | 数据存储与处理 | 代理背后的真实数据库实例 |

### 要解决的问题

- 传统应用（尤其是 **Lambda** 等无服务器架构）在高并发下会打开大量短生命周期的数据库连接
- 数据库的最大连接数有限，连接数暴涨（"连接风暴"）会耗尽数据库资源，甚至拖垮实例
- 每次数据库故障转移，所有客户端都需要重新建立连接，感知到的中断时间较长

---

## 工作原理

### 连接池化与复用

- 应用连接到 **RDS Proxy 端点**，而不是直接连接数据库
- RDS Proxy 在后端维护一个较小的、复用的数据库连接池
- 大量应用连接被**多路复用（Multiplexing）**到少量实际数据库连接上，显著降低数据库侧的连接开销

```
大量应用/Lambda 连接 → RDS Proxy（连接池化） → 少量数据库连接 → RDS / Aurora
```

### 加速故障转移

- 故障转移期间，RDS Proxy 会自动检测新的主实例，并将连接路由到新主实例
- 应用**无需重新建立连接**或修改连接字符串，中断时间大幅缩短（相较直连数据库，故障转移感知时间可减少约 66%）

---

## 部署要求

| 要求 | 说明 |
|------|------|
| **VPC 内部署** | RDS Proxy 必须与目标数据库位于同一 VPC（或通过 [[VPC Peering]] 对等连接可达） |
| **不可公网直接访问** | 只能从 VPC 内部或通过 VPN/Direct Connect 等方式访问，无公网端点 |
| **支持的数据库** | RDS（MySQL、PostgreSQL、MariaDB）和 Aurora（MySQL/PostgreSQL 兼容版） |
| **应用改动** | 仅需将连接字符串指向 Proxy 端点，无需修改业务代码逻辑 |

---

## 安全和认证

| 机制 | 说明 |
|------|------|
| **IAM 认证** | 可要求客户端使用 IAM 凭据连接 Proxy，而非数据库原生用户名密码 |
| **[[AWS Secrets Manager]] 集成** | 数据库凭据存储在 Secrets Manager 中，Proxy 自动获取并使用，凭据轮换时**无需中断连接** |
| **传输中加密** | 支持 TLS 加密客户端与 Proxy 之间的连接 |
| **凭据不落地应用代码** | 应用无需在代码或配置中硬编码数据库密码，降低泄露风险 |

---

## 适用场景

| 场景 | 说明 |
|------|------|
| **Lambda / 无服务器应用** | 避免大量并发调用直连数据库导致连接数耗尽 |
| **连接数波动大的应用** | 平滑连接峰值，保护数据库资源 |
| **对故障转移敏感的应用** | 缩短感知中断时间，无需应用层重试逻辑处理长时间连接失败 |
| **需要集中管理数据库凭据** | 结合 [[AWS Secrets Manager]] 实现凭据轮换而不影响在线连接 |

## 考试重点总结

### SAA-C02 高频考点

1. **核心作用**：连接池化 + 故障转移加速，两大核心价值
2. **无需修改应用代码**：只需切换连接端点即可透明接入
3. **必须部署在 VPC 内**：无公网访问能力
4. **配合 Lambda 使用**：解决无服务器架构下的连接风暴问题
5. **凭据轮换不中断连接**：得益于与 [[AWS Secrets Manager]] 的集成
6. **支持 RDS 和 Aurora**：但不支持所有引擎（如 SQL Server 等需具体核实支持范围）
7. **与 [[Aurora]] 配合**：进一步缩短 Aurora 本已较快的故障转移感知时间

### 场景题解题思路

```
场景分析 → 是否需要 RDS Proxy
├── "Lambda 并发调用导致数据库连接数耗尽" → RDS Proxy
├── "希望故障转移对应用透明，减少中断" → RDS Proxy
├── "需要在不中断连接的情况下轮换数据库密码" → RDS Proxy + [[AWS Secrets Manager]]
├── "希望应用使用 IAM 身份连接数据库，而非管理密码" → RDS Proxy + IAM 认证
└── "只是想扩展只读查询能力" → 使用读取副本 / Aurora Replica，而非 RDS Proxy
```

---

## 最佳实践

1. **无服务器架构默认接入**：Lambda 访问 RDS/Aurora 时优先通过 RDS Proxy，避免连接风暴
2. **结合 [[AWS Secrets Manager]]**：集中管理并自动轮换数据库凭据
3. **启用 IAM 认证**：进一步减少硬编码密码的使用
4. **部署在私有子网**：结合安全组限制可访问 Proxy 的来源
5. **不要用它替代读取扩展方案**：RDS Proxy 解决的是连接管理和故障转移问题，读取扩展仍应使用读取副本 / Aurora Replica
