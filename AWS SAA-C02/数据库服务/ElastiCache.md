# Amazon ElastiCache - 内存缓存服务

> **Amazon ElastiCache** 是一种完全托管的内存数据存储服务，支持 **Valkey** 和 **Memcached** 两种引擎，用于在应用与数据库之间加入缓存层，降低延迟并减轻后端数据库压力。
>
> 相关文档：[[RDS]] | [[Aurora]] | [[DynamoDB]] | [[Amazon Kinesis]]

> **背景说明**：Redis 商业授权变更后，AWS 与 Linux Foundation 联合推出开源分支 **Valkey**，作为 ElastiCache 上与 Redis 命令/协议兼容的推荐引擎；ElastiCache 已不再提供 Redis OSS 作为新引擎选项，考试和实际部署中应以 Valkey 为准。

---

## 核心概念

### ElastiCache 定位

| 服务 | 类型 | 场景 | 特点 |
|------|------|------|------|
| **ElastiCache** | 内存缓存 | 数据库查询缓存、会话存储 | 微秒/毫秒级延迟，减轻数据库压力 |
| [[RDS]] / [[Aurora]] | 关系型数据库 | 持久化事务数据 | 数据源，ElastiCache 通常置于其前作缓存 |
| [[DynamoDB]] + **DAX** | NoSQL + 专用缓存 | DynamoDB 查询加速 | DAX 专为 DynamoDB 设计，不适用于其他数据源 |

> **考试要点**：DAX（DynamoDB Accelerator）只服务于 DynamoDB，ElastiCache 是通用缓存服务，可置于 RDS、Aurora 或自建数据库前面。

### 两种引擎对比（考试高频考点）

| 特性 | Valkey | Memcached |
|------|-------|-----------|
| 数据结构 | 丰富（字符串、列表、集合、有序集合、哈希等） | 仅简单的键值字符串 |
| 持久化 | 支持快照（RDB）和 AOF 日志 | 不支持，重启数据丢失 |
| 复制/高可用 | 支持主从复制、Multi-AZ 自动故障转移 | 不支持复制 |
| 备份恢复 | 支持自动/手动快照 | 不支持 |
| 事务 | 支持 | 不支持 |
| 发布/订阅（Pub/Sub） | 支持 | 不支持 |
| 排序集合（排行榜场景） | 支持 | 不支持 |
| 扩展方式 | 分片（Cluster Mode Enabled） | 原生多节点分区，多线程 |
| 多线程 | 主要单线程（按分片） | 多线程，可利用多核 |

## 架构模式

### Valkey：Cluster Mode

| 模式 | 说明 |
|------|------|
| **Cluster Mode Disabled** | 单个分片，1 个主节点 + 最多 5 个只读副本，全部数据存于同一分片 |
| **Cluster Mode Enabled** | 数据跨多个分片（Shard）分布，每个分片可有自己的副本，支持在线重新分片，最高可达数百个分片 |

### Valkey 高可用

- **Multi-AZ + 自动故障转移**：主节点故障时自动将只读副本提升为新主节点
- **Global Datastore**：跨区域异步复制，用于灾难恢复和降低全球读取延迟（延迟通常为秒级）

### Memcached：水平扩展

- 通过增加/移除节点进行水平扩展，数据基于客户端哈希（或 Auto Discovery）分区存储在不同节点
- **不提供复制**：单个节点故障会丢失该节点上的缓存数据（但数据源可从数据库重新加载）
- 支持多核并行处理，适合需要高吞吐、简单键值缓存的场景

## 缓存策略

### 常见缓存模式

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **懒加载（Lazy Loading / Cache-Aside）** | 先查缓存，未命中则查数据库并写回缓存 | 只缓存实际被请求的数据，实现简单 | 首次请求有延迟（缓存穿透），可能返回过期数据 |
| **写穿透（Write-Through）** | 写数据库的同时更新缓存 | 缓存数据始终最新，不会有脏读 | 写入延迟增加，可能缓存永不会被读取的数据，浪费内存 |
| **两者结合 + TTL** | 懒加载 + 写穿透结合，并设置合理的过期时间（TTL） | 平衡新鲜度与命中率 | 需要额外设计和调优 |

### 驱逐策略（Eviction Policy）

- 通过 `maxmemory-policy` 配置，如 `allkeys-lru`（全体键 LRU 驱逐）、`volatile-lru`（仅对设置了 TTL 的键做 LRU 驱逐）等
- 建议为易变数据设置 **TTL**，避免缓存中长期存在过期或脏数据

## 安全

| 机制 | 说明 |
|------|------|
| **VPC 部署** | 集群部署在私有子网内，通过安全组控制访问 |
| **传输中加密** | Valkey 支持 TLS 加密客户端与节点间通信 |
| **静态加密** | Valkey 支持使用 [[KMS]] 加密快照和磁盘数据 |
| **AUTH 令牌** | 通过密码/Token 对数据面访问做身份验证（兼容 Redis AUTH 协议） |
| **IAM 策略** | 仅控制对 ElastiCache 管理 API 的访问，不控制缓存数据本身的读写权限 |

> **注意**：Memcached **不支持**静态加密、传输中加密或身份验证机制，安全性依赖 VPC 网络隔离。

## 备份和恢复

| 引擎 | 支持情况 |
|------|---------|
| **Valkey** | 支持自动快照和手动快照，存储于 S3，可用于恢复或创建新集群 |
| **Memcached** | 不支持备份和恢复，纯瞬态缓存，节点重启数据即丢失 |

## 监控

| 指标/工具 | 说明 |
|----------|------|
| **CloudWatch** | 监控 CPU、内存使用率、缓存命中率/未命中率、连接数、驱逐数等 |

## 应用场景

| 场景 | 推荐引擎 | 原因 |
|------|---------|------|
| **数据库查询缓存** | Valkey / Memcached | 减轻 RDS/Aurora 读取压力 |
| **会话存储（Session Store）** | Valkey | 支持持久化和复制，避免会话丢失，实现应用服务器无状态化 |
| **排行榜/实时统计** | Valkey | 有序集合（Sorted Set）原生支持排名操作 |
| **发布/订阅消息** | Valkey | 原生 Pub/Sub 能力 |
| **简单高吞吐缓存** | Memcached | 多线程、水平扩展、无需持久化 |

## 考试重点总结

### SAA-C02 高频考点

1. **Valkey vs Memcached**：需要持久化、复制、HA、复杂数据结构、事务 → Valkey；需要简单、多线程、纯瞬态缓存 → Memcached
2. **DAX vs ElastiCache**：DAX 专用于 DynamoDB，ElastiCache 是通用缓存层
3. **Cluster Mode**：Disabled = 单分片+副本，Enabled = 多分片水平扩展
4. **懒加载 vs 写穿透**：懒加载简单但可能返回旧数据，写穿透数据新鲜但有写入开销和内存浪费风险
5. **Memcached 无复制无备份**：节点故障即丢数据，仅适合可容忍缓存丢失的场景
6. **Valkey Global Datastore**：跨区域复制，用于灾难恢复和全球低延迟读取
7. **会话存储最佳实践**：使用 ElastiCache（Valkey）外部化会话，替代 ALB 粘性会话，实现应用层无状态

### 场景题解题思路

```
场景分析 → 选择缓存方案
├── "需要持久化、复制和高可用的缓存" → Valkey
├── "需要简单、可水平扩展的高吞吐缓存" → Memcached
├── "需要缓存 DynamoDB 查询结果" → DAX（不是 ElastiCache）
├── "需要外部化会话数据，实现无状态应用层" → ElastiCache Valkey
├── "需要排行榜/实时排名功能" → Valkey 有序集合
├── "需要跨区域灾难恢复的缓存" → Valkey Global Datastore
└── "需要降低 RDS/Aurora 读取压力" → ElastiCache 置于数据库前作查询缓存
```

## 最佳实践

1. **明确引擎选择依据**：持久化/复制/复杂数据结构选 Valkey，纯粹追求吞吐和简单性选 Memcached
2. **合理设置 TTL**：避免缓存雪崩和长期脏数据并存
3. **使用懒加载应对读多写少场景**：结合写穿透处理对新鲜度要求高的数据
4. **为 Valkey 启用 Multi-AZ 和自动故障转移**：生产环境避免单点故障
5. **监控命中率和驱逐数**：命中率低或驱逐频繁提示需要扩容或调整驱逐策略
6. **会话数据外部化**：使用 Valkey 存储会话，避免服务器状态耦合，便于水平扩展应用层
7. **加密和网络隔离**：生产环境优先选择 Valkey 并启用传输/静态加密，部署在私有子网
