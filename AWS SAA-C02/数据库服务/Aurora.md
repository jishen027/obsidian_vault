# Amazon Aurora - 云原生关系型数据库

> **Amazon Aurora** 是 AWS 自研的云原生关系型数据库引擎，兼容 MySQL 和 PostgreSQL，采用存储与计算分离架构，提供比标准 RDS 引擎更高的性能、可用性和弹性。
>
> 相关文档：[[RDS]] | [[Redshift]] | [[DynamoDB]] | [[KMS]]

---

## 核心概念

### Aurora 定位

| 服务 | 类型 | 场景 | 特点 |
|------|------|------|------|
| **Aurora** | OLTP（云原生） | 高可用、高吞吐关系型应用 | 存储计算分离，自动扩展 |
| [[RDS]]（其他引擎） | OLTP | 日常事务处理 | 标准托管数据库，存储固定 |
| [[Redshift]] | OLAP | 商业智能、数据分析 | 复杂查询，列式存储 |

### 架构核心：存储与计算分离

- Aurora 是 RDS 的一种引擎选项，但底层架构与其他引擎完全不同
- **计算层**：数据库实例（Writer/Reader）负责处理 SQL 请求
- **存储层**：独立的分布式存储卷，跨可用区自动复制，与计算层解耦
- 计算实例故障不影响存储层数据，恢复无需重放全部日志，启动更快

## 存储架构

### 分布式复制

| 特性 | 说明 |
|------|------|
| **复制份数** | 数据自动复制 **6 份**，跨 **3 个可用区** |
| **自动扩展** | 存储以 10GB 为增量自动扩展，最高可达 128TB，无需预置 |
| **按使用付费** | 只为实际使用的存储空间付费 |

### 容错能力（Quorum 机制）

| 场景 | 影响 |
|------|------|
| 丢失 2 份副本 | 不影响**写入**可用性（写需要 6 份中的 4 份确认） |
| 丢失 3 份副本 | 不影响**读取**可用性（读需要 6 份中的 3 份确认） |
| 存储自愈 | 自动检测并修复损坏的数据块，无需人工干预 |

## 高可用性和读取扩展

### Aurora Replicas 概览

| 特性 | 说明 |
|------|------|
| **数量** | 最多 15 个只读副本 |
| **复制延迟** | 与存储层共享数据，延迟通常在个位数毫秒级，远低于普通读取副本 |
| **故障转移** | 支持自动故障转移，可设置优先级层级（Tier 0-15），通常 30 秒内完成 |
| **对比 RDS 读取副本** | Aurora Replica 兼具读取扩展与快速故障转移能力，普通 RDS 读取副本仅用于读取扩展 |

## Aurora Replicas 深入解析

### 为什么延迟这么低

- 普通 RDS 读取副本通过**逻辑复制（binlog/WAL）**同步数据，副本需要重新执行变更，延迟通常几十毫秒到几秒不等
- Aurora Replica 与主实例**共享同一份底层分布式存储卷**，不需要复制数据文件本身，只需同步很小的元数据/redo 日志，因此延迟通常在 **10-20 毫秒**级别
- 这也是 Aurora Replica 能够用于快速故障转移的根本原因：无需等待数据追平，切换时数据已经一致

### 端点类型（Endpoints）

| 端点类型 | 说明 |
|---------|------|
| **集群端点（Cluster / Writer Endpoint）** | 始终指向当前的主实例（Writer），用于写操作；故障转移后自动指向新主实例 |
| **读取器端点（Reader Endpoint）** | 在所有 Aurora Replica 之间做**连接级别**的负载均衡（DNS 轮询），用于分担只读流量 |
| **实例端点（Instance Endpoint）** | 直接连接到某个特定实例（Writer 或某个 Replica），用于精细控制流量走向 |
| **自定义端点（Custom Endpoint）** | 用户自定义的实例子集，例如将大实例规格的副本隔离出来专门服务报表/分析查询 |

> **考试要点**：读取器端点的负载均衡发生在**建立连接时**，而不是每次查询时。长连接会一直固定在同一个副本上，因此建议配合较短生命周期的连接池，或使用 [[RDS Proxy|RDS Proxy]] 管理连接。

### 故障转移机制（Failover）详解

1. 主实例发生故障，Aurora 检测到不可用
2. 从现有 Aurora Replica 中选择一个提升为新的主实例：
   - 优先按**优先级层级（Failover Tier 0-15）**选择，数字越小优先级越高
   - 同一层级内，优先选择**实例规格更大**的副本
3. 集群端点（Writer Endpoint）的 DNS 记录更新，指向新主实例
4. 整个过程通常在 **30 秒以内**完成（比 RDS Multi-AZ 故障转移更快）

| 场景 | 行为 |
|------|------|
| **存在 Aurora Replica** | 直接提升现有副本为主实例，故障转移快 |
| **不存在任何 Aurora Replica** | Aurora 会自动创建一个全新的主实例，耗时更长（无热备可用） |

> **考试要点**：即使没有配置任何 Aurora Replica，Aurora 集群仍具备自我修复能力，但恢复时间明显更长——这是"始终建议至少创建 1 个 Aurora Replica"的原因。

### 跨区域读取副本 vs Aurora Global Database

| 方式 | 复制机制 | 延迟 | 适用场景 |
|------|---------|------|---------|
| **Aurora Replica（区域内）** | 共享存储卷 | 个位数毫秒 | 区域内读取扩展、快速故障转移 |
| **跨区域 MySQL 只读副本（旧方案）** | 基于 binlog 的逻辑复制 | 秒级 | Aurora Global Database 出现前的跨区域方案，现较少使用 |
| **Aurora Global Database** | 存储层物理复制 | 通常 < 1 秒 | 跨区域灾难恢复、全球低延迟读取（推荐） |

### 监控与连接管理

| 工具/机制 | 说明 |
|----------|------|
| **CloudWatch 指标 AuroraReplicaLag** | 监控每个副本相对主实例的滞后时间（毫秒） |
| **[[RDS Proxy - 数据库连接代理|RDS Proxy]]** | 池化并复用数据库连接，故障转移时应用无需重新建连，进一步缩短应用侧感知的中断时间 |
| **自定义端点隔离负载** | 将报表、批处理等重查询路由到指定副本，避免影响核心读写流量 |

### 限制和成本

- 单个 Aurora 集群最多 **15 个 Aurora Replica**
- 副本可以使用与主实例不同的**实例规格**，按需搭配成本与性能
- 每个 Aurora Replica 按**实例小时**单独计费（与主实例相同的计费方式），但**不产生额外存储费用**（共享同一存储卷）

### Aurora Global Database

- 面向跨区域灾难恢复和全球低延迟读取
- 一个主区域（读写）+ 最多 **5 个次要区域**（只读）
- 基于存储层的跨区域复制，延迟通常**低于 1 秒**，不占用数据库计算资源
- 支持托管的计划性故障转移（Managed Planned Failover），用于区域级灾难恢复演练或真实切换

## Aurora Serverless

| 版本 | 说明 |
|------|------|
| **v1** | 按 Aurora Capacity Unit（ACU）自动扩缩容，空闲时可自动暂停（按需计费到 0） |
| **v2** | 扩缩容更细粒度、更快，可与 Provisioned 实例混用于同一集群 |

> **适用场景**：不可预测、间歇性或有明显峰谷的工作负载，避免为峰值容量长期付费。

---

## 高级特性

| 特性 | 说明 |
|------|------|
| **Backtrack**（仅 MySQL 兼容版） | 将数据库集群快速"倒回"到之前的时间点，无需从备份恢复；不能替代常规备份 |
| **快速数据库克隆** | 基于写时复制（Copy-on-Write），几分钟内创建克隆，不复制底层存储，节省成本 |
| **并行查询**（Parallel Query，MySQL 兼容版） | 将查询下推到存储层并行执行，加速大规模数据扫描和分析型查询 |
| **Aurora 机器学习** | 直接在 SQL 语句中调用 SageMaker、Comprehend 等服务进行预测分析 |

## 安全和加密

| 机制            | 说明                                    |
| ------------- | ------------------------------------- |
| **静态加密**      | 使用 [[KMS]] 加密，必须在**创建集群时**启用，无法后续直接开启 |
| **传输中加密**     | 使用 SSL/TLS 加密客户端与集群间连接                |
| **IAM 数据库认证** | 支持使用 IAM 凭据登录，免密码                     |
| **网络隔离**      | 部署在 VPC 私有子网，通过安全组控制访问                |

---

## 备份和恢复

- 自动备份基于分布式存储的连续日志流，创建快照**不影响性能、无需停机**
- 支持时间点恢复（PITR），恢复操作会生成新的集群
- 手动快照可跨区域复制，用于灾难恢复
- 与 [[RDS]] 的备份保留规则一致：自动备份 1-35 天，手动快照永久保留直至删除

| 计费项 | 说明 |
|--------|------|
| **实例费用（Provisioned）** | 按实例类型和运行时间计费 |

## 考试重点总结

### SAA-C02 高频考点

1. **存储计算分离**：存储层独立自动扩展，最高 128TB，跨 3 AZ 复制 6 份
2. **Quorum 容错**：丢 2 份不影响写，丢 3 份不影响读
3. **Aurora Replica vs RDS 读取副本**：Aurora Replica 延迟更低且可用于故障转移
4. **Aurora Global Database**：跨区域灾难恢复 + 低延迟只读，复制延迟 < 1 秒
5. **Aurora Serverless**：应对不可预测/间歇性负载，按需自动扩缩容
6. **Backtrack**：快速回滚，不是备份的替代品
7. **快速克隆**：写时复制，成本低、创建快，适合测试环境复用生产数据
8. **加密限制**：静态加密只能在创建集群时启用

### 场景题解题思路

```
场景分析 → 选择 Aurora 特性
├── "需要更高可用性和更快故障转移" → Aurora（相较标准 RDS 引擎）
├── "负载不可预测，时高时低" → Aurora Serverless
├── "需要跨区域灾难恢复和全球只读" → Aurora Global Database
├── "误操作后需要快速回滚，不想全量恢复" → Backtrack
├── "需要快速复制生产库用于测试" → 快速数据库克隆
├── "需要对海量数据做复杂分析查询" → Parallel Query
└── "需要在数据库中直接调用机器学习模型" → Aurora 机器学习
```

## 最佳实践

1. **优先选择 Aurora**：对高可用性、弹性扩展有较高要求的关系型工作负载
2. **读写分离**：利用 Aurora Replica 承担只读流量，降低主实例压力
3. **创建集群时启用加密**：避免后续无法直接开启静态加密的限制
4. **使用快速克隆**：搭建测试/预发环境时避免全量数据复制的时间和成本
5. **配置故障转移优先级**：为关键 Aurora Replica 设置更高的 Tier，控制故障转移目标
6. **不可预测负载使用 Serverless**：避免为固定容量长期付费
7. **跨区域业务使用 Global Database**：兼顾灾难恢复与全球用户的低延迟读取体验
