# DynamoDB - NoSQL 键值/文档数据库

> **Amazon DynamoDB** 是完全托管的 **NoSQL** 数据库服务，为键值和文档数据模型提供**单毫秒级延迟**、无固定架构（Schemaless）的存储，并原生支持跨可用区、跨区域的高可用与弹性扩展。
>
> 相关文档：[[RDS]] | [[Aurora]] | [[ElastiCache]] | [[AWS Lambda]] | [[SQS]] | [[VPC]] | [[KMS]]

---

## 核心概念

### 核心特性和架构

- **非关系型设计（无固定架构）**：为多结构化或非结构化数据设计，同一张表中不同 Item（行）可以拥有不同的属性（列），无需预定义 Schema
- **分布式架构**：数据存储在 SSD 支持的多个**分区（Partitions）**上，并跨多个可用区自动同步复制，实现极低延迟和高可用性
- **主键机制**：通过主键唯一标识 Item 并决定其物理分布，主键可以是：
  - **单一分区键（Partition Key / Hash Key）**：仅靠该属性做哈希路由到分区
  - **复合主键（分区键 + 排序键 / Range Key）**：分区键决定物理分区，排序键决定分区内的排序，支持"查询某分区键下的一系列排序键范围"

### DynamoDB 定位（考试要点）

| 服务 | 类型 | 查询能力 | 典型场景 |
|------|------|---------|---------|
| **DynamoDB** | NoSQL 键值/文档 | 针对主键查询优化，单毫秒延迟 | 高并发、低延迟、按主键访问的场景（购物车、会话、游戏排行榜） |
| [[RDS]] / [[Aurora]] | 关系型（SQL） | 支持复杂 JOIN、多表关联查询 | 强 ACID 事务、复杂关系数据的传统业务系统 |
| [[Redshift]] | 数据仓库（OLAP） | 面向海量数据的复杂分析查询 | BI 报表、跨表聚合分析 |
| [[ElastiCache]] | 内存缓存 | Key-Value，最快但非持久主存储 | 缓存层，通常置于数据库前 |

> **考试陷阱**：DynamoDB 与 RDS 是**互补关系而非替代关系**——DynamoDB 针对主键查询做了极致优化，能以一致的低延迟处理每秒数万次事务，但**不擅长复杂的多表 JOIN**；题目强调"复杂关联查询/强一致性事务"通常指向 RDS/Aurora，强调"海量并发、按主键访问、弹性扩展"通常指向 DynamoDB。

## 表结构限制

| 项目 | 限制/说明 |
|------|---------|
| **Item 最大大小** | **400 KB**（含属性名和值） |
| **属性数据类型** | 标量（String/Number/Binary/Boolean/Null）、集合（String Set/Number Set）、文档（List/Map） |
| **分区键设计** | 应选择**基数高、访问分布均匀**的属性，避免"热分区（Hot Partition）"问题 |

> **考试陷阱**：题目描述"某些分区键值被频繁访问导致节流（Throttling）"→ 根本原因是**分区键设计不合理导致热分区**，解决方案是重新设计分区键（提高基数、加随机后缀分散写入），而非单纯提高预置容量。

## 性能和容量管理

### 容量模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **预置容量（Provisioned）** | 手动指定**读容量单位（RCU）**和**写容量单位（WCU）**，可配合 **Application Auto Scaling** 根据利用率自动调整 | 流量可预测，希望精细控制成本 |
| **按需模式（On-Demand）** | 按实际读写请求量计费，自动伸缩，无需预估容量 | 流量不可预测或存在突发峰值 |

- **RCU/WCU 换算**：1 RCU = 每秒 1 次强一致性读（或 2 次最终一致性读），读取的 Item ≤ 4 KB；1 WCU = 每秒 1 次写入，写入的 Item ≤ 1 KB

### 读取一致性

| 一致性模型 | 说明 | 消耗 |
|-----------|------|------|
| **最终一致性读（Eventually Consistent）** | 默认模式，可能读到几百毫秒前的旧数据，但延迟最低、吞吐最高 | 消耗 0.5 RCU / 4KB |
| **强一致性读（Strongly Consistent）** | 保证读到最新的已成功写入数据 | 消耗 1 RCU / 4KB |

## 二级索引（考试高频）

| 索引类型 | 说明 | 关键限制 |
|---------|------|---------|
| **本地二级索引（LSI, Local Secondary Index）** | 与表共享**相同分区键**，使用不同的排序键 | 必须在**建表时**创建，之后不可添加；共享表的读写容量 |
| **全局二级索引（GSI, Global Secondary Index）** | 可使用**与表不同的分区键和排序键** | 可随时创建/删除；拥有**独立的读写容量**配置，需单独预置或自动扩展 |

> **考试陷阱**：**LSI 只能在建表时定义，且最多 5 个**；若需求是"表已经在生产环境运行，后续才发现需要按新属性查询"，答案必须是 **GSI**（可随时添加），而不是 LSI。

## DynamoDB Accelerator（DAX）

- 与 DynamoDB API 兼容的**内存缓存层**，将读取延迟从毫秒级降低到**微秒级**
- 专为 DynamoDB 设计，**不能用于缓存其他数据源**（区别于通用的 [[ElastiCache]]）
- 适合读密集、对延迟极度敏感的场景（如实时竞价、游戏排行榜）

---

## DynamoDB Streams

- 捕获表中数据的**变更事件流**（新增、修改、删除），保留 24 小时
- 常与 [[AWS Lambda]] 集成：Lambda 通过事件源映射消费 Stream，实现**变更触发的实时处理**（如审计日志、跨表数据同步、实时通知）
- 是构建事件驱动架构和跨区域/跨服务数据同步的核心机制

---

## 全局表（Global Tables）

- 通过 **Global Tables** 功能，可在**多个 AWS 区域之间自动进行多主（Multi-Master）双向复制**
- 每个区域的表都可读可写，冲突通过"最后写入者获胜（Last Writer Wins）"策略自动解决
- 适用于需要**低延迟全球访问**或**跨区域灾难恢复**的应用

---

## 事务与批量操作

| 特性 | 说明 |
|------|------|
| **事务（Transactions）** | `TransactWriteItems`/`TransactGetItems`，支持跨多个表的 **ACID 事务**，最多涉及 100 个操作 |
| **批量操作** | `BatchGetItem`/`BatchWriteItem`，一次请求处理多个 Item，减少网络往返次数，但**不保证原子性**（区别于事务） |

> **考试陷阱**：题目要求"跨多个 Item 的操作要么全部成功要么全部失败"→ 使用**事务 API**；仅是"批量提升吞吐效率，不要求原子性"→ 使用**批量操作 API**，两者不可混淆。

## 安全性

| 机制 | 说明 |
|------|------|
| **静态加密** | 默认启用，使用 AWS 拥有的密钥或客户管理的 [[KMS]] 密钥 |
| **传输加密** | 所有 API 调用默认通过 HTTPS/TLS |
| **IAM 精细授权（Fine-Grained Access Control）** | 通过 IAM Policy 的 `dynamodb:LeadingKeys` 条件键，限制用户只能访问**分区键与其身份标识匹配**的 Item，实现多租户场景下的行级隔离 |
| **VPC Endpoint（网关终端节点）** | DynamoDB 是少数支持**网关终端节点**的服务之一（与 S3 同类），VPC 内资源可免费、私有地访问 DynamoDB，无需 NAT 网关 |

---

## 备份与恢复

| 功能 | 说明 |
|------|------|
| **按需备份（On-Demand Backup）** | 全量备份，长期保留，不影响表的性能或可用性 |
| **时间点恢复（PITR, Point-in-Time Recovery）** | 启用后可恢复到过去 **35 天内**任意时间点，类似 RDS 的自动备份机制 |

## 数据库服务的宏观定位

- **查询能力对比**：[[RDS]] 擅长复杂的 SQL 查询和跨表关联，而 DynamoDB 针对主键查询进行了优化，能够以一致的性能处理每秒数万次的事务
- **管理开销**：高度自动化的云原生服务，易于实现自动化部署和弹性伸缩，是 [[AWS Lambda]] 等 Serverless 服务的理想搭配——两者共同构成经典的 Serverless 应用架构

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **高并发 Web/移动应用后端** | DynamoDB + [[AWS Lambda]] + [[Amazon API Gateway]] |
| **购物车/会话状态存储** | DynamoDB（按用户 ID 作分区键） |
| **实时排行榜/竞价系统** | DynamoDB + DAX |
| **全球多区域低延迟访问** | DynamoDB Global Tables |
| **变更驱动的事件处理** | DynamoDB Streams + Lambda |
| **多租户 SaaS 应用的行级隔离** | DynamoDB + IAM `LeadingKeys` 条件 |
| **复杂关联查询、强事务需求** | 改用 [[RDS]]/[[Aurora]]，而非 DynamoDB |

## 考试重点总结

### SAA-C02 高频考点

1. **DynamoDB vs RDS**：DynamoDB 主键查询 + 海量并发 + 低延迟；RDS/Aurora 复杂关联查询 + 强 ACID 事务
2. **分区键设计决定性能**：基数低/访问不均会导致热分区和节流，需重新设计分区键而非单纯加容量
3. **LSI vs GSI**：LSI 建表时定义、共享表容量、最多 5 个；GSI 可随时创建、独立容量，是更灵活的默认选择
4. **两种容量模式**：预置模式（RCU/WCU，可配 Auto Scaling）vs 按需模式（自动伸缩，适合不可预测流量）
5. **最终一致性 vs 强一致性**：强一致性读消耗是最终一致性读的 2 倍
6. **DAX 专用于 DynamoDB**：与通用的 ElastiCache 不同，不能缓存其他数据源
7. **DynamoDB Streams + Lambda**：构建事件驱动架构和实时数据处理的标准组合
8. **Global Tables 是多主复制**：跨区域可读可写，冲突用"最后写入者获胜"解决
9. **事务 vs 批量操作**：需要原子性用 Transactions，只求吞吐效率用 Batch 操作
10. **网关终端节点免费私有访问**：DynamoDB 与 S3 同属可用网关终端节点的服务，VPC 内访问无需 NAT
11. **IAM LeadingKeys 实现行级权限**：多租户场景下限制用户只能访问自己的 Item
12. **PITR 恢复窗口 35 天**：与 RDS 自动备份的恢复能力类似

### 场景题解题思路

```
场景分析 → 选择 DynamoDB 配置
├── "海量并发、按主键访问、要求毫秒级延迟" → DynamoDB
├── "需要复杂多表 JOIN 或强 ACID 关联事务" → 改用 RDS/Aurora（而非 DynamoDB）
├── "某些分区键值被频繁访问，出现节流" → 重新设计分区键，提高基数/分散写入
├── "表已上线，后续需要按新属性查询" → 添加 GSI（而非 LSI，LSI 建表后不可添加）
├── "读取延迟要求进一步压缩到微秒级" → DAX
├── "需要根据数据变更实时触发处理逻辑" → DynamoDB Streams + Lambda
├── "需要全球多区域低延迟读写" → Global Tables
├── "需要跨多个 Item 保证原子性" → Transactions API（而非 BatchWriteItem）
├── "VPC 内需要私有、免费访问 DynamoDB" → 网关终端节点
└── "多租户应用需要行级数据隔离" → IAM Policy + dynamodb:LeadingKeys
```

## 最佳实践

1. **精心设计分区键**：优先选择基数高、访问均匀分布的属性，避免热分区
2. **优先使用 GSI 而非 LSI**：除非明确需要与表共享强一致性读，GSI 更灵活、限制更少
3. **流量不可预测时选择按需模式**：避免预置容量估算不准导致节流或浪费
4. **读密集且延迟敏感场景引入 DAX**：不要试图靠提高 RCU 来压低延迟
5. **善用 DynamoDB Streams 构建事件驱动架构**：替代轮询式的变更检测
6. **需要跨 Item 原子性时使用 Transactions**：不要用普通写入 + 应用层补偿逻辑模拟事务
7. **启用 PITR 应对误删除/误写入**：作为按需备份之外的额外保障
8. **VPC 内资源访问 DynamoDB 走网关终端节点**：避免不必要的公网出口流量和 NAT 网关费用
9. **多租户场景使用 IAM LeadingKeys**：在基础设施层面而非仅靠应用逻辑做数据隔离
