# AWS X-Ray - 分布式追踪服务

> **AWS X-Ray** 是**分布式追踪（Distributed Tracing）**服务，跟踪一个用户请求在**跨越多个微服务/组件**的完整调用链路中如何流转，记录每一跳的**耗时和错误**，并自动生成可视化的**服务地图（Service Map）**。它回答的是 [[CloudWatch]] 无法单独回答的问题——**不是"某个服务自身指标如何"，而是"一个请求在经过 A→B→C 多个服务后，究竟卡在了哪一跳"**，是排查微服务架构下端到端性能瓶颈和错误根因的核心工具。
>
> 相关文档：[[CloudWatch]] | [[AWS Lambda]] | [[Amazon API Gateway]] | [[ECS]] | [[Elastic Beanstalk]] | [[IAM]]

## 核心概念

### 核心术语（考试高频）

| 术语 | 说明 |
|------|------|
| **分段（Segment）** | 记录**单个服务/组件**处理该请求所耗费的工作数据（耗时、资源信息、注解/元数据），是追踪数据的基本单位 |
| **子分段（Subsegment）** | 在一个分段**内部**做更细粒度的耗时拆解（如该服务对 [[DynamoDB]] 或外部 HTTP 的一次调用），用于定位"这个服务自己慢在哪一步" |
| **追踪（Trace）** | 一个请求经过**所有**参与组件后产生的**全部分段集合**，拼接起来就是这次请求的完整端到端旅程 |
| **追踪 ID（Trace ID）** | 通过 HTTP 头（`X-Amzn-Trace-Id`）在服务间**跨边界传播**，让不同组件产生的分段能被正确拼接成同一条追踪 |

### 服务地图（Service Map）

- X-Ray 根据收集到的追踪数据**自动生成**可视化的服务拓扑图，用颜色和数字直观标出每个节点的**延迟、错误率、吞吐量**
- **考试要点**：**服务地图是快速定位"整条调用链里到底是哪个环节出了问题"的最直接手段**——题目描述"微服务架构下某个用户请求响应缓慢，但不清楚是哪个下游服务导致的" → 查看 X-Ray **服务地图**，直接可视化定位瓶颈节点，而不是逐个服务分别去看各自的 CloudWatch 指标再手动拼线索。

### 采样（Sampling，考试提示）

- X-Ray **默认不会追踪每一个请求**——按可配置的**采样规则**决定哪些请求被记录（默认规则：每秒的第一个请求 + 之后请求的 5% 会被采样），在**保留代表性数据**和**控制追踪开销/成本**之间取得平衡
- 采样规则**可自定义**，例如对某类关键 API 提高采样率，或对健康检查类请求降低采样率

### 注解 vs 元数据

| 类型 | 说明 |
|------|------|
| **注解（Annotations）** | 附加在分段上的**可索引**键值对，可用于在 X-Ray 控制台**按条件搜索/过滤**追踪（如按客户 ID 查找某用户的所有请求追踪） |
| **元数据（Metadata）** | 附加在分段上的**不可索引**附加信息，用于详细调试，但不能作为搜索条件 |

## 接入方式

| 服务/环境 | 接入方式 |
|----------|---------|
| **[[AWS Lambda]]** | 控制台/配置中**一键开启"主动追踪"（Active Tracing）**，无需部署守护进程；若需要追踪函数内部对下游服务的调用，仍需用 X-Ray SDK 包装相应的 SDK 调用以生成子分段 |
| **[[Amazon API Gateway]]** | 控制台**一键开启 X-Ray 追踪**开关 |
| **EC2 / [[ECS]] / 本地服务器** | 需要运行 **X-Ray 守护进程（Daemon）**——一个本地代理，负责批量收集并转发应用产生的追踪数据到 X-Ray API；应用代码本身还需要集成 **X-Ray SDK** 完成埋点 |
| **[[Elastic Beanstalk]]** | 支持在环境配置中直接开启，无需手动部署守护进程 |

> **考试要点**：**Lambda/API Gateway 只需"开关"级别的配置即可启用，EC2/ECS 等传统计算环境则需要额外部署 X-Ray 守护进程**——题目描述"在 EC2 上启用 X-Ray 追踪，但控制台看不到任何追踪数据" → 排查方向应是**守护进程是否已正确部署运行**，而非怀疑 IAM 权限或代码埋点（IAM 权限不足也会导致类似现象，但守护进程未运行是更常见的疏漏点）。

### 权限要求

- 运行追踪的计算资源（Lambda 执行角色、EC2 实例角色等）需要具备**写入 X-Ray 的 IAM 权限**（如 `AWSXRayDaemonWriteAccess` 托管策略），否则追踪数据无法上报，即使代码和守护进程都已正确配置

## AWS X-Ray vs CloudWatch（考试高频对比）

| 维度 | AWS X-Ray | [[CloudWatch]] |
|------|-----------|-----------------|
| **核心问题** | 一个请求**跨多个组件**的完整调用链路耗时/错误分布在哪 | **单个资源/服务自身**的指标（CPU、错误数、延迟）如何 |
| **数据粒度** | 请求级别的**端到端追踪**，含服务间因果关系 | 资源级别的**聚合指标**，不体现跨服务的调用关系 |
| **典型输出** | 服务地图、单条请求的完整调用时间线 | 时间序列图表、告警 |

> **考试陷阱**：**CloudWatch 能告诉你"服务 B 现在错误率很高"，但不能直接告诉你"是因为服务 A 调用服务 B 时传错了参数"这种跨服务的因果链条**——题目描述"微服务架构下需要定位一个具体用户请求经过哪些服务、每一跳耗时多少、卡在哪个环节" → **AWS X-Ray**；题目描述"需要监控某个 Lambda 函数自身的调用次数、错误率并设置告警" → **[[CloudWatch]]** 已经足够，完整边界见 [[CloudWatch]] 独立笔记。两者通常**组合使用**：CloudWatch 发现"哪个服务有问题"，X-Ray 进一步定位"问题具体发生在调用链的哪一步"。

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **微服务架构下定位用户请求的性能瓶颈** | AWS X-Ray + 服务地图 |
| **需要追踪某个特定客户/请求类型的完整调用链** | 使用注解（Annotations）标记并按条件搜索追踪 |
| **在 Lambda/API Gateway 上快速启用端到端追踪** | 一键开启 Active Tracing / X-Ray 追踪开关 |
| **在 EC2/ECS 上启用追踪但数据未上报** | 检查 X-Ray 守护进程是否运行，以及 IAM 权限是否具备写入 X-Ray 的策略 |
| **控制追踪产生的数据量和成本** | 自定义采样规则，而非追踪每一个请求 |
| **只需要监控单个服务自身的资源指标** | 改用 [[CloudWatch]]（无需引入 X-Ray） |

## 考试重点总结

### SAA-C02 高频考点

1. **X-Ray 是分布式追踪服务，追踪请求跨多个组件的完整调用链**：区别于 CloudWatch 的单资源指标监控
2. **核心术语**：分段（单组件工作数据）、子分段（组件内部细粒度耗时）、追踪（全部分段拼接成的端到端旅程）
3. **追踪 ID 通过 HTTP 头跨服务传播**：让分散在不同组件的分段能拼接成同一条追踪
4. **服务地图自动可视化整条调用链的延迟/错误分布**：快速定位瓶颈节点
5. **默认采样而非追踪每个请求**：默认规则为每秒首个请求 + 5% 额外请求，可自定义
6. **注解可索引用于搜索，元数据不可索引仅用于调试**：两者附加信息的用途不同
7. **Lambda/API Gateway 只需开关级配置，EC2/ECS 需部署 X-Ray 守护进程**：接入复杂度不同
8. **需要具备写入 X-Ray 的 IAM 权限才能上报追踪数据**：权限缺失是常见的"看不到追踪数据"排查方向之一
9. **X-Ray 与 CloudWatch 是互补而非替代关系**：CloudWatch 发现"哪个服务有问题"，X-Ray 定位"问题在调用链的哪一步"
10. **X-Ray 不是审计工具**：它追踪的是应用内部请求的性能数据，而非 CloudTrail 记录的 AWS API 调用行为

### 场景题解题思路

```
场景分析 → 判断 AWS X-Ray 相关配置
├── "微服务架构下定位用户请求卡在哪个下游服务" → AWS X-Ray + 服务地图
├── "需要追踪特定客户/类型请求的完整调用链" → 使用注解标记并搜索
├── "在 Lambda/API Gateway 上快速启用追踪" → 一键开启追踪开关
├── "EC2/ECS 上追踪数据未上报" → 检查守护进程是否运行 + IAM 权限
├── "需要控制追踪产生的数据量/成本" → 自定义采样规则
└── "只需监控单个资源自身指标，不涉及跨服务调用链" → 改用 CloudWatch
```

## 最佳实践

1. **微服务架构默认启用 X-Ray**：越早引入分布式追踪，问题定位成本越低
2. **善用注解标记关键业务维度（客户 ID、订单类型等）**：便于事后按条件精确检索特定请求的追踪
3. **EC2/ECS 环境务必确认守护进程正常运行**：这是最容易被忽略的接入前提
4. **为计算资源分配具备写入 X-Ray 权限的 IAM 角色**：避免埋点和守护进程都正确却因权限问题导致数据丢失
5. **合理调整采样规则**：关键路径适当提高采样率，健康检查等噪音请求适当降低，平衡可观测性和成本
6. **将 X-Ray 与 CloudWatch 组合使用构建完整可观测性**：CloudWatch 做告警和资源级监控，X-Ray 做跨服务的根因定位
7. **不要试图用 X-Ray 替代 CloudTrail 的审计职责**：X-Ray 关注应用性能追踪，AWS API 调用审计仍应依赖 CloudTrail
