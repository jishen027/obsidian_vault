# Amazon Macie - 敏感数据发现与保护

> **Amazon Macie** 是全托管的**数据安全服务**，使用**机器学习和模式匹配**自动扫描 [[S3]] 中的对象，发现**个人身份信息（PII）、凭证密钥、财务数据**等敏感内容，并持续评估存储桶的**安全态势**（公开访问、未加密、跨账户共享等），帮助团队回答"我的敏感数据存放在哪里、暴露风险有多大"这个人工审查几乎无法规模化覆盖的问题。
>
> 相关文档：[[S3]] | [[S3 Security]] | [[KMS]] | [[Amazon GuardDuty]] | [[Amazon Inspector]] | [[AWS Organizations]] | [[IAM]]

## 核心概念

### 为什么需要 Macie

- **人工分类的局限**：企业级 S3 环境常有成千上万个 Bucket、海量对象，逐一人工审查内容是否包含 PII 或密钥几乎不可行，也无法应对数据持续新增的动态场景
- **Macie 的核心价值**：结合**机器学习模型**（识别非结构化文本中的上下文相关敏感信息）和**托管数据标识符（Managed Data Identifiers）**（基于模式匹配识别信用卡号、SSN、API 密钥等结构化格式），自动**采样分析** S3 对象内容，无需人工编写复杂的正则规则库

### Macie 在安全监控体系中的定位（考试高频）

| 服务 | 核心问题 | 关注对象 | 典型场景 |
|------|---------|---------|---------|
| **Amazon Macie** | 我的**数据内容**有多敏感、暴露风险多大？ | S3 对象内容（PII、密钥等）+ 存储桶安全配置 | 发现存放身份证号/信用卡信息的 Bucket、误配置为公开的敏感数据桶 |
| **[[Amazon GuardDuty]]** | 是否**正在发生**攻击/异常行为？ | 跨数据源关联的威胁信号 | 凭证被盗、异常 API 调用、恶意软件通信 |
| **[[Amazon Inspector]]** | 资源存在哪些**已知软件漏洞**？ | 软件 CVE、代码缺陷 | 未打补丁的软件包、代码中的安全缺陷 |

> **考试陷阱**：**Macie 关心的是"数据本身是什么"，GuardDuty 关心"是否有人在做坏事"，Inspector 关心"软件是否有已知弱点"——三者是同一安全监控家族中互不替代的三个维度**。题目描述"需要发现 S3 中存储了哪些包含身份证号/信用卡号的对象" → **Macie**；描述"需要发现某个 S3 Bucket 是否被意外配置为公开访问" → Macie（数据安全态势评估）或 [[S3 Security]] 笔记中的 IAM Access Analyzer for S3（均可发现，但 Macie 会结合"是否含敏感数据"进一步评估风险优先级）；描述"需要检测账户是否正在被攻击" → [[Amazon GuardDuty]]。

## 核心能力

### 敏感数据发现（Sensitive Data Discovery）

| 组件 | 说明 |
|------|------|
| **托管数据标识符（Managed Data Identifiers）** | AWS 预置并持续更新的检测模式，覆盖信用卡号、SSN、护照号、AWS/云厂商密钥（如 Stripe API Key、Google Cloud API Key）等结构化敏感数据类型，开箱即用 |
| **自定义数据标识符（Custom Data Identifiers）** | 基于正则表达式定义组织专有的敏感数据格式（如内部员工编号、专有合同编号），补充托管标识符未覆盖的场景 |
| **允许列表（Allow Lists）** | 排除已知的误报模式（如测试数据中的示例信用卡号），减少不必要的告警 |

### 自动化敏感数据发现（Automated Sensitive Data Discovery）

- 启用后 Macie **自动、持续**对组织内所有 S3 Bucket 进行**低成本采样扫描**，无需手动创建和调度扫描任务（Classification Job）
- 生成**数据地图（Data Map）**：可视化展示敏感数据在各账户、各 Bucket 中的分布情况
- 为每个 Bucket 计算**敏感度评分（Sensitivity Score）**，直观反映该 Bucket 存放敏感数据的风险等级，用于优先排查

> **考试要点**：**自动化发现（持续、抽样、低成本）与手动创建的分类任务（Classification Job，可对指定 Bucket 做全量或定向深度扫描）是两种互补模式**——题目描述"希望持续、自动地掌握组织内敏感数据分布，无需每次手动配置扫描范围" → 自动化敏感数据发现；描述"需要对某个特定 Bucket 做一次性全量精确扫描" → 手动创建 Classification Job。

### 数据安全态势评估

- Macie 持续评估 S3 Bucket 的**安全配置**，自动生成 Finding 提示：
  - Bucket **未加密**或加密配置薄弱
  - Bucket 被配置为**公开可访问**
  - Bucket 被**共享给组织外部账户**
  - Bucket **禁用了版本控制**等影响数据保护能力的配置
- 这类 Finding **不依赖内容扫描**，即使 Bucket 中暂无敏感数据也会评估，是持续的配置合规检查

---

## Finding 与严重程度

- 每次发现敏感数据或安全配置问题会生成一个 **Finding**，包含受影响的 Bucket/对象、敏感数据类型、数量、严重程度评级
- 支持**安全审查（Secure Review）**：直接在 Macie 控制台安全地查看 Finding 所指向对象中的具体敏感内容样本，无需额外下载对象或授予审查人员完整的 S3 读取权限
- 支持**抑制规则（Suppression Rules）**：对已确认可接受的场景（如合规保留的历史数据）自动归档 Finding，减少噪音

---

## 多账户管理

- 支持指定**委派管理员账户**，结合 [[AWS Organizations]] 实现组织级的集中数据安全管理——委派管理员可查看组织内所有成员账户的数据地图和 Finding，这一治理模式与 [[Amazon GuardDuty]]、[[Amazon Inspector]] 的委派管理员机制一致
- 可跨成员账户统一启用自动化敏感数据发现，避免因个别账户遗漏配置产生盲区

---

## 集成与响应

| 集成方式 | 说明 |
|---------|------|
| **[[Amazon EventBridge]]** | Finding 可作为事件源触发自动化响应（如自动隔离含敏感数据且被公开的 Bucket、通知数据治理团队） |
| **AWS Security Hub** | Finding 可汇总到 Security Hub，与 [[Amazon GuardDuty]]、[[Amazon Inspector]] 等其他安全服务的发现统一呈现在中心化的安全态势看板 |
| **[[KMS]]** | Macie 使用 [[KMS]] 加密其自身生成的敏感数据发现结果和元数据 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **需要发现 S3 中存储了哪些 PII/信用卡号/密钥等敏感数据** | Macie 敏感数据发现（托管数据标识符） |
| **组织有专有格式的敏感数据类型（内部编号等）** | Custom Data Identifiers |
| **希望持续、自动掌握敏感数据在组织内的分布** | 自动化敏感数据发现 + 数据地图 |
| **需要对特定 Bucket 做一次性全量精确扫描** | 手动创建 Classification Job |
| **需要发现意外公开或未加密的存储桶** | Macie 数据安全态势评估 |
| **需要安全查看 Finding 涉及的具体敏感内容，且不额外授予完整读取权限** | Secure Review 功能 |
| **组织级集中管理多账户的数据安全** | 委派管理员 + AWS Organizations |
| **发现敏感数据暴露后自动触发响应** | Macie + EventBridge + Lambda |
| **需要判断软件是否存在已知漏洞，而非数据内容风险** | 改用 [[Amazon Inspector]]（而非 Macie） |
| **需要检测是否正在遭受攻击，而非评估数据敏感度** | 改用 [[Amazon GuardDuty]]（而非 Macie） |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：全托管数据安全服务，用机器学习和模式匹配自动发现 S3 中的敏感数据（PII、密钥等）
2. **判断依据**：关注"数据内容有多敏感"选 Macie；关注"是否正在被攻击"选 [[Amazon GuardDuty]]；关注"软件是否有已知漏洞"选 [[Amazon Inspector]]
3. **托管数据标识符 vs 自定义数据标识符**：前者开箱即用覆盖常见格式，后者用正则表达式定义组织专有敏感数据类型
4. **自动化敏感数据发现 vs 手动 Classification Job**：前者持续低成本采样、无需手动配置，后者可对指定 Bucket 做一次性全量深度扫描
5. **数据地图与敏感度评分**：可视化敏感数据分布，量化风险优先级，辅助资源投入排序
6. **数据安全态势评估独立于内容扫描**：检测未加密、公开访问、跨账户共享等配置风险，即使暂无敏感数据也会评估
7. **Secure Review 支持安全查看敏感内容样本**：无需额外下载对象或授予完整读取权限
8. **委派管理员支持组织级集中管理**：与 GuardDuty、Inspector 的治理模式一致
9. **响应依赖 EventBridge 集成**：Finding 触发自动化响应（如隔离桶、通知团队）的标准模式
10. **Macie + GuardDuty + Inspector 三者互补构成安全监控矩阵**：数据敏感度、实时威胁检测、软件漏洞评估，缺一不可覆盖完整的云安全画面

### 场景题解题思路

```
场景分析 → 判断使用 Macie 的哪个能力
├── "需要发现 S3 中存储了哪些包含 PII/信用卡号/密钥的对象" → Macie 敏感数据发现
├── "组织有专有格式的敏感数据类型需要识别" → Custom Data Identifiers
├── "希望持续自动掌握敏感数据分布，无需手动配置" → 自动化敏感数据发现 + 数据地图
├── "需要对特定 Bucket 做一次性全量精确扫描" → 手动创建 Classification Job
├── "需要发现意外配置为公开/未加密的存储桶" → Macie 数据安全态势评估
├── "需要安全查看告警涉及的具体敏感内容" → Secure Review
├── "组织级集中管理多账户数据安全" → 委派管理员 + Organizations
├── "发现敏感数据暴露后需要自动触发响应" → Macie + EventBridge + Lambda
├── "需要判断软件是否存在已知漏洞" → 改用 Amazon Inspector
└── "需要检测是否正在遭受攻击" → 改用 Amazon GuardDuty
```

## 最佳实践

1. **优先启用自动化敏感数据发现覆盖全组织**：以低成本持续掌握敏感数据分布，而非依赖零散的手动扫描任务
2. **结合数据地图和敏感度评分排定治理优先级**：优先处理高敏感度且配置存在风险的 Bucket
3. **补充自定义数据标识符覆盖组织专有敏感格式**：托管标识符无法覆盖所有行业/企业特定的数据类型
4. **对存放敏感数据的 Bucket 额外叠加 [[S3 Security]] 中的强制加密和 Block Public Access**：Macie 负责发现风险，实际防护仍需配置到位
5. **善用 Secure Review 而非直接下载对象排查告警**：减少不必要的敏感数据二次暴露和权限授予
6. **组织级环境使用委派管理员统一管理**：确保新账户不会因遗漏配置产生数据安全盲区
7. **结合 EventBridge 构建自动化响应管道**：对"公开访问 + 含敏感数据"这类高风险 Finding 实现自动隔离
8. **Macie 与 [[Amazon GuardDuty]]、[[Amazon Inspector]] 组合部署**：三者分别覆盖数据敏感度、威胁检测、漏洞评估，共同构成完整的安全监控体系
