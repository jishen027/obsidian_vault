# AWS IAM - 身份与访问管理

> **AWS Identity and Access Management (IAM)** 是 AWS 账户内身份与访问控制的核心服务，管理"谁（身份）能对哪些资源执行哪些操作"，是几乎所有 AWS 服务权限模型的基础。IAM 本身是**全局性**服务，不局限于特定区域。
>
> 相关文档：[[Cognito]] | [[AWS Directory Service]] | [[AWS Organizations]] | [[KMS]] | [[CloudTrail]] | [[AWS Config]] | [[S3 Security]] | [[VPC]]

---

## 核心身份（Identities）

| 身份类型 | 说明 |
|---------|------|
| **Root 用户** | 账户创建时默认产生，拥有**最高权限**，无法被任何策略限制。最佳实践：启用 **MFA**、删除所有**访问密钥（Access Keys）**、仅在必要操作（如修改账单方案、关闭账户）时使用 |
| **IAM 用户（Users）** | 持久身份，可分配**控制台密码**或**程序化访问密钥（Access Key）**，遵循"最小特权原则"按需授权 |
| **IAM 组（Groups）** | 用户的集合，用于简化权限分配；**组不是"可信实体（Principal）"，不能被直接假设（Assume）**，仅是批量挂载策略的容器 |
| **IAM 角色（Roles）** | **临时身份**，不具备长期凭证，通过 **AWS STS** 获取包含 `Access Key ID`、`Secret Access Key`、`Session Token` 的临时令牌 |

> **考试要点**：**角色（Role）是 AWS 服务间授权和跨账户访问的标准方式**——EC2 实例、Lambda 函数等 AWS 资源应通过附加 IAM 角色获取权限，而非在代码中硬编码长期访问密钥；这是"如何让 EC2 安全访问 S3"这类场景题的标准答案。

## 策略（Policies）与授权

### 策略基础

- IAM 策略使用 **JSON** 格式编写，定义 `Effect`（Allow/Deny）、`Action`（操作）、`Resource`（资源）、可选的 `Condition`（条件）
- **策略是全局性的**：一个 IAM 用户/角色的权限不因所在区域而改变（区别于某些资源本身是区域级的）

### 策略类型（考试高频）

| 分类维度 | 类型 | 说明 |
|---------|------|------|
| **附加对象** | **身份策略（Identity-Based）** | 附加到用户/组/角色，定义"这个身份能做什么" |
| **附加对象** | **资源策略（Resource-Based）** | 附加到资源本身（如 S3 Bucket Policy），定义"谁能访问这个资源"，是**唯一能直接指定跨账户主体**的策略类型 |
| **管理方式** | **AWS 托管策略（AWS Managed）** | AWS 预定义并维护，覆盖常见场景，随 AWS 更新自动演进 |
| **管理方式** | **客户托管策略（Customer Managed）** | 用户自行创建和维护，可被多个身份复用，独立于身份存在 |
| **管理方式** | **内联策略（Inline）** | 直接嵌入单个身份内部，与该身份**生命周期绑定**（身份删除策略随之删除），不可被其他身份复用 |

### 策略评估逻辑（考试陷阱高发区）

1. 默认**隐式拒绝（Implicit Deny）**——没有任何策略明确允许的操作，默认不允许
2. 若任意适用策略中存在**显式拒绝（Explicit Deny）**，无论其他策略是否允许，**最终结果都是拒绝**——显式拒绝优先级始终最高
3. 若无显式拒绝，且存在**显式允许（Explicit Allow）**，则允许

> **考试陷阱**：**跨账户访问场景需要"双向都允许"**——账户 A 的用户要访问账户 B 的 S3 Bucket，既需要账户 A 一侧的身份策略允许该操作，**也**需要账户 B 一侧的 Bucket Policy（资源策略）允许账户 A 的主体访问，缺一不可；题目描述"IAM 策略已授权但跨账户访问依然失败"，通常是资源策略一侧未授权。

### 权限边界（Permission Boundaries）vs 服务控制策略（SCP）

| 机制 | 作用范围 | 说明 |
|------|---------|------|
| **权限边界（Permission Boundary）** | 单个 IAM 用户/角色 | 设置该身份权限的"天花板"，即使附加了 `AdministratorAccess`，实际有效权限也不能超出边界定义的范围 |
| **[[AWS Organizations]] 服务控制策略（SCP）** | 整个组织/OU/账户 | 组织级的权限天花板，作用范围更广，影响该账户下的所有身份（管理账户除外） |

> **考试要点**：**两者都是"限制而非授予"权限的机制，且可以同时生效**——最终有效权限 = 身份策略 ∩ 权限边界 ∩（若适用）SCP；题目强调"限制单个用户/角色能做什么，即使被误授予管理员权限也不能超限"用 Permission Boundary；强调"限制整个账户/组织范围内所有身份的权限上限"用 SCP。

### 策略变量与条件键

- **策略变量（Policy Variables）**：在策略中引用运行时值（如 `${aws:username}`），实现"用户只能访问以自己用户名命名的 S3 前缀"这类动态、可复用的策略模板，无需为每个用户单独写策略
- **条件键（Condition Keys）**：基于请求上下文（来源 IP、MFA 是否验证、请求时间等）进一步收窄策略生效范围，如"仅当启用 MFA 时才允许删除操作"

## AWS STS 与角色扮演（AssumeRole）

- **AWS STS（Security Token Service）**是 IAM 权限分配的技术支撑，专门负责发放有时效性的**临时凭证**（默认几小时后过期，比长期访问密钥更安全）
- **信任策略（Trust Policy）vs 权限策略（Permission Policy）**：角色包含两部分——信任策略定义"**谁**可以扮演（Assume）这个角色"，权限策略定义"扮演后**能做什么**"，两者职责分离
- **跨账户访问的标准模式**：账户 B 创建一个角色，信任策略中信任账户 A 的主体；账户 A 的用户通过 `sts:AssumeRole` 获取临时凭证后即可在账户 B 内以该角色的权限操作，无需在账户 B 创建长期用户

## 身份联邦（Federation）

### SAML 2.0（企业级 SSO）

- **SAML 2.0** 是企业级单点登录（SSO）的行业标准协议
- **工作流**：本地系统（如企业 Active Directory）验证用户 → 发送 **SAML 断言**给 AWS → **STS** 发放临时令牌 → 用户登录 AWS 控制台，全程无需在 AWS 中创建独立的 IAM 用户

### AWS IAM Identity Center（现代化 SSO 方案）

- 原名 **AWS SSO**，是 AWS 官方推荐的**多账户、多应用统一身份管理**方案，构建在 [[AWS Organizations]] 之上
- 支持连接企业已有的身份源（Active Directory、Okta 等第三方 IdP）或使用内置身份存储，用户登录一次即可访问被授权的所有成员账户和应用，无需为每个账户单独管理联邦配置
- 相比手动搭建 SAML 联邦，Identity Center 提供**集中化的权限集（Permission Set）管理**，简化多账户环境下的用户访问治理

### 辅助身份工具（考试要点）

| 工具 | 定位 |
|------|------|
| **IAM** | 面向 **AWS 账户内部**的身份（管理员、运维人员、AWS 资源本身） |
| **[[Cognito]]** | 面向**外部 App 注册用户**（移动端/Web 应用的终端消费者），详见 [[Cognito]] 独立笔记 |
| **[[AWS Directory Service]]（Managed Microsoft AD）** | 将**本地 AD 域**扩展到云端 VPC，供依赖传统 Windows AD 的应用直接使用 |
| **IAM Identity Center** | 面向**企业内部员工**跨多账户/多应用的统一 SSO 访问 |

## 安全强化机制

### 多因素认证（MFA）

| 类型 | 说明 |
|------|------|
| **虚拟 MFA** | 手机 App 生成的一次性验证码（如 Google Authenticator） |
| **硬件 MFA** | 物理令牌设备 |
| **U2F/FIDO 安全密钥** | USB 硬件密钥，防钓鱼能力更强 |

### IAM Access Analyzer

- 持续分析资源策略，识别**意外授予外部账户/公网访问权限**的资源（如公开的 S3 Bucket、可被外部 Assume 的角色），是主动发现权限配置错误的工具
- 也可用于在编写策略前**生成基于访问活动的最小权限策略建议**

### 凭证报告与访问顾问

| 工具 | 说明 |
|------|------|
| **凭证报告（Credential Report）** | 账户级别的 CSV 报告，列出所有 IAM 用户及其密码/密钥的状态和最后使用时间，用于审计长期未轮换或未使用的凭证 |
| **访问顾问（Access Advisor）** | 显示某个身份**实际使用过**哪些服务权限，帮助识别并收紧"授予了但从未用到"的多余权限 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **EC2/Lambda 等 AWS 资源需要访问其他 AWS 服务** | 附加 IAM 角色，而非硬编码长期访问密钥 |
| **跨账户访问另一账户的资源** | 目标账户创建角色 + 信任策略信任源账户，源账户 AssumeRole 获取临时凭证 |
| **企业员工需要用现有 AD 账号登录 AWS 控制台** | SAML 2.0 联邦 或 IAM Identity Center 连接企业 IdP |
| **多账户环境需要统一管理员工的访问权限** | IAM Identity Center 集中管理权限集 |
| **限制某个高权限角色的实际可用权限上限** | Permission Boundary |
| **限制整个组织/账户范围内所有身份的权限上限** | [[AWS Organizations]] SCP |
| **需要发现被意外授予外部访问权限的资源** | IAM Access Analyzer |
| **需要审计哪些用户长期未轮换密钥/未登录** | 凭证报告（Credential Report） |
| **移动/Web 应用的终端用户注册登录** | 改用 [[Cognito]]，而非在 IAM 中创建用户 |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：全局性的账户内身份与访问管理服务，是几乎所有 AWS 权限模型的基础
2. **角色是 AWS 服务间授权的标准方式**：EC2/Lambda 等应通过角色获取权限，而非硬编码密钥
3. **组不是可信实体**：不能被 Assume，仅用于批量管理用户权限
4. **策略评估：显式拒绝 > 显式允许 > 隐式拒绝**：任意一处显式拒绝即最终拒绝
5. **跨账户访问需要双向授权**：身份策略（源账户）+ 资源策略（目标账户）都必须允许
6. **信任策略 vs 权限策略**：前者定义谁能扮演角色，后者定义扮演后能做什么
7. **Permission Boundary vs SCP**：前者限制单个身份，后者限制整个组织/账户，两者都是"限制"而非"授予"机制，可叠加生效
8. **身份策略 vs 资源策略**：只有资源策略能直接指定跨账户主体
9. **托管策略 vs 内联策略**：内联策略与身份生命周期绑定、不可复用，托管策略可独立管理和复用
10. **IAM Identity Center 是现代化多账户 SSO 方案**：构建在 Organizations 之上，优于手动逐账户配置 SAML 联邦

### 场景题解题思路

```
场景分析 → 判断使用 IAM 的哪个机制
├── "AWS 资源需要访问其他 AWS 服务" → IAM 角色（而非硬编码密钥）
├── "需要跨账户访问另一账户的资源" → 目标账户角色 + 信任策略 + AssumeRole
├── "IAM 策略已授权但跨账户访问依然失败" → 检查目标账户的资源策略是否也已授权
├── "策略中出现允许和拒绝冲突" → 显式拒绝始终优先
├── "需要限制单个角色的权限上限，即使被误授予管理员权限" → Permission Boundary
├── "需要限制整个组织/账户的权限上限" → AWS Organizations SCP
├── "企业员工需要用现有 AD 账号登录多个 AWS 账户" → SAML 联邦 / IAM Identity Center
├── "需要发现被意外授予外部访问权限的资源" → IAM Access Analyzer
├── "需要审计长期未使用/未轮换的凭证" → 凭证报告
└── "面向外部 App 终端用户的注册登录" → 改用 Cognito（而非 IAM 用户）
```

## 最佳实践

1. **Root 用户仅用于必要操作**：启用 MFA、删除访问密钥，日常管理使用 IAM 用户/角色
2. **优先使用角色而非长期密钥**：AWS 资源间授权、跨账户访问均应通过角色获取临时凭证
3. **遵循最小特权原则**：从最小权限开始，结合 Access Advisor 识别并收紧未使用的多余权限
4. **善用策略变量减少重复策略**：如按用户名动态限定 S3 前缀访问范围，避免为每个用户单独写策略
5. **高权限角色叠加 Permission Boundary**：防止误操作或提权导致权限超出预期范围
6. **多账户环境优先使用 IAM Identity Center**：而非在每个账户手动配置独立的联邦或 IAM 用户
7. **定期审查凭证报告和 Access Analyzer 发现项**：主动发现未轮换的密钥和意外的外部访问授权
8. **敏感操作启用 MFA 条件键**：结合 Condition 要求关键操作必须在 MFA 验证后才能执行
9. **内联策略仅用于与特定身份强绑定的场景**：其余情况优先使用可复用的托管策略，便于统一维护
