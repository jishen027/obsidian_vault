# Amazon Cognito - 应用身份管理

> **Amazon Cognito** 是 AWS 安全与身份体系中专门为**移动和 Web 应用程序**设计的身份管理服务，通过用户池和身份池分别解决终端用户的**身份验证（Authentication）**和**授权（Authorization）**问题，让应用无需自建用户系统。
>
> 相关文档：[[IAM]] | [[AWS Directory Service]] | [[Amazon API Gateway]] | [[S3]] | [[DynamoDB]] | [[VPC]]

---

## 核心概念

### Cognito 定位（考试要点）

| 服务 | 面向对象 | 核心职责 | 典型场景 |
|------|---------|---------|---------|
| **Cognito** | 应用的**外部终端用户**（App 注册用户、社交登录用户） | 身份验证 + 临时 AWS 凭证授权 | 移动/Web 应用的用户登录与资源访问 |
| [[IAM]] | AWS 账户内的**员工/服务/资源** | 管控对 AWS 控制台和 API 的访问权限 | 运维人员、应用服务器、CI/CD 流水线 |
| [[AWS Directory Service]] | **企业内部**员工目录 | 将本地 AD 域扩展到云端 VPC | 企业内部系统的目录集成 |

> **考试陷阱**：Cognito 与 IAM 面向的用户群体完全不同——**Cognito 管理应用的最终用户（成千上万的外部消费者）**，**IAM 管理 AWS 账户内部的身份（员工、角色、服务）**；题目描述"移动 App 的注册用户登录"应选 Cognito，而非直接为每个用户创建 IAM User（IAM User 数量有限且不适合面向海量消费者）。

### 两大核心组件

Cognito 通过两个相对独立又可协同工作的组件，分别解决**身份验证**和**授权**：

| 组件 | 职责 | 说明 |
|------|------|------|
| **用户池（User Pools）** | **身份验证（Authentication）** | 一个可扩展的用户目录，管理用户注册、登录、密码找回、多因素认证（MFA），验证成功后签发 JWT 令牌 |
| **身份池（Identity Pools）** | **授权（Authorization）** | 将已验证（或未验证的访客）身份**映射到 IAM 角色**，为用户签发**临时 AWS 凭证**，使其能够直接访问 [[S3]]、[[DynamoDB]] 等 AWS 资源 |

> **考试陷阱**：**用户池验证"你是谁"，身份池决定"你能访问什么 AWS 资源"**——两者经常配合使用（用户先在用户池登录，再用登录令牌换取身份池签发的临时凭证），但也可以**单独使用**：只需要用户名密码登录、不直接访问 AWS 资源时只用用户池；只需要给匿名访客签发临时凭证访问 S3 时可以单独使用身份池（无需用户池）。

## 用户池（User Pools）详解

| 功能 | 说明 |
|------|------|
| **用户注册/登录** | 内置托管 UI，支持用户名/邮箱/手机号 + 密码登录 |
| **多因素认证（MFA）** | 支持 SMS 或 TOTP（如 Google Authenticator）二次验证 |
| **社交/企业身份联合登录** | 支持通过 Google、Facebook、Amazon、Apple 或企业 **SAML 2.0 / OIDC** 身份提供商登录 |
| **JWT 令牌** | 登录成功后签发 **ID Token（身份信息）**、**Access Token（授权访问用户池资源）**、**Refresh Token（刷新令牌）** |
| **Lambda 触发器** | 可在注册前/后、登录前/后等生命周期节点触发 [[AWS Lambda]] 函数，实现自定义验证逻辑 |

### 与 API Gateway 集成

- [[Amazon API Gateway]] 可直接使用**用户池授权方（Cognito Authorizer）**验证请求携带的 JWT 令牌，无需编写自定义 Lambda 授权逻辑
- 验证通过后，API Gateway 会将令牌中的用户声明（Claims）传递给后端，供业务逻辑做进一步的细粒度判断

## 身份池（Identity Pools）详解

- 核心功能：为用户（无论是否登录）签发**临时的、权限受限的 AWS 凭证**（通过 [[IAM]] 的 STS `AssumeRoleWithWebIdentity`/`AssumeRoleWithCognitoIdentity`）
- 支持**已验证身份（Authenticated）**和**未验证身份（Unauthenticated，即访客）**两种角色，分别关联不同的 IAM 角色，实现差异化权限
- **身份提供商来源可以是**：Cognito 用户池、第三方社交登录（Google/Facebook 等）、企业 SAML/OIDC 提供商，或完全匿名的访客身份

### 精细化权限控制

- 通过将身份池与特定 IAM 角色关联，并在角色的信任策略/权限策略中使用**策略变量**（如 `${cognito-identity.amazonaws.com:sub}`），可以实现"**每个用户只能访问自己的数据**"这类行级/前缀级权限隔离
- 典型应用：限制用户只能读写 S3 中以自己身份 ID 为前缀的对象路径（如 `bucket/${user-id}/*`），或只能访问 DynamoDB 中分区键等于自己身份 ID 的 Item（类似 [[DynamoDB]] 中 `dynamodb:LeadingKeys` 的思路）

## 在安全和身份体系中的宏观定位

- **身份联邦（Identity Federation）**：Cognito 是实现身份联邦的关键工具，允许外部用户（如 Google、Facebook 账号持有者）**无需创建 IAM 用户**即可访问 AWS 资源，避免为海量消费者用户逐一创建 IAM User
- **最小权限原则**：通过身份池将不同用户群体（已验证/未验证）关联到范围受限的特定 IAM 角色，精确控制移动端/Web 端用户的数据访问权限
- **目录集成**：隶属于 AWS 身份服务家族，可与其他身份提供商（企业 AD、社交平台）协同工作，简化跨平台的身份管理逻辑

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **移动/Web App 用户注册登录** | Cognito 用户池（含 MFA） |
| **App 用户直接上传文件到私有 S3 Bucket** | 用户池验证身份 + 身份池签发临时凭证，按用户 ID 前缀限制 S3 访问 |
| **通过 API Gateway 保护后端 API** | API Gateway + Cognito 用户池授权方（JWT 验证） |
| **社交账号一键登录** | 用户池 + Google/Facebook/Apple 联合登录 |
| **允许匿名访客临时访问部分资源** | 身份池的未验证身份角色 |
| **企业员工访问 AWS 控制台/API** | 改用 [[IAM]]（Cognito 面向的是应用终端用户，而非企业内部员工） |

## 考试重点总结

### SAA-C02 高频考点

1. **Cognito 面向应用终端用户，IAM 面向 AWS 账户内部身份**：两者服务对象不同，不能混淆
2. **用户池管身份验证，身份池管授权（临时 AWS 凭证）**：功能互补，可单独使用也可组合使用
3. **身份池签发临时凭证的机制**：通过 STS AssumeRole 系列 API，映射到具体的 IAM 角色
4. **已验证 vs 未验证身份**：分别对应登录用户和匿名访客，可关联不同权限的 IAM 角色
5. **与 API Gateway 原生集成**：Cognito Authorizer 直接验证 JWT，无需自定义 Lambda 授权逻辑
6. **支持社交/企业身份联合登录**：Google/Facebook/Apple 或 SAML/OIDC 企业身份提供商
7. **策略变量实现行级权限隔离**：`${cognito-identity.amazonaws.com:sub}` 让每个用户只能访问自己的数据
8. **避免为海量消费者创建 IAM User**：这是 Cognito 存在的核心原因之一，IAM User 不适合面向大规模外部用户
9. **Lambda 触发器实现自定义逻辑**：注册前/后等生命周期节点可插入自定义验证或处理
10. **MFA 原生支持**：无需额外服务即可为用户池启用多因素认证

### 场景题解题思路

```
场景分析 → 选择 Cognito 组件
├── "移动/Web App 需要用户注册登录" → Cognito 用户池
├── "登录用户需要直接访问 S3/DynamoDB 等 AWS 资源" → 用户池 + 身份池组合
├── "只需要给匿名访客签发临时凭证访问部分资源" → 身份池（未验证身份角色）
├── "希望用户只能访问自己名下的数据" → 身份池 + IAM 角色策略变量
├── "API Gateway 需要验证用户身份，不想自己写验证逻辑" → Cognito Authorizer（JWT）
├── "希望支持 Google/Facebook 一键登录" → 用户池 + 社交身份联合登录
├── "企业员工需要访问 AWS 控制台/API" → 改用 IAM（而非 Cognito）
└── "注册流程需要自定义校验逻辑（如黑名单邮箱拦截）" → 用户池 Lambda 触发器
```

## 最佳实践

1. **区分好 Cognito 与 IAM 的适用边界**：外部消费者用 Cognito，AWS 账户内部身份用 IAM
2. **登录 + 访问 AWS 资源的场景组合使用用户池和身份池**：不要试图只用一个组件解决全部需求
3. **启用 MFA 提升账户安全性**：尤其是涉及敏感数据访问的应用
4. **善用策略变量做行级隔离**：避免所有用户共享同一宽泛 IAM 角色导致越权访问
5. **优先使用 Cognito Authorizer 集成 API Gateway**：减少自定义 Lambda 授权器的开发和维护成本
6. **未验证身份角色权限要最小化**：匿名访客角色应仅授予真正需要公开的最小权限
7. **社交登录场景验证第三方身份提供商配置**：确保回调 URL、密钥等配置正确，避免登录失败
