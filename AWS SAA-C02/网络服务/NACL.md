# NACL - Network Access Control List

> **网络 ACL (Network Access Control List, NACL)** 是 VPC 中的一个可选安全层，充当控制**子网**进出流量的虚拟防火墙。与 [[Security Group]] 不同，NACL 工作在子网级别，且是**无状态**的。
>
> 相关文档：[[Security Group]] | [[虚拟私有云 - VPC]] | [[子网和路由表 - Subnet & Route table]] | [[Network Interface]]

---

## 核心概念

### 作用范围

- NACL 直接关联在**子网 (Subnet)** 上，而非实例网卡（这一点与 [[Security Group]] 相反）
- 进入该子网的**所有流量**都必须先通过 NACL 的过滤，才能到达子网内的实例
- **一个子网只能关联一个 NACL**，但**一个 NACL 可以同时关联多个子网**

### 默认 NACL vs 自定义 NACL（考试重点）

| 类型 | 入站默认规则 | 出站默认规则 | 说明 |
|------|------------|------------|------|
| **默认 NACL** | 允许所有 | 允许所有 | VPC 创建时自动生成，行为类似"无防火墙" |
| **自定义 NACL** | 拒绝所有 | 拒绝所有 | 新建 NACL 默认拒绝一切，需手动添加允许规则 |

---

## 核心特性：无状态 (Stateless)

这是 NACL 最重要的技术特征。**"无状态"**意味着它不会记忆连接状态。

- 如果通过入站规则允许了某个请求，**必须手动**在出站规则中也允许对应的响应流量（反之亦然）
- 由于这种特性，配置 NACL 时通常需要开放**临时端口 (Ephemeral Ports)** 以允许返回流量放行

### 常见临时端口范围

| 客户端类型 | 临时端口范围 |
|-----------|------------|
| Linux (较新内核) | 32768 - 60999 |
| Windows | 49152 - 65535 |
| Elastic Load Balancer | 1024 - 65535 |

> **考试陷阱**：如果只放行了入站的 80/443 端口，却忘记在出站规则中放行对应的临时端口，客户端将**无法收到响应**，看起来像是"请求超时"，本质原因是无状态特性导致响应流量被拒绝。

---

## 规则逻辑

### 编号排序

- NACL 规则按**编号从小到大**顺序执行
- 一旦流量匹配到某条规则，就会立即执行该规则的动作（允许或拒绝），**不再评估后续规则**
- 建议编号间隔（如 100、200、300）以便未来插入新规则

### 支持"拒绝"规则

- 与 [[Security Group]] 只能设置"允许"规则不同，NACL 显式支持**"拒绝 (Deny)"**规则
- 这使它非常适合**封禁特定的恶意 IP 地址段**（黑名单场景）

### 默认结尾规则

- 每个 NACL 末尾都有一条带星号 (`*`) 的默认规则，用于**拒绝所有**不匹配前面任何规则的流量
- 该规则**不可编辑或删除**，是所有 NACL 规则求值链的兜底

## NACL vs Security Group（考试高频考点）

| 特性 | [[Security Group]] | NACL |
|------|--------------------|------|
| **作用范围** | 实例/网卡（[[Network Interface#ENI]]）级别 | 子网（Subnet）级别 |
| **状态属性** | 有状态（Stateful） | 无状态（Stateless） |
| **规则类型** | 仅支持"允许"规则（白名单） | 支持"允许"和"拒绝"规则 |
| **生效顺序** | 评估所有规则后决定是否放行 | 按规则编号从小到大顺序匹配，命中即停止 |
| **默认行为** | 入站全拒绝，出站全允许 | 默认 NACL 全允许；自定义 NACL 全拒绝 |
| **返回流量** | 自动放行 | 需手动配置对应方向的规则 |
| **关联对象** | 可关联多个实例 | 一个子网仅关联一个 NACL，一个 NACL 可关联多个子网 |

## 常见应用场景

在多层架构设计中，NACL 常用于提供额外的**纵深防御 (Defense in Depth)**。

- **封锁恶意 IP**：在子网级别直接拒绝来自已知恶意区域或攻击源的 IP 段，无需逐个修改安全组
- **分层防护**：NACL 负责子网级别的粗粒度过滤，[[Security Group]] 负责实例级别的精细访问控制
- **合规隔离**：为特定子网（如数据库子网）设置更严格的访问白名单

### 场景题解题思路

```
场景分析 → 选择 NACL 还是 Security Group
├── "需要显式拒绝某个 IP / IP 段" → NACL（支持 Deny 规则）
├── "子网级别的统一流量控制" → NACL
├── "实例级别的精细访问控制" → Security Group
├── "流量看似被允许却无响应" → 检查 NACL 出站规则是否放行了临时端口
└── "需要多层防御" → NACL（子网层）+ Security Group（实例层）组合使用
```

## 考试重点总结

1. **无状态**：入站/出站规则需分别配置，必须放行临时端口以允许响应流量
2. **支持 Deny 规则**：这是 NACL 相对 Security Group 唯一能实现的"黑名单"能力
3. **规则按编号顺序匹配**：命中即停止，编号越小优先级越高
4. **默认拒绝规则不可更改**：自定义 NACL 末尾始终有一条隐式的拒绝所有规则
5. **子网级别**：一个子网只能绑定一个 NACL，与 Security Group 的实例级别形成互补防线

## 最佳实践

1. **规则编号预留间隔**：便于后续插入新规则而不打乱现有顺序
2. **明确放行临时端口**：避免因无状态特性导致响应流量被意外拦截
3. **结合 Security Group 使用**：NACL 做粗粒度子网防护，Security Group 做精细实例控制，形成纵深防御
4. **谨慎使用自定义 NACL**：默认拒绝所有流量，上线前务必测试所有必要端口是否已放行
5. **记录变更**：结合 CloudTrail 审计 NACL 规则变更，便于排查网络故障
