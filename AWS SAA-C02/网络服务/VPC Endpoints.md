# VPC Endpoints - VPC 终端节点

> **VPC 终端节点（VPC Endpoint）**让 [[VPC]] 内的资源**私密访问** AWS 服务（或其他 VPC 内的自建服务），流量完全走 **AWS 内部网络**，无需经过 [[Internet Gateway]]、[[NAT Gateway]] 或公网，兼顾了安全性（不暴露公网）和成本（避免 NAT 数据处理费）。终端节点分为**网关型（Gateway）**和**接口型（Interface，基于 PrivateLink 技术）**两大类，后者进一步延伸出**跨账号私密共享自有服务**的能力。
>
> 相关文档：[[VPC]] | [[Subnet]] | [[Route Table]] | [[NAT Gateway]] | [[ENI]] | [[Security Group]] | [[Amazon API Gateway]] | [[AWS Load Balance]]

---

## 核心概念

### 为什么需要 VPC 终端节点

- **默认情况下**，VPC 内资源访问 S3、DynamoDB 等 AWS 服务需要经过公网（通过 IGW 或 [[NAT Gateway]]），这既产生**数据处理/传输费用**，也意味着流量**离开了 AWS 私有网络边界**
- **VPC 终端节点的核心价值**：在 VPC 与目标 AWS 服务之间建立**私有连接**，流量全程留在 AWS 骨干网络内，既降低成本（尤其避免 NAT 网关的数据处理费）又缩小攻击面

---

## 两种终端节点类型对比（考试最高频）

| 维度 | 网关终端节点（Gateway Endpoint） | 接口终端节点（Interface Endpoint） |
|------|----------------------------------|--------------------------------------|
| **底层技术** | [[Route Table]] 路由条目 | **AWS PrivateLink** |
| **支持的服务** | **仅 S3 和 DynamoDB** | 大多数 AWS 服务（[[AWS Lambda]]、SSM、STS、[[Amazon API Gateway]] 等），**S3 也支持接口型**（用于本地网络经 [[Direct Connect]]/VPN 访问 S3 等网关型无法覆盖的场景） |
| **网络实现** | 无 [[ENI]]，仅在路由表中添加指向该服务的路由条目 | 在指定子网创建 **ENI**，绑定**私有 IP**，作为服务访问入口 |
| **可用区概念** | 无 AZ 概念，VPC 级生效 | **按子网创建**，建议跨多 AZ 部署以实现高可用 |
| **访问方式** | 通过路由表自动生效，客户端**无需修改**服务的默认公网域名 | 通过 ENI 的**私有 IP**或**私有 DNS 名称**访问 |
| **成本** | **完全免费** | 按小时 + 数据处理量计费 |
| **安全组** | 不适用（无 ENI） | **可关联 Security Group**，精细控制哪些客户端能访问该终端节点 |
| **跨 VPC/账号访问** | 不支持 | 支持（PrivateLink 架构原生支持跨账号） |

> **考试要点**：**"仅 S3 和 DynamoDB"是网关终端节点最容易被考察的限制**——题目描述"需要私密、免费地访问 DynamoDB" → 网关终端节点；描述"需要私密访问 Lambda/SSM/API Gateway 等其他服务" → 只能用接口终端节点；描述"本地数据中心需要经 Direct Connect 私密访问 S3"（网关终端节点仅服务 VPC 内部，本地网络无法直接使用）→ 需要改用 **S3 的接口终端节点**。

---

## 网关终端节点（Gateway Endpoint）

- 创建后，AWS 会在指定的**路由表**中自动添加（或需手动添加）一条指向该服务的**前缀列表（Prefix List）**路由，VPC 内资源访问 S3/DynamoDB 时会**透明地**通过该私有路径，无需修改应用代码或服务端点
- **完全免费**，是"零成本却能立即提升安全性和降低 NAT 费用"的高性价比优化项
- 只能被创建它的 **VPC 内部**使用，无法从 Peering 对端 VPC、本地网络或其他账号直接访问（除非通过 [[Transit Gateway]] 等额外手段中转）

---

## 接口终端节点（Interface Endpoint）

- 本质是在指定子网内创建一个绑定**私有 IP** 的 **ENI**，客户端通过访问该 ENI 的私有 IP（或对应的私有 DNS 名称）来访问目标 AWS 服务
- 可关联 [[Security Group]]，基于来源 IP/协议/端口精细控制谁能使用该终端节点
- 建议在**每个可用区**的子网中都创建对应的接口终端节点 ENI，避免单 AZ 故障影响整体可用性

### 私有 DNS（Private DNS，考试提示）

- 创建接口终端节点时可选择启用**"私有 DNS 名称"**——启用后，服务的**标准公网域名**（如 `s3.us-east-1.amazonaws.com`）在 VPC 内会被**自动解析到终端节点的私有 IP**
- 这意味着**现有应用代码/SDK/CLI 无需任何改动**，调用标准服务域名时会**透明地**通过接口终端节点访问，而非绕行公网

> **考试陷阱**：**不启用私有 DNS 时，应用必须显式使用终端节点专属的 DNS 名称才能走私有路径**——若题目描述"创建了接口终端节点，但应用调用标准 SDK 域名时流量仍然经过公网/NAT" → 检查是否**遗漏启用私有 DNS 名称**这一选项，这是接口终端节点最常见的配置疏漏。

---

## 终端节点策略（Endpoint Policy，考试提示）

- 可为终端节点本身附加一份**资源策略（Endpoint Policy）**，控制"**通过这个终端节点**能访问哪些资源/操作"——默认策略允许所有操作，可收紧为白名单
- 这是与 [[IAM]] 身份策略、目标资源自身策略（如 S3 Bucket Policy）**并行的第三层控制**：一次通过终端节点发起的请求，需要**同时满足** IAM 身份策略、终端节点策略、目标资源策略三者的授权交集，才能成功

> **考试要点**：题目描述"希望限制某个 VPC 只能通过终端节点访问**特定的** S3 Bucket，即使 IAM 权限允许访问所有 Bucket" → 在**终端节点策略**中收紧允许访问的 Bucket 范围，这是网络边界层面的额外收紧手段，不同于身份或资源层面的权限控制。

## PrivateLink（VPC Endpoint Service）：跨账号私密共享自有服务

接口终端节点的底层技术 **AWS PrivateLink**，同样可以反过来用于**将自己 VPC 内的服务，私密地共享给其他 AWS 账号**。

### 架构组成

| 组件 | 角色 | 说明 |
|------|------|------|
| **网络负载均衡器（NLB）** | 服务提供者 | 指向服务提供者 VPC 内的应用实例 |
| **终端节点服务（Endpoint Service）** | 服务发布 | 基于 NLB 创建，暴露给消费者账号 |
| **接口终端节点（Interface Endpoint）** | 服务消费者 | 在消费者账号的 VPC 内创建，连接到该终端节点服务 |

```
服务提供者 VPC                    AWS 网络                    服务消费者 VPC
┌──────────────────┐                                    ┌──────────────────┐
│  NLB             │                                    │  Interface       │
│  (Endpoint       │←──────────────────────────────────→│  Endpoint        │
│   Service)       │                                    │                  │
│  ↓               │                                    │  ↓               │
│  应用实例         │                                    │  消费者应用       │
└──────────────────┘                                    └──────────────────┘
```

### 核心优势

| 优势 | 说明 |
|------|------|
| **私密性** | 流量完全通过 AWS 内部网络传输，不经过公网 |
| **跨账号共享** | 不同 AWS 账号可安全访问服务提供方发布的服务 |
| **无需复杂配置** | 不需要 [[VPC Peering]]、[[NAT Gateway]] 或复杂路由 |
| **天然容错** | 服务本身构建在 NLB + 接口终端节点之上，自带高可用性 |
| **安全访问** | 可通过服务策略（类似终端节点策略）控制哪些账号可以访问 |

### PrivateLink vs API Gateway（考试重点）

| 特性 | PrivateLink | [[Amazon API Gateway]] |
|------|-----------|-------------|
| **主要用途** | VPC 内服务跨账号共享 | RESTful/WebSocket API 发布 |
| **网络层级** | 网络层（L4） | 应用层（L7） |
| **后端集成** | NLB/ALB | Lambda、HTTP、EC2、ECS 等 |
| **安全特性** | 服务策略、终端节点 | API Key、IAM、Cognito、限流 |
| **适用场景** | NLB + 跨账号 + 服务提供者模型 | 客户端 API 调用、协议转换 |
| **考试关键词** | "NLB"、"服务提供者"、"跨账号 VPC" | "REST API"、"身份验证"、"限流" |

### PrivateLink vs VPC Peering（考试提示）

| 维度 | PrivateLink | [[VPC Peering]] |
|------|-------------|-------------------|
| **共享粒度** | 仅暴露 NLB 背后的**特定服务** | **打通整个网络**，双方可互访所有资源 |
| **CIDR 重叠限制** | 无此限制（不基于路由打通网络） | **不支持**双方 CIDR 重叠 |
| **路由复杂度** | 无需修改路由表 | 需双方手动添加路由 |
| **适用场景** | "只想暴露一个服务，不想打通整个网络" | "需要两个 VPC 之间的资源互相自由访问" |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **VPC 内资源私密、免费访问 S3/DynamoDB** | 网关终端节点 |
| **VPC 内资源私密访问 Lambda/SSM/API Gateway 等其他服务** | 接口终端节点 |
| **本地数据中心经 Direct Connect/VPN 访问 S3** | S3 的接口终端节点（网关终端节点仅限 VPC 内部使用） |
| **希望现有代码无需改动即可透明走私有路径** | 接口终端节点 + 启用私有 DNS 名称 |
| **限制某 VPC 只能通过终端节点访问特定 Bucket/表** | 收紧终端节点策略（Endpoint Policy） |
| **需要将自有 NLB 服务安全共享给其他 AWS 账号** | PrivateLink（创建 Endpoint Service） |
| **只想暴露单一服务，不想打通两个 VPC 的完整网络** | PrivateLink（而非 VPC Peering） |
| **需要两个 VPC 间资源自由互访** | 改用 [[VPC Peering]]（而非 PrivateLink） |

## 考试重点总结

### SAA-C02 高频考点

1. **网关终端节点仅支持 S3 和 DynamoDB，且完全免费**：基于路由表条目实现，无 ENI 概念
2. **接口终端节点覆盖大多数服务（含 S3），基于 PrivateLink 技术**：创建 ENI，按小时+数据处理量计费
3. **网关终端节点仅限 VPC 内部使用**：本地网络/其他 VPC 无法直接访问，需要接口终端节点覆盖此类场景
4. **私有 DNS 名称让现有代码无需改动**：不启用则必须显式使用终端节点专属域名才能走私有路径
5. **终端节点策略是第三层权限控制**：与 IAM 身份策略、资源自身策略并行生效，三者取交集
6. **接口终端节点可关联安全组，网关终端节点不行**：因为后者没有 ENI
7. **PrivateLink 的本质是"共享单一服务"，而非"打通整个网络"**：与 VPC Peering 打通全部资源的模式形成对比
8. **PrivateLink 不受 CIDR 重叠限制**：因为它不依赖路由打通网络，这是相对 VPC Peering 的独特优势
9. **PrivateLink 架构三要素**：NLB（服务提供者）+ Endpoint Service（发布）+ Interface Endpoint（消费者接入）
10. **判断依据是"共享粒度"**：只想暴露一个服务选 PrivateLink，需要双向自由访问选 VPC Peering

### 场景题解题思路

```
场景分析 → 判断使用哪种 VPC 终端节点方案
├── "私密、免费访问 S3/DynamoDB" → 网关终端节点
├── "私密访问 Lambda/SSM/API Gateway 等其他服务" → 接口终端节点
├── "本地数据中心经专线访问 S3" → S3 接口终端节点（非网关型）
├── "接口终端节点建好但流量仍走公网" → 检查是否遗漏启用私有 DNS 名称
├── "限制终端节点只能访问特定 Bucket/表" → 收紧终端节点策略
├── "需要跨账号安全共享自有 NLB 服务" → PrivateLink
├── "只想暴露单一服务，不想打通整个网络" → PrivateLink（而非 VPC Peering）
└── "需要两个 VPC 之间资源自由互访" → VPC Peering（而非 PrivateLink）
```

## 最佳实践

1. **默认为 S3/DynamoDB 流量启用网关终端节点**：零成本即可提升安全性并降低 NAT 网关费用，几乎没有理由不用
2. **接口终端节点跨多可用区部署**：在每个使用该服务的 AZ 子网中创建对应 ENI，避免单 AZ 故障影响可用性
3. **接口终端节点默认启用私有 DNS 名称**：让现有应用/SDK 无需任何代码改动即可透明享受私有访问路径
4. **为终端节点配置最小权限的终端节点策略**：尤其在共享 VPC 或多团队场景，收紧到真正需要访问的资源范围
5. **接口终端节点的安全组遵循最小权限**：仅放行真正需要访问该服务的客户端来源
6. **只需共享单一服务时优先选择 PrivateLink 而非 VPC Peering**：避免不必要地打通整个网络，缩小信任边界
7. **持续评估 NAT 网关流量构成**：将访问量大的 AWS 服务流量迁移到对应的 VPC 终端节点，显著降低数据处理费用
