# Security Group - 安全组

> **安全组（Security Group）**是附加在**网络接口（[[ENI]]）**上的**有状态虚拟防火墙**，控制单个或多个资源（[[EC2]]、[[AWS Load Balance]]、RDS 等）的入站和出站流量。它只支持"允许"规则（白名单模型），与工作在**子网级别、支持拒绝规则**的 [[NACL]] 形成实例级与子网级的两层纵深防御。
>
> 相关文档：[[VPC]] | [[NACL]] | [[ENI]] | [[EC2]] | [[Subnet]] | [[VPC Peering]] | [[AWS Load Balance]]

---

## 核心概念

### 有状态（Stateful，最核心特征）

- **有状态**意味着安全组会**自动跟踪连接状态**——只要入站请求被某条规则**允许**，其对应的**响应流量会自动放行**，无需额外配置出站规则（反之，出站发起的请求，其响应流量也会自动允许入站）
- 这与 [[NACL]] 的**无状态**行为形成鲜明对比：NACL 需要**分别**为请求和响应显式配置规则，完整对比见 [[NACL]] 独立笔记

### 默认规则

| 方向 | 默认行为 |
|------|---------|
| **入站（Inbound）** | 新建安全组默认**拒绝所有**入站流量，需手动添加白名单规则（如放行 22/80/443 端口） |
| **出站（Outbound）** | 默认**允许所有**流量离开（目的地 `0.0.0.0/0`） |

### 规则的构成要素

每条规则需定义三个核心参数：

| 参数 | 说明 |
|------|------|
| **协议（Protocol）** | TCP、UDP、ICMP 等 |
| **端口范围（Port Range）** | 如 80（HTTP）、443（HTTPS）、22（SSH） |
| **源/目的地（Source/Destination）** | 可以是 [[CIDR]] 地址段，也可以是**另一个安全组 ID** |

> **考试要点**：**将另一个安全组设为"源"，是"只允许特定层的资源访问下一层"这类分层架构题的标准答案**——例如数据库层安全组的入站规则中，源设置为 **Web 层安全组的 ID**（而非具体的 IP/CIDR），无论 Web 层实例如何扩缩容、IP 如何变化，规则**始终自动生效**，无需随实例变化维护 IP 白名单。

---

## 规则评估逻辑（考试提示）

- 安全组**评估所有规则后决定是否放行**——只要**任意一条**规则允许该流量，请求就会通过；规则之间是**并集（OR）**关系，**没有编号顺序、没有拒绝规则**
- 与 [[NACL]] 按编号从小到大**顺序匹配、命中即停止**的逻辑完全不同——这是两者规则模型的本质差异，也是无法在安全组中实现"先允许后拒绝"这类优先级逻辑的原因

> **考试陷阱**：**安全组无法显式"拒绝"某个 IP**——若题目描述"需要封禁特定恶意 IP 段的访问"，安全组做不到这一点（它只能选择不放行，无法主动拒绝并覆盖其他允许规则），必须改用支持 Deny 规则的 **[[NACL]]**。

---

## 安全组关联规则

- 安全组附加在 **[[ENI]]** 上，而非直接附加在实例上——一个实例若拥有多个 ENI（如双宿主架构），不同 ENI 可以关联**不同的**安全组
- **一个 ENI 可同时关联多个安全组**（默认配额 **5 个**，可申请提升），此时该 ENI 生效的规则是**所有已关联安全组规则的并集**
- **安全组规则的修改会立即生效**，无需重启或重新部署已关联的资源——这是它相对于修改防火墙软件配置的显著优势

### 默认安全组（Default Security Group）

- 每个 VPC 创建时会自动生成一个**默认安全组**：入站拒绝所有外部流量，但**允许该安全组内部资源之间互相通信**（即默认安全组的入站规则里包含一条"源为自身"的允许规则）
- 新建的**自定义安全组**创建时规则为空，需要手动添加

## 安全组 vs NACL（考试高频对比）

| 特性 | 安全组（Security Group） | [[NACL]] |
|------|---------------------------|----------|
| **作用范围** | 实例/网卡（[[ENI]]）级别 | 子网（[[Subnet]]）级别 |
| **状态属性** | **有状态**（Stateful） | **无状态**（Stateless） |
| **规则类型** | 仅支持"允许"规则（白名单） | 支持"允许"和"拒绝"规则 |
| **生效顺序** | 评估所有规则后决定是否放行（并集） | 按规则编号从小到大顺序匹配，命中即停止 |
| **默认行为** | 入站全拒绝，出站全允许 | 默认 NACL 全允许；自定义 NACL 全拒绝 |
| **返回流量** | 自动放行 | 需手动配置对应方向的规则 |
| **关联对象** | 可关联多个实例/ENI | 一个子网仅关联一个 NACL，一个 NACL 可关联多个子网 |
| **典型定位** | 精细的实例级访问控制 | 粗粒度的子网级防线，尤其适合黑名单封禁 |

---

## 跨 VPC 引用安全组（考试提示）

- **[[VPC Peering]] 建立后，可以在安全组规则中直接引用对端 VPC 内的安全组 ID**（而非只能用 CIDR），实现更精细、随对端实例动态变化自动生效的访问控制
- **限制**：这种跨 VPC 安全组引用**仅支持同区域**的 VPC Peering，**跨区域（Inter-Region）Peering 不支持**，跨区域场景必须改用 CIDR 范围而非安全组 ID 作为规则的源/目标

> **考试陷阱**：题目描述"两个同区域 VPC 已建立 Peering，希望在安全组中直接引用对方安全组" → **支持**；描述"跨区域 Peering 场景" → **不支持**安全组引用，必须改用 CIDR，这是 [[VPC Peering]] 笔记中安全组引用规则的延伸考点。

## 配额限制

| 项目 | 默认值 |
|------|--------|
| **每个网络接口关联的安全组数** | 5（可申请提升到 16） |
| **每个安全组的入站/出站规则数** | 各 60 条（可申请提升） |
| **每个区域的安全组数量** | 有默认配额，可申请提升 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **只允许 Web 层实例访问数据库层，且 Web 层会动态扩缩容** | 数据库安全组的入站规则引用 Web 层安全组 ID，而非固定 CIDR |
| **需要显式封禁某个恶意 IP 段** | 改用 [[NACL]]（安全组无法显式拒绝） |
| **实例需要接收 HTTP/HTTPS 公网请求** | 入站放行 80/443 端口，源设为 `0.0.0.0/0` |
| **修改安全组规则后是否需要重启实例** | 无需，规则立即生效 |
| **同区域 VPC Peering 场景下的精细访问控制** | 安全组规则直接引用对端安全组 ID |
| **跨区域 VPC Peering 场景下的访问控制** | 只能使用 CIDR，不支持安全组引用 |
| **子网级别粗粒度封锁 + 实例级精细放行** | [[NACL]]（子网层）+ 安全组（实例层）组合 |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：附加在 ENI 上的有状态虚拟防火墙，仅支持允许规则
2. **有状态特性**：入站/出站的响应流量自动放行，无需额外配置
3. **默认规则**：入站全拒绝，出站全允许，自定义安全组创建时规则为空
4. **规则评估为并集（OR）**：任意一条规则允许即放行，没有编号顺序、没有拒绝规则
5. **无法显式拒绝**：需要黑名单/封禁能力必须改用 NACL
6. **源/目的地可引用另一个安全组 ID**：实现"只允许特定层访问"且随实例动态变化自动生效
7. **一个 ENI 可关联多个安全组（默认 5 个）**：生效规则是所有已关联安全组的并集
8. **规则修改立即生效**：无需重启或重新部署资源
9. **同区域 Peering 支持安全组互相引用，跨区域不支持**：跨区域只能用 CIDR
10. **安全组（实例级）+ NACL（子网级）构成纵深防御**：两者互补而非替代

### 场景题解题思路

```
场景分析 → 判断安全组相关配置
├── "只允许特定层资源访问，且该层会动态扩缩容" → 安全组规则引用对方安全组 ID
├── "需要显式拒绝/封禁某个 IP 段" → 改用 NACL（安全组做不到）
├── "修改安全组规则后资源多久生效" → 立即生效，无需重启
├── "一个实例的多个 ENI 需要不同的访问控制策略" → 为不同 ENI 关联不同安全组
├── "同区域 VPC Peering 后想直接引用对方安全组" → 支持
├── "跨区域 VPC Peering 后想直接引用对方安全组" → 不支持，改用 CIDR
└── "需要子网级 + 实例级双重防御" → NACL + 安全组组合
```

## 最佳实践

1. **分层架构优先使用安全组引用而非硬编码 CIDR**：数据库层引用 Web 层安全组 ID，避免 IP 变化导致规则失效
2. **入站规则遵循最小权限，仅放行必要端口和来源**：避免使用过宽的 `0.0.0.0/0` 尤其是管理端口
3. **需要黑名单/封禁能力时结合 NACL**：不要试图用安全组实现拒绝逻辑
4. **善用默认安全组做内部资源互通，但生产环境建议使用自定义安全组**：便于按业务分层精细管理规则
5. **同区域 Peering 架构优先用安全组引用简化维护**：跨区域场景需提前规划好 CIDR 方案作为替代
6. **定期审计安全组规则，移除不再使用的放行项**：减少不必要的攻击面
7. **规划大规模架构时提前评估安全组和规则数量配额**：避免后期因达到默认上限而阻塞变更
