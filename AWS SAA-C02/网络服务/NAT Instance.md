# NAT Instance - 自管理 NAT 实例

> **NAT 实例（NAT Instance）**是一台运行网络地址转换/IP 转发软件的**普通 EC2 实例**，部署在公有子网中，代理私有子网实例访问互联网。与全托管的 [[NAT Gateway]] 相比，它需要用户**自行承担实例选型、打补丁、扩容和高可用**的运维责任，但换来了 NAT 网关不具备的能力——**安全组过滤、端口转发、堡垒机复用**。AWS 官方目前**默认推荐 NAT 网关**，NAT 实例更多是特定场景下的补充方案。
>
> 相关文档：[[NAT Gateway]] | [[Internet Gateway]] | [[VPC]] | [[Subnet]] | [[Route Table]] | [[Security Group]] | [[EC2]] | [[Auto Scaling]] | [[Bastion Hosts]]

## 核心概念

### NAT 实例的本质

- 本质上就是一台**装有 IP 转发/地址转换软件（iptables NAT 规则等）**的 EC2 实例——它接收来自私有子网的出站流量，将源地址转换为自己的公网 IP 后转发至 [[Internet Gateway]]，并将返回流量转发回原始私有实例
- 与 [[NAT Gateway]] 实现相同的"只出不进"目标，但**实现方式是用户自行配置的软件层**，而非 AWS 托管的网络层服务

### 源/目的地检查（Source/Destination Check，考试最高频配置项）

- EC2 实例默认会检查网络接口收发的数据包，若数据包的**源地址或目的地址与该 ENI 本身的 IP 不匹配**，会被自动**丢弃**——这是防止实例意外转发不属于自己流量的默认安全行为
- NAT 实例的核心职责恰恰是**转发不属于自己的流量**（私有子网实例的流量），因此**必须在该实例的 ENI 上显式禁用源/目的地检查**，否则所有经过它的转发流量都会被静默丢弃

> **考试陷阱**：**"配置看似正确，但私有子网实例仍无法访问互联网"这类题目，第一排查项永远是源/目的地检查是否已禁用**——这是 NAT 实例特有的配置步骤，[[NAT Gateway]] 作为托管服务不存在也不需要这项配置，是两者最核心的操作差异点。

## 部署要求

| 要求 | 说明 |
|------|------|
| **必须位于公有子网** | 因为自身也需要通过 [[Internet Gateway]] 访问公网，路由表须指向 IGW |
| **需要公网 IP 或弹性 IP** | 与普通面向公网的 EC2 实例要求一致 |
| **禁用源/目的地检查** | 见上文，最容易被遗漏的配置项 |
| **私有子网路由表指向该 NAT 实例** | 路由目标（Target）设置为该实例的 ID，而非网关类型的目标 |
| **安全组规则** | 需**入站**放行来自私有子网 CIDR 的相应端口流量、**出站**放行到互联网的流量——这是 NAT 网关所没有的**额外配置项**，但也带来了更精细的过滤能力 |

## 独特能力（NAT Gateway 不具备，考试提示）

| 能力 | 说明 |
|------|------|
| **端口转发（Port Forwarding）** | 可通过 iptables 等工具配置**目标地址转换（DNAT）**规则，将特定端口的入站流量转发到私有子网内的指定实例，实现"反向暴露"特定服务，这是 NAT 网关完全不支持的能力 |
| **兼作堡垒机（[[Bastion Hosts\|Bastion Host]]）** | 由于本质是普通 EC2 实例且位于公有子网，可以**同时承担** SSH/RDP 跳板机的角色，无需为堡垒机单独部署实例，完整的堡垒机加固要求和现代替代方案见 [[Bastion Hosts]] 独立笔记 |
| **安全组精细过滤** | 作为 EC2 实例可关联 [[Security Group]]，基于协议/端口/来源 CIDR 精细控制哪些流量能被转发，NAT 网关没有安全组概念，无法在网关层面做这类过滤 |
| **成本可控性** | 可根据实际流量选择更小规格甚至 **Spot 实例**降低成本，适合流量较低、对可用性要求不高的开发/测试环境 |

> **考试要点**：题目描述"需要在 NAT 设备上按端口/来源做精细过滤"、"需要将 NAT 设备兼作堡垒机"、或"需要端口转发暴露内部服务" → 这些都是 **NAT 实例**相对 NAT 网关的差异化答案；除此之外的绝大多数"私有子网需要访问公网"场景，默认答案仍是 [[NAT Gateway]]。

## 高可用性（需自行构建）

- NAT 实例**没有原生的高可用机制**——它就是一台普通 EC2 实例，宕机、维护、AZ 故障都会导致其代理的所有私有子网**瞬间失去出站能力**
- **常见自建高可用方案**：
  - 使用 **Auto Scaling 组**（通常设置为固定 1 个实例）确保实例故障后自动替换，但替换过程中仍存在**短暂的服务中断**
  - 结合 **CloudWatch 告警 + Lambda 自动化脚本**：监测 NAT 实例健康状态，故障时自动将私有子网路由表的目标切换到备用 NAT 实例
  - 部署在**多个可用区**并配合脚本实现跨 AZ 故障转移，但整体复杂度和运维成本显著高于直接使用每 AZ 一个的 NAT 网关

> **考试陷阱**：**NAT 实例的高可用不是开箱即用的**——题目描述"需要开箱即用的高可用出站方案，尽量减少运维投入" → 明确指向 [[NAT Gateway]]；只有题目强调"愿意自行承担运维复杂度以换取端口转发/堡垒机等特殊能力"时，NAT 实例才是更合理的选择。

## 官方 NAT AMI 现状（考试提示）

- AWS 早期提供官方维护的 **NAT AMI**（基于 Amazon Linux），但该 AMI 长期未更新，其底层系统版本已进入**生命周期终止（EOL）**状态，AWS **不再积极维护**这一官方镜像
- **当前实践**：若确需部署 NAT 实例，通常需要用户**基于当前受支持的 Amazon Linux 版本自行构建**具备 IP 转发能力的 AMI，或采用社区维护的开源替代方案
- 这进一步印证了 AWS 官方立场——**NAT 网关是绝大多数场景下的默认推荐**，NAT 实例定位为需要特殊能力或有历史遗留部署时的补充选项

---

## 带宽与性能

- NAT 实例的吞吐能力**完全取决于所选 EC2 实例类型**，不像 NAT 网关那样自动扩展到 100 Gbps——流量增长时需要**手动升级实例规格**，否则该实例会成为整条出站链路的瓶颈
- 需要持续监控实例的 **CPU 利用率、网络吞吐、连接跟踪表（Connection Tracking）**等指标，提前规划扩容，避免高峰期出现性能瓶颈或连接丢失

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **私有子网访问公网，追求免运维和高可用** | 改用 [[NAT Gateway]]（默认推荐） |
| **需要按端口/来源做精细流量过滤** | NAT 实例 + Security Group |
| **需要将出站网关兼作堡垒机，减少实例数量** | NAT 实例（同时承担跳板机角色） |
| **需要端口转发，将公网请求转发到私有子网内的特定服务** | NAT 实例 + iptables DNAT 规则 |
| **开发/测试环境流量小，希望进一步压缩成本** | NAT 实例（可选 Spot/小规格实例） |
| **私有子网无法访问公网，且使用的是 NAT 实例** | 检查源/目的地检查是否已禁用、路由表目标是否正确指向该实例 |
| **需要为出站流量提供开箱即用的高可用** | 改用 [[NAT Gateway]]，避免自建复杂的故障转移脚本 |

## 考试重点总结

### SAA-C02 高频考点

1. **NAT 实例本质是普通 EC2 实例**：运行 NAT/IP 转发软件，部署在公有子网
2. **必须禁用源/目的地检查**：否则会丢弃不属于自己的转发流量，是最高频的排障考点
3. **需要显式配置安全组规则**：入站放行私有子网 CIDR、出站放行公网，这是与 NAT 网关的关键差异
4. **拥有 NAT 网关不具备的三项能力**：端口转发、堡垒机复用、安全组精细过滤
5. **没有原生高可用**：需自行搭建 Auto Scaling / 故障转移脚本，运维成本显著高于 NAT 网关
6. **带宽受限于实例类型**：不会自动扩展，需手动升级规格应对流量增长
7. **官方 NAT AMI 已过时**：现实部署通常需自建镜像或使用第三方方案，进一步佐证 NAT 网关是默认推荐
8. **私有子网路由表需指向 NAT 实例 ID**：与指向网关类型目标（NAT Gateway/IGW）的配置方式不同
9. **默认答案仍是 NAT 网关**：只有题目明确强调端口转发/堡垒机/精细过滤等特殊需求时才选 NAT 实例
10. **成本可通过 Spot/小规格实例压缩**：适合低流量、可容忍中断的非关键环境

### 场景题解题思路

```
场景分析 → 判断是否该用 NAT 实例
├── "私有子网需要访问公网，免运维、要高可用" → NAT Gateway（默认答案）
├── "需要按端口/来源精细过滤转发流量" → NAT 实例 + Security Group
├── "需要将 NAT 设备兼作堡垒机" → NAT 实例
├── "需要端口转发暴露内部服务" → NAT 实例 + iptables DNAT
├── "私有子网无法访问公网（使用 NAT 实例）" → 检查源/目的地检查、路由表目标配置
├── "开发测试环境希望进一步压缩成本" → NAT 实例（Spot/小规格）
└── "需要开箱即用的高可用出站方案" → NAT Gateway（而非自建 NAT 实例高可用）
```

## 最佳实践

1. **默认优先选择 [[NAT Gateway]]**：仅在明确需要端口转发、堡垒机复用或精细安全组过滤时才引入 NAT 实例
2. **部署 NAT 实例后立即核对源/目的地检查已禁用**：这是最容易遗漏也最容易排查的第一步
3. **持续监控实例的网络吞吐和 CPU 利用率**：提前规划扩容，避免实例规格成为出站链路瓶颈
4. **需要高可用时提前设计故障转移方案**：Auto Scaling + 健康检查脚本或 CloudWatch 告警联动路由表切换，而非假设它会自动故障转移
5. **自行构建当前受支持系统版本的 AMI**：不要依赖已过时的官方 NAT AMI，避免安全补丁缺失的风险
6. **安全组规则遵循最小权限**：仅放行私有子网真正需要的出站端口，而非笼统允许所有流量
7. **低流量非关键环境可评估 Spot 实例降本**：但需接受 Spot 实例可能被回收带来的可用性风险
