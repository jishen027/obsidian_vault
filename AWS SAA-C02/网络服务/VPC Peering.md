# VPC 对等连接 (VPC Peering)

> **VPC 对等连接（VPC Peering）**是两个 [[VPC]] 之间的**一对一**网络连接，通过 AWS 的骨干网络私密路由流量，双方 VPC 内的资源可以像在同一网络中一样使用私有 IP 互相通信。它是最简单、最基础的 VPC 互联方式，但**不支持传递路由**，规模化场景通常改用 Transit Gateway。
>
> 相关文档：[[VPC]] | [[Virtual Private Gateway]] | [[Security Group]] | [[NACL]] | [[Subnet & Route table]] | [[Route 53 DNS]] | [[AWS EFS]]

---

## 核心概念

### 为什么需要 VPC Peering

- **VPC 默认相互隔离**：不同 VPC 天生是独立的网络边界，即使属于同一账户，彼此也无法直接通信，这种隔离是安全设计的默认状态
- **Peering 的核心价值**：在两个 VPC 之间建立**私有的点对点连接**，流量完全走 AWS 内部骨干网络，不经过公网、IGW 或 VPN 网关，实现低延迟、高带宽的跨 VPC 私有通信

### 建立连接的基本流程

1. **发起请求方**在源 VPC 中创建对等连接请求，指定目标 VPC（可以是同账户、跨账户，甚至同一 AWS 组织内的其他账户）
2. **接受方**在目标 VPC 中**接受**该请求，连接状态变为 Active
3. 双方分别在各自的**路由表**中添加指向对方 CIDR 的路由条目，**Peering 本身不会自动更新路由表**
4. 按需调整双方的 [[Security Group]] / [[NACL]] 规则，放行来自对方 VPC CIDR 的流量

## 核心限制（考试高频）

### 不支持重叠 CIDR

- 两个 VPC 的 **CIDR 范围不能有任何重叠**，否则无法建立对等连接——这是规划多 VPC 架构时必须提前考虑的约束，一旦 CIDR 冲突，唯一解决方式是重新规划其中一方的 IP 地址空间

### 不支持传递路由（Transitive Routing，最高频考点）

> **考试陷阱**：**VPC Peering 是严格的点对点连接，不具备传递性**——若 VPC A 与 VPC B 建立了对等连接，VPC B 与 VPC C 也建立了对等连接，**VPC A 无法通过 VPC B 访问 VPC C**，必须为 A 和 C 之间**单独建立一条对等连接**。这个限制同样适用于**站点到站点 VPN**场景：若 VPC A 通过 [[Virtual Private Gateway]] 连接了本地数据中心，即使 VPC A 与 VPC B 建立了 Peering，本地数据中心也**不能**经由 VPC A 访问 VPC B（完整的不可传递路由说明见 [[Virtual Private Gateway]] 笔记）。

- **架构影响**：当需要互联的 VPC 数量增多时，点对点特性会导致连接数量呈**平方级增长**（N 个 VPC 全互联需要 N×(N-1)/2 条连接），管理复杂度迅速失控——这正是 **Transit Gateway**（星型枢纽拓扑，原生支持传递路由）被设计用来解决的问题，完整对比见下方"VPC Peering vs Transit Gateway"

### 不支持多播/广播

- 仅支持标准的单播（Unicast）流量，无法在对等连接上传输多播或广播流量

### 边界网关协议（BGP）不适用

- 与 VPN/Direct Connect 不同，Peering 不涉及任何动态路由协议，路由完全依赖手动在路由表中配置的静态条目

## 范围与适用性

| 维度 | 支持情况 |
|------|---------|
| **同账户 VPC** | 支持 |
| **跨账户 VPC** | 支持（需接受方账户批准请求） |
| **同区域** | 支持 |
| **跨区域（Inter-Region Peering）** | 支持，流量通过 AWS 全球骨干网络加密传输，**无需额外配置加密** |
| **跨可用区** | 天然支持（VPC 本身跨越多可用区） |

> **考试要点**：**跨区域对等连接的流量默认经过 AWS 主干网络自动加密**，不同于跨区域 VPN 需要手动配置加密隧道；但跨区域连接会产生**跨区域数据传输费用**，这是与同区域 Peering（仅有跨可用区数据传输费，且更低）的重要成本差异点。

---

## DNS 解析

- 默认情况下，跨 Peering 连接使用**公网 DNS 名称**解析时会返回**公网 IP**，即使实际流量应该走私有对等连接
- 需显式启用**"DNS 主机名解析私有对等连接（Allow DNS resolution to private IP）"**选项，开启后跨 VPC 使用私有 DNS 名称查询时会解析为**私有 IP**，确保流量真正走对等连接而非绕行公网

> **考试陷阱**：题目描述"两个已建立 Peering 的 VPC，实例间使用私有 DNS 名称互相访问，但流量却经过公网/返回公网 IP" → 检查并启用对等连接的 **DNS 解析设置**，这是该场景的标准排查方向。

---

## 安全组引用（考试提示）

- 对等连接的两个 VPC 之间，**同区域场景下可以直接在安全组规则中引用对方 VPC 的安全组 ID**（而非只能用 CIDR），实现更精细、随实例动态变化自动生效的访问控制
- **跨区域对等连接不支持**这种安全组互相引用，跨区域场景必须使用 CIDR 范围而非安全组 ID 作为规则的源/目标

## VPC Peering vs Transit Gateway（考试高频）

| 维度 | VPC Peering | Transit Gateway |
|------|-------------|-----------------|
| **拓扑** | 点对点（Mesh 需 N² 级连接） | 星型枢纽，中心化管理 |
| **传递路由** | **不支持** | **原生支持**，可通过 TGW 中转访问其他已连接的 VPC/VPN/DX |
| **适用规模** | 少量 VPC（2-10 个左右）互联 | 大规模（几十到上千个）VPC/VPC 与本地网络混合互联 |
| **成本** | 连接本身免费，仅数据传输费（跨区域） | 按连接数 + 数据处理量计费，规模大时更具性价比 |
| **管理复杂度** | VPC 数量增多时呈平方级增长，难以维护 | 集中管理路由表，新增 VPC 只需接入枢纽 |
| **典型场景** | 两三个 VPC 之间的简单直连 | 企业级多账户、多 VPC、混合云架构 |

> **考试要点**：**判断依据是"需要互联的 VPC 数量"和"是否需要传递路由"**——题目描述"仅需连接两个 VPC" → Peering 已经足够，无需引入 Transit Gateway 的额外成本和复杂度；题目描述"需要连接数十上百个 VPC，或需要通过中心枢纽统一管理路由、支持传递访问" → **Transit Gateway**。

---

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **两个 VPC 之间简单直连，数量不多** | VPC Peering |
| **跨账户共享特定 VPC 内的资源** | VPC Peering（发起方 + 接受方账户批准） |
| **跨区域灾备架构需要私有互联** | Inter-Region VPC Peering（流量自动加密，无需额外 VPN） |
| **[[AWS EFS]] 需要被其他 VPC 内的实例挂载** | VPC Peering 或 Transit Gateway（取决于规模），详见 [[AWS EFS]] 笔记 |
| **大规模多 VPC/多账户/混合云统一互联** | 改用 Transit Gateway（而非维护大量 Peering 连接） |
| **私有 DNS 名称访问对方 VPC 资源却解析成公网 IP** | 启用对等连接的"私有 DNS 解析"设置 |
| **需要在安全组规则中动态引用对方 VPC 的实例** | 同区域 Peering + 安全组 ID 互相引用 |
| **本地数据中心需要访问已 Peering 的另一 VPC** | 不支持传递路由，需为本地网络与目标 VPC 单独建立连接（VPN/DX） |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：两个 VPC 之间的一对一私有网络连接，流量走 AWS 骨干网络
2. **不支持重叠 CIDR**：建立连接的前提条件，规划阶段必须提前避免地址冲突
3. **不支持传递路由**：这是全场最高频的考点——A-B、B-C 各自 Peering 不代表 A 能访问 C，VPN 场景同理
4. **需要手动更新路由表**：接受连接后不会自动配置路由，必须双方分别添加
5. **支持跨账户、跨区域**：跨区域流量默认自动加密，但产生跨区域数据传输费
6. **DNS 解析需显式启用**：否则私有 DNS 名称会解析为公网 IP，绕开对等连接
7. **同区域可安全组互相引用**：跨区域则只能用 CIDR
8. **N 个 VPC 全互联连接数呈平方级增长**：规模扩大时应改用 Transit Gateway
9. **不支持多播/广播、无动态路由协议**：仅支持单播，路由完全静态配置
10. **判断 Peering vs Transit Gateway**：连接数量少选 Peering；数量多或需要传递路由选 Transit Gateway

### 场景题解题思路

```
场景分析 → 判断 VPC Peering 相关配置
├── "两个 VPC 需要私有互访，数量不多" → VPC Peering
├── "跨账户共享 VPC 内资源" → VPC Peering（对方账户接受请求）
├── "跨区域私有互联，且不想额外配置加密" → Inter-Region VPC Peering
├── "Peering 后仍无法互通" → 检查双方路由表是否已添加对方 CIDR 路由
├── "本地网络能否经 VPC A 访问已 Peering 的 VPC B" → 不能，不支持传递路由
├── "私有 DNS 名称解析成了公网 IP" → 启用对等连接的 DNS 解析设置
├── "希望安全组规则随对方实例动态变化" → 同区域 Peering + 安全组 ID 引用
└── "需要互联几十上百个 VPC，或需要传递路由" → 改用 Transit Gateway
```

## 最佳实践

1. **架构规划阶段统一 IP 地址管理，避免 CIDR 重叠**：一旦冲突，唯一解法是重新规划地址空间，代价高昂
2. **仅在少量 VPC 直连场景使用 Peering**：预计连接数量会增长到较大规模时，尽早转向 Transit Gateway，避免后期迁移成本
3. **建立连接后立即检查双方路由表**：Peering 状态为 Active 不代表流量已能互通，路由表配置是必需步骤
4. **需要私有 DNS 解析时显式启用该设置**：避免流量意外绕行公网
5. **同区域场景优先用安全组引用而非硬编码 CIDR**：更安全、随实例变化自动生效，减少维护成本
6. **跨账户 Peering 严格审查接受方的信任边界**：避免与不可信账户建立不必要的私有网络连接
7. **涉及本地数据中心的多跳访问需求，评估 Transit Gateway 而非依赖多条 Peering 拼凑**：Peering 的不可传递性无法通过嵌套连接绕过
