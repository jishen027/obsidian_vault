# VPC Traffic Mirroring - 流量镜像

> **VPC Traffic Mirroring（流量镜像）**将进出指定 [[ENI]] 的**完整网络数据包（包括 payload 内容）**复制一份，发送到指定的监控/分析目标，而**不影响原始流量的转发路径或延迟**——这是一种**带外（Out-of-Band）**的流量复制机制。它与只记录**元数据**的 [[VPC Flow Logs]] 是互补而非替代关系：需要判断"流量是否发生/被谁拒绝" → Flow Logs；需要"检查数据包实际内容做深度检测" → Traffic Mirroring。
>
> 相关文档：[[VPC]] | [[ENI]] | [[VPC Flow Logs]] | [[VPC Peering]] | [[Transit Gateway]] | [[Security Group]] | [[NACL]]

---

## 核心概念

### 为什么需要 Traffic Mirroring

- **Flow Logs 只记录元数据**：无法回答"这个数据包里到底传输了什么内容"，也无法支撑需要检查载荷（payload）的深度包检测（DPI）、入侵检测/防御（IDS/IPS）类需求
- **Traffic Mirroring 的核心价值**：在**不修改原始网络路径、不引入额外延迟给业务流量**的前提下，把原始数据包**原样复制一份**送到独立的分析/安全设备，实现实时或近实时的流量取证、协议分析、异常检测

### 三大核心组件（考试高频）

| 组件 | 角色 |
|------|------|
| **镜像源（Mirror Source）** | 被镜像的 **ENI**——可以是 EC2 实例网卡、NAT 网关、Transit Gateway 附件等的 ENI |
| **镜像目标（Mirror Target）** | 接收镜像流量的目的地：可以是一个 **[[ENI\|网络接口]]**（如安全设备实例），或一个 **网络负载均衡器（NLB）**（前置一组分析设备，便于横向扩展） |
| **镜像会话（Mirror Session）** | 将**镜像源**、**镜像目标**、**镜像过滤器**关联起来的配置对象，并可指定会话**优先级编号**（决定多会话同时匹配时的处理顺序）和最大**数据包长度**（超出部分被截断，节省带宽） |

### 镜像过滤器（Mirror Filter）

- 通过**入站/出站规则**（协议、端口范围、CIDR）精确控制**哪些流量**被镜像，而不是无差别复制源 ENI 的全部流量
- 规则支持 **accept（接受镜像）** 或 **reject（排除）**，按**规则编号**从小到大依次匹配，逻辑与 [[NACL]] 的编号优先级类似
- **考试要点**：**精细化配置过滤器是控制镜像成本和目标设备负载的关键手段**——题目描述"只需要镜像特定端口（如可疑的非标准端口）的流量，而非全部流量" → 配置**镜像过滤器**限定协议/端口，而非镜像整个 ENI 的全部流量后再在目标端过滤。

## 部署范围与网络要求

- **源 ENI 和目标必须支持增强型网络（ENA）**——仅 **Nitro 系统**实例支持 Traffic Mirroring，老旧的非 Nitro 实例类型无法作为镜像源或目标
- **镜像目标可以跨越以下范围**：
  - **同一 VPC** 内的 ENI/NLB
  - **[[VPC Peering]]** 对等连接的另一个 VPC（同区域）
  - 通过 **[[Transit Gateway]]** 中转互联的其他 VPC（含跨区域场景）
- 镜像流量使用 **VXLAN** 封装后传输到目标，目标端需要按 VXLAN 格式解封装还原原始数据包

> **考试陷阱**：**Traffic Mirroring 并非只能在同一 VPC 内使用**——很多人误以为镜像流量无法跨 VPC，实际上通过 [[VPC Peering]] 或 [[Transit Gateway]] 完全可以将流量集中镜像到**中心化的安全监控 VPC**，这也是大规模多账户架构下集中式流量检测的标准做法。

## Traffic Mirroring vs Flow Logs（考试高频对比）

完整的 Flow Logs 能力见 [[VPC Flow Logs]] 独立笔记，核心差异：

| 维度 | VPC Flow Logs | VPC Traffic Mirroring |
|------|----------------|--------------------------|
| **记录内容** | 流量**元数据**（五元组、字节数、动作） | **完整数据包**（含 payload） |
| **典型用途** | 连接性排查、访问模式分析、安全审计 | 深度包检测（DPI）、入侵检测、协议级故障排查 |
| **性能开销** | 极低，不影响转发路径 | 需要额外镜像流量到目标，开销更高，且要求 Nitro/ENA |
| **实时性** | 近实时（有聚合窗口延迟） | 实时镜像 |
| **是否影响原始流量路径** | 否 | 否（带外复制，与下文 GWLB 的"在线"模式不同） |

## Traffic Mirroring vs Gateway Load Balancer（考试陷阱）

- **[[AWS Load Balance|Gateway Load Balancer（GWLB）]]** 是**在线（Inline）**方案：流量在到达目的地**之前**必须先经过第三方安全设备处理，设备可以**主动拦截/修改**流量，客户端和服务端对此透明
- **Traffic Mirroring** 是**带外（Out-of-Band）**方案：只复制一份流量副本给分析设备，**原始流量不受影响**，镜像目标设备**无法拦截或修改**任何原始流量，只能被动分析

> **考试陷阱**：**题目描述"需要主动阻断检测到的恶意流量" → GWLB（在线部署，具备拦截能力）；题目描述"需要被动分析/取证，同时绝对不能影响生产流量的路径或延迟" → Traffic Mirroring（带外复制，无拦截能力）**——两者常被误认为是同一类工具的不同名字，实际上"能否主动拦截流量"是区分两者适用场景的核心依据。

---

## 定价（考试提示）

- **Traffic Mirroring 功能本身不收取额外的服务费**
- 实际成本来自**镜像流量产生的标准数据传输费用**（尤其是跨 AZ、跨 VPC Peering、经由 Transit Gateway 的场景），以及承载分析设备的 **EC2/NLB** 本身的费用
- **考试要点**：题目描述"担心大规模镜像流量导致高昂的数据传输成本" → 通过**镜像过滤器**缩小镜像范围、**限制最大数据包长度**、以及**尽量将镜像目标部署在与源相同的 AZ/VPC 内**来控制成本，而非误以为存在单独的"镜像服务费"可以优化。

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **需要检查数据包实际内容/做深度协议分析** | Traffic Mirroring（Flow Logs 无法满足） |
| **部署第三方 IDS/IPS 做被动流量分析，不能影响生产流量路径** | Traffic Mirroring 到 NLB 前置的分析设备集群 |
| **需要主动拦截/阻断恶意流量** | 改用 [[AWS Load Balance\|Gateway Load Balancer]]（在线部署） |
| **只关心特定可疑端口/协议的流量** | 配置镜像过滤器，仅镜像匹配的流量 |
| **多账户/多 VPC 需要集中式流量安全监控** | 通过 [[VPC Peering]] 或 [[Transit Gateway]] 将流量镜像到中心化安全 VPC |
| **担心镜像流量产生高额数据传输费用** | 精细化过滤器 + 限制包长度 + 目标尽量同 AZ 部署 |
| **排查协议级异常（如 TLS 握手失败的具体原因）** | Traffic Mirroring 结合抓包分析工具（如 Wireshark） |

## 考试重点总结

### SAA-C02 高频考点

1. **Traffic Mirroring 复制完整数据包（含 payload），Flow Logs 只记录元数据**：这是两者最本质的区别
2. **带外（Out-of-Band）复制，不影响原始流量路径和延迟**：与 GWLB 的"在线"模式形成对比
3. **三大组件**：镜像源（ENI）、镜像目标（ENI 或 NLB）、镜像会话（关联源/目标/过滤器）
4. **镜像过滤器控制镜像范围**：按协议/端口/CIDR 的 accept/reject 规则，编号从小到大匹配
5. **仅 Nitro 系统（支持 ENA）的实例可作为源或目标**：老旧非 Nitro 实例类型不支持
6. **镜像目标可跨 VPC Peering / Transit Gateway**：不局限于同一 VPC 内，支持集中式安全监控架构
7. **镜像流量使用 VXLAN 封装**：目标端需按此格式解封装
8. **Traffic Mirroring 无法主动拦截流量**：需要拦截能力应改用 Gateway Load Balancer（在线部署）
9. **无独立服务费，成本来自数据传输 + 承载分析设备的资源费用**：可通过过滤器和包长度限制控制成本
10. **与 [[Amazon GuardDuty]] 等托管威胁检测服务是互补关系**：GuardDuty 分析已有的 Flow Logs/DNS 日志做自动化威胁检测，Traffic Mirroring 则为**自建/第三方**深度检测工具提供原始数据包

### 场景题解题思路

```
场景分析 → 判断 Traffic Mirroring 相关配置
├── "需要检查数据包实际内容/深度协议分析" → Traffic Mirroring
├── "需要主动拦截/阻断恶意流量" → 改用 Gateway Load Balancer（在线部署）
├── "只需要镜像特定端口/协议的流量" → 配置镜像过滤器
├── "镜像目标是一组可横向扩展的分析设备" → 目标选 NLB
├── "多账户/多 VPC 需要集中式流量安全监控" → 经 VPC Peering/Transit Gateway 镜像到中心化 VPC
├── "老旧实例类型无法配置 Traffic Mirroring" → 检查是否为 Nitro 系统实例（需支持 ENA）
├── "担心镜像流量产生高额数据传输成本" → 精细化过滤器 + 限制包长度 + 目标同 AZ 部署
└── "需要判断流量是否发生/被拒绝而非检查内容" → 改用 VPC Flow Logs（更轻量）
```

## 最佳实践

1. **优先配置镜像过滤器而非镜像全部流量**：既降低目标设备负载，也显著减少数据传输成本
2. **需要主动拦截能力时不要误用 Traffic Mirroring**：带外复制无法阻断流量，拦截场景应部署 Gateway Load Balancer
3. **大规模架构下使用 NLB 作为镜像目标**：便于横向扩展分析设备集群，避免单个 ENI 目标成为瓶颈
4. **确认参与镜像的实例均为 Nitro 系统类型**：规划安全监控架构前先核实实例类型兼容性，避免上线后才发现不支持
5. **尽量将镜像目标部署在与源相同的可用区**：减少跨 AZ 数据传输费用
6. **多账户/多 VPC 场景规划集中式安全监控 VPC**：通过 Transit Gateway 统一汇聚镜像流量，避免在每个 VPC 内重复部署分析设备
7. **将 Traffic Mirroring 定位为 Flow Logs 的补充而非替代**：常规可见性和访问审计仍以低开销的 Flow Logs 为主，仅在需要深度包检测时才引入 Traffic Mirroring
