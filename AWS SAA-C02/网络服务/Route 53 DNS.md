# Amazon Route 53 - DNS 服务

> **Amazon Route 53** 是一种高可用且可扩展的域名系统（DNS）服务，提供域名注册、DNS 解析、健康检查和多种高级流量路由策略，帮助用户构建高可用、低延迟的全球架构。
>
> 相关文档：[[VPC]] | [[CDN - CloudFront]] | [[AWS Load Balance]] | [[CloudWatch]]

---

## 核心功能

| 功能 | 说明 |
|------|------|
| **域名注册** | 可直接通过 Route 53 注册、管理和转移域名 |
| **DNS 管理** | 通过托管区域（Hosted Zone）管理域名的 DNS 记录 |
| **健康检查** | 持续监控端点可用性，配合路由策略自动排除不健康的目标 |
| **高级路由策略** | 支持多种路由策略，实现流量分发、就近访问、故障转移等 |
| **混合云集成** | 通过 Route 53 Resolver 实现本地数据中心与 VPC 之间的 DNS 互通 |

---

## 托管区域（Hosted Zone）

| 类型 | 说明 |
|------|------|
| **公有托管区域（Public）** | 管理可在公网访问的域名解析记录 |
| **私有托管区域（Private）** | 仅在关联的 [[VPC]] 内部生效，用于内部服务发现，不对公网暴露 |

> **考试要点**：私有托管区域可同时关联**多个 VPC**（包括跨账户），常用于混合云或多 VPC 架构下的内部域名解析。

## 路由策略 ^2a255f

### 策略总览（考试高频考点）

| 策略 | 说明 | 是否支持健康检查 | 典型场景 |
|------|------|:---:|---------|
| **简单路由（Simple）** | 单条记录返回一个或多个值，客户端随机选取 | ❌ | 单一资源、无需高可用的简单场景 |
| **加权路由（Weighted）** | 按设定权重比例分发流量 | ✅ | A/B 测试、蓝绿部署、灰度发布 |
| **延迟路由（Latency-based）** | 将请求路由到延迟最低的区域 | ✅ | 面向全球用户、优化响应速度 |
| **故障转移路由（Failover）** | 主/备模式，主记录不健康时自动切到备用记录 | ✅（必须） | 灾难恢复、主备架构 |
| **地理位置路由（Geolocation）** | 按用户所在的洲/国家/州划分并路由 | ✅ | 内容本地化、访问限制（合规） |
| **地理邻近路由（Geoproximity）** | 按资源与用户的地理位置路由，可通过 Bias 调整流量偏向 | ✅ | 需要通过 Traffic Flow 配置，精细调整区域流量占比 |
| **多值应答路由（Multivalue Answer）** | 返回多个健康记录（最多 8 个），客户端随机选择 | ✅ | 简单路由的增强版，兼顾基础的可用性检查 |
| **基于 IP 的路由（IP-based）** | 根据客户端 IP 所属的 CIDR 段路由 | ✅ | 按网络运营商/网络拓扑优化路由 |

### 常见混淆点

- **简单路由 vs 多值应答路由**：两者都可返回多个值，但只有多值应答路由支持**健康检查**，能自动剔除不健康的记录
- **地理位置路由 vs 延迟路由**：地理位置路由基于用户**物理位置**（用于合规/内容限制），延迟路由基于**网络延迟**（用于性能优化），两者目标不同，不能互相替代
- **地理邻近路由**需要使用 **Traffic Flow** 才能配置，且是唯一支持 **Bias** 参数（人为调整某区域吸引更多/更少流量）的策略

## 健康检查（Health Checks）

- 支持对 HTTP、HTTPS、TCP 端点进行监控，也可以监控其他健康检查的状态（**Calculated Health Check**）或 [[CloudWatch]] 告警
- 由分布在全球的健康检查器发起探测，通常连续多次失败后才判定为不健康，避免因单点网络抖动误判
- 健康检查失败的记录会被路由策略自动排除，直到恢复健康后重新纳入

> **考试要点**：故障转移路由**必须**配置健康检查，否则 Route 53 无法判断何时应切换到备用记录。

## Alias 记录 vs CNAME（考试高频考点）

| 特性 | Alias 记录 | CNAME |
|------|-----------|-------|
| **是否 Route 53 专有** | 是，AWS 对标准 DNS 的扩展 | 否，标准 DNS 记录类型 |
| **能否用于根域名（Zone Apex）** | ✅ 可以（如 `example.com`） | ❌ 不可以，DNS 标准限制 |
| **指向目标** | 只能指向 AWS 资源（ELB、CloudFront、S3 静态网站端点、API Gateway、VPC 端点、其他 Route 53 记录等） | 可指向任意域名 |
| **查询费用** | 指向 AWS 资源时免费 | 正常按查询计费 |
| **健康感知** | 自动感知目标资源状态变化 | 无 |

> **考试要点**：需要在**根域名**直接指向负载均衡器或 CloudFront 时，必须使用 **Alias 记录**，CNAME 无法满足这一需求。

## 混合云和全球可视化

### Route 53 Resolver

- 实现**本地数据中心**与 [[VPC]] 之间的双向 DNS 解析
- **入站端点（Inbound Endpoint）**：允许本地网络查询 VPC 内的私有域名
- **出站端点（Outbound Endpoint）**：允许 VPC 内资源将特定域名的查询转发到本地 DNS 服务器

### Route 53 Application Recovery Controller

- 提供跨区域的**就绪检查（Readiness Check）**和**路由控制（Routing Control）**，用于精细化管理多区域故障转移

---

## DNSSEC

- Route 53 支持为公有托管区域启用 **DNSSEC（域名系统安全扩展）**签名，防止 DNS 欺骗和缓存投毒攻击
- 需要在注册商和托管区域两端分别配置，启用后对递归解析器验证响应真实性

## 定价模型

| 计费项 | 说明 |
|--------|------|
| **托管区域费用** | 按每个托管区域每月计费 |
| **查询费用** | 按 DNS 查询次数计费（标准查询与延迟/地理位置等高级路由查询费率不同） |
| **健康检查费用** | 按健康检查数量和检查类型计费 |
| **域名注册/续费** | 按顶级域名（TLD）类型每年计费 |

> Alias 记录指向 AWS 资源（如 ELB、CloudFront）时的查询**不收费**。

## 考试重点总结

### SAA-C02 高频考点

1. **路由策略选择**：性能优化用延迟路由，合规/内容限制用地理位置路由，主备容灾用故障转移路由
2. **Alias vs CNAME**：根域名场景只能用 Alias，且指向 AWS 资源免费
3. **故障转移路由依赖健康检查**：没有健康检查就无法实现自动切换
4. **私有托管区域**：可关联多个 VPC，用于内部服务发现
5. **多值应答 vs 简单路由**：多值应答支持健康检查，简单路由不支持
6. **地理邻近路由**：唯一支持 Bias 偏向调整的策略，需通过 Traffic Flow 配置
7. **Route 53 Resolver**：解决混合云环境下的双向 DNS 解析问题

### 场景题解题思路

```
场景分析 → 选择路由策略
├── "希望用户访问延迟最低的区域" → 延迟路由
├── "按国家/地区限制或定制内容" → 地理位置路由
├── "需要主备容灾，自动切换" → 故障转移路由（配合健康检查）
├── "灰度发布/A-B 测试，按比例分流" → 加权路由
├── "需要人为调整某区域流量占比" → 地理邻近路由（Bias）
├── "根域名需要指向 ALB/CloudFront" → Alias 记录
├── "本地数据中心需要解析 VPC 内私有域名" → Route 53 Resolver 入站端点
└── "VPC 内资源需要查询本地私有域名" → Route 53 Resolver 出站端点
```

## 最佳实践

1. **根域名统一使用 Alias 记录**：兼容性更好且指向 AWS 资源免费
2. **故障转移路由必须配置健康检查**：否则无法实现自动切换
3. **多区域架构结合延迟路由 + 健康检查**：兼顾性能与可用性
4. **私有托管区域用于内部服务发现**：避免将内部域名暴露在公网
5. **合规场景使用地理位置路由**：明确设置默认记录，避免未覆盖地区无法解析
6. **混合云环境部署 Resolver 端点**：实现本地与云上 DNS 的双向互通
7. **为关键域名启用 DNSSEC**：防止 DNS 欺骗类攻击
