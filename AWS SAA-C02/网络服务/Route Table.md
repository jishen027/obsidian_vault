# Route Table - 路由表

> **路由表（Route Table）**是 [[VPC]] 中决定网络流量**去向**的核心组件——一组"目标 CIDR → 下一跳目标"的规则集合，[[Subnet]] 通过关联路由表来决定自己是公有还是私有、以及能访问哪些网络。理解路由表的关联规则、路由优先级和常见目标类型，是排查几乎所有"资源无法联网"类考题的第一步。
>
> 相关文档：[[VPC]] | [[Subnet]] | [[NAT Gateway]] | [[NAT Instance]] | [[Internet Gateway]] | [[VPC Peering]] | [[Virtual Private Gateway]] | [[Transit Gateway]] | [[Direct Connect]] | [[AWS Outposts]] | [[ENI]] | [[CIDR]] | [[VPC Endpoints]]

---

## 核心概念

### 路由表是什么

- 每条路由记录一个**目标（Destination，CIDR 格式）**和一个**目标位置（Target，下一跳）**，流量按目标地址匹配到对应的路由，被转发到指定的下一跳
- 路由表本身**不是防火墙**——它只负责"流量该往哪个方向走"，不做允许/拒绝判断（允许/拒绝分别由 [[NACL]] 和 [[Security Group]] 负责，三者共同决定一次网络请求能否成功）

### 主路由表 vs 自定义路由表（考试高频）

| 类型 | 特性 |
|------|------|
| **主路由表（Main Route Table）** | VPC 创建时**自动生成**，初始只包含本地路由；任何**未显式关联**自定义路由表的子网都会**隐式使用**主路由表 |
| **自定义路由表（Custom Route Table）** | 用户创建并**显式关联**到特定子网，用于实现与主路由表不同的路由策略（如区分公有/私有子网） |

> **考试陷阱**：**修改主路由表会影响所有仍隐式关联它的子网**——若某子网从未显式关联过自定义路由表，它会**自动跟随**主路由表的任何变更；题目描述"新建子网默认继承了整个 VPC 意料之外的路由行为" → 检查该子网是否遗漏了显式关联专属的自定义路由表，而误用了主路由表。

### 本地路由（Local Route，不可变）

- 每个路由表创建时都**隐式包含**一条指向 **VPC 自身完整 CIDR** 的本地路由，目标（Target）为 `local`
- 该路由**无法编辑或删除**，确保同一 VPC 内**所有子网之间默认可以互相通信**，不受路由表差异影响

---

## 路由表与子网的关联规则

- **一个子网必须关联且只能关联一个路由表**（要么隐式使用主路由表，要么显式关联某个自定义路由表）
- **一个路由表可以同时关联多个子网**——多个子网若需要相同的路由策略（如同属一批私有子网），可共享同一张自定义路由表，无需逐个重复配置
- 子网可以**随时更换**关联的路由表，切换是即时生效的（不影响子网本身的 CIDR 或其他配置）

> **考试要点**：题目描述"多个私有子网需要统一的出站策略，且未来新增子网也应自动沿用" → 创建**一张**自定义路由表，将所有相关私有子网关联到它，而非为每个子网各建一张路由表（增加不必要的管理复杂度）。

## 路由匹配逻辑：最长前缀匹配（考试高频）

- 当一次请求的目标地址能同时匹配路由表中的**多条**路由时，AWS **总是选择前缀最精确（子网掩码最长）**的那一条，而非按路由添加的先后顺序，[[CIDR]] 前缀长度的记法和计算方式详见 [[CIDR]] 独立笔记
- 例如：路由表中同时存在 `0.0.0.0/0 → IGW` 和 `10.0.1.0/24 → VPC Peering 连接`，目标为 `10.0.1.5` 的流量会匹配**更精确**的 `/24` 路由，走对等连接，而非默认路由

> **考试陷阱**：**"路由表中路由的先后顺序"不影响路由选择**——很多人误以为路由表和 [[NACL]] 一样按编号/顺序求值，实际上路由表**只看前缀精确度**，唯一的例外是 AWS 官方文档中"静态路由优先于通过 BGP 传播的动态路由"这条特殊优先级规则（同等前缀长度时）。

## 常见路由目标（Target）类型

| 目标类型 | 典型用途 |
|---------|---------|
| **[[Internet Gateway]] (IGW)** | 子网访问/被访问公网的路由，判定"公有子网"的核心依据，完整能力见 [[Internet Gateway]] 独立笔记 |
| **[[NAT Gateway]] / [[NAT Instance]]** | 私有子网实例的出站互联网访问，详见 [[NAT Gateway]] 和 [[NAT Instance]] 独立笔记 |
| **VPC Peering 连接** | 访问已建立对等连接的另一 VPC 的 CIDR 范围，需**双方**路由表都手动添加，详见 [[VPC Peering]] 独立笔记 |
| **Virtual Private Gateway (VGW)** | 访问通过 Site-to-Site VPN 连接的本地数据中心网络，详见 [[Virtual Private Gateway]] 独立笔记 |
| **[[Transit Gateway]]** | 访问通过 Transit Gateway 中转互联的其他 VPC/本地网络，支持传递路由（与 VPC Peering 的核心差异），完整能力见 [[Transit Gateway]] 独立笔记 |
| **网关型 [[VPC Endpoints\|VPC 终端节点]]（Gateway Endpoint）** | 私密访问 S3/DynamoDB，必须在路由表中显式添加终端节点路由才能生效（接口型终端节点不需要，走 ENI 私有 IP），完整对比见 [[VPC Endpoints]] 独立笔记 |
| **Egress-Only Internet Gateway** | IPv6 私有子网的仅出站访问，与 IPv4 场景下的 NAT Gateway 对应 |
| **本地网络接口（ENI）** | 将流量定向到特定实例（如自建的 NAT 实例、软件防火墙、入侵检测设备） |
| **本地网关（Local Gateway, LGW）** | [[AWS Outposts]] 子网访问本地站点网络的出口，角色类似 IGW 但面向本地局域网而非公网，完整能力见 [[AWS Outposts]] 独立笔记 |

## 路由传播（Route Propagation，考试提示）

- 当 [[Virtual Private Gateway]] 或 [[Direct Connect]] Gateway 通过 **BGP** 与本地网络交换动态路由时，可在路由表上启用**"路由传播（Route Propagation）"**，让对端通告的路由**自动**写入路由表，无需手动逐条添加
- 未启用路由传播时，管理员必须**手动**在路由表中维护指向本地网络的静态路由，本地网络拓扑变化时容易出现遗漏

> **考试要点**：题目描述"本地数据中心的网络拓扑经常变化，静态维护路由表容易出错/遗漏" → 启用路由表的**路由传播**并使用**基于 BGP 的动态 VPN**，而非依赖手动静态路由。

## 配额与限制

| 项目 | 默认值 |
|------|--------|
| **每个路由表的路由数上限** | 默认 **50 条**（不含本地路由和传播路由），可申请提升配额 |
| **每个 VPC 的路由表数量** | 有默认配额限制，可申请提升 |
| **子网与路由表的关联** | 1 个子网仅能关联 1 个路由表，1 个路由表可关联多个子网 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **区分公有/私有子网的出站策略** | 分别创建关联 IGW 和 NAT Gateway 的两张自定义路由表 |
| **多个子网需要共享同一套路由策略** | 关联到同一张自定义路由表，而非逐个重复配置 |
| **新建子网意外继承了非预期的路由行为** | 检查是否遗漏显式关联自定义路由表，误用了主路由表 |
| **VPC Peering 建立后仍无法互通** | 检查双方路由表是否都已添加指向对方 CIDR 的路由 |
| **私密访问 S3/DynamoDB** | 确认路由表中已添加网关型 VPC 终端节点的路由条目 |
| **本地网络拓扑频繁变化，静态路由难以维护** | 启用路由表的路由传播 + 基于 BGP 的动态 VPN |
| **需要判断多条匹配路由中哪条生效** | 前缀最精确（掩码最长）的路由优先，而非添加顺序 |

## 考试重点总结

### SAA-C02 高频考点

1. **路由表只负责流量方向，不做允许/拒绝判断**：允许/拒绝分别由 NACL 和 Security Group 负责
2. **主路由表自动生成，未显式关联的子网隐式使用它**：修改主路由表会波及所有隐式关联的子网
3. **本地路由不可编辑删除**：保证同一 VPC 内跨子网默认互通
4. **一个子网只能关联一个路由表，一个路由表可关联多个子网**：与 NACL 的关联模式一致
5. **最长前缀匹配决定路由优先级**：而非路由添加的先后顺序
6. **网关型 VPC 终端节点必须显式添加路由条目**：接口型终端节点走 ENI 私有 IP，无需修改路由表
7. **VPC Peering 需要双方手动添加路由**：建立连接本身不会自动更新任何一方的路由表
8. **路由传播让 BGP 动态路由自动写入路由表**：避免本地网络拓扑变化时手动维护路由遗漏
9. **每个路由表默认最多 50 条路由**（不含本地/传播路由）：可申请提升配额
10. **Transit Gateway 路由支持传递性，VPC Peering 不支持**：这是判断两者适用场景的核心依据，详见 [[VPC Peering]]

### 场景题解题思路

```
场景分析 → 判断路由表相关配置
├── "判断子网是公有还是私有" → 查看关联路由表是否有指向 IGW 的路由
├── "新建子网出现非预期的路由行为" → 检查是否误用了主路由表
├── "VPC Peering 建立后仍无法互通" → 检查双方路由表是否都添加了对方 CIDR 路由
├── "私密访问 S3/DynamoDB 失败" → 检查路由表是否已添加网关终端节点路由
├── "本地网络拓扑多变，路由维护困难" → 启用路由传播 + 动态 BGP VPN
├── "多条路由同时匹配，哪条生效" → 前缀最精确（掩码最长）的一条
├── "需要大规模多 VPC 互联并支持传递访问" → Transit Gateway（而非 VPC Peering）
└── "多个子网需要同一套出站策略" → 共享同一张自定义路由表
```

## 最佳实践

1. **避免依赖主路由表承载业务路由策略**：为公有/私有子网分别创建显式的自定义路由表，减少"意外继承"风险
2. **善用路由表的多对一关联能力**：功能相同的子网共享同一张路由表，而非逐个重复配置
3. **变更路由表前排查所有关联子网**：一次修改可能同时影响多个业务，尤其是主路由表
4. **VPC Peering/Transit Gateway 部署后立即核对双方路由表**：连接建立成功不代表流量已能互通
5. **本地网络接入场景优先启用路由传播 + BGP 动态路由**：减少人工维护静态路由的出错概率
6. **规划路由数量时预留配额余量**：大型架构涉及多个 Peering/终端节点/VGW 路由时，提前评估是否接近 50 条默认上限
7. **排查"资源无法联网"问题时按路由表 → NACL → Security Group 顺序逐层检查**：路由决定"能不能到"，NACL/Security Group 决定"允不允许"，两者缺一不可
