# Amazon QuickSight - 商业智能可视化服务

> **Amazon QuickSight** 是全托管、无服务器的**商业智能（BI）**服务，让用户能够从多种数据源构建**交互式仪表盘、可视化图表和数据故事**，并通过**自动伸缩、按使用量计费**的方式服务从个人到组织级的大规模用户，无需部署或运维任何 BI 服务器。
>
> 相关文档：[[Redshift]] | [[Amazon Athena]] | [[Amazon EMR]] | [[AWS Glue]] | [[RDS]] | [[Aurora]] | [[S3]] | [[Amazon Timestream]] | [[Amazon OpenSearch]] | [[IAM]]

---

## 核心概念

### 为什么需要 QuickSight

- **传统 BI 工具的短板**：自建 BI 服务器（如 Tableau Server、自托管 BI 工具）需要预置固定容量、承担闲时的资源浪费，且难以应对使用高峰（如月末报表集中查看）时的并发压力
- **QuickSight 的核心价值**：**无服务器架构**自动应对负载波动，按**访问会话（Session）**或**用户订阅**计费，无需为闲置容量付费；作为 AWS 数据分析生态的"最后一公里"，把 [[Redshift]]/[[Amazon Athena]]/RDS 等服务中的数据转化为业务用户可直接消费的可视化洞察
- **在数据分析管道中的定位**：QuickSight 通常是数据处理链路的**终点**——数据经过 [[Amazon EMR]]/[[AWS Glue]] 处理、存储在 S3/Redshift，最终通过 QuickSight 呈现给业务决策者，而非数据处理的中间环节

### QuickSight 在数据分析服务中的定位（考试要点）

| 服务 | 类型 | 核心能力 | 典型场景 |
|------|------|---------|---------|
| **QuickSight** | 无服务器 BI 可视化 | 交互式仪表盘、自然语言问答、嵌入式分析 | 业务报表、高管仪表盘、面向终端用户的数据可视化 |
| [[Amazon Athena]] | 无服务器 SQL 查询 | 对 S3 数据跑 SQL | 探索性 SQL 查询，通常作为 QuickSight 的数据源之一 |
| [[Redshift]] | 数据仓库（OLAP） | 复杂关联查询、聚合分析 | 长期稳定的数据仓库，通常作为 QuickSight 的底层数据源 |
| Amazon EMR | 大数据处理平台 | Spark/Hadoop 复杂 ETL | 数据处理链路的上游环节，处理结果供 QuickSight 可视化 |

> **考试陷阱**：题目描述**"需要为业务用户构建交互式仪表盘、图表，供决策使用"** → 答案是 **QuickSight**，而非 Athena/Redshift 本身——**Athena/Redshift 负责查询和存储数据，QuickSight 负责把查询结果转化为可视化界面**，题目若只强调"查询"而非"可视化呈现"，则不一定需要 QuickSight。

## 数据源与连接方式

### 支持的数据源

| 数据源类别 | 示例 |
|-----------|------|
| **AWS 原生数据源** | [[Redshift]]、[[Amazon Athena]]（S3 数据湖）、[[RDS]]/[[Aurora]]、[[Amazon Timestream]]、[[Amazon OpenSearch]] |
| **第三方/SaaS 数据源** | Salesforce、Jira、ServiceNow 等 |
| **本地数据源** | 通过 **QuickSight VPC 连接**访问私有网络内的本地数据库 |
| **文件上传** | 直接上传 CSV/Excel/JSON 等文件 |

### 两种查询模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **直接查询（Direct Query）** | 每次刷新仪表盘时实时查询底层数据源 | 数据变化频繁，要求仪表盘反映最新数据 |
| **SPICE（内存优化计算引擎）** | 将数据导入 QuickSight 专有的**内存计算引擎**，查询直接在 SPICE 中完成，无需每次访问底层数据源 | 需要极快的仪表盘交互响应速度，减轻底层数据源查询压力 |

> **考试要点**：**SPICE 是 QuickSight 性能优化的核心**——数据被导入 SPICE 后，仪表盘的查询、筛选、钻取等交互都在内存中完成，响应速度远快于每次直接查询数据源；题目问"仪表盘交互卡顿、底层数据库查询压力过大" → 答案通常是启用/配置 **SPICE**，通过定时刷新而非每次交互都直接查询源数据库。

## 用户模型与定价

| 角色 | 权限 | 计费模式 |
|------|------|---------|
| **作者（Author）** | 创建、编辑数据集和仪表盘 | 按月/按会话订阅付费 |
| **读者（Reader）** | 仅查看已发布的仪表盘，可交互筛选但不能编辑 | **按访问会话（Session-based）**付费，无固定坐席成本，成本随实际使用量弹性变化 |

> **考试要点**：**Reader 角色按会话付费**是 QuickSight 面向大规模只读用户群（如全公司数千名员工查看报表）的成本优化关键——相比传统 BI 工具的固定坐席授权模式，大幅降低了向组织内广泛用户开放报表访问的成本。

## 生成式 BI：Amazon Q in QuickSight

- 基于 **Amazon Bedrock** 大语言模型，支持通过**自然语言**提问直接获得数据洞察（Q&A），无需手动构建查询或图表
- **执行摘要（Executive Summaries）**：自动生成仪表盘的文字洞察摘要，帮助决策者快速抓住关键信息
- **自然语言仪表盘创作**：通过自然语言描述即可生成可视化图表和复杂计算字段，降低非技术用户创建仪表盘的门槛
- **多可视化问答（Multi-Visual Q&A）**：可嵌入到自建应用中，让终端用户通过自然语言探索数据

---

## 嵌入式分析（Embedded Analytics）

- 支持将 QuickSight 仪表盘/可视化组件**嵌入到自建 Web 应用**中，面向应用的终端用户（而非仅限 AWS 控制台内部用户）提供数据可视化能力
- 常用于 **SaaS 应用**为自己的客户提供内嵌的数据分析功能，无需自建可视化前端
- 支持**匿名用户嵌入（Anonymous Embedding）**和**已注册用户嵌入（Registered User Embedding）**两种模式，适配公开访问和身份认证场景

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 权限控制** | 控制用户对 QuickSight 资源（数据集、分析、仪表盘）的访问和管理权限 |
| **行级安全（Row-Level Security, RLS）** | 基于用户身份动态过滤数据行，实现"不同用户看到同一仪表盘但数据范围不同"的多租户/部门隔离场景 |
| **列级安全（Column-Level Security, CLS）** | 限制特定用户对敏感列（如薪资、PII）的访问 |
| **VPC 连接** | 通过 [[VPC]] 连接访问私有子网中的数据源，无需将数据库暴露公网 |
| **静态加密** | SPICE 中的数据默认加密存储 |

| 场景 | 推荐配置 |
|------|---------|
| **高管/业务报表仪表盘** | Redshift/Athena 作为数据源 + QuickSight SPICE |
| **面向全公司大规模只读用户的报表** | QuickSight Reader（按会话计费），控制大规模授权成本 |
| **SaaS 应用内嵌数据分析功能** | QuickSight 嵌入式分析（Embedded Analytics） |
| **多租户/多部门的数据隔离展示** | QuickSight 行级安全（RLS） |
| **业务用户通过自然语言探索数据** | Amazon Q in QuickSight |
| **仪表盘交互响应慢、底层数据库压力大** | 启用 SPICE，定时刷新而非每次直接查询 |
| **IoT/时序监控数据可视化** | [[Amazon Timestream]]/CloudWatch + QuickSight |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：无服务器 BI 可视化服务，是数据分析管道的呈现层，而非数据处理或存储层
2. **判断依据**：题目强调"可视化呈现、仪表盘、供决策使用"时选 QuickSight；仅强调"查询/存储"时看具体是 Athena/Redshift/RDS
3. **SPICE 引擎**：内存优化计算引擎，导入数据后查询在内存完成，大幅提升交互响应速度、减轻源数据库压力
4. **直接查询 vs SPICE**：数据需要实时反映选直接查询；追求交互性能、减轻源库压力选 SPICE
5. **两种用户角色**：Author（创建编辑，订阅付费）vs Reader（只读，按会话付费）
6. **Reader 按会话计费**：面向大规模只读用户群时显著降低成本，是"如何低成本向全公司开放报表"的标准答案
7. **行级安全（RLS）**：同一仪表盘按用户身份动态过滤数据行，实现多租户/部门数据隔离
8. **嵌入式分析**：可将仪表盘嵌入自建应用，服务应用终端用户而非仅 AWS 控制台用户
9. **Amazon Q in QuickSight**：基于 Bedrock 的生成式 BI，支持自然语言问答和仪表盘创作
10. **支持广泛数据源**：Redshift/Athena/RDS/Aurora 等 AWS 原生源，以及第三方 SaaS 和本地数据源（通过 VPC 连接）

### 场景题解题思路

```
场景分析 → 判断是否用 QuickSight
├── "需要为业务用户构建交互式仪表盘/图表" → Amazon QuickSight
├── "仪表盘交互卡顿，底层数据库查询压力大" → 启用 SPICE，定时刷新而非每次直连数据源
├── "需要向全公司数千名只读用户开放报表，控制成本" → QuickSight Reader（按会话计费）
├── "不同用户查看同一仪表盘应看到不同范围的数据" → 行级安全（RLS）
├── "SaaS 应用需要为自己的客户提供内嵌数据分析功能" → QuickSight 嵌入式分析
├── "业务用户希望用自然语言直接提问获得数据洞察" → Amazon Q in QuickSight
├── "需要访问私有子网内的本地数据库做可视化" → QuickSight VPC 连接
└── "只需要查询/处理数据，不需要可视化呈现" → 使用 Athena/Redshift/EMR 本身，无需引入 QuickSight
```

## 最佳实践

1. **追求交互性能时优先启用 SPICE**：减少对底层数据源的重复查询压力，提升仪表盘响应速度
2. **大规模只读用户群体优先使用 Reader 角色**：按会话付费比固定坐席订阅更具成本优势
3. **多租户/多部门场景使用行级安全而非创建多份仪表盘**：降低维护成本，同一份仪表盘服务不同权限用户
4. **敏感字段启用列级安全**：如薪资、PII 数据，避免通过仪表盘意外暴露给无权限用户
5. **面向应用终端用户的场景优先使用嵌入式分析**：而非重复造轮子自建可视化前端
6. **本地数据源接入使用 VPC 连接**：避免为满足 QuickSight 访问而将数据库暴露公网
7. **数据处理链路遵循分层原则**：EMR/AWS Glue 处理 → S3/Redshift 存储 → QuickSight 呈现，职责分离更利于维护
8. **评估 Amazon Q 降低非技术用户门槛**：让业务用户通过自然语言直接创建分析和获取洞察，减少对数据团队的依赖
