# AWS Database Migration Service (DMS) - 数据库迁移服务

> **AWS Database Migration Service（DMS）**是全托管的数据库迁移服务，支持将数据库迁移到 AWS（或在 AWS 内部的数据库之间迁移），且**源数据库在迁移过程中通常可以继续对外提供服务**，最大限度降低停机时间。DMS 只负责**数据本身**的迁移和持续复制——当源和目标是**不同数据库引擎**（异构迁移）时，还需要搭配 **AWS Schema Conversion Tool（SCT）**先完成表结构、视图、存储过程等**模式（Schema）**层面的转换，两者分工明确、缺一不可。
>
> 相关文档：[[RDS]] | [[Aurora]] | [[Redshift]] | [[DynamoDB]] | [[S3]] | [[AWS DataSync]] | [[Amazon AppFlow]] | [[AWS Elastic Disaster Recovery]] | [[AWS Application Discovery Service]] | [[Disaster Recovery On AWS]]

## 核心概念

### 为什么需要 DMS

- **停机窗口是数据库迁移的最大痛点**：直接导出再导入通常需要长时间停机，业务无法接受
- **DMS 的核心价值**：先做一次**全量加载（Full Load）**，再通过**持续复制（CDC）**追平全量加载期间产生的新变更，让源库和目标库**持续保持同步**，直到业务选择合适的时间窗口一次性割接，把停机时间压缩到分钟级甚至接近零

### 复制实例（Replication Instance）

- DMS 迁移任务运行在一个**基于 EC2 的复制实例**上，负责连接源/目标端点、执行迁移任务、缓存迁移过程中的日志
- 支持配置为 **Multi-AZ**：提升的是**迁移任务本身的可用性**（复制实例故障时自动切换），而非数据库本身的高可用——不要将其与 [[RDS]]/[[Aurora]] 的 Multi-AZ 混淆

### 迁移任务的三种模式（考试高频）

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **仅全量加载（Full Load）** | 一次性迁移源库当前的全部数据 | 源库可以接受停机，或数据静态不再变化 |
| **全量加载 + CDC** | 先全量加载，再持续捕获并同步加载期间及之后的增量变更 | **绝大多数生产迁移场景的标准选择**——业务持续运行，最终选择低峰期完成割接 |
| **仅 CDC** | 目标库已通过其他方式预置了截至某个时间点的数据（如从备份恢复），DMS 只负责追平之后的增量变更 | 目标库已有基线数据（如从快照/备份恢复），只需补齐增量 |

> **考试要点**：**题目描述"业务不能停机，需要在数据持续变化的情况下完成数据库迁移"** → **全量加载 + CDC**是标准答案；题目描述"已经用备份把目标库恢复到某个时间点，现在只想同步之后的变更" → **仅 CDC**模式，避免重复全量加载浪费时间。

### 同构迁移 vs 异构迁移（考试陷阱）

| 类型 | 定义 | 是否需要 SCT |
|------|------|-------------|
| **同构迁移（Homogeneous）** | 源和目标是**相同的数据库引擎**（如 MySQL → MySQL，Oracle → Oracle） | **不需要**——表结构直接兼容 |
| **异构迁移（Heterogeneous）** | 源和目标是**不同的数据库引擎**（如 Oracle → Aurora PostgreSQL，SQL Server → MySQL） | **需要**——必须先用 SCT 转换 Schema |

> **考试陷阱**：**DMS 本身不做 Schema/存储过程/视图的转换，只搬运数据**——题目描述"需要将 Oracle 数据库迁移到 Aurora PostgreSQL，且包含大量存储过程和自定义函数" → 必须**先用 AWS Schema Conversion Tool 转换 Schema，再用 DMS 迁移数据**，两步缺一不可；很多人误以为 DMS 能一站式完成异构迁移的全部工作。
>
> **考试要点**：**同构迁移场景下，AWS 官方建议优先考虑数据库引擎原生的复制/导出导入工具**（如 MySQL 原生复制、`mysqldump`、RDS 快照跨区域复制），DMS 更适合**异构迁移**或**需要持续复制、最小化停机**的场景，而非"只要是数据库迁移就无脑用 DMS"。

## AWS Schema Conversion Tool（SCT）

- **只负责 Schema 层面的转换**：表结构、索引、视图、存储过程、函数等数据库对象，将源引擎的语法**自动转换**为目标引擎兼容的等价形式
- 无法自动转换的部分（复杂的存储过程/自定义逻辑）会被标记出来，需要**人工介入**手动改写
- **典型流程**：SCT 转换 Schema → 在目标库应用转换后的 Schema → DMS 执行全量加载 + CDC 迁移实际数据

---

## 灵活的源/目标端点

- **源端**：不仅限于自建/云上的关系型数据库，也支持 [[DynamoDB]] 等非关系型数据库作为源或目标
- **目标端不仅限于数据库**：DMS 也可以将数据持续复制到 [[S3]]、[[Redshift]]、Kinesis Data Streams、OpenSearch 等**非数据库目标**，是构建**数据湖/数据仓库持续摄取管道**的常见工具，而不只是"一次性搬家"工具

> **考试要点**：题目描述"需要将 [[RDS]]/[[DynamoDB]] 中的数据持续同步到 [[Redshift]] 或 [[S3]] 做分析" → DMS 的持续复制（CDC）能力同样适用，这是它区别于"仅用于一次性迁移"这类刻板印象的重要考点。

## 与相关服务的边界（考试陷阱）

| 服务 | 迁移/同步对象 | 与 DMS 的关系 |
|------|--------------|---------------|
| **[[AWS DataSync]]** | **文件/对象**数据（本地文件系统 ↔ S3/EFS/FSx） | 完全不同的对象类型——数据库迁移场景不应使用 DataSync，完整边界见 [[AWS DataSync]] 独立笔记 |
| **[[AWS Elastic Disaster Recovery]]** | **整台服务器**（操作系统 + 应用 + 数据库）的块级复制 | 面向灾难恢复/服务器级迁移，粒度比 DMS 粗得多，不做数据库内部的 Schema 感知，完整能力见 [[AWS Elastic Disaster Recovery]] 独立笔记 |
| **RDS/Aurora 原生跨区域只读副本** | 同引擎数据库的**只读副本** | 适合同构、无需转换的场景，运维更简单；DMS 更适合异构迁移或需要一次性割接到新账号/新引擎的场景 |

> **考试陷阱**：**"迁移数据库"不等于自动联想到 DMS**——若题目描述的是迁移本地文件到 S3，答案是 [[AWS DataSync]]；若描述的是迁移整台服务器（含操作系统），答案是 [[AWS Elastic Disaster Recovery]] 或 Application Migration Service；只有明确是**数据库到数据库**（或数据库到数据仓库/数据湖）的数据搬迁，才对应 DMS。

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **将本地 Oracle 数据库迁移到 Aurora PostgreSQL，且业务不能长时间停机** | AWS SCT 转换 Schema + DMS 全量加载 + CDC |
| **相同引擎（如 MySQL → MySQL）之间的简单迁移** | 优先评估数据库原生复制/导出导入工具，DMS 作为备选 |
| **目标库已从备份恢复到某个时间点，只需同步之后的增量** | DMS 仅 CDC 模式 |
| **需要将 RDS/DynamoDB 数据持续同步到 Redshift/S3 做分析** | DMS 持续复制（CDC）到非数据库目标 |
| **迁移涉及大量自定义存储过程和触发器的异构数据库** | 先用 SCT 转换并人工修正无法自动转换的部分，再用 DMS 迁移数据 |
| **需要迁移整台数据库服务器（含操作系统本身）** | 改用 [[AWS Elastic Disaster Recovery]]（服务器级复制），而非 DMS |

## 考试重点总结

### SAA-C02 高频考点

1. **DMS 只迁移数据，不转换 Schema**：异构迁移必须先用 AWS Schema Conversion Tool（SCT）转换表结构、视图、存储过程
2. **同构迁移不需要 SCT**：源和目标引擎相同时，表结构天然兼容
3. **三种迁移模式**：仅全量加载、全量加载 + CDC（最常用）、仅 CDC（目标已有基线数据）
4. **全量加载 + CDC 是最小化停机的标准做法**：迁移过程中源库持续可用，最后再择机完成割接
5. **复制实例的 Multi-AZ 提升的是迁移任务本身的可用性**：不是数据库的高可用，不要混淆
6. **DMS 目标端不限于数据库**：可持续复制到 S3、Redshift、Kinesis、OpenSearch，用于数据湖/数仓摄取管道
7. **同构迁移场景优先考虑数据库原生工具**：DMS 并非所有数据库迁移场景的默认最优解
8. **DMS 不等于 AWS DataSync**：DataSync 处理文件/对象数据，DMS 处理数据库
9. **DMS 不等于 AWS Elastic Disaster Recovery**：DRS 是服务器级块复制，DMS 是数据库内部的数据/Schema 级迁移
10. **DMS 支持源/目标为 DynamoDB 等非关系型数据库**：不局限于传统关系型数据库之间的迁移

### 场景题解题思路

```
场景分析 → 判断 Database Migration Service 相关配置
├── "业务不能停机，需要在数据持续变化中完成数据库迁移" → DMS 全量加载 + CDC
├── "异构数据库迁移，包含大量存储过程/自定义函数" → 先用 SCT 转换 Schema，再用 DMS 迁移数据
├── "目标库已从备份恢复到某个时间点，只需补齐增量" → DMS 仅 CDC 模式
├── "相同引擎之间的简单迁移" → 优先评估数据库原生工具，而非默认选 DMS
├── "需要把数据库数据持续同步到 Redshift/S3 做分析" → DMS 持续复制到非数据库目标
├── "需要迁移的是本地文件而非数据库" → AWS DataSync（而非 DMS）
└── "需要迁移整台服务器（含操作系统）" → AWS Elastic Disaster Recovery（而非 DMS）
```

## 最佳实践

1. **异构迁移前务必先用 SCT 评估转换复杂度**：提前识别无法自动转换的存储过程/自定义逻辑，预留人工改写时间
2. **生产迁移优先选择"全量加载 + CDC"模式**：避免为了停机窗口牺牲业务连续性
3. **同构迁移先评估数据库原生工具**：只有在需要持续复制、最小化停机或目标引擎不同的场景才引入 DMS
4. **迁移完成后使用 DMS 的数据校验功能核对源目标一致性**：不要仅凭"任务显示完成"就认为迁移绝对无误
5. **复制实例按迁移数据量和并发任务数合理选择规格**：避免大规模迁移时复制实例本身成为瓶颈
6. **善用 DMS 持续复制能力构建数据湖摄取管道**：不要把 DMS 局限于"一次性迁移工具"的固有印象
7. **明确 DMS 与 DataSync、AWS Elastic Disaster Recovery 的边界**：按迁移对象的粒度（文件/数据库/整机）正确选型，避免张冠李戴
