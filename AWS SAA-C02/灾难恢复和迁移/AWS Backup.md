# AWS Backup - 集中化备份管理服务

> **AWS Backup** 是**集中化、策略驱动**的备份管理服务，让用户在**一个地方**为 [[EBS]]、[[RDS]]/[[Aurora]]、[[DynamoDB]]、[[AWS EFS]]、[[AWS FSx]]、[[Amazon DocumentDB]]、Amazon Neptune、[[Redshift]]、S3、Storage Gateway 卷、EC2/VMware 等**几乎所有存储和数据库服务**统一定义备份计划、生命周期和跨区域/跨账号复制策略，而不需要为每个服务单独编写和维护备份脚本。它是 [[Disaster Recovery On AWS]] 笔记中"**备份恢复（Backup & Restore）**"策略的标准落地工具，也是应对**勒索软件**等账户级威胁的关键防线（通过跨账号复制和不可变的 Vault Lock）。
>
> 相关文档：[[Disaster Recovery On AWS]] | [[EBS]] | [[RDS]] | [[Aurora]] | [[DynamoDB]] | [[AWS EFS]] | [[AWS FSx]] | [[Amazon DocumentDB]] | [[Redshift]] | [[S3]] | [[KMS]] | [[AWS Organizations]] | [[Amazon GuardDuty]]

## 核心概念

### 为什么需要 AWS Backup

- **分散管理的痛点**：不使用 AWS Backup 时，每个服务的备份策略（快照计划、保留期、跨区域复制）需要**各自独立配置**，规则不统一、审计困难、容易遗漏
- **AWS Backup 的核心价值**：提供**统一的策略层**，一次定义备份计划即可应用到跨服务、跨账号、跨区域的所有目标资源，并配合审计工具持续验证合规性

### 三大核心组件

| 组件 | 作用 |
|------|------|
| **备份计划（Backup Plan）** | 定义**何时**备份（调度频率、备份窗口）、**保留多久**（生命周期规则，如 N 天后转入冷存储、M 天后过期删除）、**备份到哪个 Vault** |
| **备份保管库（Backup Vault）** | 存储恢复点（Recovery Point）的逻辑容器，使用 **[[KMS]]** 密钥加密，可对 Vault 设置访问策略控制谁能读取/删除其中的恢复点 |
| **资源分配（Resource Assignment）** | 通过**标签**或**显式资源 ID**，将实际资源（某个 RDS 实例、某个 EFS 文件系统等）关联到备份计划——新增符合标签规则的资源会**自动**被纳入备份范围 |

> **考试要点**：**基于标签的资源分配是"确保新资源自动纳入备份"的标准做法**——题目描述"团队经常创建新的 RDS 实例，希望它们都能自动被现有备份策略覆盖，而不需要每次手动添加" → 使用**标签**关联备份计划，而非逐个手动指定资源 ID。

## 备份保管库锁（Vault Lock，考试高频）

- 对 Backup Vault 启用 **Vault Lock** 后，其中的备份策略（保留期等）变为**不可篡改**——即使是**账户 Root 用户**或 **AWS 自身**，在锁定生效后也**无法缩短保留期或提前删除**恢复点
- 两种模式：
  - **治理模式（Governance Mode）**：具备特定权限的用户仍可在一定条件下解锁或覆盖策略，适合内部治理场景
  - **合规模式（Compliance Mode）**：**任何人（包括 Root 和 AWS）都无法覆盖**，一旦锁定即不可逆，专为满足监管合规要求设计
- **考试陷阱**：**Vault Lock 的合规模式是防范"内部人员或攻击者删除备份"的终极手段**——题目描述"担心攻击者获取账户权限后删除所有备份以勒索企业" → 启用 **Vault Lock 合规模式**，确保即使账户被攻破，备份也无法被删除或缩短保留期。

---

## 逻辑气隙保管库（Logically Air-Gapped Vault，考试提示）

- 一种特殊的 Backup Vault，物理上位于 **AWS 管理的独立账户环境**中，与用户自己的账户**逻辑隔离**
- 即使用户的**主账户完全被攻破**（勒索软件加密、凭证泄露、内部人员恶意删除），存放在逻辑气隙保管库中的恢复点依然**不受影响**，需要通过独立的恢复流程才能取回
- 是应对"账户级别沦陷"这一最坏场景的最高等级防护，[[Amazon Neptune]] 等服务已支持将备份纳入逻辑气隙保管库

> **考试要点**：**普通跨账号备份复制 vs 逻辑气隙保管库的区别**——普通跨账号复制仍需要用户自行管理目标账号的权限边界；逻辑气隙保管库由 **AWS 托管**目标环境，进一步降低"备份账号也被一并攻破"的风险，适合对勒索软件防护要求最高的场景。

## 与 Amazon GuardDuty 的集成：恢复前恶意软件扫描

- **Malware Protection for AWS Backup**（[[Amazon GuardDuty]] 的能力模块）可在**恢复操作执行前**扫描备份数据中的恶意软件
- **考试要点**：题目描述"担心从备份恢复时把已潜伏的恶意软件一并带回生产环境" → 启用 **GuardDuty Malware Protection for AWS Backup**，在恢复前拦截被污染的恢复点，而不是恢复后再排查，完整能力见 [[Amazon GuardDuty]] 独立笔记。

## AWS Backup Audit Manager（合规审计）

- 持续根据预定义的**控制规则（Control）**（如"每个资源必须在 X 小时内完成一次备份"、"备份必须启用跨区域复制"）自动评估账户内的备份活动是否合规
- 生成**合规评分报告**，可用于满足内部治理或外部监管审计要求，无需手动逐个资源核对备份状态

---

## 恢复测试（Restore Testing）

- 支持配置**定期自动化的恢复测试计划**，从恢复点实际发起一次恢复操作并验证结果，而不是仅确认"备份任务显示成功"
- **考试要点**：**"备份成功"不等于"能够恢复"**——题目描述"需要验证备份的实际可恢复性，而不只是确认备份任务本身没有报错" → 配置 Restore Testing 定期做真实恢复演练，这也是 [[Disaster Recovery On AWS]] 笔记中"DR 方案需要定期演练"最佳实践的具体工具。

---

## 组织级集中管理

- 结合 **[[AWS Organizations]]** 的**备份策略（Backup Policies）**，可在组织管理账户层面**集中定义并强制**成员账户遵循统一的备份计划，避免个别账户遗漏配置备份，完整机制见 [[AWS Organizations]] 独立笔记
- 支持**跨账号备份复制**：将恢复点复制到组织内的另一个专用备份账号，进一步降低单账户被攻陷导致备份一并丢失的风险

## 支持的资源范围（覆盖面广，非仅存储服务）

| 类别 | 支持的服务 |
|------|-----------|
| **计算** | EC2 实例、VMware 虚拟机（通过 AWS Backup 网关） |
| **块/文件存储** | [[EBS]]、[[AWS EFS]]、[[AWS FSx]]、Storage Gateway 卷 |
| **关系型/NoSQL 数据库** | [[RDS]]、[[Aurora]]、[[DynamoDB]]、[[Amazon DocumentDB]]、Amazon Neptune |
| **数据仓库** | [[Redshift]] |
| **对象存储** | [[S3]] |

> **考试要点**：**AWS Backup 不是"只管存储服务"**——它同样覆盖数据库和计算层资源，题目描述"需要为组织内 RDS、DynamoDB、EFS 等多种资源类型统一制定备份策略"时，AWS Backup 是标准答案，而非为每种资源单独设计方案。

---

## 定价（考试提示）

- **服务本身的编排/管理功能不额外收费**
- 实际成本来自：**备份存储的用量**（区分"热"备份存储和转入冷存储后的用量）、**跨区域/跨账号复制产生的数据传输费**
- 生命周期规则（如"30 天后转冷存储，180 天后过期删除"）是控制长期存储成本的关键手段

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **需要跨 RDS/DynamoDB/EFS 等多种服务统一管理备份策略** | AWS Backup 备份计划 + 标签资源分配 |
| **担心攻击者获取账户权限后删除全部备份进行勒索** | Backup Vault Lock（合规模式） |
| **需要防范整个主账户被攻陷导致备份一并丢失** | 逻辑气隙保管库 / 跨账号备份复制 |
| **担心从备份恢复时带回潜伏的恶意软件** | GuardDuty Malware Protection for AWS Backup |
| **需要验证备份是否真的可以恢复，而非只看任务状态** | 配置 Restore Testing 定期自动化恢复演练 |
| **组织内多个成员账户需要统一强制执行备份合规要求** | AWS Organizations 备份策略 + Backup Audit Manager |
| **新创建的资源需要自动纳入现有备份策略** | 基于标签的资源分配，而非手动逐个添加 |

## 考试重点总结

### SAA-C02 高频考点

1. **AWS Backup 是集中化的备份策略编排层**：覆盖 EBS/RDS/Aurora/DynamoDB/EFS/FSx/DocumentDB/Neptune/Redshift/S3 等几乎全部存储和数据库服务
2. **三大组件**：备份计划（何时/保留多久）、备份保管库（存储位置+加密）、资源分配（标签或显式 ID）
3. **基于标签的资源分配可自动覆盖新建资源**：无需手动逐个添加
4. **Vault Lock 合规模式一旦生效不可逆**：即使 Root 或 AWS 自身也无法缩短保留期或删除恢复点
5. **逻辑气隙保管库防范账户级沦陷**：备份存放在 AWS 托管的独立隔离环境，主账户被攻破也不受影响
6. **GuardDuty Malware Protection for AWS Backup 在恢复前扫描恶意软件**：避免把潜伏威胁一并恢复回生产环境
7. **Restore Testing 验证真实可恢复性**：备份任务成功不等于恢复一定成功
8. **AWS Backup Audit Manager 持续评估备份合规性**：自动生成合规评分报告
9. **可结合 AWS Organizations 备份策略实现组织级强制执行**：避免个别成员账户遗漏配置
10. **是"备份恢复（Backup & Restore）"DR 策略的标准实现**：完整的 DR 策略谱系见 [[Disaster Recovery On AWS]]

### 场景题解题思路

```
场景分析 → 判断 AWS Backup 相关配置
├── "需要跨多种服务统一管理备份策略" → AWS Backup 备份计划
├── "新建资源需自动纳入备份范围" → 基于标签的资源分配
├── "担心攻击者删除全部备份进行勒索" → Vault Lock（合规模式）
├── "担心主账户整体被攻陷导致备份也丢失" → 逻辑气隙保管库 / 跨账号复制
├── "担心恢复时带回潜伏的恶意软件" → GuardDuty Malware Protection for AWS Backup
├── "需要验证备份真的可恢复" → Restore Testing
├── "组织内多账户需要统一强制备份合规" → Organizations 备份策略 + Backup Audit Manager
└── "需要长期低成本保留备份，同时控制存储成本" → 生命周期规则（转冷存储 + 过期删除）
```

## 最佳实践

1. **优先使用标签而非显式资源 ID 分配备份计划**：确保团队新建的资源自动被现有策略覆盖
2. **对关键业务的备份保管库启用 Vault Lock 合规模式**：防范账户被攻陷后备份被一并删除
3. **高价值/强合规要求的场景评估逻辑气隙保管库**：作为跨账号复制之外更高等级的隔离防护
4. **启用 GuardDuty Malware Protection for AWS Backup**：在恢复前拦截被污染的恢复点，而非恢复后才发现问题
5. **定期配置 Restore Testing 而非仅信任备份任务的成功状态**：只有真实做过恢复验证的备份才是可信的备份
6. **多账户组织使用 Organizations 备份策略统一强制执行**：结合 Backup Audit Manager 持续监控合规状况
7. **合理设计生命周期规则平衡成本与保留需求**：避免长期保留全部热存储备份导致成本失控
8. **将 AWS Backup 定位为"备份恢复"策略的基础设施，而非唯一的 DR 手段**：更高的可用性/恢复速度需求仍需评估 [[Disaster Recovery On AWS]] 笔记中的引导恢复/温备份/多活等策略
