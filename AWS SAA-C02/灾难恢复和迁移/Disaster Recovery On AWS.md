# Disaster Recovery on AWS - AWS 灾难恢复策略

> **灾难恢复（Disaster Recovery, DR）**是指为应对**区域级重大故障**（自然灾害、区域性服务中断、大规模误操作）而提前准备的恢复方案，核心是在**成本**与**恢复速度**之间做权衡。AWS Well-Architected 框架定义了四种由轻到重的标准 DR 策略——**备份恢复（Backup & Restore）→ 引导恢复（Pilot Light）→ 温备份（Warm Standby）→ 多活（Multi-Site Active/Active）**——策略越靠后，**恢复越快、成本越高**。选择哪种策略完全取决于业务能接受的 **RTO（恢复时间目标）**和 **RPO（恢复点目标）**，而非"预算无限就无脑选最贵的"。
>
> 相关文档：[[AWS Elastic Disaster Recovery]] | [[AWS Backup]] | [[RDS]] | [[Aurora]] | [[DynamoDB]] | [[ElastiCache]] | [[Redshift]] | [[Amazon DocumentDB]] | [[Amazon Keyspaces]] | [[EBS]] | [[S3]] | [[S3 Glacier Archive]] | [[Route 53 DNS]] | [[EC2]] | [[Auto Scaling]] | [[KMS]] | [[AWS Secrets Manager]] | [[AWS CloudHSM]] | [[AWS Snowball]] | [[AWS Systems Manager]]

## 核心概念

### RTO 与 RPO（考试最高频考点）

| 指标 | 全称 | 回答的问题 | 度量方向 |
|------|------|-----------|---------|
| **RTO（Recovery Time Objective，恢复时间目标）** | 灾难发生后，业务**最多能容忍多长时间不可用** | "多久能恢复服务？" | 从故障发生**向后**度量到服务恢复 |
| **RPO（Recovery Point Objective，恢复点目标）** | 灾难发生后，业务**最多能接受丢失多长时间的数据** | "最多能接受丢多少数据？" | 从故障发生**向前**回溯到最后一次可用的数据副本 |

> **考试陷阱**：**RTO 和 RPO 是两个独立的维度，不能互相替代**——题目描述"数据库允许最多丢失 5 分钟数据，但可以接受 2 小时的停机来恢复" → RPO = 5 分钟（决定备份/复制频率），RTO = 2 小时（决定恢复流程的自动化程度）；很多人误以为两者是同一件事，实际上**低 RPO 要求频繁的数据复制**，**低 RTO 要求现成可用的基础设施**，二者驱动完全不同的架构决策。

### DR 与高可用（HA）的区别（考试陷阱）

- **高可用（如 [[EC2]]/[[RDS]] 的 Multi-AZ）** 应对的是**单个组件或单个可用区**的故障，通常在**同一区域内**自动完成故障转移，不需要人工介入
- **灾难恢复** 应对的是**整个区域**级别的故障（区域性服务中断、自然灾害），需要**跨区域**的预案，往往涉及**手动或半自动**的故障转移决策

> **考试陷阱**：**"某数据库配置了 Multi-AZ" 不等于"已具备灾难恢复能力"**——Multi-AZ 只解决区域内的可用区故障，题目描述"需要应对整个区域不可用的场景" → 必须评估**跨区域**方案（读取副本、Global Database、Global Tables 等），而不能认为已有的 Multi-AZ 配置已经足够。

## 四种 DR 策略（考试高频，成本与恢复速度的权衡谱系）

```
成本 低 ────────────────────────────────────────────→ 高
      备份恢复          引导恢复          温备份         多活
   Backup & Restore   Pilot Light    Warm Standby   Multi-Site Active/Active
恢复速度 慢 ──────────────────────────────────────────→ 快
   (RTO: 小时~天)    (RTO: 分钟~小时)   (RTO: 分钟)     (RTO: 接近 0)
```

| 策略                               | 核心思路                                             | DR 区域的运行状态                            | 典型 RTO   | 典型 RPO          | 成本  |
| -------------------------------- | ------------------------------------------------ | ------------------------------------- | -------- | --------------- | --- |
| **备份恢复（Backup & Restore）**       | 定期将备份/快照复制到 DR 区域，灾难发生时从备份**重建**整套环境             | **不运行任何资源**，仅存储备份数据                   | 数小时到数天   | 取决于备份频率（通常数小时）  |     |
| **引导恢复（Pilot Light）**            | 仅**数据层**（数据库）在 DR 区域持续复制运行，计算层（应用服务器）**平时缩容到 0** | 数据库持续同步，应用层处于"待激活"状态（AMI/模板已就绪但未启动实例） | 数十分钟到数小时 | 分钟级（取决于复制延迟）    | 低   |
| **温备份（Warm Standby）**            | DR 区域运行**功能完整但缩小规模**的生产环境副本，灾难时**扩容**到全量规模       | 完整技术栈以**较小容量**持续运行                    | 分钟级      | 秒级到分钟级          |     |
| **多活（Multi-Site Active/Active）** | 多个区域**同时**以**生产全量规模**对外提供服务，流量通过 Route 53 分发     | 与主区域**完全对等**运行                        | 接近 0     | 接近 0（需处理多主复制冲突） | 高   |

> **考试要点**：**判断题目应选哪种策略，先看题目给出的 RTO/RPO 数字，再反推策略**，而非凭"预算充足就选最贵方案"的直觉——"允许数小时甚至数天恢复，预算有限" → 备份恢复；"数据库需持续可用，但应用服务器可以临时启动" → 引导恢复；"需要分钟级恢复，愿意为待命容量付费" → 温备份；"完全不能停机，多区域同时服务用户" → 多活。

## 备份恢复（Backup & Restore）

- **核心机制**：定期创建备份（[[EBS]] 快照、[[RDS]]/[[Aurora]] 快照、[[S3 Glacier Archive|S3 Glacier]] 归档等）并**跨区域复制**到 DR 区域，平时 DR 区域**不运行任何计算资源**，几乎零日常成本
- **[[AWS Backup]]**：跨多种服务（EBS、RDS、DynamoDB、EFS、FSx 等）提供**集中化的备份编排**，支持自动化备份计划、跨区域/跨账号复制备份、生命周期策略，避免为每个服务单独维护备份脚本，完整能力（Vault Lock、逻辑气隙保管库等）见 [[AWS Backup]] 独立笔记
- **恢复流程**：灾难发生后，从 DR 区域的备份**重新创建**基础设施（EC2 从 AMI 启动、RDS 从快照恢复），通常需要人工触发且耗时较长
- 数据量极大、网络带宽不足以支撑跨区域复制时，可使用 **[[AWS Snowball]] Edge** 导出/导入数据作为补充手段

> **考试要点**：**这是四种策略中成本最低、RTO/RPO 最差的方案**——适合非关键业务、离线批处理系统，或作为其他策略之外的"最后一道防线"（即使采用了更高级策略，通常仍会保留一份低成本的完整备份）。

## 引导恢复（Pilot Light）

- **核心机制**：只让**最关键的核心组件（通常是数据库）**在 DR 区域**持续运行并保持数据同步**，其余应用层组件（Web/App 层）**平时不运行**，但已提前准备好 AMI、启动模板、[[Auto Scaling]] 配置
- **典型实现**：
  - 数据层：[[RDS]] 跨区域只读副本、[[Aurora]] Global Database、[[DynamoDB]] Global Tables、[[Amazon Keyspaces]] 多区域复制表、[[Amazon DocumentDB]] Global Clusters、[[ElastiCache]] Global Datastore 均是"引导恢复"数据层的标准实现
  - 应用层：预先构建好的 **AMI** + 已配置但**容量为 0** 的 Auto Scaling Group，故障时快速扩容启动
- **故障转移**：触发后需要**启动应用层实例**、将只读副本**提升为主库**、切换 DNS（[[Route 53 DNS]] 故障转移路由），耗时通常在几十分钟量级
- **全托管实现**：无需自建复制管道和手动维护 AMI/启动模板，可直接使用 **[[AWS Elastic Disaster Recovery]]**——它把整台服务器（不仅是数据库）的持续块级复制、低成本暂存、按需启动恢复实例全流程产品化，完整能力见 [[AWS Elastic Disaster Recovery]] 独立笔记

> **考试要点**：**"引导恢复"得名于"只保留最核心的火苗（数据库），其余在需要时才点燃（启动应用层）"**——题目描述"数据库需要持续复制保持最新，但应用服务器平时不需要运行以节省成本" → 引导恢复是标准答案；题目描述"需要对整台服务器（含操作系统和应用）做低成本持续复制，而非只复制数据库" → **AWS Elastic Disaster Recovery**。

---

## 温备份（Warm Standby）

- **核心机制**：DR 区域运行一套**功能完整**但**规模缩小**（更少实例数/更小实例规格）的生产环境副本，**始终对外可用**（可用于低流量场景或作为只读服务），灾难发生时**扩容**到生产规模
- 与引导恢复的核心差异：**应用层在 DR 区域本身就在运行**（只是容量小），而不是平时完全停机等待启动——这让故障转移速度更快，但日常成本也更高
- 结合 [[Route 53 DNS]] 的**故障转移路由**或**加权路由**，可以让 DR 区域平时承接**少量流量**做健康校验，主区域故障时通过健康检查自动/半自动切换全部流量

> **考试要点**：**"引导恢复 vs 温备份"是最容易混淆的一对**——判断依据是"DR 区域的应用层平时是否在运行"：完全不运行（容量为 0）→ 引导恢复；以缩小规模持续运行 → 温备份。

---

## 多活（Multi-Site Active/Active）

- **核心机制**：**多个区域同时**以**生产全量规模**对外提供服务，用户流量通过 [[Route 53 DNS]] 的**延迟路由**或**地理邻近路由**分发到最近的健康区域，任一区域故障时 Route 53 健康检查自动将流量导向其余区域
- **数据一致性是最大挑战**：多区域**同时读写**同一份数据集时需要处理**写冲突**——[[DynamoDB]] Global Tables 采用"最后写入者获胜（Last Writer Wins）"自动解决冲突；[[Aurora]] Global Database 的托管故障转移仍是"一个主区域可写，其余只读"，并非真正意义上的多主写入
- **成本和复杂度最高**：需要在多个区域**长期维持全量生产规模**的资源，且必须设计能容忍最终一致性/写冲突的应用逻辑

> **考试陷阱**：**多活不等于"零风险"**——它提供接近零的 RTO/RPO，但引入了**跨区域数据冲突**的新风险；题目描述"需要多个区域都能读写同一份数据，且不同区域偶尔会更新同一条记录" → 必须评估应用层能否容忍**最后写入者获胜**这类冲突解决策略，而非假设多活架构能自动保证强一致性。

## 关键 AWS 服务构建模块速查

| 层次 | 服务能力 | 适用的 DR 策略 |
|------|---------|----------------|
| **数据库跨区复制** | [[Aurora]] Global Database、[[RDS]] 跨区域只读副本、[[DynamoDB]] Global Tables、[[Amazon Keyspaces]] 多区域复制、[[Amazon DocumentDB]] Global Clusters、[[ElastiCache]] Global Datastore | 引导恢复 / 温备份 / 多活 |
| **整机（服务器级）持续复制** | **[[AWS Elastic Disaster Recovery]]**：对物理机/虚拟机/其他云实例做持续块级复制，低成本暂存 + 按需启动恢复实例，全托管实现引导恢复 | 引导恢复（可配置向温备份靠拢） |
| **对象/文件存储备份** | [[S3]] 跨区域复制（CRR）、[[S3 Glacier Archive\|S3 Glacier]] 长期归档、[[EBS]] 快照跨区域复制、AWS FSx/EFS 备份跨区域恢复 | 备份恢复（也是其余策略的静态数据基础） |
| **集中化备份编排** | **[[AWS Backup]]**：跨 EBS/RDS/DynamoDB/EFS/FSx 等服务统一管理备份计划、生命周期、跨区域/跨账号复制 | 备份恢复 |
| **DNS 故障转移** | [[Route 53 DNS]] 故障转移路由（主备）、延迟/地理邻近路由（多活分流）+ 健康检查 | 温备份 / 多活（故障切换入口） |
| **密钥与凭证的跨区域可用性** | [[KMS]] 多区域密钥（避免"数据在异地却无法解密"）、[[AWS Secrets Manager]] Secret 跨区域自动复制 | 所有策略（加密数据的前提条件） |
| **自建密钥管理的特殊情况** | [[AWS CloudHSM]]：密钥的备份与灾难恢复**完全是客户责任**，AWS 无法代为恢复丢失的密钥材料 | 需要客户自行设计 DR 方案，而非依赖 AWS |
| **大规模数据离线迁移** | [[AWS Snowball]] Edge：网络带宽不足以支撑跨区域复制时的物理传输补充手段 | 备份恢复（尤其是初始种子数据或灾难后紧急导出） |
| **故障转移流程自动化** | [[AWS Systems Manager]] Automation Runbook：编排跨多步骤的故障转移/DR 演练流程，减少人工操作失误 | 所有策略（降低"人工执行复杂手册"带来的 RTO 风险） |

## 典型应用场景

| 场景 | 推荐策略 |
|------|---------|
| **非关键批处理系统，可接受数小时到数天恢复** | 备份恢复（[[AWS Backup]] + 跨区域快照复制） |
| **数据库要求持续同步，应用层平时无需运行以节省成本** | 引导恢复 |
| **需要对整台本地服务器做低成本、全托管的持续灾难恢复复制** | [[AWS Elastic Disaster Recovery]] |
| **需要分钟级恢复，且愿意为待命容量付费** | 温备份 |
| **完全不能停机，多区域需同时服务全球用户** | 多活（Multi-Site Active/Active） |
| **需要在合规要求下长期归档灾备数据** | S3 Glacier + 跨区域复制 |
| **网络带宽不足以支撑大规模跨区域数据复制** | AWS Snowball Edge 作为补充传输手段 |
| **自建 CloudHSM 集群丢失且未备份** | 无法恢复——凸显客户自行做好密钥 DR 规划的重要性 |
| **需要将复杂的故障转移步骤自动化、减少人为失误** | AWS Systems Manager Automation Runbook |

## 考试重点总结

### SAA-C02 高频考点

1. **RTO 回答"多久恢复"，RPO 回答"能丢多少数据"**：两个独立维度，分别驱动恢复流程设计和数据复制频率设计
2. **DR 策略的选择由业务给定的 RTO/RPO 决定**：而非无脑选择成本最高的方案
3. **四种策略按成本与恢复速度递增排列**：备份恢复 < 引导恢复 < 温备份 < 多活
4. **备份恢复：DR 区域平时不运行任何计算资源**：成本最低，恢复最慢
5. **引导恢复：只有数据层持续运行，应用层容量为 0**：故障时才启动应用层实例
6. **温备份：应用层已在 DR 区域以缩小规模持续运行**：与引导恢复的核心区别点
7. **多活：多区域同时全量对外服务**：需要额外设计写冲突解决策略（如 DynamoDB Global Tables 的 Last Writer Wins）
8. **Multi-AZ 是高可用，不是灾难恢复**：Multi-AZ 只应对区域内可用区故障，无法应对整个区域不可用
9. **Route 53 故障转移路由是灾难恢复流程的入口**：结合健康检查实现主备或多活的流量切换
10. **CloudHSM 的密钥灾难恢复完全是客户责任**：与 KMS（AWS 托管，内部具备更完善的灾难恢复机制）形成对比

### 场景题解题思路

```
场景分析 → 判断灾难恢复策略
├── "预算有限，可接受数小时到数天恢复" → 备份恢复
├── "数据库需持续同步，应用服务器平时不用运行" → 引导恢复
├── "需要分钟级恢复，愿意为待命容量付费" → 温备份
├── "完全不能停机，多区域同时服务用户" → 多活
├── "已配置 Multi-AZ，是否已具备灾难恢复能力" → 否，Multi-AZ 只是高可用，需评估跨区域方案
├── "多个区域同时读写同一份数据，如何处理冲突" → 评估 Last Writer Wins 等冲突解决策略
├── "网络带宽不足以支撑跨区域数据复制" → AWS Snowball Edge
└── "需要将故障转移流程自动化" → AWS Systems Manager Automation Runbook
```

## 最佳实践

1. **先明确业务的 RTO/RPO 要求，再选择 DR 策略**：不要脱离具体数字讨论"应该用哪种策略"
2. **不要把 Multi-AZ 等同于灾难恢复**：跨区域业务连续性需求必须单独评估跨区域方案
3. **即使采用了更高级的 DR 策略，仍建议保留一份低成本的完整备份**：作为最后一道防线应对极端场景（如逻辑错误导致的跨区域数据污染）
4. **多活架构上线前必须明确写冲突解决策略**：不要假设多区域读写会自动保持强一致
5. **善用 [[AWS Backup]] 集中管理跨服务的备份策略**：避免为每个服务单独维护备份脚本和生命周期规则
6. **DR 方案需要定期演练（Game Day）**：仅有架构设计不足以保证真实故障时按预期工作，应结合 Systems Manager Automation Runbook 定期验证故障转移流程
7. **确认加密密钥/凭证在 DR 区域同样可用**：提前配置 KMS 多区域密钥和 Secrets Manager 跨区域复制，避免"数据到了但解密不了"
8. **自建密钥管理（CloudHSM）场景务必自行制定并测试密钥备份方案**：不能假设 AWS 会在密钥丢失时提供任何形式的恢复
