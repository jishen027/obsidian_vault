# AWS Elastic Disaster Recovery (DRS) - 弹性灾难恢复

> **AWS Elastic Disaster Recovery（DRS）**是全托管的灾难恢复服务，通过在源服务器（物理机、VMware/Hyper-V 虚拟机、其他云的实例，也包括 AWS 内部跨区域/跨账号）上安装轻量代理，持续进行**块级复制（Block-Level Replication）**到 AWS 一个**低成本的暂存区（Staging Area）**——平时只产生极低的存储和最小化实例成本，故障发生时才**按需启动**全规格的恢复实例。它本质是把 [[Disaster Recovery On AWS]] 笔记中"**引导恢复（Pilot Light）**"策略**产品化、自动化**，免去了自建复制管道和手动维护 AMI/启动模板的运维负担。
>

## 核心概念

### 为什么需要 DRS

- **自建引导恢复架构的痛点**：需要自行搭建跨区域/跨云的数据复制管道、维护最新的 AMI 和启动模板、手动编排故障转移流程——运维复杂度高，且容易在真正故障时才发现流程有问题
- **DRS 的核心价值**：**全托管**地完成持续复制、暂存、按需启动恢复实例的全流程，把"引导恢复"降低到只需安装代理、配置一次即可长期免维护的水平

### 持续块级复制

- 在源服务器上安装**轻量级复制代理**，以**块级别**持续将磁盘变更复制到 AWS
- 复制到 AWS 后先落地在**低成本的暂存区**：使用低成本 EBS 卷 + 少量轻量级复制服务器，**不会**为每台源服务器预先启动对应规格的 EC2 实例
- **考试要点**：**平时暂存区几乎不产生计算费用**，这是 DRS 相比"温备份（Warm Standby）"更省钱的关键——只有真正触发恢复或做恢复演练时，才会按源服务器的规格**临时启动**全尺寸 EC2 实例

### 多个恢复点（Point-in-Time Recovery，考试陷阱）

- DRS **保留多个历史时间点的恢复快照**，而非只保留"最新状态"的一份复制
- **考试陷阱**：**题目描述"源服务器已被勒索软件感染，最新的复制数据也已被污染，能否恢复到感染前的状态"** → **可以**，选择**感染发生之前**的历史恢复点启动实例即可；很多人误以为持续复制意味着"只能恢复到最新状态"，实际上 DRS 的多恢复点机制专门覆盖了"最新数据本身已损坏"这一场景。

### 非破坏性恢复演练（Drill）

- 可以在**隔离的网络环境**（独立子网）中启动恢复实例进行**演练测试**，验证故障转移流程是否可行，且**不会中断**正在进行的持续复制
- 是 [[Disaster Recovery On AWS]] 笔记中"DR 方案需要定期演练"这一最佳实践的具体落地工具

### 故障回切（Failback）

- 源环境恢复正常后，DRS 支持**反向复制**——将 AWS 中恢复实例上产生的数据变更**同步回原始源基础设施**，完成**故障回切（Failback）**
- 这是相比"自建引导恢复架构"的显著优势：大多数自建方案只考虑了"如何切到 AWS"，而 DRS 原生支持"如何再切回去"

## AWS Elastic Disaster Recovery vs AWS Application Migration Service（考试高频对比）

两者底层都基于同源的**持续块级复制代理技术**（源自 AWS 收购的 CloudEndure），但定位完全不同：

| 维度 | AWS Elastic Disaster Recovery (DRS) | AWS Application Migration Service (MGN) |
|------|--------------------------------------|--------------------------------------------|
| **定位** | 长期、持续的灾难恢复就绪状态 | **一次性**的迁移上云（Lift-and-Shift） |
| **复制持续时间** | 长期持续运行，随时可能触发恢复 | 迁移**切换（Cutover）完成后即可停用**复制 |
| **典型触发** | 真实灾难事件或定期演练 | 计划内的迁移窗口，一次性切换 |
| **是否支持故障回切** | 支持（Failback 到原始环境） | 不适用（目标就是永久迁移到 AWS，不回切） |

> **考试陷阱**：**不要仅凭"都用持续块级复制"就认为两个服务可以互换**——题目描述"需要长期保持灾难恢复就绪状态，随时可能切回原环境" → **DRS**；题目描述"计划将本地服务器一次性迁移上云，迁移完成后不再需要复制" → **Application Migration Service**；选择依据是**业务意图（长期 DR vs 一次性迁移）**，而非复制技术本身。

## 在 DR 策略谱系中的定位

完整的四种 DR 策略（备份恢复/引导恢复/温备份/多活）及其权衡见 [[Disaster Recovery On AWS]] 独立笔记。DRS 的定位：

- **默认形态接近"引导恢复"**：平时暂存区几乎零计算成本，故障时才启动全尺寸实例
- **可灵活升级为"温备份"**：对 RTO 要求更高的场景，可以配置在暂存之外**始终运行一份缩小规模**的恢复实例，牺牲部分成本换取更快恢复
- **RPO 通常为秒级**（取决于源服务器变更速率和网络带宽），**RTO 通常为数分钟**（启动全尺寸实例 + 引导所需时间），显著优于"备份恢复"策略的数小时到数天

## 部署要求

| 要求 | 说明 |
|------|------|
| **源服务器** | 物理机、VMware/Hyper-V 虚拟机、其他公有云实例、AWS 内部跨区域/跨账号实例均可作为源 |
| **网络连接** | 源服务器需要能通过公共互联网或 [[VPC]]（经 VPN/Direct Connect）访问 AWS 端点 |
| **暂存子网** | 需要在目标 VPC 中划出专门的暂存子网，承载低成本的暂存资源 |
| **启动设置（Launch Settings）** | 需为每台源服务器预先配置恢复时的目标实例类型、子网、安全组等，确保触发恢复时能正确启动 |

## 定价（考试提示）

- **按每台被复制的源服务器、按小时计费**，与源服务器的规格无关（不管源服务器是大是小，复制费用结构一致）
- 暂存区的 **EBS 存储**和少量**轻量复制服务器**另计费用，但显著低于运行一台对应全尺寸 EC2 实例的成本
- 触发恢复演练或真实故障转移后，**启动的全尺寸恢复实例按标准 EC2 价格计费**，仅在实际运行期间产生

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **本地数据中心需要低成本、持续就绪的灾难恢复方案** | AWS Elastic Disaster Recovery |
| **需要定期验证灾难恢复流程但不能影响生产复制** | DRS 的非破坏性恢复演练（Drill） |
| **勒索软件污染了最新数据，需要恢复到感染前状态** | DRS 的历史恢复点（Point-in-Time Recovery） |
| **灾难恢复触发后，原环境修复完毕需要切回** | DRS 故障回切（Failback） |
| **计划一次性将本地服务器迁移上云，之后不再需要复制** | 改用 AWS Application Migration Service（而非 DRS） |
| **希望灾难恢复站点继续使用 VMware 工具管理，而非转换为原生 EC2** | 改用 [[VMware Cloud on AWS]] + VMware Site Recovery（而非 DRS） |
| **对 RTO 要求极高，愿意为部分待命容量付费** | 在 DRS 基础上配置常驻的缩小规模恢复实例（贴近温备份） |
| **网络带宽不足以支撑初始全量复制** | 结合 [[AWS Snowball]] 做初始数据种子传输 |

## 考试重点总结

### SAA-C02 高频考点

1. **DRS 是"引导恢复"策略的全托管产品化实现**：省去自建复制管道和手动维护 AMI 的运维负担
2. **平时暂存区几乎零计算成本**：只在真正恢复或演练时才启动全尺寸 EC2 实例
3. **支持多个历史恢复点**：可恢复到数据污染/勒索软件感染**之前**的状态，而非只有最新一份复制
4. **恢复演练不影响持续复制**：在隔离网络中启动测试实例，验证流程但不中断生产复制
5. **支持故障回切（Failback）**：恢复后可将变更同步回原始环境，这是相比自建方案的核心优势
6. **DRS vs Application Migration Service 的区别在于业务意图**：长期灾难恢复用 DRS，一次性迁移上云用 MGN，而非复制技术本身
7. **按源服务器数量和小时计费**：与服务器规格无关，恢复实例运行期间另按标准 EC2 价格计费
8. **RPO 通常为秒级、RTO 通常为数分钟**：显著优于备份恢复策略
9. **源服务器可以是物理机、虚拟机、其他云或 AWS 内部跨区域实例**：适用范围不局限于"本地数据中心"
10. **可灵活调整为更接近温备份的形态**：为关键业务额外保留一份缩小规模的常驻恢复实例

### 场景题解题思路

```
场景分析 → 判断 AWS Elastic Disaster Recovery 相关配置
├── "本地数据中心需要低成本、持续就绪的灾难恢复" → AWS Elastic Disaster Recovery
├── "需要验证故障转移流程但不能影响生产复制" → 非破坏性恢复演练（Drill）
├── "最新数据已被勒索软件污染，需要恢复到更早状态" → 选择历史恢复点
├── "故障恢复后需要切回原始环境" → DRS 故障回切（Failback）
├── "计划一次性迁移上云，之后不再需要持续复制" → 改用 Application Migration Service
├── "对 RTO 要求极高，可接受额外成本" → 常驻缩小规模恢复实例（贴近温备份）
└── "初始全量复制的数据量过大，带宽不足" → 结合 AWS Snowball 做种子传输
```

## 最佳实践

1. **定期执行非破坏性恢复演练**：仅有复制配置不代表恢复流程真的可行，应结合 Drill 定期验证
2. **为关键源服务器预先配置好启动设置**：包括目标实例类型、子网、安全组，避免真正触发恢复时手忙脚乱
3. **明确 DRS 与 Application Migration Service 的选型边界**：按"长期 DR 就绪"还是"一次性迁移"的业务意图决策，而非技术相似性
4. **对极端场景保留历史恢复点的意识**：不要假设"复制是最新的"就等于"复制是干净可用的"，数据污染场景应优先排查更早的恢复点
5. **对 RTO 要求苛刻的关键业务考虑常驻缩小规模实例**：在 DRS 默认的引导恢复形态基础上向温备份靠拢
6. **初始迁移阶段评估网络带宽是否足够支撑全量复制**：带宽不足时结合 AWS Snowball 做种子数据传输，避免复制迟迟无法追上变更速率
7. **将 DRS 纳入整体的 [[Disaster Recovery On AWS]] 策略规划**：作为"引导恢复"层的具体落地工具，而非孤立看待
