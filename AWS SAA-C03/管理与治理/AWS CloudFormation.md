# AWS CloudFormation - 基础设施即代码

> **AWS CloudFormation** 是 AWS 的**基础设施即代码（IaC）**服务，使用 JSON 或 YAML 格式的**声明式模板**来定义、创建和管理整套 AWS 基础设施——你描述"最终想要什么资源"，而不是编写"如何一步步创建它们"的命令式脚本，CloudFormation 负责计算出创建、更新或删除资源的具体执行顺序。它是 AWS 治理体系的底层引擎：[[AWS Service Catalog]]、[[Elastic Beanstalk]]、[[AWS Control Tower]] 的 Account Factory 等更上层的服务，本质上都是在 CloudFormation 之上做的易用性或治理封装。
>
> 相关文档：[[AWS Service Catalog]] | [[AWS Control Tower]] | [[AWS Organizations]] | [[AWS Config]] | [[AWS Systems Manager]] | [[AWS OpsWorks]] | [[Elastic Beanstalk]] | [[IAM]]

## 核心概念

### 模板（Template）与堆栈（Stack）

| 概念 | 说明 |
|------|------|
| **模板（Template）** | 描述所需资源及其配置的**声明式文本文件**（JSON/YAML），是架构的蓝图，可纳入版本控制 |
| **堆栈（Stack）** | 通过模板创建的一组 AWS 资源的**单一管理单元**——作为一个整体创建、更新或删除，而非逐个资源单独操作 |

### 逻辑 ID vs 物理 ID（考试提示）

- **逻辑 ID**：模板中定义资源时使用的名称（如 `MyVPC`），是模板内部引用该资源的标识符
- **物理 ID**：AWS 实际创建出的资源 ID（如 `vpc-0380...`），是该资源在 AWS 控制台/API 中的真实标识

> **考试要点**：模板内部通过**逻辑 ID**用 `Ref`/`Fn::GetAtt` 等**内在函数（Intrinsic Functions）**相互引用（如让一个安全组规则引用另一个资源的逻辑 ID），而不需要预先知道创建后的物理 ID——这是模板能够被反复复用、部署到不同环境而无需修改硬编码 ID 的关键。

## 关键功能

### 参数、映射与条件

| 功能 | 作用 |
|------|------|
| **参数（Parameters）** | 创建堆栈时**动态输入值**（如 AMI ID、密钥对名称、实例类型），避免将固定值硬编码在模板中，使同一模板可复用于不同环境 |
| **映射（Mappings）** | 定义类似查找表的键值对（如"按区域选择对应的 AMI ID"），在模板内根据条件静态查表取值 |
| **条件（Conditions）** | 根据参数值决定**是否创建某个资源**或**采用哪种配置**（如"仅生产环境才创建 Multi-AZ 数据库"） |
| **输出（Outputs）** | 堆栈创建完成后**导出**特定资源的属性值（如 VPC ID、负载均衡器域名），供其他堆栈通过 `Fn::ImportValue` 引用，是跨堆栈共享信息的标准方式 |

### 嵌套堆栈（Nested Stacks）vs StackSets（考试高频陷阱）

| 概念 | 部署范围 | 用途 |
|------|---------|------|
| **嵌套堆栈（Nested Stacks）** | **单个账户、单个区域**内，一个堆栈作为另一个堆栈的组成部分 | **模块化**——如网络团队维护底层网络堆栈，应用团队在其之上引用构建应用堆栈，避免重复定义相同的基础资源 |
| **StackSets** | **跨多个账户、跨多个区域**，用**同一份模板**批量创建/更新/删除堆栈实例 | **规模化统一部署**——如结合 [[AWS Organizations]] 把同一套基线模板（日志、安全基线等）批量部署到组织内所有成员账户 |

> **考试陷阱**：**"模块化单个架构内的资源"用嵌套堆栈；"把同一套模板复制到多个账户/区域"用 StackSets**——两者解决的是完全不同维度的问题，题目描述"网络团队和应用团队需要复用彼此的堆栈输出，同属一个环境" → 嵌套堆栈；题目描述"需要把同一套安全基线模板部署到组织内的所有账户和区域" → **StackSets**，完整的组织级批量部署机制见 [[AWS Organizations]] 独立笔记。

### 变更集（Change Sets）

- 在**正式更新堆栈前**生成变更集，预览 CloudFormation 将**如何修改资源**（新增、修改、还是替换/删除并重建），防止意外的停机或数据丢失
- **考试要点**：**部分资源属性的修改会触发"替换"而非"原地更新"**（如某些数据库参数），变更集能提前暴露这类风险，题目描述"担心更新堆栈会意外删除并重建关键资源（如数据库）" → 先生成**变更集**核查影响范围，而不是直接执行更新。

## 失败处理与资源保护（考试高频）

### 自动回滚（Rollback）

- **堆栈创建失败时，CloudFormation 默认自动回滚**——删除本次操作中已创建的所有资源，恢复到操作前的状态，避免留下"半成品"堆栈
- **堆栈更新失败时同样默认自动回滚**到更新前的配置
- **考试提示**：排查复杂失败原因时，可临时**禁用回滚（Disable Rollback）**保留失败现场用于诊断，但这不是默认行为，需要显式设置

### 终止保护（Termination Protection）

- 对关键生产堆栈启用**终止保护**后，任何人尝试直接删除该堆栈都会被 CloudFormation **拒绝**，必须先显式关闭保护开关才能删除——防止误操作删除整套生产基础设施

### DeletionPolicy（资源级别的删除行为）

| 策略 | 堆栈删除/资源移除时的行为 |
|------|--------------------------|
| **Delete（默认）** | 直接删除底层 AWS 资源 |
| **Retain** | **保留**底层资源，仅将其从堆栈管理中移除，资源本身继续存在 |
| **Snapshot** | 删除前先为支持快照的资源（如 [[RDS]]、[[EBS]]）**创建快照**，再删除资源本身 |

> **考试陷阱**：**终止保护防止的是"整个堆栈被删除"，DeletionPolicy 控制的是"堆栈删除时某个具体资源该怎么处理"，二者是不同层级的保护机制**——题目描述"数据库所在的堆栈被删除时，不希望数据库被一并删除" → 为该数据库资源设置 **`DeletionPolicy: Retain`**（或 `Snapshot`）；题目描述"防止任何人误删整个生产堆栈" → 启用**堆栈的终止保护**。

## 安全与治理

### 堆栈策略（Stack Policies）

- 一份 JSON 文档，定义**更新堆栈期间**哪些资源**可以/不可以**被修改，防止核心资源（如生产数据库）在一次看似无关的堆栈更新中被意外替换或删除
- 与 DeletionPolicy 的区别：堆栈策略作用于**更新（Update）**操作期间的保护，DeletionPolicy 作用于**删除（Delete）**操作时的资源处理方式

### 漂移检测（Drift Detection）

- 检测**实际资源状态**与**模板定义**之间是否存在差异——例如有人绕过 CloudFormation，直接在控制台手动修改了某个安全组规则
- **考试要点**：**漂移检测只负责"发现"不一致，不会自动修复或阻止手动变更**；题目描述"担心团队成员绕过 IaC 流程手动改动资源，导致模板与实际状态不一致" → 定期运行**漂移检测**识别偏差，再决定是更新模板还是修正实际资源，使二者重新对齐。

### CloudFormation Hooks（部署前拦截，考试提示）

- 在资源**实际创建/更新前**执行自定义校验逻辑，一旦校验不通过可以**真正阻止**部署继续进行
- 与 [[AWS Config]] 的"主动型规则（Proactive Rules）"形成互补：Config 主动型规则只给出合规判定结果、**不会**自动拦截部署；要实现"发现不合规配置就真正拦截"，需要额外引入 **CloudFormation Hooks**（或 [[AWS Organizations]] 的 SCP），完整的对比说明见 [[AWS Config]] 独立笔记。

## 与相关服务的边界（考试高频）

| 服务 | 定位 | 与 CloudFormation 的关系 |
|------|------|--------------------------|
| **[[AWS Service Catalog]]** | 面向最终用户的自助部署治理层 | 底层产品本质就是预先审批的 CloudFormation 模板，让用户无需 CloudFormation 权限即可自助部署，完整边界见 [[AWS Service Catalog]] 独立笔记 |
| **[[Elastic Beanstalk]]** | 面向应用的 PaaS | 底层由 CloudFormation 驱动资源编排，是 CloudFormation 之上的**易用性封装**，开发者只需上传代码 |
| **[[AWS OpsWorks]]** | 基于 Chef/Puppet 的配置管理 | CloudFormation 负责**创建基础架构本身**（VPC、实例等）；OpsWorks 负责**配置这些资源内部的运行环境**（安装软件、应用部署），两者面向的层次不同 |
| **[[AWS Systems Manager]]** | 已运行实例的运维管理 | CloudFormation 面向"资源的创建和生命周期"，Systems Manager 面向"已创建实例的日常运维"，完整对比见 [[AWS Systems Manager]] 独立笔记 |
| **[[AWS Control Tower]]** | 多账户着陆区自动化 | 底层大量使用 CloudFormation StackSets 批量部署账户基线资源 |

> **考试陷阱**：**这几个服务最容易在场景题中被混淆，判断依据是"处于基础设施生命周期的哪个阶段、面向哪类用户"**——创建资源本身用 CloudFormation；配置资源内部运行环境用 OpsWorks；管理已运行资源的日常运维用 Systems Manager；把 CloudFormation 包装成给最终用户自助部署的产品用 Service Catalog。

## 成本与优势

- **服务本身免费**：只需为通过它创建出来的底层 AWS 资源（EC2、RDS 等）付费，CloudFormation 的编排能力不额外收费
- **核心优势**：环境一致性（生产/开发环境可以完全相同）、自动化快速部署、基础设施可版本控制和代码评审（IaC 的核心价值主张）

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **需要声明式、可重复地创建整套基础设施** | CloudFormation 模板 + 堆栈 |
| **网络团队和应用团队需要复用彼此的基础资源，同属一个环境** | 嵌套堆栈（Nested Stacks） |
| **需要把同一套模板批量部署到组织内所有账户/区域** | StackSets（+ [[AWS Organizations]]） |
| **担心堆栈更新会意外替换/删除关键资源** | 先生成变更集核查，并配置堆栈策略保护核心资源 |
| **堆栈删除时不希望数据库被一并删除** | 为数据库资源设置 `DeletionPolicy: Retain` 或 `Snapshot` |
| **防止团队误删整个生产堆栈** | 启用堆栈终止保护 |
| **担心有人绕过 IaC 流程手动改动资源** | 定期运行漂移检测 |
| **需要在资源创建前真正拦截不合规配置** | CloudFormation Hooks（而非仅依赖 Config 主动型规则） |
| **希望最终用户自助部署但不给予 CloudFormation 权限** | 改用 [[AWS Service Catalog]] 封装标准化产品 |

## 考试重点总结

### SAA-C02 高频考点

1. **CloudFormation 是声明式 IaC**：描述目标状态，由服务本身计算执行顺序，而非命令式脚本
2. **逻辑 ID 用于模板内部引用，物理 ID 是实际创建的资源标识**：内在函数（Ref/GetAtt）让模板无需硬编码物理 ID
3. **嵌套堆栈解决单环境内的模块化，StackSets 解决跨账户/跨区域的批量部署**：不要混淆两者的适用维度
4. **变更集在正式更新前预览影响，尤其是"替换"类高风险变更**
5. **失败时默认自动回滚**：创建失败会清理已创建的资源，更新失败会恢复到更新前状态
6. **终止保护防止整个堆栈被删除，DeletionPolicy 控制堆栈删除时单个资源的处理方式**：二者是不同层级的保护机制
7. **堆栈策略保护更新期间的资源不被意外修改**：与作用于删除时的 DeletionPolicy 是不同阶段的机制
8. **漂移检测只发现差异，不自动修复或阻止手动变更**
9. **CloudFormation Hooks 才能真正阻止不合规部署**：Config 主动型规则只判定合规性，不能单独实现强制拦截
10. **服务本身免费，只为底层创建的资源付费**

### 场景题解题思路

```
场景分析 → 判断 CloudFormation 相关配置
├── "网络/应用团队需复用彼此堆栈，同一环境内" → 嵌套堆栈
├── "同一模板需批量部署到多账户/多区域" → StackSets（+ Organizations）
├── "担心更新会意外替换/删除关键资源" → 变更集 + 堆栈策略
├── "堆栈删除时数据库不能被一并删除" → DeletionPolicy: Retain / Snapshot
├── "防止误删整个生产堆栈" → 堆栈终止保护
├── "担心有人绕过 IaC 手动改资源" → 漂移检测
├── "需要在部署前真正拦截不合规配置" → CloudFormation Hooks
└── "希望最终用户自助部署但不给 CloudFormation 权限" → AWS Service Catalog
```

## 最佳实践

1. **重大更新前始终先生成变更集**：尤其是涉及数据库、网络等核心资源的模板改动
2. **为有状态关键资源显式设置 DeletionPolicy**：不要依赖默认的 Delete 行为，避免堆栈删除时数据被一并清除
3. **生产堆栈默认启用终止保护**：将误删的可能性降到最低
4. **善用嵌套堆栈拆分职责边界，善用 StackSets 实现跨账户规模化**：不要用嵌套堆栈勉强模拟跨账户部署
5. **定期执行漂移检测，尤其在允许控制台临时手动操作的环境中**：及时发现模板与实际状态的偏离
6. **需要真正阻止不合规资源创建时引入 CloudFormation Hooks**：不要误以为 Config 主动型规则已经具备拦截能力
7. **面向最终用户的自助部署场景改用 Service Catalog 封装**：避免直接给最终用户开放 CloudFormation 权限导致治理失控
8. **模板全程纳入版本控制并配合代码评审**：让基础设施变更像应用代码一样可追溯、可回滚
