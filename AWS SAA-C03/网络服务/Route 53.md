# Amazon Route 53 - DNS 服务

> **Amazon Route 53** 是一种高可用且可扩展的域名系统（DNS）服务，提供域名注册、DNS 解析、健康检查和多种高级流量路由策略，帮助用户构建高可用、低延迟的全球架构。
>
> 相关文档：[[VPC]] | [[CloudFront]] | [[AWS Load Balance]] | [[CloudWatch]] | [[Disaster Recovery On AWS]] | [[AWS Global Accelerator]]

---

## 核心功能

| 功能 | 说明 |
|------|------|
| **域名注册** | 可直接通过 Route 53 注册、管理和转移域名 |
| **DNS 管理** | 通过托管区域（Hosted Zone）管理域名的 DNS 记录 |
| **健康检查** | 持续监控端点可用性，配合路由策略自动排除不健康的目标 |
| **高级路由策略** | 支持多种路由策略，实现流量分发、就近访问、故障转移等 |
| **混合云集成** | 通过 Route 53 Resolver 实现本地数据中心与 VPC 之间的 DNS 互通 |

---

## 托管区域（Hosted Zone）

| 类型 | 说明 |
|------|------|
| **公有托管区域（Public）** | 管理可在公网访问的域名解析记录 |
| **私有托管区域（Private）** | 仅在关联的 [[VPC]] 内部生效，用于内部服务发现，不对公网暴露 |

> **考试要点**：私有托管区域可同时关联**多个 VPC**（包括跨账户），常用于混合云或多 VPC 架构下的内部域名解析。

### 私有托管区域无法解析：先检查 VPC 的两个 DNS 开关（考试易漏点）

> 私有托管区域的 DNS 查询**只能由 VPC 内置的 Amazon DNS 服务器**处理，如果关联 VPC 的这两个设置没有同时开启，即使托管区域和记录都配置正确，查询依然无法解析。

| VPC 设置 | 作用 | 未开启的后果 |
|---------|------|-------------|
| **`enableDnsHostnames`（DNS 主机名）** | 允许实例获得公有/私有 DNS 主机名 | 非默认方式创建的 VPC 该项默认关闭，私有托管区域无法生效 |
| **`enableDnsSupport`（DNS 解析）** | 允许使用 VPC 内置 DNS 服务器（VPC CIDR 基址+2 的保留 IP，即 Route 53 Resolver）做域名解析 | 关闭后 VPC 内置 DNS 不可用，私有托管区域无法解析 |

> **注意 DHCP 选项集陷阱**：如果 VPC 使用了指向第三方 DNS 服务器的**自定义 DHCP 选项集**，`enableDnsSupport` 并**不会**被关闭，但实例的 DNS 查询会直接发往自定义 DNS 服务器，而不是 Amazon DNS，因此私有托管区域同样无法解析。解决办法：让自定义 DNS 服务器把相关域名的查询转发给 VPC 内置 Resolver（基址+2）。

> **考试关键词识别**："创建了私有托管区域并关联了 VPC，但 DNS 查询始终无法解析" → 先检查该 VPC 是否同时启用了 `enableDnsHostnames` 和 `enableDnsSupport`，而不是去改 NS/SOA 记录（这两个是公有托管区域的机制）或排查命名空间重叠（重叠时 Resolver 按最长匹配路由，不会导致完全无法解析）。

## 路由策略 ^2a255f

### 策略总览（考试高频考点）

| 策略 | 说明 | 是否支持健康检查 | 典型场景 |
|------|------|:---:|---------|
| **简单路由（Simple）** | 单条记录返回一个或多个值，客户端随机选取 | ❌ | 单一资源、无需高可用的简单场景 |
| **加权路由（Weighted）** | 按设定权重比例分发流量 | ✅ | A/B 测试、蓝绿部署、灰度发布 |
| **延迟路由（Latency-based）** | 将请求路由到延迟最低的区域 | ✅ | 面向全球用户、优化响应速度 |
| **故障转移路由（Failover）** | 主/备模式，主记录不健康时自动切到备用记录 | ✅（必须） | [[Disaster Recovery On AWS\|灾难恢复]]、主备架构 |
| **地理位置路由（Geolocation）** | 按用户所在的洲/国家/州划分并路由 | ✅ | 内容本地化、访问限制（合规） |
| **地理邻近路由（Geoproximity）** | 按资源与用户的地理位置路由，可通过 Bias 调整流量偏向 | ✅ | 精细调整区域流量占比（可通过 Traffic Flow 或直接创建记录配置） |
| **多值应答路由（Multivalue Answer）** | 返回多个健康记录（最多 8 个），客户端随机选择 | ✅ | 简单路由的增强版，兼顾基础的可用性检查 |
| **基于 IP 的路由（IP-based）** | 根据客户端 IP 所属的 CIDR 段路由 | ✅ | 按网络运营商/网络拓扑优化路由 |

### 常见混淆点

- **简单路由 vs 多值应答路由**：两者都可返回多个值，但只有多值应答路由支持**健康检查**，能自动剔除不健康的记录
- **地理位置路由 vs 延迟路由**：地理位置路由基于用户**物理位置**（用于合规/内容限制），延迟路由基于**网络延迟**（用于性能优化），两者目标不同，不能互相替代
- **地理邻近路由**是唯一支持 **Bias** 参数（人为调整某区域吸引更多/更少流量）的策略；早期只能通过 **Traffic Flow** 配置，现在也可以像其他策略一样直接创建记录（旧题目/资料中仍常见"需 Traffic Flow"的说法）

## 健康检查（Health Checks）

- 支持对 HTTP、HTTPS、TCP 端点进行监控，也可以监控其他健康检查的状态（**Calculated Health Check**）或 [[CloudWatch]] 告警
- 由分布在全球的健康检查器发起探测，通常连续多次失败后才判定为不健康，避免因单点网络抖动误判
- 健康检查失败的记录会被路由策略自动排除，直到恢复健康后重新纳入

> **考试陷阱：健康检查无法直接探测私有资源**——Route 53 健康检查器位于公网，无法访问 VPC 内私有 IP 或本地私有端点。监控私有资源的正确做法：为该资源创建 [[CloudWatch]] 指标 + 告警，再让 Route 53 健康检查**监控该 CloudWatch 告警**。

> **考试要点**：故障转移路由**必须**配置健康检查，否则 Route 53 无法判断何时应切换到备用记录。

> **考试陷阱：Route 53 故障转移路由的切换速度受 DNS TTL 和客户端/中间层 DNS 缓存制约，不是"实时"切换**——健康检查发现异常后，Route 53 会更新返回的记录，但客户端/中间 DNS 解析器可能仍持有旧记录的缓存直到 TTL 过期（部分解析器甚至会忽略/延长 TTL），导致故障转移实际耗时可能达数分钟甚至更久。如果题目强调**"故障切换要快/近乎实时""不希望受 DNS 缓存影响"**，标准答案是 **[[AWS Global Accelerator]]**（基于固定 Anycast IP + 健康检查，秒级切换，无需依赖 DNS 传播），而不是 Route 53 故障转移路由。

## Alias 记录 vs CNAME（考试高频考点）

| 特性 | Alias 记录 | CNAME |
|------|-----------|-------|
| **是否 Route 53 专有** | 是，AWS 对标准 DNS 的扩展 | 否，标准 DNS 记录类型 |
| **能否用于根域名（Zone Apex）** | ✅ 可以（如 `example.com`） | ❌ 不可以，DNS 标准限制 |
| **指向目标** | 只能指向 AWS 资源（ELB、CloudFront、S3 静态网站端点、API Gateway、VPC 端点、其他 Route 53 记录等） | 可指向任意域名 |
| **查询费用** | 指向 AWS 资源时免费 | 正常按查询计费 |
| **健康感知** | 自动感知目标资源状态变化 | 无 |

> **考试要点**：需要在**根域名**直接指向负载均衡器或 CloudFront 时，必须使用 **Alias 记录**，CNAME 无法满足这一需求。
>
> **考试陷阱**：Alias 记录**不能指向 EC2 实例的 DNS 名称**（EC2 需用 A 记录指向其 IP/弹性 IP）；Alias 记录也**无法自定义 TTL**，TTL 由目标资源决定。

## 混合云 DNS 与多区域恢复

### Route 53 Resolver

> **Route 53 Resolver 就是每个 VPC 内置的 DNS 服务器**（VPC CIDR 基址+2，如 `10.0.0.2`，也可通过 `169.254.169.253` 访问，即 "AmazonProvidedDNS"）。默认负责解析公网域名、关联到该 VPC 的私有托管区域以及 AWS 内部域名（EC2 主机名、VPC 端点等），但**默认只服务 VPC 内部的查询**，本地网络无法使用它，它也不知道本地域名（如 `corp.local`）。

- 通过 **Resolver 端点**实现**本地数据中心**与 [[VPC]] 之间的双向 DNS 解析（前提：已通过 VPN 或 Direct Connect 打通网络）
- 端点本质是部署在子网中的一组 **ENI**（带私有 IP），建议跨**至少 2 个 AZ** 部署以实现高可用
- **入站端点（Inbound Endpoint）**：允许本地网络查询 VPC 内的私有域名（本地 DNS 服务器配置条件转发，把查询转发到入站端点的 IP）
- **出站端点（Outbound Endpoint）**：允许 VPC 内资源将特定域名的查询转发到本地 DNS 服务器（需配合**转发规则**：指定域名 + 目标本地 DNS 服务器 IP）

```
本地 DNS 服务器                              VPC（Route 53 Resolver）
"app.internal.aws 是什么？"
      │ 条件转发
      └──────────────────────────────→ 入站端点（ENI IP）→ 从私有托管区域应答

                                        EC2 查询 "db.corp.local"
                                        → 命中转发规则
      ←──────────────────────────────┘ 出站端点
本地 DNS 应答 corp.local
```

> **🚩 反复出错提醒：方向判断口诀**——"谁发起查询，就用谁这一侧的端点"：
>
> | 场景 | 谁发起查询 | 用哪个端点 | 记忆方式 |
> |------|-----------|-----------|---------|
> | 本地数据中心的 DNS 服务器要解析 **AWS VPC 内**的域名 | 本地 DNS 服务器 | **入站端点（Inbound）**，本地 DNS 服务器把查询转发**进来**给 Route 53 Resolver | "进" VPC → 入站 |
> | **VPC 内**的资源要解析本地数据中心的域名 | Route 53 Resolver | **出站端点（Outbound）**，Resolver 把查询转发**出去**给本地 DNS 服务器 | "出" VPC → 出站 |
>
> 两个方向需要同时双向解析时，必须**同时创建两个端点**（一个入站+一个出站），并为出站端点配置转发规则（指定要转发的域名和本地 DNS 服务器 IP）——这是"选二"类题目的标准答案组合，不要因为两者都叫"端点"就误以为任选一个方向就能覆盖两个方向。

#### Resolver 相关扩展考点

| 功能 | 说明 | 考试关键词 |
|------|------|-----------|
| **转发规则跨账户共享** | 通过 **AWS RAM** 将转发规则共享给其他账户/VPC，多个 VPC 共用一个集中的出站端点（Hub-and-Spoke） | "多账户统一解析本地域名，避免每个 VPC 都建端点" |
| **规则优先级** | 按**最长域名匹配**，更具体的转发规则（如 `corp.local`）覆盖默认的系统规则 | "部分域名转发本地，其余走 AWS" |
| **Resolver DNS Firewall** | 过滤 VPC 发出的 DNS 查询，按域名列表允许/阻止，防止 DNS 数据外泄或访问恶意域名，可通过 Firewall Manager 集中管理 | "阻止 EC2 解析已知恶意域名" |
| **Resolver 查询日志** | 记录 VPC 内发出的 DNS 查询，投递到 CloudWatch Logs / S3 / Firehose | "审计 VPC 内的 DNS 查询" |

> **一句话总结**：Route 53 Resolver = VPC 内置 DNS（基址+2）；入站端点让本地解析 AWS 私有域名，出站端点 + 转发规则让 AWS 解析本地域名；规则可通过 RAM 共享；DNS Firewall 负责过滤出站 DNS 查询。

### Route 53 Application Recovery Controller

- 提供跨区域的**就绪检查（Readiness Check）**和**路由控制（Routing Control）**，用于精细化管理多区域故障转移

## DNSSEC

- Route 53 支持为公有托管区域启用 **DNSSEC（域名系统安全扩展）**签名，防止 DNS 欺骗和缓存投毒攻击
- 需要在注册商和托管区域两端分别配置，启用后对递归解析器验证响应真实性

## 考试重点总结

### SAA-C03 高频考点

1. **路由策略选择**：性能优化用延迟路由，合规/内容限制用地理位置路由，主备容灾用故障转移路由
2. **Alias vs CNAME**：根域名场景只能用 Alias，且指向 AWS 资源免费
3. **故障转移路由依赖健康检查**：没有健康检查就无法实现自动切换
4. **私有托管区域**：可关联多个 VPC，用于内部服务发现
5. **多值应答 vs 简单路由**：多值应答支持健康检查，简单路由不支持
6. **地理邻近路由**：唯一支持 Bias 偏向调整的策略
7. **Route 53 Resolver**：VPC 内置 DNS；入站/出站端点解决混合云环境下的双向 DNS 解析问题，规则可通过 RAM 共享
8. **DNS 故障转移的速度局限**：受 TTL 和 DNS 缓存制约，需要秒级切换时应改用 [[AWS Global Accelerator]]
9. **健康检查不能直接探测私有资源**：需通过 CloudWatch 告警间接监控
10. **Alias 不能指向 EC2 DNS 名称**，且不能自定义 TTL

### 场景题解题思路

```
场景分析 → 选择路由策略
├── "希望用户访问延迟最低的区域" → 延迟路由
├── "按国家/地区限制或定制内容" → 地理位置路由
├── "需要主备容灾，自动切换" → 故障转移路由（配合健康检查）
├── "灰度发布/A-B 测试，按比例分流" → 加权路由
├── "需要人为调整某区域流量占比" → 地理邻近路由（Bias）
├── "故障切换必须秒级完成，不能受 DNS 缓存影响" → [[AWS Global Accelerator]]（不是 Route 53 故障转移路由）
├── "根域名需要指向 ALB/CloudFront" → Alias 记录
├── "本地数据中心需要解析 VPC 内私有域名" → Route 53 Resolver 入站端点
├── "VPC 内资源需要查询本地私有域名" → Route 53 Resolver 出站端点 + 转发规则
├── "多个账户共用本地域名转发规则" → 通过 AWS RAM 共享 Resolver 规则
├── "阻止 VPC 内实例解析恶意域名" → Route 53 Resolver DNS Firewall
└── "对私有 IP 资源做健康检查" → CloudWatch 告警 + 监控告警的健康检查
```

## 最佳实践

1. **根域名统一使用 Alias 记录**：兼容性更好且指向 AWS 资源免费
2. **故障转移路由必须配置健康检查**：否则无法实现自动切换
3. **多区域架构结合延迟路由 + 健康检查**：兼顾性能与可用性
4. **私有托管区域用于内部服务发现**：避免将内部域名暴露在公网
5. **合规场景使用地理位置路由**：明确设置默认记录，避免未覆盖地区无法解析
6. **混合云环境部署 Resolver 端点**：实现本地与云上 DNS 的双向互通
7. **为关键域名启用 DNSSEC**：防止 DNS 欺骗类攻击
