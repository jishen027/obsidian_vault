# Customer Gateway - 客户网关

> **客户网关（Customer Gateway, CGW）**是 AWS 侧的一个**逻辑资源**，用于向 AWS 描述你本地数据中心的 VPN 设备信息（公网 IP、路由方式、BGP ASN 等），配合 **[[Virtual Private Gateway]]** 或 [[Transit Gateway]] 建立 [[Site to Site VPN]] 连接。**它本身不是物理设备**——真正收发流量的物理路由器/防火墙是**客户网关设备（Customer Gateway Device）**，部署在客户机房内，CGW 资源只是 AWS 用来"认识"这台设备的配置元数据。这个"资源 vs 设备"的区分是 CGW 相关考题中最容易被忽略的一点。
>
> 相关文档：[[Site to Site VPN]] | [[Virtual Private Gateway]] | [[Transit Gateway]] | [[VPC]] | [[Route Table]] | [[CIDR]]

---

## 核心概念

### 客户网关资源 vs 客户网关设备（考试最高频陷阱）

> **考试陷阱**：**"客户网关（Customer Gateway）"在 AWS 语境下有两层含义，题目常故意混用**：
> - **客户网关资源（Customer Gateway Resource）**：在 AWS 账户中创建的**逻辑对象**，仅包含描述性信息（IP、ASN、路由类型），本身不处理任何流量
> - **客户网关设备（Customer Gateway Device）**：部署在**本地机房**的**真实物理或软件设备**（路由器、防火墙、VPN 网关软件），负责实际建立和维护 IPsec 隧道
>
> 题目描述"创建 VPN 连接时报错，提示客户网关信息与实际设备不匹配" → 检查的是 **AWS 侧的 CGW 资源配置**（IP/ASN）是否与**本地实际设备**的配置一致，两者必须在两侧**分别配置**且保持同步，AWS 不会自动感知本地设备的真实状态。

### 创建 CGW 资源需要的信息

| 属性 | 说明 |
|------|------|
| **公网 IP 地址** | 客户网关设备的**静态、可公网路由**的 IPv4 地址；若设备位于 NAT 之后，应使用 NAT **对外暴露**的公网 IP |
| **路由类型** | **静态路由**或**动态路由（BGP）**，需与后续 VPN 连接的路由方式保持一致 |
| **BGP ASN** | 使用动态路由时必填——可以是客户**已拥有的公网 ASN**，也可以是**私有 ASN**（如 65000-65534 段），但**不能与 [[Virtual Private Gateway]] 侧使用的 ASN 冲突**（VGW 默认私有 ASN 为 64512） |
| **设备类型（可选）** | 指定具体厂商/型号（如 Cisco、Juniper、Palo Alto、Fortinet 等）后，AWS 可生成**对应厂商语法的参考配置文件**，用于快速配置本地物理设备；选择"Generic"（通用）类型则获得通用参考配置 |

> **考试要点**：**"选择设备厂商类型"这一步的唯一作用是让 AWS 生成对应语法的配置模板文件，方便运维人员参考配置本地设备**——它**不会**让 AWS 反过来管理或访问客户的本地设备，客户网关设备的实际配置工作仍需在本地设备上手动完成。

---

## IP 地址要求（考试提示）

- CGW 资源中登记的 IP **必须是静态的公网可路由地址**——若该地址后续发生变化（如 ISP 重新分配动态 IP），需要**重新创建**或更新 CGW 资源并可能导致隧道中断
- 若本地设备实际部署在私有网络中并通过 NAT 设备接入公网，CGW 中登记的应是 **NAT 设备对外的公网 IP**，而非设备自身的私有 IP

---

## BGP ASN 的选择（考试提示）

- **私有 ASN** 范围通常在 `64512-65534`（16 位）或更大的 32 位私有段——若企业内部网络已有既定的 ASN 规划，应直接复用，避免与 VGW 默认的 `64512` 冲突
- **公网 ASN**：若企业本身拥有已在互联网上注册的公网 ASN，也可以直接使用，无需额外申请私有段
- ASN 冲突会导致 **BGP 邻居关系无法建立**，VPN 隧道即使物理连通，路由也不会被正确交换——完整的 VGW 侧 ASN 自定义说明见 [[Virtual Private Gateway]] 笔记

---

## 一个 CGW 资源可被多条 VPN 连接复用

- 同一个客户网关资源可以被**多条 VPN 连接**引用——例如同一台本地设备需要同时连接多个 VPC（各自对应不同的 VGW）时，无需为每条连接重复创建 CGW 资源，只需在创建每条 VPN 连接时都引用**同一个** CGW
- 这与 [[Site to Site VPN]] 笔记中 **VPN CloudHub**（单 VGW + 多 CGW）是相反方向的复用关系：CloudHub 是"一个 VGW 服务多个 CGW（多个远程站点）"，此处则是"一个 CGW（一台本地设备）服务多条连接（多个 VPC）"

---

## 本地设备的高可用考量

- **CGW 资源本身没有"高可用"的概念**——它只是描述单个设备/单个 IP 的元数据；若本地需要**双机热备**的物理设备做故障切换，通常需要为**每台物理设备单独创建一个 CGW 资源**（各自登记不同的公网 IP），并分别与 AWS 侧建立独立的 VPN 连接
- AWS 侧的高可用（双隧道）已经覆盖了"AWS 端点故障"的场景，但**本地设备自身的故障**需要客户在本地架构层面单独规划冗余，这是常被忽略的责任边界

---

## 证书认证（新特性，考试提示）

- 除了传统的**预共享密钥（Pre-Shared Key, PSK）**认证方式，AWS Site-to-Site VPN 也支持基于 **AWS Private CA 颁发的证书**做隧道身份验证，为客户网关设备提供比静态密钥更强的身份认证机制
- 使用证书认证时，客户网关设备需要支持基于证书的 IKE 认证，并信任对应的私有证书颁发机构

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **首次建立 Site-to-Site VPN，需要告知 AWS 本地设备信息** | 创建 CGW 资源，登记静态公网 IP、路由方式、ASN |
| **本地设备位于 NAT 之后** | CGW 登记 NAT 对外暴露的公网 IP，而非设备私有 IP |
| **希望获得设备厂商对应语法的配置参考** | 创建 CGW 时选择对应的设备类型（如 Cisco/Juniper） |
| **同一台本地设备需要连接多个 VPC** | 复用同一个 CGW 资源，为每个 VPC 分别创建 VPN 连接 |
| **本地部署了双机热备的 VPN 设备** | 为每台物理设备分别创建独立的 CGW 资源和 VPN 连接 |
| **本地设备的公网 IP 发生变化** | 需更新/重建 CGW 资源，隧道会短暂中断 |
| **需要比预共享密钥更强的身份认证** | 使用基于 AWS Private CA 证书的认证方式 |
| **VPN 连接建立失败，怀疑配置不一致** | 分别核对 AWS 侧 CGW 资源与本地设备的实际配置（IP/ASN）是否匹配 |

## 考试重点总结

### SAA-C02 高频考点

1. **CGW 资源 ≠ 客户网关设备**：前者是 AWS 中的逻辑配置对象，后者是本地真实的物理/软件设备，两者需分别配置并保持一致
2. **CGW 资源本身不处理流量**：真正建立和维护隧道的是本地的客户网关设备
3. **创建 CGW 需要静态公网 IP**：设备在 NAT 后应登记 NAT 对外的公网 IP
4. **动态路由需要 BGP ASN，且不能与 VGW 侧冲突**：VGW 默认私有 ASN 为 64512
5. **设备类型选择仅用于生成参考配置文件**：不代表 AWS 会代管本地设备
6. **一个 CGW 资源可被多条 VPN 连接复用**：同一设备连接多个 VPC 时无需重复创建
7. **CGW 资源没有内置高可用概念**：本地双机热备需要分别创建多个 CGW 资源
8. **公网 IP 变化需要更新/重建 CGW 资源**：会导致隧道短暂中断
9. **支持基于证书的认证方式**：作为预共享密钥之外更强的身份验证选项
10. **VPN 连接故障排查需两侧对照配置**：AWS 侧 CGW 信息与本地设备实际配置不一致是常见故障原因

### 场景题解题思路

```
场景分析 → 判断 Customer Gateway 相关配置
├── "首次建立 VPN，需要让 AWS 认识本地设备" → 创建 CGW 资源（IP + 路由类型 + ASN）
├── "本地设备在 NAT 之后，该登记哪个 IP" → NAT 对外暴露的公网 IP
├── "希望获得设备厂商语法的配置参考" → 创建 CGW 时选择对应设备类型
├── "同一本地设备需连接多个 VPC" → 复用同一个 CGW 资源，多条 VPN 连接
├── "本地部署了双机热备设备" → 为每台设备分别创建独立 CGW 资源
├── "VPN 建立失败，配置疑似不一致" → 核对 AWS 侧 CGW 与本地设备的实际配置
├── "本地 ASN 与 VGW 默认 ASN 冲突" → 更改其中一方 ASN（详见 [[Virtual Private Gateway]]）
└── "需要比预共享密钥更强的认证" → 使用 AWS Private CA 证书认证
```

## 最佳实践

1. **创建 CGW 前确认本地设备的公网 IP 是静态的**：避免因动态 IP 变化导致隧道频繁中断
2. **提前规划 ASN，避免与 VGW 默认值冲突**：企业内部已有 ASN 规划时应直接复用并同步告知网络团队
3. **创建 CGW 时选择匹配的设备类型获取参考配置**：加快本地设备配置速度，减少手动排查语法问题
4. **本地关键 VPN 设备规划物理层面的高可用**：不要假设 AWS 侧的双隧道能覆盖本地设备自身故障的风险
5. **变更本地设备公网 IP 前提前规划维护窗口**：更新 CGW 资源会导致依赖它的隧道短暂中断
6. **多 VPC 连接同一本地设备时复用同一 CGW 资源**：避免重复创建带来的管理混乱
7. **对安全要求更高的场景评估证书认证**：替代传统预共享密钥，降低密钥泄露风险
