# Bastion Host - 堡垒机

> **堡垒机（Bastion Host）**是部署在**公有子网**中的加固 EC2 实例，作为管理员访问**私有子网**内资源（EC2、RDS 等）的唯一**跳板（Jump Box）**——管理员先 SSH/RDP 登录堡垒机，再从堡垒机二次跳转到私有子网内的目标实例，从而避免让私有子网内的所有资源直接暴露公网入口。这是 SAA-C02 中"传统"的私有资源远程访问方案，但 AWS 目前**更推荐**用 **Session Manager**（完全消除入站端口）或 **EC2 Instance Connect Endpoint**（无需公网 IP）替代它。
>
> 相关文档：[[VPC]] | [[Subnet]] | [[Security Group]] | [[NAT Instance]] | [[NAT Gateway]] | [[AWS Systems Manager]] | [[IAM]] | [[EC2]]

---

## 核心概念

### 为什么需要堡垒机

- **私有子网资源不应直接暴露公网**：数据库、内部应用服务器等资源部署在私有子网，没有公网 IP，管理员无法从公网直接 SSH/RDP 连接
- **堡垒机的核心价值**：作为**唯一**允许从公网发起管理连接的入口，收敛整个 VPC 的管理访问面——只需集中加固、监控这**一台**实例，而不是为每个私有实例单独暴露访问入口

### 典型架构

```
管理员（公网）→ 堡垒机（公有子网，SSH/RDP）→ 私有子网内的目标实例（EC2/RDS 等）
```

- 管理员 **SSH Agent Forwarding** 或 **ProxyJump（`-J` 参数）**方式，通过堡垒机"跳转"到私有实例，无需在堡垒机上存放目标实例的私钥
- 私有子网内实例的安全组**仅放行来自堡垒机安全组（或私有 IP）**的 SSH/RDP 流量，其余来源一律拒绝

## 部署与加固要求（考试高频）

| 要求 | 说明 |
|------|------|
| **位于公有子网** | 需要公网 IP/弹性 IP 才能被管理员从公网直接连接 |
| **安全组严格限制来源** | 入站规则**仅放行**管理员的**特定 IP/CIDR**（如公司出口 IP），而非 `0.0.0.0/0`，这是堡垒机安全组配置中最常被考察的点 |
| **私有实例安全组引用堡垒机安全组** | 私有子网内实例的入站规则应指向**堡垒机的安全组 ID**，而非放行整个 VPC CIDR，缩小信任范围 |
| **最小化软件与攻击面** | 堡垒机上只安装必要的 SSH/RDP 客户端工具，不部署业务应用，降低被攻破的风险 |
| **密钥认证 + 禁用密码登录** | 使用 SSH 密钥对而非密码认证，进一步降低暴力破解风险 |
| **会话审计与日志** | 结合 CloudTrail、[[CloudWatch]] Logs 或第三方工具记录堡垒机上的操作历史，满足合规审计要求 |

> **考试陷阱**：**堡垒机本身就是一个额外的攻击面和单点故障**——它拥有公网 IP，若被攻破，攻击者即可借道访问整个私有子网；题目描述"需要进一步降低攻击面/消除入站端口暴露"时，标准答案通常**不是"继续加固堡垒机"**，而是改用 **Session Manager** 或 **EC2 Instance Connect Endpoint**（详见下文）。

---

## 高可用考量

- 单台堡垒机是**单点故障**——若挂机，管理员将失去访问私有子网的唯一入口
- 常见做法：在**多个可用区**分别部署堡垒机（配合 Auto Scaling 或手动多实例），或结合弹性 IP 快速漂移到备用实例
- 相比自建高可用，**Session Manager 天然没有单点故障问题**（不依赖某一台跳板实例），是更省心的替代方案

## 现代替代方案（考试最高频对比）

### AWS Systems Manager Session Manager

- **无需开放任何入站端口（SSH 22/RDP 3389）**，无需部署或维护堡垒机，无需管理 SSH 密钥——管理员通过 IAM 权限直接获得实例的交互式 Shell，会话经由 **SSM Agent 主动发起的出站连接**建立
- 访问权限完全由 **IAM 策略**控制，会话内容可记录到 CloudWatch Logs/S3，审计能力优于自建堡垒机的日志方案
- 完整能力（Run Command、Patch Manager、Just-in-Time 访问等）见 [[AWS Systems Manager]] 独立笔记

> **考试陷阱**：**题目描述"需要安全访问私有子网内的 EC2 实例，且不希望开放任何入站端口/不希望管理堡垒机" → 标准答案是 Session Manager，而非"部署一台加固的堡垒机"**——这是近年 SAA-C02 中"传统方案 vs 云原生方案"类考题的典型模式，堡垒机是历史/兜底选项，Session Manager 是默认推荐。

### EC2 Instance Connect Endpoint（ICE）

- 允许通过 AWS 控制台/CLI 使用**临时推送的公钥**对实例发起 SSH/RDP 连接，**无需实例拥有公网 IP**，也无需部署堡垒机
- 通过在 VPC 内创建的 **Instance Connect Endpoint**（本质是私有子网内的 ENI）代理连接，流量始终在 AWS 网络内部，不经过公网
- 与 Session Manager 的区别：ICE **仍使用标准 SSH/RDP 协议和短期凭证**，更贴近"临时堡垒机"的使用习惯；Session Manager 则完全通过 SSM Agent 通道，**不依赖 SSH/RDP 协议本身**

### 三种方案对比

| 维度 | 堡垒机（Bastion Host） | Session Manager | EC2 Instance Connect Endpoint |
|------|------------------------|------------------|-------------------------------|
| **入站端口** | 需开放 22/3389 | **无需开放任何入站端口** | 无需开放入站端口（连接经 Endpoint 代理） |
| **公网 IP 需求** | 堡垒机本身需要 | 目标实例**无需**公网 IP | 目标实例**无需**公网 IP |
| **运维负担** | 需自行加固、打补丁、维护高可用 | **AWS 全托管**，无需运维 | 需创建并维护 Endpoint（远低于堡垒机） |
| **权限模型** | SSH 密钥 + 安全组 IP 白名单 | **IAM 策略** | IAM 策略 + 临时公钥 |
| **单点故障风险** | 有（除非自建多 AZ 高可用） | 无 | 无（Endpoint 可配置高可用） |
| **审计能力** | 需自行搭建日志方案 | 原生集成 CloudWatch Logs/S3 | 依赖 CloudTrail 记录连接事件 |

## 与 NAT 实例的关系（考试提示）

- 堡垒机和 [[NAT Instance]] 都部署在**公有子网**，且都可以是普通 EC2 实例——在成本敏感场景下，两者角色**可以合并**到同一台实例上（NAT 实例兼作堡垒机），减少需要维护的实例数量，完整说明见 [[NAT Instance]] 笔记
- 但 [[NAT Gateway]] **不能**兼作堡垒机（它不是可登录的实例），若已采用 NAT 网关，堡垒机（或其替代方案）必须**独立部署**

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **需要安全访问私有子网 EC2，且不希望开放入站端口/管理堡垒机** | 改用 Session Manager（默认推荐） |
| **希望保留 SSH/RDP 使用习惯，但不给实例分配公网 IP** | EC2 Instance Connect Endpoint |
| **遗留架构/合规要求必须使用传统堡垒机模式** | 部署加固的堡垒机 + 安全组 IP 白名单 + 密钥认证 |
| **成本敏感场景，希望减少需要维护的公有子网实例数量** | NAT 实例兼作堡垒机（而非分别部署两台） |
| **需要对管理会话做集中审计** | Session Manager（原生审计）优于自建堡垒机日志方案 |
| **堡垒机单点故障，管理员失去访问入口** | 多可用区部署堡垒机，或直接迁移到 Session Manager 消除该风险 |

## 考试重点总结

### SAA-C02 高频考点

1. **堡垒机是部署在公有子网的加固跳板实例**：作为访问私有子网资源的唯一入口
2. **安全组必须限制到特定管理员 IP**：而非 `0.0.0.0/0`，私有实例安全组应引用堡垒机安全组
3. **堡垒机本身是攻击面和单点故障**：这是它相较云原生方案的核心劣势
4. **Session Manager 是当前默认推荐**：无需开放入站端口、无需管理密钥、IAM 权限控制、原生审计
5. **EC2 Instance Connect Endpoint 是"无公网 IP 版"SSH/RDP**：保留协议使用习惯，但目标实例无需公网 IP
6. **"不希望开放入站端口"是识别 Session Manager 答案的关键词**：题目出现该表述时几乎不会是堡垒机
7. **堡垒机高可用需自行搭建**：多 AZ 部署或弹性 IP 漂移，Session Manager 天然无此问题
8. **NAT 实例可兼作堡垒机，NAT 网关不能**：这是选择 NAT 实例而非 NAT 网关的场景之一
9. **审计能力对比**：堡垒机需自建日志方案，Session Manager 原生集成 CloudWatch Logs/S3
10. **传统方案 vs 云原生方案是常见考题模式**：堡垒机代表"传统"，Session Manager/ICE 代表"云原生"，多数新题倾向后者

### 场景题解题思路

```
场景分析 → 判断访问私有子网资源的方案
├── "不希望开放入站端口，不想管理堡垒机" → Session Manager
├── "希望保留 SSH/RDP 习惯，但实例不能有公网 IP" → EC2 Instance Connect Endpoint
├── "遗留系统/合规要求必须用传统跳板机模式" → 部署加固堡垒机
├── "堡垒机是单点故障，需要提高可用性" → 多 AZ 部署，或迁移到 Session Manager
├── "希望减少公有子网内维护的实例数量" → NAT 实例兼作堡垒机
├── "需要对管理会话做审计" → Session Manager（原生审计）
└── "私有实例的安全组该如何配置" → 仅放行堡垒机安全组/私有 IP 来源
```

## 最佳实践

1. **新架构优先评估 Session Manager 而非部署堡垒机**：消除入站端口暴露和堡垒机的运维/安全负担
2. **确需使用堡垒机时严格限制安全组来源**：仅放行管理员的特定出口 IP，而非任意来源
3. **私有实例安全组引用堡垒机安全组 ID**：而非放行整个 VPC CIDR，缩小信任范围
4. **堡垒机上只安装必要工具，及时打补丁**：最小化攻击面，降低被攻破概率
5. **启用会话日志与审计**：无论选择堡垒机还是 Session Manager，都应保留管理访问的完整审计记录
6. **多可用区部署堡垒机避免单点故障**：若暂不能迁移到 Session Manager，至少保证堡垒机本身的高可用
7. **逐步淘汰长期存活的堡垒机架构**：向 Session Manager/EC2 Instance Connect Endpoint 迁移，从根本上消除入站端口攻击面
