# AWS Outposts - 本地部署的 AWS 基础设施

> **AWS Outposts** 把**由 AWS 设计、AWS 负责运维**的物理硬件（机架式服务器）直接部署到客户的**本地数据中心或机房**，让客户能用**与云上完全一致的 API、控制台、工具链**在本地运行 EC2、EBS、[[ECS]]/[[EKS]]、RDS 等 AWS 服务——本质是把一小片 AWS 区域"物理搬到"客户现场。它面向的是"**数据必须留在本地**（合规/数据主权）"或"**需要对本地系统超低延迟**"这两类无法单纯依赖公有云区域解决的场景，与 Local Zones、Wavelength 一起构成 AWS 覆盖"云—边缘—本地"全谱系的基础设施选项。
>
> 相关文档：[[VPC]] | [[Subnet]] | [[Route Table]] | [[Direct Connect]] | [[Site to Site VPN]] | [[EC2]] | [[S3]]

## 核心概念

### 物理形态

| 形态 | 说明 |
|------|------|
| **Outposts 机架（Rack）** | 标准 42U 机架，容量可按需扩展，多机架可组网，适合大规模本地算力需求 |
| **Outposts 服务器（Server）** | 更小的 1U/2U 服务器形态，适合空间受限或算力需求较小的边缘场所（如零售门店、工厂车间） |

- **硬件的采购、安装、监控、打补丁、故障更换均由 AWS 远程负责**——客户只需要管理**运行在其上的工作负载**，不涉及底层硬件运维，这与自建本地数据中心的运维模式有本质区别

### VPC 的物理延伸（考试高频）

- 一个 Outpost **关联到某个 AWS 区域**，并**附加到客户已有的 [[VPC]]**——在其上创建的**子网（Outpost 子网）**是该 VPC 地址空间的**自然延伸**，与云上子网共享同一套 CIDR 规划、[[Security Group]]、[[NACL]] 等安全机制
- **考试要点**：**Outposts 子网不是一个独立的网络，而是现有 VPC 的一部分**——题目描述"需要让本地机房的资源与云上 VPC 内的资源使用统一的私有 IP 空间、安全组规则" → Outposts 子网天然满足，无需额外搭建 VPN/Peering 去"打通"两边（两边本来就是同一个 VPC）。

### 本地网关（Local Gateway, LGW）

- Outposts 子网通过**本地网关（Local Gateway）**访问 Outpost **所在本地站点的网络**，角色类似于云上子网通过 [[Internet Gateway]] 访问公网——只是这里访问的目标是**本地局域网**而非互联网
- 完整的路由目标类型对照见 [[Route Table]] 独立笔记

### 与父区域的连接依赖（考试陷阱）

- Outposts **必须通过 [[Direct Connect]] 或 [[Site to Site VPN]] 与所属的父 AWS 区域保持可靠、低延迟的网络连接**，用于同步控制平面操作（创建资源、监控、计费等）
- **考试陷阱**：**与父区域的连接中断不会导致本地已运行的工作负载立即停止**——已经在跑的 EC2 实例等资源可以继续在本地处理数据（数据平面独立运行）；但**无法创建新资源、无法调用触达区域控制平面的 API**，因此"完全断网长期运行"并非 Outposts 的设计目标，题目描述"要求即使与云端完全断开也能长期新增资源" → Outposts 无法满足这一假设，仍需要基本的网络连接。

### 并非所有 AWS 服务都支持 Outposts

- Outposts 支持的服务是**精选子集**（EC2、EBS、[[ECS]]/[[EKS]]、RDS、[[S3]] on Outposts 等），并非把整个 AWS 服务目录都搬到本地
- **S3 on Outposts 是独立且能力受限的产品**：本地固定容量的对象存储，API 与云上 S3 兼容但**不等同于**标准 S3（如不具备与云上 S3 完全一致的存储类别体系和默认跨区域复制能力），不要将其与标准 S3 的存储类别混为一谈

## AWS Outposts vs Local Zones vs Wavelength（考试高频对比）

| 维度 | AWS Outposts | AWS Local Zones | AWS Wavelength |
|------|-------------|------------------|-----------------|
| **物理位置** | **客户自己的**数据中心/机房 | AWS 运营的、部署在**大城市都会区**的基础设施扩展点 | 嵌入**电信运营商的 5G 网络**内部 |
| **硬件归属与运维** | AWS 硬件，但物理装在客户场地，客户仍需提供机房空间/电力 | 完全由 AWS 拥有和运营，客户**无需**提供任何物理场地 | 完全由 AWS 和电信运营商共同运营 |
| **核心目标** | 数据主权/合规要求数据**必须留在本地**，或需要对**本地遗留系统**超低延迟 | 让应用**物理上更接近特定城市的最终用户**，降低延迟，但仍是"云"的一部分 | 让应用**物理上更接近 5G 移动设备**，服务于移动边缘计算场景 |
| **使用方式** | 需要**申请、安装物理机架/服务器** | 像选择一个额外的**可用区**一样直接在 VPC 中创建子网即可，无需管理硬件 | 类似 Local Zones，在支持的运营商网络区域创建子网 |

> **考试陷阱**：**三者都解决"低延迟/贴近特定位置"的问题，但物理归属和适用场景完全不同**——题目描述"合规要求某些数据必须永久保存在企业自己的机房内，不能进入 AWS 数据中心" → 只有 **Outposts** 能满足（数据物理上留在客户场地）；题目描述"需要降低某个大城市终端用户的访问延迟，但不想自己管理任何硬件" → **Local Zones**；题目描述"移动应用需要与 5G 网络设备之间达到最低延迟" → **Wavelength**。三者混淆是这一知识点最常见的失分点。

## 计费模式

- 按 Outposts **物理容量**订阅计费（通常为 1 年或 3 年期），类似 Reserved 的承诺型定价结构
- 运行在 Outposts 上的具体服务（EC2、EBS 等）**另计使用费**，与云上对应服务的计费逻辑基本一致

## 典型应用场景

| 场景 | 推荐方案 |
|------|---------|
| **合规要求数据必须物理保留在企业自有机房** | AWS Outposts |
| **工厂/门店等本地场所需要对本地设备低延迟处理，同时希望用统一的 AWS API 管理** | AWS Outposts |
| **需要让本地机房资源与云上 VPC 资源共享同一套私有 IP 和安全组规则** | AWS Outposts 子网（VPC 的自然延伸） |
| **只是想降低某个都会区终端用户的访问延迟，不想自建/托管硬件** | 改用 AWS Local Zones |
| **移动应用需要贴近 5G 网络的最低延迟** | 改用 AWS Wavelength |
| **需要长期完全离线运行并持续创建新资源** | 均不满足——所有方案都需要与父区域保持基本连接 |

## 考试重点总结

### SAA-C02 高频考点

1. **Outposts 是物理装在客户自有场地的 AWS 硬件**：由 AWS 远程运维，客户只管理其上的工作负载
2. **Outposts 子网是现有 VPC 的自然延伸**：共享同一套 CIDR、安全组、NACL，而非独立网络
3. **本地网关（LGW）负责 Outposts 子网访问本地站点网络**：角色类似云上的 Internet Gateway，但面向本地局域网
4. **必须通过 Direct Connect 或 Site-to-Site VPN 连接父区域**：用于控制平面操作
5. **与父区域断连不会中断已运行的工作负载，但无法新建资源**：数据平面独立、控制平面依赖连接
6. **并非所有 AWS 服务都支持 Outposts**：S3 on Outposts 是能力受限的独立产品，不等同于标准 S3
7. **Outposts vs Local Zones vs Wavelength 判断依据是"硬件物理归属"和"目标延迟对象"**：客户自有机房 → Outposts；都会区终端用户 → Local Zones；5G 移动设备 → Wavelength
8. **Local Zones/Wavelength 无需客户管理硬件**：像选择一个额外可用区一样直接使用
9. **计费为物理容量订阅（1/3 年）+ 具体服务使用费**：与 Reserved 定价结构类似
10. **不能假设 Outposts 支持完全离线长期运行**：网络连接是设计前提，而非可选项

### 场景题解题思路

```
场景分析 → 判断 AWS Outposts 相关配置
├── "数据必须物理留在企业自有机房，不能进入 AWS 数据中心" → AWS Outposts
├── "本地资源需要与云上 VPC 共享私有 IP/安全组" → Outposts 子网（VPC 延伸）
├── "本地站点内部网络访问" → 本地网关（Local Gateway）
├── "只需降低某都会区用户延迟，不想管硬件" → AWS Local Zones
├── "移动应用需贴近 5G 网络最低延迟" → AWS Wavelength
├── "与父区域断连后能否继续新建资源" → 不能，只有已运行的工作负载不受影响
└── "怀疑某 AWS 服务能否在 Outposts 上运行" → 需核查 Outposts 支持的服务列表，而非默认全部支持
```

## 最佳实践

1. **部署前核实所需服务是否在 Outposts 支持列表内**：避免假设所有 AWS 服务都能本地运行
2. **规划可靠的 Direct Connect 或 Site-to-Site VPN 连接父区域**：这是 Outposts 持续可用的前提，而非锦上添花的选项
3. **不要把 S3 on Outposts 当作标准 S3 的本地版本**：两者能力和存储类别体系并不完全对等，需按实际限制规划容量和使用方式
4. **合规驱动的场景优先评估 Outposts，延迟驱动但无硬件托管能力的场景优先评估 Local Zones/Wavelength**：避免为了"降低延迟"而不必要地承担本地硬件的场地和电力成本
5. **把 Outposts 子网当作现有 VPC 规划的一部分，而非独立环境**：统一纳入整体的 CIDR 规划和安全组策略设计
6. **评估容量需求时预留增长空间**：物理机架的扩容周期远长于云上按需扩容，需要提前规划
