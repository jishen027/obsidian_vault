# Internet Gateway - 互联网网关

> **互联网网关（Internet Gateway, IGW）**是 [[VPC]] 与公共互联网之间的**双向**连接组件——既允许 VPC 内拥有公网 IP 的资源**接受**来自互联网的入站请求，也允许它们**主动**访问互联网。它与只允许"单向出站"的 [[NAT Gateway]]、只服务 IPv6 的 Egress-Only Internet Gateway 共同构成 VPC 的三种互联网边界网关，也是判定"公有子网"的核心依据。
>
> 相关文档：[[VPC]] | [[Subnet]] | [[Route Table]] | [[NAT Gateway]] | [[Security Group]] | [[NACL]] | [[Virtual Private Gateway]]

---

## 核心概念

### IGW 的双向连接能力

- **入站**：允许拥有**公网 IP（或弹性 IP）**的实例接受来自互联网的连接请求
- **出站**：允许 VPC 内实例**主动**发起对互联网的访问
- 这种**双向**特性是 IGW 与 [[NAT Gateway]]（仅允许出站，阻止入站）最本质的区别——题目描述"需要允许双向通信" → IGW；描述"只允许主动出站，禁止外部主动连入" → NAT 网关

### 管理特性

| 特性 | 说明 |
|------|------|
| **水平扩展、高可用、无带宽限制** | IGW 是 AWS 托管的**分布式冗余组件**，不存在单点故障，也**无需为可用性或带宽做任何额外配置** |
| **不占用物理 IP/带宽瓶颈** | 不同于 EC2 实例或 NAT 网关，IGW 本身不消耗实例资源，纯粹作为逻辑网关组件存在 |
| **一对一绑定** | **每个 VPC 只能关联一个 IGW**，一个 IGW 也只能附加到一个 VPC |
| **需要显式创建并附加** | IGW 需要先创建，再显式**附加（Attach）**到目标 VPC；新建的默认 VPC 会自动创建并附加好 IGW |
| **免费** | IGW 本身**不产生费用**，仅通过它传输的数据可能产生标准的数据传输费用 |

## IGW 如何判定"公有子网"（考试最高频）

**子网本身没有固有的"公有/私有"属性**——只有当子网关联的**路由表**中存在一条指向该 IGW 的默认路由（`0.0.0.0/0 → igw-xxxxx`）时，该子网才被视为"公有子网"，完整的判定逻辑和常见误区见 [[Subnet]] 笔记中"公有子网 vs 私有子网"章节。

> **考试陷阱**：**"公有子网"是四个条件共同作用的结果，而不是配置了 IGW 就万事俱备**——真正让一台 EC2 实例能够被公网访问，需要**同时满足**：① VPC 已附加 IGW；② 实例所在子网的路由表指向该 IGW；③ 实例本身拥有**公网 IP 或弹性 IP**；④ [[Security Group]] 和 [[NACL]] 均放行相应流量。题目中若这四项任一缺失，都会导致"实例在公有子网却无法从公网访问"——这是 SAA-C02 中最常见的排障类题型，解题时应逐一排查这四层，而非只检查其中一项就下结论。

---

## IGW 的地址转换职责（考试提示）

- 当实例拥有**公网 IP 或弹性 IP** 时，实际的**一对一网络地址转换（1:1 NAT）**是由 **IGW 在网关层面**完成的——它在实例的私有 IP 和公网 IP 之间做地址映射，实例自身的操作系统内部**始终只感知私有 IP**
- 这一点常被误解为"公有子网的地址转换也需要 NAT 网关"——**并不需要**：[[NAT Gateway]] 只服务**私有子网**的出站场景；公有子网内拥有公网 IP 的实例，其地址转换完全由 **IGW 自身**处理，不涉及 NAT 网关

---

## Egress-Only Internet Gateway（IPv6 专用，考试提示）

IPv6 地址空间充足，**默认所有地址均可公网路由**，不存在"私网地址转公网地址"的 NAT 概念。当 IPv6 私有子网中的资源需要"只出不进"（主动访问外部、但拒绝外部主动连入）时，使用**仅出站互联网网关（Egress-Only Internet Gateway, EIGW）**：

| 维度 | Internet Gateway (IGW) | Egress-Only Internet Gateway (EIGW) |
|------|------------------------|--------------------------------------|
| **适用地址族** | IPv4 / IPv6 均可 | 仅 **IPv6** |
| **通信方向** | 双向（入站 + 出站） | **仅出站**，天然阻止外部主动发起的入站连接 |
| **对应的 IPv4 概念** | 无直接对应 | 相当于 IPv4 场景下的 [[NAT Gateway]] |
| **部署方式** | 附加到 VPC，需路由表指向 | 附加到 VPC，需在私有子网路由表中添加指向它的 IPv6 默认路由（`::/0 → eigw-xxxxx`） |
| **是否需要弹性 IP** | 否（自身不需要地址） | 否 |

> **考试要点**：**IPv4 私有子网出站用 NAT 网关，IPv6 私有子网出站用 Egress-Only Internet Gateway**——两者概念不可混用，也不能互相替代；EIGW 是**有状态**的，自动放行已建立连接的返回流量，行为上更接近 NAT 网关而非普通 IGW。

## IGW vs NAT Gateway vs Virtual Private Gateway（考试高频对比）

| 维度 | Internet Gateway | [[NAT Gateway]] | [[Virtual Private Gateway]] |
|------|-------------------|-------------------|-------------------------------|
| **连接对象** | 公共互联网 | 公共互联网（代理私有子网出站） | 本地数据中心（VPN） |
| **通信方向** | 双向 | 仅出站 | 双向（经加密隧道） |
| **典型部署** | 附加到 VPC，公有子网路由指向它 | 部署在公有子网，私有子网路由指向它 | 附加到 VPC，作为 VPN 的云端锚点 |
| **每 VPC 数量限制** | 1 个 | 无限制（通常每 AZ 一个） | 传统 VGW 为 1 个 |
| **判定公有子网** | ✅ 是核心依据 | ❌ 不影响子网公私属性 | ❌ 不影响子网公私属性 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **面向公网提供服务（Web 服务器、负载均衡器）** | VPC 附加 IGW + 公有子网路由表指向 IGW + 实例分配公网 IP |
| **私有子网 IPv4 资源需要出站但拒绝入站** | 改用 [[NAT Gateway]]（而非 IGW） |
| **私有子网 IPv6 资源需要出站但拒绝入站** | Egress-Only Internet Gateway |
| **实例在"公有子网"却无法被公网访问** | 按四层逐一排查：IGW 是否已附加 → 路由表是否指向 IGW → 实例是否有公网 IP → Security Group/NACL 是否放行 |
| **需要与本地数据中心建立双向加密连接** | 改用 [[Virtual Private Gateway]]（而非 IGW） |
| **判断某公有子网内实例的地址转换由谁完成** | IGW 自身完成 1:1 NAT，无需 NAT 网关参与 |

## 考试重点总结

### SAA-C02 高频考点

1. **IGW 提供双向连接**：允许入站也允许出站，与只允许出站的 NAT 网关本质不同
2. **每个 VPC 仅能关联一个 IGW**：需要显式创建并附加，默认 VPC 已自动配置好
3. **IGW 水平扩展、高可用、免费、无带宽瓶颈**：无需为它做任何容量规划
4. **公有子网判定需要"四件套"同时满足**：VPC 附加 IGW + 路由表指向 IGW + 实例有公网 IP + Security Group/NACL 放行
5. **公网 IP 的地址转换由 IGW 完成，而非 NAT 网关**：NAT 网关只服务私有子网出站场景
6. **IPv6 场景用 Egress-Only Internet Gateway 替代 NAT 网关**：EIGW 仅出站、有状态，是 IPv4 NAT 网关的 IPv6 对应物
7. **IGW 不做防火墙式过滤**：允许/拒绝判断仍由 [[Security Group]]/[[NACL]] 负责，完整机制见 [[NAT Gateway]] 笔记中的相关陷阱
8. **IGW ≠ Virtual Private Gateway**：前者连接公共互联网，后者连接本地数据中心（VPN），两者不可混淆
9. **IGW 不占用物理 IP、不消耗实例资源**：纯逻辑网关组件，区别于需要绑定 EC2/EIP 的 NAT 实例或 NAT 网关
10. **判断题干关键词**："双向通信/接受入站连接" → IGW；"仅主动出站，禁止入站" → NAT 网关（IPv4）或 EIGW（IPv6）

### 场景题解题思路

```
场景分析 → 判断 Internet Gateway 相关配置
├── "需要允许公网双向访问 VPC 内资源" → Internet Gateway
├── "实例在公有子网却无法被公网访问" → 按四层排查：IGW 附加 → 路由表 → 公网IP → SG/NACL
├── "公有子网实例的公网 IP 转换由谁完成" → IGW 自身（无需 NAT 网关）
├── "私有子网 IPv4 资源需要出站但拒绝入站" → NAT Gateway（而非 IGW）
├── "私有子网 IPv6 资源需要出站但拒绝入站" → Egress-Only Internet Gateway
├── "需要与本地数据中心建立双向加密连接" → Virtual Private Gateway（而非 IGW）
└── "判断某子网是否为公有子网" → 检查路由表是否有指向 IGW 的路由
```

## 最佳实践

1. **公有子网架构必须完整核对"四件套"**：附加 IGW、路由表指向 IGW、实例公网 IP、Security Group/NACL 放行，缺一不可，这是排查"公有子网无法访问"的标准流程
2. **敏感资源始终部署在私有子网，不依赖 IGW**：即使需要出站访问，也应通过 NAT 网关或 Egress-Only Internet Gateway，而非让实例直接挂载公网 IP
3. **IPv6 架构规划阶段明确区分 IGW 与 Egress-Only Internet Gateway 的角色**：不要用处理 IPv4 NAT 的思维直接套用到 IPv6 场景
4. **不要把 IGW 当作访问控制手段**：流量过滤职责始终交给 Security Group 和 NACL，IGW 只负责连通性
5. **多 VPC 架构中注意 IGW 的一对一限制**：每个 VPC 需要独立附加自己的 IGW，不能跨 VPC 共享
6. **审计公网暴露面时优先检查 IGW + 路由表的组合**：这是判断"哪些子网理论上可被公网访问"最快速的入口，而非逐个检查安全组
