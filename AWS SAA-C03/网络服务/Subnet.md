# Subnet - 子网

> **子网（Subnet）**是对 [[VPC]] CIDR 地址空间的进一步细分，是部署 [[EC2]] 等资源的实际落地位置。每个子网**严格绑定单一可用区（AZ）**，并通过关联的**路由表**决定自己是"公有"还是"私有"——这个由路由表而非其他配置决定"公私属性"的机制，是子网相关考点中最容易被误解的地方。
>
> 相关文档：[[VPC]] | [[NACL]] | [[Security Group]] | [[ENI]] | [[VPC Peering]] | [[Virtual Private Gateway]] | [[Route Table]] | [[NAT Gateway]] | [[Internet Gateway]] | [[CIDR]]

---

## 核心概念

### 子网与可用区的绑定关系

- 一个子网**必须完全落在单一可用区内**，不能跨可用区——这与 VPC 本身"跨越区域内所有可用区"形成鲜明对比
- **高可用架构的标准做法**：在**多个可用区分别创建子网**（如每个 AZ 各一个公有 + 一个私有子网），确保单个 AZ 故障不会导致服务整体不可用

### 子网 CIDR 规划

- 子网 [[CIDR]] 必须是其所属 VPC CIDR 的**子集**，且**不能与同一 VPC 内的其他子网重叠**
- 支持的子网掩码范围与 VPC 一致：**`/16` 到 `/28`**（即最大 65,536、最小 16 个 IP 地址），CIDR 记法、前缀长度计算方式详见 [[CIDR]] 独立笔记
- **每个子网 AWS 固定预留 5 个 IP 地址**，规划容量时必须扣除这部分损耗：

| IP 地址 | 用途 |
|---------|------|
| `x.x.x.0` | 网络地址 |
| `x.x.x.1` | VPC 隐式路由器 |
| `x.x.x.2` | DNS 解析（Amazon 提供的 DNS 服务器） |
| `x.x.x.3` | AWS 保留，供未来使用 |
| `x.x.x.255` | 网络广播地址（AWS 不支持广播，但仍保留该地址） |

> **考试要点**：题目要求"子网需要容纳 X 台主机"时，必须在计算可用 IP 数量时**额外减去 5 个保留地址**，而非直接套用 CIDR 理论上的可用主机数公式。

## 公有子网 vs 私有子网（考试最高频考点）^public-subnet-def

**子网本身没有"公有"或"私有"的固有属性——这个属性完全由其关联的路由表中是否存在指向互联网网关（[[Internet Gateway|IGW]]）的路由决定**：

| 类型 | 判定依据 | 路由表关键条目 |
|------|---------|--------------|
| **公有子网** | 路由表中存在指向 **[[Internet Gateway\|IGW]]** 的默认路由 | `0.0.0.0/0 → igw-xxxxx` |
| **私有子网** | 路由表中**没有**直接指向 IGW 的路由 | 出站通常指向 [[NAT Gateway|NAT 网关]]：`0.0.0.0/0 → nat-xxxxx` |

> **考试陷阱**：**"公有子网"不等于"子网内实例能被公网访问"**——即使子网关联的路由表指向 IGW，实例仍需**同时满足**以下两个条件才能真正与公网通信：① 分配了**公网 IP 或弹性 IP**；② 所在子网的路由表**确实**指向 IGW。题目描述"EC2 位于公有子网但仍无法从公网访问" → 检查该实例是否忘记分配公网 IP（或是否在启动时勾选"自动分配公有 IP"），而非怀疑路由表配置错误；反之，"实例有公网 IP 却无法联网" → 检查子网的路由表是否真的指向了 IGW。完整的四层判定条件（IGW 附加、路由表、公网 IP、Security Group/NACL）见 [[Internet Gateway]] 独立笔记。

### 自动分配公有 IP

- 子网级别有一个开关**"自动分配公有 IPv4 地址"**，开启后该子网内新启动的实例会自动获得公网 IP，无需手动指定
- 默认 VPC 中的默认子网**默认开启**此选项；自定义 VPC 中新建子网**默认关闭**，需要显式开启或在启动实例时手动指定

## 路由表关联

- **每个子网必须（且只能）关联一个路由表**；一个路由表可以同时关联**多个**子网
- **主路由表（Main Route Table）**：VPC 创建时自动生成，未显式关联自定义路由表的子网默认使用主路由表
- **自定义路由表**：可创建并显式关联到特定子网，实现公有/私有子网使用不同出站策略
- **本地路由（Local Route）**：每个路由表都隐式包含一条指向 VPC 自身 CIDR 的本地路由，**不可编辑或删除**，确保同一 VPC 内子网间默认可以互通
- **最长前缀匹配（Longest Prefix Match）**：当多条路由都能匹配目标地址时，路由表选择**前缀最精确（掩码最长）**的一条，而非按添加顺序生效

> **考试要点**：题目描述"需要为某个子网设置区别于默认路由的出站规则，而不影响其他子网" → 创建**自定义路由表**并显式关联到该子网，而非修改主路由表（会影响所有仍关联主路由表的子网）。

> 路由表的完整目标类型（VGW/[[Transit Gateway]]/[[VPC Endpoints|终端节点]]等）、路由传播机制和配额限制，见 [[Route Table]] 独立笔记

## 子网级别的安全组件

| 组件 | 关联方式 | 说明 |
|------|---------|------|
| **[[NACL]]** | 子网级，一个子网仅关联一个 NACL | 无状态，子网进出流量的第一道防线，完整能力见 [[NACL]] 独立笔记 |
| **[[Security Group]]** | 实例（[[ENI]]）级，非子网级 | 有状态，是更细粒度的第二道防线 |

- 子网本身**不直接承载安全组**，安全组挂载在实例的 [[ENI]] 上；但**流量进入子网时必须先通过 NACL**，再到达实例的安全组，两者共同构成纵深防御（完整对比见 [[NACL]] 笔记中"NACL vs Security Group"章节）

## IPv6 子网（考试提示）

- VPC 若启用 IPv6，会获得一个 **`/56`** 的 IPv6 CIDR 块；子网从中划分 IPv6 CIDR 时，**大小固定为 `/56` 中的 `/64`**，不像 IPv4 子网掩码那样可灵活调整
- IPv6 地址**默认全部可公网路由**（无 NAT 概念），若需要私有子网中的实例主动访问外部但不接受入站连接，需使用**仅出站的互联网网关（Egress-Only Internet Gateway）**，而非普通 [[NAT Gateway|NAT 网关]]

> **考试要点**：**IPv4 私有子网出站用 [[NAT Gateway|NAT 网关]]，IPv6 私有子网出站用 Egress-Only Internet Gateway**——两者概念不可混用，因为 IPv6 地址空间充足，AWS 采用"仅出站网关 + 有状态防火墙规则"而非地址转换来实现类似效果。

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **面向公网的 Web 服务器/负载均衡器** | 公有子网（路由表指向 IGW）+ 实例分配公网 IP |
| **数据库、应用服务器等不应直接暴露公网的资源** | 私有子网（路由表指向 [[NAT Gateway|NAT 网关]]出站） |
| **高可用架构** | 每个可用区各创建公有 + 私有子网，跨 AZ 部署 |
| **不同子网需要差异化的出站/安全策略** | 创建自定义路由表，分别关联到对应子网 |
| **子网级别粗粒度访问控制（如封禁恶意 IP 段）** | 关联自定义 [[NACL]] |
| **IPv6 私有子网需要主动访问外部但拒绝入站** | Egress-Only Internet Gateway |
| **EC2 位于公有子网却无法被公网访问** | 检查是否遗漏分配公网 IP/弹性 IP |

## 考试重点总结

### SAA-C02 高频考点

1. **子网严格绑定单一 AZ**：不能跨可用区，这是高可用架构必须多子网部署的根本原因
2. **公/私有属性由路由表决定，而非其他配置**：路由表存在指向 IGW 的路由 → 公有子网
3. **"公有子网"≠"实例可被公网访问"**：还需实例本身具备公网 IP，两个条件缺一不可
4. **每个子网预留 5 个 IP**：容量规划必须扣除这部分损耗
5. **一个子网只能关联一个路由表，一个路由表可关联多个子网**：与 NACL 的关联模式一致
6. **本地路由不可删除**：保证同一 VPC 内跨子网互通的默认能力
7. **最长前缀匹配决定路由优先级**：而非路由添加的先后顺序
8. **IPv6 子网固定为 `/64`**：不像 IPv4 子网掩码可灵活调整
9. **IPv6 私有子网出站用 Egress-Only Internet Gateway**：与 IPv4 的 [[NAT Gateway|NAT 网关]]是不同的机制
10. **NACL 子网级、Security Group 实例级**：流量先过 NACL 再到安全组，两层纵深防御

### 场景题解题思路

```
场景分析 → 判断子网相关配置
├── "需要判断某子网是公有还是私有" → 检查路由表是否有指向 IGW 的路由
├── "实例在公有子网却无法被公网访问" → 检查实例是否分配了公网 IP/弹性 IP
├── "实例有公网 IP 却无法联网" → 检查子网路由表是否真正指向 IGW
├── "需要为特定子网设置独立的出站策略" → 创建并关联自定义路由表
├── "子网需要容纳 N 台主机，如何计算 CIDR" → 可用 IP = 2^(32-掩码) - 5（[[CIDR]] 计算公式）
├── "需要跨可用区容错" → 每个 AZ 分别创建子网
├── "IPv6 私有子网需要出站但拒绝入站" → Egress-Only Internet Gateway（非 [[NAT Gateway|NAT 网关]]）
└── "子网级别封禁恶意 IP 段" → 关联自定义 NACL
```

## 最佳实践

1. **高可用架构跨多可用区部署子网**：每个 AZ 至少一个公有 + 一个私有子网，避免单 AZ 故障导致整体不可用
2. **公有/私有子网使用独立的自定义路由表**：不要依赖主路由表承载差异化的出站策略
3. **子网 CIDR 规划时预留增长空间**：结合每子网 5 个保留 IP 的损耗，避免后期扩容需要重建子网
4. **数据库等敏感资源始终部署在私有子网**：即使需要访问互联网更新补丁，也应通过 [[NAT Gateway|NAT 网关]]而非直接暴露公网 IP
5. **IPv6 架构提前规划 Egress-Only Internet Gateway**：不要沿用 IPv4 的 NAT 思维处理 IPv6 出站需求
6. **善用 NACL + Security Group 的双层防御**：子网级粗粒度过滤 + 实例级精细控制，而非只依赖其中一层
7. **变更路由表前确认关联的子网范围**：修改主路由表会影响所有未显式关联自定义路由表的子网，避免误操作波及不相关资源
