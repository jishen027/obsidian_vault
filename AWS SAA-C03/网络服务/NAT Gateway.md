# NAT Gateway - 私有子网出站访问

> **NAT 网关（NAT Gateway）**让**私有子网**中的实例能够**主动发起**对互联网的访问（如下载补丁、调用外部 API），同时**阻止**互联网上的主机反向发起连接——这与允许双向连接的**互联网网关（[[Internet Gateway|IGW]]）**共同构成 VPC 边界流量控制的两个核心组件，也是判断"公有子网 vs 私有子网"的关键依托。
>
> 相关文档：[[VPC]] | [[Subnet]] | [[Route Table]] | [[Internet Gateway]] | [[NAT Instance]] | [[Bastion Hosts]] | [[VPC Endpoints]] | [[Security Group]] | [[NACL]] | [[EC2]] | [[AWS Lambda]]

## 核心概念

### 互联网网关（[[Internet Gateway|Internet Gateway, IGW]]）

- **核心功能**：为 VPC 提供连接互联网的能力，允许拥有公网 IP 的实例**双向通信**——既能主动访问公网，也能**接受**来自公网的入站请求
- **管理特性**：IGW 是**水平扩展、高可用、无带宽限制**的托管组件，不占用物理 IP；**每个 VPC 只能关联一个 IGW**
- **判定公有子网的依据**：子网路由表中存在指向 IGW 的默认路由（`0.0.0.0/0 → igw-xxxxx`）即为公有子网，完整的公私判定逻辑和常见误区见 [[Subnet]] 笔记中"公有子网 vs 私有子网"章节
- IGW 的完整特性、地址转换机制、与 NAT 网关/[[Virtual Private Gateway]] 的对比及 Egress-Only Internet Gateway 详见 [[Internet Gateway]] 独立笔记

### 为什么私有子网还需要出站能力

- **私有子网的资源**（如数据库、内部应用服务器）通常**不应该**接受来自公网的入站连接，但仍需要**主动**访问互联网完成软件更新、调用第三方 API 等操作
- **NAT（网络地址转换）设备**正是为这类"只出不进"的需求设计——私有子网实例的出站流量经 NAT 设备转换源地址后送达 IGW，响应流量能原路返回，但公网**无法主动发起**连接到私有子网内的实例

## NAT Gateway vs NAT Instance（考试最高频对比）

> NAT 实例的部署要求、独特能力（端口转发/[[Bastion Hosts|堡垒机]]复用/安全组过滤）、自建高可用方案及官方 NAT AMI 现状详见 [[NAT Instance]] 独立笔记

| 维度 | NAT 网关（NAT Gateway） | [[NAT Instance\|NAT 实例（NAT Instance）]] |
|------|------------------------|--------------------------|
| **管理方式** | AWS **全托管**服务 | 运行特定 AMI 的普通 EC2 实例，需**自行管理** |
| **带宽** | 自动扩展，最高 **100 Gbps** | 取决于所选实例类型，需手动升级规格应对增长 |
| **可用性** | 单个 NAT 网关部署在**单个可用区**内，AWS 保证该 AZ 内高可用 | 需自行配置高可用（如 Auto Scaling + 故障转移脚本） |
| **部署位置** | **必须**部署在**公有子网** | 可部署在任意子网（但需要访问公网时也应在公有子网） |
| **弹性 IP** | 必须分配一个弹性 IP | 需要分配弹性 IP 或使用公网 IP |
| **源/目的地检查** | **无需配置**（AWS 托管，自动处理） | **必须手动禁用**，否则实例会拒绝转发不属于自己的流量 |
| **安全组** | **不支持**关联安全组（NAT 网关本身没有安全组概念） | 作为 EC2 实例，**可以**关联安全组进行精细流量控制 |
| **端口转发/堡垒机复用** | **不支持**，只做地址转换 | **支持**，可同时兼作堡垒机（Bastion Host）或端口转发网关 |
| **打补丁/维护** | AWS 负责，用户无需干预 | 用户需自行维护操作系统补丁和安全更新 |
| **成本** | 按小时运行费 + 数据处理量计费 | EC2 实例费 + 弹性 IP 费用，通常小规格实例更便宜但需承担运维成本 |

> **考试陷阱**：**"源/目的地检查（Source/Destination Check）"是 NAT 实例区别于 NAT 网关最核心的配置动作**——EC2 实例默认会检查数据包的源/目的地址是否与自身匹配，不匹配则丢弃；NAT 实例的职责恰恰是**转发不属于自己的流量**，因此必须**显式禁用**该检查，否则私有子网实例的流量会被 NAT 实例丢弃，表现为"配置看似正确但私有子网仍无法访问公网"。NAT 网关是托管服务，**不存在**这项配置。

## 部署与高可用

- **NAT 网关必须部署在公有子网**（因为它自己也需要通过 IGW 访问公网），私有子网中的实例通过路由表将默认出站流量指向 NAT 网关
- **单个 NAT 网关仅存在于一个可用区**，若该 AZ 故障，依赖它的所有私有子网都会**失去出站能力**
- **高可用标准做法**：在**每个可用区**分别部署一个 NAT 网关，并让该 AZ 内的私有子网路由表指向**同 AZ 的 NAT 网关**，避免跨 AZ 依赖（同时也避免不必要的跨 AZ 数据传输费用）

## 网络架构与路由逻辑

```
私有子网实例 → 私有子网路由表（0.0.0.0/0 → NAT 网关）
             → NAT 网关（位于公有子网，绑定弹性 IP）
             → 公有子网路由表（0.0.0.0/0 → IGW）
             → IGW → 互联网
```

- 这种架构实现了**资源隔离**：私有子网的服务器既能持续获取互联网上的更新，又不会直接暴露公网入口，符合纵深防御原则
- **IPv6 场景没有 NAT 概念**：IPv6 地址空间充足，默认全部可公网路由；私有子网需要"只出不进"时应使用 **Egress-Only Internet Gateway**，而非 NAT 网关，完整对比见 [[Subnet]] 笔记中"IPv6 子网"章节

## 考试易混淆点

> **考试陷阱**：**NAT 网关/IGW 都不是防火墙，不做流量内容层面的允许/拒绝判断**——它们只负责"流量该怎么转发"；真正决定"这条流量是否被允许"的是 [[Security Group]] 和 [[NACL]]。题目描述"NAT 网关能否阻止某个特定 IP 访问" → 不能，需要在 [[NACL]] 层面添加 Deny 规则。

> **考试陷阱**：**NAT 网关无法让公网主动访问私有子网内的资源**——这是"只出不进"的本质决定的；若题目要求"公网能主动连接到某台实例"，无论是否配置了 NAT 网关，该实例都必须拥有公网 IP 且位于**公有子网**，NAT 网关无法反向开放入站访问。

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **私有子网实例需要访问互联网下载补丁/调用外部 API** | NAT 网关（首选，免运维） |
| **需要精细控制出站流量、复用为堡垒机、或做端口转发** | [[NAT Instance\|NAT 实例]]（承担自行运维成本换取灵活性） |
| **追求高可用，避免单 AZ 故障影响所有私有子网出站** | 每个可用区独立部署一个 NAT 网关 |
| **IPv6 私有子网需要出站但拒绝入站** | Egress-Only Internet Gateway（而非 NAT 网关） |
| **VPC 内资源需要访问 S3/DynamoDB，希望避免 NAT 网关费用** | 改用网关型 [[VPC Endpoints\|VPC Endpoint]]（免费、不经过 NAT） |
| **Lambda 函数配置进 VPC 私有子网后需要访问公网/其他 AWS 服务** | NAT 网关或对应的 VPC Endpoint，否则调用超时（详见 [[AWS Lambda]] 笔记） |
| **私有子网配置看似正确但仍无法访问公网** | 若使用 [[NAT Instance\|NAT 实例]]，检查是否忘记禁用源/目的地检查 |

## 考试重点总结

### SAA-C02 高频考点

1. **IGW 允许双向通信，每个 VPC 仅能关联一个**：是判定公有子网的核心依据
2. **NAT 设备只允许"出"不允许"进"**：私有子网主动访问公网，公网无法反向发起连接
3. **NAT 网关全托管、自动扩展、最高 100 Gbps**：无需管理底层基础设施
4. **NAT 实例需手动禁用源/目的地检查**：这是与 NAT 网关最核心的配置差异，也是最高频的排障考点
5. **NAT 网关必须部署在公有子网**：自身也需要经 IGW 访问公网
6. **NAT 网关不支持安全组，NAT 实例支持**：因为 NAT 实例本质是 EC2 实例
7. **单 NAT 网关仅覆盖单一可用区**：高可用架构需每个 AZ 独立部署
8. **NAT 网关/IGW 不做防火墙式过滤**：允许/拒绝判断仍由 Security Group/NACL 负责
9. **IPv6 场景用 Egress-Only Internet Gateway 替代 NAT 网关**：IPv6 没有地址转换的概念
10. **[[NAT Instance|NAT 实例]]可复用为堡垒机/端口转发网关，NAT 网关不能**：这是选择 NAT 实例而非 NAT 网关的少数合理场景之一

### 场景题解题思路

```
场景分析 → 判断 IGW/NAT 相关配置
├── "私有子网实例需要访问互联网，免运维" → NAT 网关
├── "需要精细流量控制/兼做堡垒机/端口转发" → NAT 实例（详见 [[NAT Instance]]）
├── "私有子网流量无法通过 NAT 实例转发" → 检查是否禁用了源/目的地检查
├── "追求高可用，避免单 AZ 故障影响全部私有子网" → 每个 AZ 独立部署 NAT 网关
├── "IPv6 私有子网需要出站但拒绝入站" → Egress-Only Internet Gateway
├── "访问 S3/DynamoDB 希望避免 NAT 网关费用" → 网关型 VPC Endpoint
├── "NAT 网关能否按 IP 拦截特定流量" → 不能，需用 NACL/Security Group
└── "公网需要主动连接到某实例" → 该实例需在公有子网并拥有公网 IP，与 NAT 网关无关
```

## 最佳实践

1. **默认优先选择 NAT 网关而非 [[NAT Instance|NAT 实例]]**：免去运维负担和单点故障风险，仅在明确需要端口转发/堡垒机复用等特殊能力时才考虑 NAT 实例
2. **每个可用区独立部署 NAT 网关**：避免单 AZ 故障导致全局私有子网失去出站能力，同时降低跨 AZ 数据传输成本
3. **优先用网关型 [[VPC Endpoints|VPC Endpoint]] 访问 S3/DynamoDB**：免费且不经过 NAT 网关，显著降低数据处理费用
4. **使用 [[NAT Instance|NAT 实例]]时务必禁用源/目的地检查**：这是最容易被遗漏的配置项，也是排障的第一检查点
5. **不要把 NAT 网关当作访问控制手段**：出站流量的精细过滤仍需依赖 Security Group/NACL，NAT 网关只负责地址转换和转发
6. **IPv6 架构规划阶段就采用 Egress-Only Internet Gateway 思路**：避免沿用 IPv4 NAT 网关的架构惯性
7. **监控 NAT 网关的数据处理量和连接数**：数据处理费用可能随流量增长而显著上升，必要时评估是否可通过 VPC Endpoint 分流部分流量
