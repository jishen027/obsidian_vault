# Amazon RDS - 关系型数据库服务

> **Amazon RDS (Relational Database Service)** 是一种完全托管的关系型数据库服务，负责处理数据库设置、修补、备份和高可用等基础设施工作，专为联机事务处理（OLTP）场景优化。
>
> 相关文档：[[Aurora]] | [[Amazon Redshift]] | [[DynamoDB]] | [[Amazon Neptune]] | [[Amazon Keyspaces]] | [[Amazon Timestream]] | [[Amazon DocumentDB]] | [[KMS]] | [[CloudWatch]] | [[Disaster Recovery On AWS]] | [[Database Migration Service]]

---

## 核心概念

### RDS 定位

| 服务 | 类型 | 场景 | 特点 |
|------|------|------|------|
| **RDS** | OLTP | 日常事务处理 | 频繁读写，低延迟，行式存储 |
| [[Amazon Redshift]] | OLAP | 商业智能、数据分析 | 复杂查询，批量分析，列式存储 |
| [[DynamoDB]] | NoSQL | 键值/文档存储 | 单毫秒延迟，无固定架构，弹性扩展 |
| [[Amazon Neptune]] | 图数据库 | 深度关联查询 | 节点+边建模，社交网络、推荐引擎、欺诈检测 |
| [[Amazon Keyspaces]] | 宽列 NoSQL（Cassandra 兼容） | 兼容 CQL，主键查询 | 已有 Cassandra 应用迁移，宽列高吞吐写入 |
| [[Amazon Timestream]] | 时序数据库 | 带时间戳，按时间范围查询 | IoT 传感器数据、监控指标、时序分析 |
| [[Amazon DocumentDB]] | 文档数据库（MongoDB 兼容） | 兼容 MongoDB 驱动，JSON 文档 | 已有 MongoDB 应用迁移，半结构化文档存储 |

### 支持引擎

| 引擎                                       | 说明                                      |
| ---------------------------------------- | --------------------------------------- |
| **MySQL** / **MariaDB** / **PostgreSQL** | 开源引擎                                    |
| **Oracle** / **SQL Server**              | 商业引擎，支持包含许可或自带许可（BYOL）                  |
| **Aurora**                               | AWS 自研云原生引擎，兼容 MySQL/PostgreSQL，性能与弹性更强 |

### 许可模式

| 模式 | 说明 |
|------|------|
| **License Included** | 许可费用包含在 RDS 实例价格中 |
| **Bring Your Own License (BYOL)** | 使用已有许可，适用于 Oracle、SQL Server |

### RDS Custom（考试易混淆点：标准 RDS 不允许访问底层主机）

> **标准 RDS 不允许访问数据库主机操作系统**，托管服务的代价就是牺牲底层访问权限。当题目要求"需要自定义数据库环境或底层操作系统（如打特殊补丁、调整 OS 设置以支持第三方软件的特殊权限要求）"时，标准 RDS（包括其 Multi-AZ/Read Replica）都**无法满足**，必须使用 **Amazon RDS Custom**（目前支持 Oracle 和 SQL Server）——它在托管服务的基础上开放了对数据库主机和操作系统的访问与自定义能力，同时仍支持 Multi-AZ 高可用配置。

| 需求 | 该用哪个 |
|------|---------|
| 只需要标准的托管关系型数据库，不需要碰底层 OS | 标准 RDS（Multi-AZ 保证高可用） |
| 需要访问/自定义数据库主机的操作系统（打补丁、装第三方软件） | **RDS Custom**（Oracle / SQL Server） |
| 需要完全自主掌控服务器 + 高可用，愿意自己承担运维 | 自建 EC2 上的数据库集群（维护成本最高，除非其他方案都不满足才考虑） |

> **考试关键词识别**："数据库管理员（DBA）需要访问和自定义数据库服务器主机及操作系统" → RDS Custom；"最小化底层基础设施维护工作量，同时满足上述自定义需求" → RDS Custom 的 Multi-AZ 配置（而不是自建 EC2，那样维护成本远高于 RDS Custom）。

## 存储和性能优化

### 存储类型

| 存储类型 | 说明 | 适用场景 |
|---------|------|---------|
| **通用型 SSD (gp2/gp3)** | 性价比均衡 | 大多数工作负载 |
| **预置 IOPS SSD (io1/io2)** | 稳定的高 IOPS | I/O 密集型、关键业务数据库 |
| **磁性存储 (Magnetic)** | 上一代存储，成本低 | 已弃用，仅兼容旧场景 |

### 性能衡量

- RDS 的性能主要通过每秒输入输出操作次数（**IOPS**）衡量
- 存储容量与 IOPS 可独立配置（gp3/io1/io2），便于按需调优

## 可扩展性

### 垂直扩展 vs 水平扩展

| 扩展方式 | 说明 |
|---------|------|
| **垂直扩展** | 升级到更强大的实例类型（更多 CPU/内存） |
| **水平扩展（读取副本）** | 最多添加 5 个读取副本（Aurora 最多 15 个），分担读取压力 |

### 读取副本（Read Replicas）

| 特性       | 说明                                                    |
| -------- | ----------------------------------------------------- |
| **复制方式** | 异步复制，存在一定延迟                                           |
| **用途**   | 分担读取流量、报表查询，不用于故障转移                                   |
| **可读写**  | 可直接读取，部分引擎支持提升为独立可写实例                                 |
| **跨区域**  | 支持跨 AWS 区域创建，用于[[Disaster Recovery On AWS]]或降低跨区域读取延迟 |
| **前提条件** | 源实例必须开启自动备份                                           |

## 高可用性 - Multi-AZ

### 工作原理

- 在另一个可用区维护**同步复制**的备用实例（Standby）
- 备用实例**不可直接读写**，仅用于故障转移
- 主实例故障时自动切换到备用实例，DNS 端点保持不变

### Multi-AZ vs 读取副本（考试重点）

| 特性 | Multi-AZ 备用实例 | 读取副本 |
|------|------------------|---------|
| 复制方式 | 同步 | 异步 |
| 是否可读 | ❌ 不可读 | ✅ 可读 |
| 主要目的 | 高可用、故障转移 | 扩展读取性能 |
| 是否跨区域 | 单区域内跨 AZ | 可跨区域 |
| 是否需要手动触发 | 自动故障转移 | 需手动提升为独立实例 |

> **注意**：Multi-AZ 解决的是可用性问题，读取副本解决的是可扩展性问题，二者可以同时使用。

### 存储自动扩展（Storage Autoscaling，考试易漏点）

> 应用负载突增导致数据库存储空间即将耗尽，是紧急场景题的常见开场——**优先考虑开启存储自动扩展，而不是急着迁移引擎或迁移数据库类型**。

- 对不可预测的工作负载，可在 RDS 实例上直接**启用存储自动扩展**，无需应用改造或迁移
- 触发条件（同时满足）：可用空闲空间低于已分配存储的 **10%**、低存储状态持续至少 **5 分钟**、距离上一次存储变更至少 **6 小时**
- 需要设置**自动扩展的最大存储阈值**上限，扩展不会无限进行
- **考试关键词识别**："RDS MySQL/PostgreSQL 存储可能耗尽，要求最小化开发和运维工作量的紧急方案" → 直接**为现有 RDS 实例启用存储自动扩展**；迁移到 Aurora（虽然也支持存储自动扩展）或迁移到 DynamoDB 都涉及明显更高的迁移/重构成本，只有在"直接启用自动扩展"选项不存在时才考虑；创建读取副本**不能**解决主实例存储空间不足的问题，只是常见的干扰项

---

### 引擎版本升级：Multi-AZ 不能避免停机（考试易混淆点）

> 不要把"Multi-AZ 提供高可用"和"Multi-AZ 下所有维护操作都零停机"划等号——**数据库引擎版本升级是明确的例外**。

- 常规的**故障转移**（如硬件故障、AZ 中断）由 Multi-AZ 自动处理，切换到备用实例通常只需几十秒
- 但**数据库引擎版本升级**是另一回事：无论是否开启 Multi-AZ，**主实例和备用实例会被同时触发升级**，升级过程中产生的停机时间无法通过 Multi-AZ 规避，停机时长随实例规格增大而增加
- **考试关键词识别**："Multi-AZ RDS 实例计划做引擎版本升级维护，升级期间是否会有停机" → 会，主备实例同时升级，这与"日常故障转移不停机"是两回事，不要被"Multi-AZ = 永远不停机"的直觉误导

---

### Aurora 高可用特性

- 存储层跨 **3 个可用区**自动复制 **6 份数据副本**
- 计算与存储分离，存储自动扩展，最高至 128 TB
- Aurora Replica 兼具读取扩展与故障转移能力，最多 15 个，故障转移优先级高于普通读取副本
- 详见 [[Aurora]]

## 备份和恢复

### 备份类型对比

| 类型 | 说明 | 保留期 |
|------|------|--------|
| **自动备份** | 每日快照 + 事务日志，支持时间点恢复（PITR） | 1-35 天，默认开启 |
| **手动快照** | 用户手动创建，不受保留期限制 | 直到手动删除 |

### 恢复方式

- 恢复操作会创建一个**新的 RDS 实例**，无法原地覆盖恢复
- 支持从自动备份进行任意时间点恢复（Point-In-Time Recovery）
- 快照可跨区域复制，用于灾难恢复

### 跨账户共享加密快照（考试易混淆点）

> 需要把数据库的**独立副本**交给外部审计方/合作方（对方有自己的 AWS 账户），且该数据库是**加密**的，正确路径是分享快照本身，而不是绕道 S3 或搭建读取副本。

- **正确做法**：创建**加密的手动快照**，直接与对方 AWS 账户共享该快照，同时把加密所用的 **KMS 密钥策略**也授权给对方账户（否则对方拿到快照也无法解密还原数据库）
- **为什么不能"导出快照到 S3 再共享"**：RDS 快照存储在 AWS 托管的 S3 桶中，**客户没有直接访问权限**，无法把这些底层对象当作普通 S3 对象共享出去
- **为什么不用读取副本**：读取副本是持续同步的只读实例，不是"给对方一份独立数据库副本"的语义，且题目要求的是**一次性**的数据交付，而非建立持续复制关系，用副本明显是过度设计
- **考试关键词识别**："需要把加密的 RDS 数据库共享给外部账户，对方需要自己独立的一份副本" → 加密手动快照 + 共享快照 + 共享 KMS 密钥策略

## 安全和加密

### 加密

| 加密类型 | 说明 |
|---------|------|
| **静态加密** | 使用 [[KMS]] 加密存储、快照、只读副本和日志 |
| **传输中加密** | 使用 SSL/TLS 加密客户端与数据库间的连接 |

> **重要**：静态加密必须在**创建实例时**启用，无法对已有未加密实例直接开启，只能通过快照复制到新的加密实例实现。

### 访问控制

| 机制 | 说明 |
|------|------|
| **[[Security Group|安全组]]** | 控制可访问数据库实例的网络流量 |
| **IAM 数据库认证** | 部分引擎（MySQL、PostgreSQL）支持使用 IAM 凭据登录，免密码 |
| **[[IAM]] 策略** | 控制对 RDS 管理 API 的访问 |
| **VPC 私有子网** | 数据库实例部署在私有子网，避免公网直接暴露 |

## 数据库的宏观定位

- **OLTP 优化**：RDS 专为联机事务处理场景（OLTP）优化，适用于需要频繁读取、写入和预定义模式的应用
- **与 Redshift 对比**：RDS 处理日常事务，[[Amazon Redshift]] 是托管数据仓库服务，针对复杂的联机分析处理（OLAP）优化
- **与 DynamoDB 对比**：RDS 处理结构化数据并遵循 ACID 事务，[[DynamoDB]] 是非关系型数据库，可处理每秒数万次的事务并保持低延迟
- **数据迁移**：利用 **[[Database Migration Service|AWS Database Migration Service（DMS）]]**，用户可以在不同引擎之间无缝迁移数据，完整的迁移模式和 Schema 转换流程见 [[Database Migration Service]] 独立笔记

## 考试重点总结

### SAA-C02 高频考点

1. **Multi-AZ vs 读取副本**：同步不可读（高可用） vs 异步可读（扩展性）
2. **读取副本前提**：源实例必须开启自动备份
3. **静态加密限制**：只能在创建时启用，已有实例需通过快照迁移开启
4. **备份保留期**：自动备份 1-35 天，手动快照永久保留
5. **恢复方式**：从快照/PITR 恢复会生成新实例
6. **Aurora 存储架构**：跨 3 AZ 复制 6 份数据，最多 15 个 Aurora Replica
7. **与 Redshift 区别**：RDS 是 OLTP，Redshift 是 OLAP
8. **与 DynamoDB 区别**：RDS 关系型 + ACID，DynamoDB 非关系型 + 高吞吐

### 场景题解题思路

```
场景分析 → 选择解决方案
├── "需要提升数据库可用性/自动故障转移" → Multi-AZ
├── "需要分担只读查询压力" → 读取副本
├── "需要跨区域灾难恢复" → 跨区域读取副本 / Aurora Global Database
├── "需要极致弹性存储和最高可用性" → Aurora
├── "需要免密码数据库登录" → IAM 数据库认证
└── "需要在不同数据库引擎间迁移数据" → [[Database Migration Service|AWS DMS]]
```

## 最佳实践

1. **区分 Multi-AZ 与读取副本**：高可用用 Multi-AZ，扩展读取用读取副本，二者可组合使用
2. **创建实例时启用加密**：避免后期需要通过快照迁移才能开启静态加密
3. **开启自动备份**：既提供 PITR 能力，也是创建读取副本的前提
4. **使用 Performance Insights**：定位慢查询和性能瓶颈
5. **优先考虑 Aurora**：对高可用性和弹性有更高要求时，Aurora 优于原生引擎
6. **数据库部署在私有子网**：结合安全组限制访问来源
