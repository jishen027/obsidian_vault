# AWS Transfer Family - 托管文件传输服务

> **AWS Transfer Family** 是全托管的文件传输服务，让依赖 **SFTP / FTPS / FTP / AS2** 等传统协议的客户端和合作方，无需修改自己的工作流程，就能把文件直接传输到 [[S3]] 或 [[AWS EFS]]，同时享受托管服务的可扩展性和低运维成本。
>
> 相关文档：[[S3]] | [[AWS EFS]] | [[IAM]] | [[Cognito]] | [[VPC]] | [[Route 53]] | [[AWS DataSync]]

---

## 核心概念

### 为什么需要 Transfer Family

- **典型痛点**：外部合作方/供应商的遗留系统只支持 **SFTP**，无法或不愿意为了对接 S3 而改用 REST API/SDK 上传方式
- **核心价值**：让这些合作方**继续使用原有的 SFTP 客户端和工作流**，后端由 Transfer Family 无缝把文件落地到 S3（或 EFS），公司无需自建、打补丁、扩容任何 SFTP 服务器
- 完全托管、自动扩缩容，官方文档强调"零基础设施管理"

### 支持的协议

| 协议 | 说明 |
|------|------|
| **SFTP** | 基于 SSH 的安全文件传输，最常见的遗留系统协议 |
| **FTPS** | 基于 TLS 的加密 FTP |
| **FTP** | 明文 FTP，通常仅限内网（VPC 内）场景使用 |
| **AS2** | 面向 EDI（电子数据交换）场景，常见于供应链/物流/医疗行业 |

## 用户与访问控制（考试高频）

### 用户到 IAM 角色的映射

- 每个 SFTP 用户在 Transfer Family 中被映射到一个 **IAM 角色**，该角色的策略决定了这个用户能访问 S3 桶的哪个**前缀（prefix）**
- 通过"一个用户 → 一个专属 IAM 角色 → 限定到特定前缀"的模式，可以让多个外部供应商共用同一个 S3 桶，同时严格隔离彼此的数据（如 `s3://company-ingest/vendor1/`、`s3://company-ingest/vendor2/`）

### 身份联邦（Identity Provider 集成）

- 除了 Transfer Family 自带的用户管理，还可以对接**外部身份提供商**：Amazon Cognito、SAML 2.0 第三方 IdP，或自定义身份提供商（通过 API Gateway + Lambda 实现）
- 联邦后，用户认证发生在外部 IdP，认证通过后再按属性（用户名/组）**动态映射**到对应的 IAM 角色和 S3 前缀权限
- **价值**：不需要为每个新增供应商在 Transfer Family 里手动创建用户，扩展性和集中式身份治理能力更强，尤其适合供应商数量会持续增长的场景

> **考试陷阱**：**Amazon Route 53（含私有托管区域）不参与 Transfer Family 的访问控制**，它只负责域名解析，题目里出现"用 Route 53 私有托管区域给不同供应商分配专属子域名来做访问隔离"是无意义的干扰项——真正的隔离机制永远是 **IAM 角色 + S3 前缀策略**，最多再叠加身份联邦。

## 与其他方案的边界（考试高频）

| 方案 | 是否适合"遗留 SFTP 客户对接 S3" | 原因 |
|------|-------------------------------|------|
| **AWS Transfer Family（SFTP）** | ✅ 标准答案 | 全托管，原生 SFTP，直接落地 S3/EFS，无需合作方改造 |
| **自建 EC2 + OpenSSH 做 SFTP 服务器** | ❌ | 需要自己打补丁、做高可用、扩容、监控磁盘，完全违背"全托管、最小运维"的要求 |
| **Amazon AppFlow** | ❌ | 面向 **SaaS 应用间**的数据集成（Salesforce、Zendesk 等 API 集成），不支持 SFTP 协议，无法承接遗留文件传输场景 |
| **[[AWS DataSync]]** | ❌（场景不匹配） | DataSync 面向"已有网络连接的存储系统"之间的**持续同步**（NFS/SMB/S3/EFS 之间），不是给外部第三方提供 SFTP 接入点的工具 |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **外部供应商仍在用遗留 SFTP 上传数据到公司数据湖** | Transfer Family SFTP 终端节点，落地到 S3 |
| **多个供应商共享同一个 S3 桶，要求严格按前缀隔离** | 每个用户映射独立 IAM 角色，限定各自前缀 |
| **供应商数量多且持续增长，不想逐个手动建用户** | 集成 Cognito / SAML IdP，做身份联邦 + 动态角色映射 |
| **EDI/供应链场景需要 AS2 协议** | Transfer Family AS2 终端节点 |
| **需要把文件落地到共享文件系统而非对象存储** | Transfer Family 落地到 [[AWS EFS]] |

## 考试重点总结

### SAA-C03 高频考点

1. **核心定位**：全托管，让遗留 SFTP/FTPS/FTP/AS2 客户端无缝对接 S3/EFS，客户端无需任何改造
2. **访问隔离的核心机制永远是 IAM 角色 + S3 前缀**，不是 Route 53、不是安全组
3. **身份联邦（Cognito/SAML/自定义 IdP）用于规模化、集中化的用户治理**，减少手动建用户的运维负担
4. **AppFlow 不支持 SFTP**：面向 SaaS API 集成，不能替代 Transfer Family
5. **自建 EC2 SFTP 服务器不满足"全托管/最小运维"要求**：即使技术可行也不是最优解

### 场景题解题思路

```
场景分析 → 判断 Transfer Family 相关配置
├── "遗留系统只支持 SFTP，要求全托管、无需改造客户端" → AWS Transfer Family
├── "多供应商共享一个 S3 桶，要求按前缀隔离" → 每用户独立 IAM 角色 + 前缀限定策略
├── "供应商数量多、要集中管理身份" → 集成 Cognito/SAML/自定义 IdP 联邦
├── "用 Route 53 做访问隔离" → 无效干扰项，Route 53 不参与访问控制
├── "用 AppFlow 对接遗留 SFTP" → 无效，AppFlow 不支持 SFTP
└── "自建 EC2 + OpenSSH" → 技术可行但不满足全托管/最小运维要求
```

---

## 最佳实践

1. **优先使用身份联邦而非手动逐个建用户**：供应商规模会增长时尤其重要
2. **每个用户/供应商映射独立 IAM 角色并严格限定 S3 前缀**：避免跨供应商数据泄露
3. **结合 CloudTrail 审计每次 SFTP 会话和文件操作**：满足审计合规要求
4. **协议选择优先 SFTP/FTPS（加密）而非明文 FTP**：明文 FTP 仅限内网可信环境
