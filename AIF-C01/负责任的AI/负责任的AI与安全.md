## 负责任 AI 核心原则

| 原则 | 描述 |
|------|------|
| **公平性 (Fairness)** | AI 系统不应对特定群体产生歧视性结果 |
| **可解释性 (Explainability)** | 能够说明 AI 做出某个决策的原因 |
| **透明度 (Transparency)** | 对 AI 系统的工作方式保持开放和透明 |
| **隐私保护 (Privacy)** | 保护个人数据，防止未授权访问和泄露 |
| **安全性 (Security)** | 防范 AI 系统被恶意攻击或滥用 |
| **可靠性 (Reliability)** | 确保 AI 系统在各种条件下稳定运行 |
| **问责制 (Accountability)** | 明确 AI 系统行为的责任归属 |

> **负责任 AI 的开发生命周期**：与常规 ML 生命周期并行——在**确定使用案例**阶段就评估潜在风险人群和场景，在**数据准备**阶段检查代表性和数据来源合法性，在**训练/评估**阶段用 SageMaker Clarify 等工具量化偏见和可解释性，在**部署**阶段配置 Bedrock Guardrails，在**监控**阶段持续追踪公平性指标和用户反馈——负责任 AI **不是上线前的一次性检查，而是贯穿全流程的持续实践**。

## AI 面临的挑战与责任 (AI Challenges and Responsibilities)

> AI/ML 系统（不限于生成式 AI）在实际落地中普遍面临的一组挑战。AIF-C01 要求考生能够识别每类挑战，并知道对应的缓解思路——**组织在采用 AI 时需要主动承担识别和管理这些风险的责任**。

| 挑战 | 描述 | 缓解思路 |
|------|------|---------|
| **偏见 (Bias)** | 模型对不同群体表现不一致 | 详见 [[#AI 偏见 (Bias)]] |
| **毒性内容 (Toxicity)** | 模型生成仇恨、歧视、暴力等有害内容 | 内容过滤、Bedrock Guardrails、RLHF 对齐 |
| **可解释性不足 (Interpretability)** | 难以说明模型为何做出某个决策 | 详见 [[#可解释性 (Explainability)]] |
| **幻觉 (Hallucinations)** | 模型自信地输出虚假或编造的信息 | RAG、降低 Temperature、要求引用来源 |
| **非确定性 (Nondeterminism)** | 相同输入在不同调用中可能产生不同输出（采样随机性所致） | 降低 Temperature/Top-P、固定随机种子（若支持）、对高一致性要求场景增加人工校验 |
| **知识产权侵权 (IP Infringement)** | 训练数据或生成内容可能侵犯他人版权/专利 | 审查训练数据授权来源、使用有合法授权的基础模型、内容溯源 |
| **抄袭与学术诚信 (Plagiarism)** | 用户将 AI 生成内容冒充为原创工作 | 制定使用披露政策、AI 生成内容水印/标识 |
| **数据质量与治理不足** | 训练数据存在噪声、缺失、未授权采集 | 数据策管流程、数据血缘追踪、[[#AI 治理 (Governance for AI)]] |
| **监管违规风险** | 未满足行业或地区法规要求 | 详见 [[#AI 合规性 (Compliance for AI)]] |
| **社会与环境影响** | 就业替代、算力/能耗环境成本、数字鸿沟 | 负责任部署评估、透明沟通、渐进式引入 |

> **考试要点**：题目若描述"模型输出内容听起来很自信但实际是编造的" → **幻觉 (Hallucination)**；描述"同样的提示词每次得到不同的答案" → **非确定性 (Nondeterminism)**；描述"担心生成内容抄袭/侵犯版权" → **知识产权侵权**，而非幻觉。

## 生成式 AI 特有挑战 (GenAI Challenges)

> 相比传统判别式 ML，**生成式 AI 因为直接产出面向终端用户的自然语言/图像/代码等内容**，放大了以下几类挑战，是 Domain 2/4 的高频考点。

| 挑战 | 描述 | AWS/最佳实践应对 |
|------|------|-------------------|
| **幻觉 (Hallucinations)** | 生成看似合理但事实错误的内容，且语气自信、难以察觉 | RAG（用权威知识库约束回答）、降低 Temperature、要求模型引用来源、Bedrock Guardrails 的 **Grounding（基础真实性）检查** |
| **可解释性 (Interpretability)** | LLM 的内部推理过程是"黑箱"，难以追溯某个具体输出是如何产生的 | 思维链提示（CoT）展示中间推理步骤、限定输出结构、结合人工复核 |
| **非确定性 (Nondeterminism)** | 相同提示词在不同调用间可能产生不同措辞甚至不同结论 | 降低 Temperature/Top-P 提升一致性、对关键业务流程增加确定性校验层 |
| **毒性 (Toxicity)** | 模型可能生成冒犯性、歧视性或不当内容 | Bedrock Guardrails 内容过滤、RLHF 阶段的 HHH 对齐 |
| **知识产权/版权问题** | 训练语料可能包含受版权保护的内容，生成结果可能构成侵权或抄袭 | 选择有明确数据授权/知识产权保障条款的基础模型提供商，审查服务条款 |
| **披露义务 (Disclosure)** | 用户应被明确告知自己正在与 AI 交互，而非真人 | 在产品界面明确标注"由 AI 生成/由 AI 驱动"，符合透明度原则 |
| **数据隐私（训练与推理两端）** | 训练数据可能包含 PII；用户提示词中也可能无意输入敏感信息 | 详见 [[#数据隐私与 PII]] 与 [[#AI 的安全与隐私 (Security and Privacy for AI)]] |

> **考试陷阱**：**幻觉、毒性、知识产权、抄袭、披露义务、不可解释性、非确定性**——这些是 AWS 官方培训材料中反复强调的生成式 AI 责任使用（Responsible Use of GenAI）挑战清单，题目常以场景描述形式考查"这属于哪种挑战"。

## AI 偏见 (Bias)

> **AI 偏见**是指在不同群体之间模型的性能存在差异——结果会倾向于或背离特定类别的结果。**模型的质量取决于基础数据的质量和数量。**

### 具体示例：贷款审批模型

> 场景：使用 ML 模型自动批准贷款申请。训练数据包含"应获批准"和"不应获批准"的申请示例。

训练数据中包含的申请特征：收入、工作经历、年龄、性别、地点

**偏见如何产生**：若训练数据中没有任何来自"威斯康星州 25 岁女性"的获批申请，模型会学习到"尽管其收入和工作经历符合资格，也不应批准"的偏见模式。

### 偏见来源

| 来源 | 描述 | 示例 |
|------|------|------|
| **数据偏见** | 训练数据不具有代表性，未覆盖足够多的不同人群 | 贷款数据未包含特定地区/年龄/性别的申请 |
| **标注偏见** | 人工标注者的主观偏见影响标签 | 标注者对特定性别/种族有刻板印象 |
| **算法偏见** | 优化目标与公平性目标冲突 | 优化准确率导致忽视少数群体 |
| **部署偏见** | 模型应用于与训练数据分布不同的环境 | 在不同地区部署的模型表现差异大 |

### 缓解偏见的方法

| 方法 | 描述 |
|------|------|
| **调整特征权重** | 直接降低引入噪声的特征（如性别）的权重，减少其对预测的影响 |
| **排除偏见特征** | 完全从模型中排除某些特征（例如完全不让模型考虑性别因素） |
| **提高数据多样性** | 确保训练数据覆盖各种群体和场景，是最根本的解决方法 |
| **公平性指标监控** | 监控不同群体的模型性能差异 |
| **SageMaker Clarify** | AWS 工具，检测数据和模型中的偏见，提供可解释性报告 |
| **人工审核** | 在敏感决策场景中引入人工复核 |

### 负责任 AI 最佳实践

> **在创建模型之前**，应从一开始就确定公平性约束条件（例如年龄和性别歧视）。

1. **事前**：定义公平性约束（不得基于年龄/性别歧视）
2. **训练前**：检查和评估训练数据中的潜在偏差
3. **持续**：通过检查结果的公平性来持续评估已部署的模型

## 可解释性 (Explainability)

> AI 可解释性是指能够理解和说明 AI 模型做出特定预测或决策的原因。

### 可解释性工具

| 工具 | 描述 |
|------|------|
| **SageMaker Clarify** | 提供特征重要性分析，解释模型预测 |
| **SHAP 值** | 量化每个特征对预测结果的贡献 |
| **LIME** | 局部可解释模型，解释单个预测 |

### 为什么可解释性重要

- **监管合规**：金融、医疗等行业要求解释 AI 决策
- **调试模型**：帮助发现偏见和错误
- **建立信任**：让用户和利益相关者理解 AI 行为
- **问责制**：明确 AI 错误的责任归属

## 数据隐私与 PII

> **PII（个人身份信息）** 是能够识别特定个人身份的数据，AI 系统必须谨慎处理。

### 常见 PII 类型

| 类型 | 示例 |
|------|------|
| **身份信息** | 姓名、身份证号、护照号 |
| **联系信息** | 电话、邮件、地址 |
| **财务信息** | 银行账号、信用卡号 |
| **健康信息** | 医疗记录、基因数据 |
| **位置信息** | GPS 坐标、家庭地址 |

### AWS 中的 PII 处理

| 服务/功能 | 处理方式 |
|---------|---------|
| **[[Amazon Macie]]** | 自动发现 **S3 中存放的训练/参考数据集**是否含 PII（静态数据阶段） |
| **Amazon Comprehend** | 检测**文本内容**中的 PII 实体（推理输入阶段） |
| **Bedrock Guardrails** | 遮蔽或屏蔽 **LLM 输入/输出**中的 PII（生成式 AI 阶段） |
| **Amazon Transcribe** | 从转录文字中自动移除 PII |
| **Amazon Rekognition** | 检测图像中的人脸（需合规处理） |

> **考试要点**：三者按 **AI 数据处理阶段**区分——**Macie 管"训练数据集（存储在 S3 的静态数据）"**，**Comprehend 管"一段文本内容"**，**Bedrock Guardrails 管"LLM 的输入/输出"**，完整对比见 [[Amazon Macie]] 独立笔记中的 AIF-C01 考试视角章节。

## Amazon Bedrock Guardrails（详细）

> **Guardrails** 是 Bedrock 的内容安全过滤层，可应用于任何基础模型的输入和输出。

### 过滤类型详解

| 过滤类型 | 功能 | 配置说明 |
|---------|------|---------|
| **内容过滤 (Content Filter)** | 检测仇恨言论、暴力、色情、歧视内容 | 设置过滤强度（低/中/高） |
| **禁止话题 (Denied Topics)** | 禁止讨论特定主题 | 最多 30 个话题，每个可提供 5 个示例短语 |
| **词汇过滤 (Word Filter)** | 屏蔽特定词汇 | 可添加自定义词汇黑名单 |
| **PII 过滤** | 处理个人身份信息 | 可选：遮蔽（Mask）或屏蔽（Block） |
| **基础真实性 (Grounding)** | 验证响应是否有参考来源支持 | 需提供参考文档 |
| **相关性 (Relevance)** | 验证响应是否与用户查询相关 | — |

## AI 的安全与隐私 (Security and Privacy for AI)

> AI 系统的安全与隐私覆盖**数据、模型、基础设施**三个层面，目标是防止未授权访问、数据泄露和模型被滥用。这是 Domain 5 的核心主题，与下方 [[#AI 安全威胁]]（具体攻击类型）互为补充——本节关注**防护体系**，下一节关注**具体威胁**。

### 保护数据（训练与推理两端）

| 措施                               | 说明                | AWS 服务                                      |
| -------------------------------- | ----------------- | ------------------------------------------- |
| **静态加密 (Encryption at Rest)**    | 存储中的训练数据、模型构件加密   | [[KMS]]、S3 默认加密                             |
| **传输加密 (Encryption in Transit)** | API 调用、数据传输全程加密   | TLS                                         |
| **数据脱敏/匿名化**                     | 移除或替换可识别个人的字段     | Amazon Comprehend PII 检测、Bedrock Guardrails |
| **敏感数据发现**                       | 自动扫描 S3 等存储中的敏感数据 | **[[Amazon Macie]]**                            |
| **最小权限访问**                       | 仅授予完成任务所需的最小权限    | [[IAM]] 策略、SageMaker Role Manager           |

### 保护模型与基础设施

| 措施 | 说明 |
|------|------|
| **防止模型窃取** | API 调用速率限制、访问日志审计，防止攻击者通过大量查询逆向工程模型 |
| **安全的模型端点** | 使用 VPC 端点/PrivateLink，避免推理流量经过公网 |
| **威胁检测** | **Amazon GuardDuty** 持续监控账户和工作负载中的异常/恶意活动 |
| **硬件级隔离** | **AWS Nitro System** 从硬件层面强制隔离，保护训练/推理工作负载和数据不被云运营商或同机租户访问 |
| **安全的 MLOps 流水线** | 训练/部署管道使用独立、最小权限的 IAM 角色，产物（模型构件、镜像）全程加密与版本控制 |

### 隐私增强技术 (Privacy-Enhancing Technologies)

| 技术 | 说明 | 适用场景 |
|------|------|---------|
| **差分隐私 (Differential Privacy)** | 在训练数据或模型输出中注入可控噪声，使得无法从结果反推出单条具体记录，同时保留整体统计规律 | 防范[[#其他 AI 安全威胁（考试重点）\|模型反演]]攻击、发布聚合统计数据 |
| **联邦学习 (Federated Learning)** | 模型在数据本地（如各家医院、各台设备）训练，只汇总模型更新而非原始数据 | 数据不能离开本地环境的强合规场景（医疗、金融） |
| **数据匿名化/假名化** | 移除或替换直接标识符，使数据无法（或需额外信息才能）关联回个人 | 训练数据预处理、数据共享前的合规处理 |
| **合成数据 (Synthetic Data)** | 使用算法生成统计特征相似但不对应真实个体的人工数据集 | 缺乏真实数据、或真实数据涉及高敏感隐私的场景 |

> **考试要点**：题目描述"希望在不共享原始患者数据的前提下，跨多家医院联合训练模型" → **联邦学习**；描述"发布统计报告时不希望任何人能反推出具体某个人的数据" → **差分隐私**；描述"需要持续监控 AWS 账户中的可疑/恶意活动" → **Amazon GuardDuty**；描述"需要自动发现 S3 存储桶中的敏感数据" → **[[Amazon Macie]]**。

## AI 安全威胁

### 提示注入 (Prompt Injection)

> 攻击者通过构造特殊输入，覆盖或绕过系统提示，使 LLM 执行未授权操作。

| 类型 | 描述 |
|------|------|
| **直接提示注入** | 攻击者直接在用户输入中嵌入恶意指令 |
| **间接提示注入** | 恶意指令嵌入在 LLM 会读取的外部文档/网页中 |

**防御措施：**

```
防御提示注入
├── 使用 Bedrock Guardrails 过滤输入
├── 将用户输入与系统提示明确分离
├── 限制 LLM 可调用的后端系统权限
├── 在敏感操作前加入人工审核
└── 定期监控 LLM 输入/输出日志（CloudWatch）
```

### 其他 AI 安全威胁（考试重点）

| 威胁 | 描述 | 防御 |
|------|------|------|
| **数据投毒 (Data Poisoning)** | 在训练数据中注入恶意样本，影响模型行为 | 数据来源验证、数据质量检查、策管流程 |
| **模型反演 (Model Inversion)** | 通过模型输出逆向推断训练数据中的私密信息（如推断出患者数据） | 差分隐私、访问控制、速率限制 |
| **模型窃取 (Model Stealing)** | 通过大量查询逆向工程模型权重和架构 | API 访问限制、速率限制 |
| **对抗性攻击 (Adversarial Attack)** | 精心构造输入使模型产生错误预测 | 对抗性训练、输入验证 |
| **幻觉 (Hallucination)** | 模型自信地生成虚假信息 | RAG、降低 Temperature、添加溯源要求 |

> **AI 系统特定漏洞**（考试需记）：**提示词注入**、**数据中毒**、**模型反演漏洞** ← 这三类是 AIF-C01 明确要求掌握的 AI 安全威胁。

> **安全措施**：实施**加密**、**多重身份验证 (MFA)**、**持续监控**（CloudWatch），并确保与合规框架保持一致，以防范隐私违例、数据操纵、滥用和决策受损等风险。

## GenAI 安全范围矩阵 (GenAI Security Scoping Matrix)（考试重点）

> **GenAI Security Scoping Matrix** 是 AWS 提出的框架，用于根据组织对生成式 AI 应用的**控制程度**，判断自己应承担哪些安全与治理责任——本质上是**共享责任模型在生成式 AI 场景下的延伸**：越靠近"自建/自训练"，客户承担的责任越多；越靠近"直接使用第三方消费级应用"，供应商承担的责任越多。

### 五个范围 (Scope)

| Scope | 名称 | 定义 | 典型示例 | 客户控制程度 |
|-------|------|------|---------|-------------|
| **Scope 1** | **消费级应用 (Consumer App)** | 直接使用面向公众的第三方生成式 AI 应用，原样使用，不做任何定制 | 公开可用的 AI 聊天网站/APP | 最低——只能决定是否使用及输入什么内容 |
| **Scope 2** | **企业级应用 (Enterprise App)** | 使用已内置生成式 AI 能力的第三方**企业级**应用（通常受企业协议约束，而非公开条款） | 企业版协作/办公软件内置的 AI 助手 | 较低——受企业采购合同条款保护，但底层模型不可控 |
| **Scope 3** | **预训练模型 (Pre-trained Models)** | 通过 API 调用现成的基础模型构建自己的应用，不做微调 | 直接调用 [[Amazon Bedrock]] 基础模型（Claude、Titan 等） | 中等——控制应用层、提示词工程、Guardrails 配置 |
| **Scope 4** | **微调模型 (Fine-tuned Models)** | 在现有基础模型上使用自有数据进行微调/持续预训练 | 使用 Bedrock Fine-tuning 或 SageMaker 定制基础模型 | 较高——额外控制训练数据和微调过程，但基座模型仍来自第三方 |
| **Scope 5** | **自训练模型 (Self-trained Models)** | 完全自行构建、训练、托管模型，不基于任何第三方基础模型 | 使用 SageMaker 从零训练自有模型 | 最高——对数据、训练、部署全流程负全部责任 |

> **记忆技巧**：Scope 编号越大 = **越靠近"自己动手"** = 客户可定制的空间越大，但**需要自行承担的安全、合规、风险管理责任也越大**；Scope 编号越小 = **越依赖第三方现成产品**，客户责任越小但可控性和差异化能力也越弱。

### 每个 Scope 都要评估的五个责任维度

| 维度 | 关注问题 |
|------|---------|
| **治理与合规 (Governance & Compliance)** | 谁负责制定该应用的使用策略？是否符合行业和地区法规？ |
| **法律与知识产权 (Legal & IP)** | 训练数据、生成内容的知识产权归属和使用授权如何界定？ |
| **风险管理 (Risk Management)** | 谁负责识别和缓解偏见、幻觉、安全漏洞等风险？ |
| **数据隐私与安全 (Data Privacy & Security)** | 输入/输出数据如何被存储、使用、是否用于训练供应商的模型？ |
| **应用韧性 (Resilience)** | 服务的可用性、性能和持续运营由谁保障？ |

> **考试要点**：题目描述"公司直接使用一个公开的第三方 AI 聊天工具处理业务问题" → **Scope 1**，需重点评估该工具的服务条款，避免输入敏感/专有数据；题目描述"公司调用 Bedrock API 构建自己的客服应用，未做任何模型定制" → **Scope 3**；题目描述"公司用自有客服历史数据对基础模型做了微调" → **Scope 4**；题目描述"公司从零开始训练了一个专有模型" → **Scope 5**，需自行承担全部数据治理和安全责任。**Scope 越高，客户自身承担的安全/合规/风险责任越重。**

## AI 治理 (Governance for AI)

> **AI 治理**是组织为确保 AI 系统的开发、部署和使用符合内部政策、法律要求和伦理标准而建立的**流程、角色和控制体系**——回答"谁能做什么、如何审批、如何追溯"这类结构性问题，是把 [[#负责任 AI 核心原则]] 落地为可执行流程的关键抓手。

### 治理体系的核心组成

| 组成部分 | 说明 |
|---------|------|
| **政策与流程 (Policies & Procedures)** | 明确 AI 使用的允许范围、审批流程、数据使用规范等书面规定 |
| **AI 治理委员会/评审组 (Review Board)** | 跨职能团队（法务、安全、业务、数据科学）对高风险 AI 应用进行评审和放行决策 |
| **透明度标准 (Transparency Standards)** | 通过标准化文档（如模型卡片）向内外部利益相关者说明模型的用途、局限性和风险 |
| **数据治理 (Data Governance)** | 管理数据的采集、质量、血缘（Lineage）、生命周期和访问权限 |
| **监控与问责 (Monitoring & Accountability)** | 持续监控已部署模型的表现，并明确出现问题时的责任归属 |

### AWS 治理相关工具

| 工具 | 说明 |
|------|------|
| **AWS AI Service Cards** | AWS 官方发布的服务级文档，公开说明各 AI 服务（如 Bedrock、Rekognition）的预期用途、设计选择、性能局限和负责任使用建议 |
| **SageMaker Model Cards** | 为**自建模型**创建标准化文档，记录用途、训练数据、评估指标、已知局限性 |
| **SageMaker Model Registry** | 集中管理模型版本，内置**部署前审批工作流**（Approved / Rejected / Pending Manual Approval） |
| **SageMaker Role Manager** | 基于预定义角色人设快速生成范围明确的 [[IAM]] 权限策略，落实最小权限原则 |
| **SageMaker Model Dashboard** | 组织级已部署模型的统一视图，集中呈现状态、资源使用和监控告警 |
| **ML 血缘追踪 (ML Lineage Tracking)** | 自动记录数据、代码、参数、模型构件之间的关联关系，支持审计追溯 |
| **AWS Well-Architected Framework – Generative AI Lens** | 针对生成式 AI 工作负载的架构最佳实践指南，覆盖治理、安全、成本、可靠性等维度 |

> 治理工具的完整对比与场景判断见 [[AIF-C01 考试概览]] 中 Domain 5 小结；本节聚焦"为什么需要治理"和"治理体系由哪些要素构成"。

## AI 合规性 (Compliance for AI)

> **合规**是指 AI 系统的构建、部署和运营满足适用的**法律法规、行业标准和内部政策**要求。与"治理"（内部流程/结构）不同，合规更强调**对外部规则的符合性**，通常需要可验证的证据（审计记录、认证报告）。

### 常见法规与标准（考试认知层面即可，无需记忆细节）

| 法规/标准 | 适用范围 | 核心关注点 |
|----------|---------|-----------|
| **GDPR（欧盟通用数据保护条例）** | 处理欧盟居民个人数据的组织 | 数据主体权利、数据最小化、跨境传输限制 |
| **HIPAA（美国健康保险流通与责任法案）** | 处理美国医疗健康信息的组织 | 患者健康信息（PHI）的保护 |
| **NIST AI 风险管理框架 (AI RMF)** | 通用 AI 风险管理指南（美国） | 识别、评估、管理 AI 全生命周期风险 |
| **ISO/IEC 42001** | AI 管理体系国际标准 | 组织级 AI 治理体系的建立与认证 |
| **EU AI Act（欧盟人工智能法案）** | 在欧盟境内提供/使用 AI 系统的组织 | 按风险等级（不可接受/高风险/有限风险/最小风险）分级监管 |
| **PCI DSS** | 处理支付卡数据的 AI 应用 | 支付卡数据的安全存储和处理 |
| **行业专属法规** | 金融（如 FINRA）、政府等 | 行业特定的审计、留痕和披露要求 |

### AWS 合规相关资源

| 资源 | 说明 |
|------|------|
| **[[AWS Artifact]]** | 按需下载 AWS 的合规报告和认证证书（如 SOC、ISO、PCI DSS），用于向审计方证明底层基础设施的合规性 |
| **[[AWS Audit Manager]]** | 持续自动收集合规审计所需的证据，简化审计准备工作——**⚠️ 已于 2026-04-30 起进入维护模式，停止向新账户开放**，新需求 AWS 推荐改用 [[AWS Config]] 的 Conformance Packs |
| **[[AWS Config]]** | 持续评估和记录 AWS 资源配置是否符合预设的合规规则，完整能力与 AIF-C01 简化版考点见 [[AWS Config]] 独立笔记 |
| **数据驻留/数据主权 (Data Residency/Sovereignty)** | 选择特定 AWS 区域部署，确保数据存储和处理位置满足所在地法律要求 |

> **考试要点**：**判断依据是"评估对象是谁"**——**[[AWS Artifact]]** 下载 **AWS 自身**的合规报告（证明底层基础设施合规）；**[[AWS Audit Manager]]** 持续收集**我方系统**的审计证据（简化审计流程）；**[[AWS Config]]** 持续评估**我方资源配置**是否合规（如 S3 桶是否加密）——三者容易混淆，题目问"需要下载 SOC 2 报告给审计方" → **[[AWS Artifact]]**；题目问"需要自动化、持续地收集合规证据" → **[[AWS Audit Manager]]**；题目问"需要持续检测我们自己的资源配置是否符合安全基准" → **[[AWS Config]]**。完整的 Artifact 功能（Reports/Agreements）见 [[AWS Artifact]] 独立笔记，Audit Manager 的框架/评估机制见 [[AWS Audit Manager]] 独立笔记，Config 的规则/修复机制见 [[AWS Config]] 独立笔记。

## 考试重点总结

### AIF-C01 高频考点

1. **负责任 AI 原则**：公平性、可解释性、透明度、隐私、安全
2. **AI 偏见**：数据偏见最常见，SageMaker Clarify 可检测
3. **PII 处理**：Comprehend 检测，Guardrails 遮蔽/屏蔽
4. **提示注入**：直接 vs 间接，用 Guardrails 防御
5. **Guardrails**：禁止话题（30个）、词汇过滤、PII、内容过滤
6. **CloudWatch 日志**：监控 Bedrock 调用记录
7. **GenAI 挑战清单**：幻觉、毒性、非确定性、知识产权侵权、抄袭、披露义务、可解释性不足——题目常以场景描述考查"这属于哪种挑战"
8. **隐私增强技术**：联邦学习（数据不出本地，共享模型更新）vs 差分隐私（结果注入噪声，防止反推个体数据）
9. **威胁检测服务**：[[Amazon GuardDuty]]（异常/恶意活动监控）vs [[Amazon Macie]]（敏感数据自动发现）
10. **GenAI Security Scoping Matrix**：Scope 1（消费级应用）→ Scope 5（自训练模型），**Scope 越高，客户自身承担的安全/合规责任越大**
11. **治理 vs 合规**：治理关注内部流程/角色/结构（谁能做什么），合规关注是否满足外部法规（GDPR/HIPAA/NIST AI RMF 等）
12. **[[AWS Artifact]] vs [[AWS Audit Manager]] vs [[AWS Config]]**：Artifact 下载 AWS 自身合规报告；Audit Manager 持续收集我方审计证据；Config 持续评估我方资源配置是否合规

### 场景题解题思路

```
场景分析 → 选择负责任 AI 措施
├── "AI 对某些群体预测准确率低" → 检查数据偏见，使用 Clarify
├── "防止 LLM 讨论竞争产品" → Guardrails 禁止话题过滤
├── "LLM 输出包含用户个人信息" → Guardrails PII 过滤（遮蔽）
├── "用户输入覆盖了系统指令" → 提示注入 → Guardrails 输入过滤
├── "需要解释为什么 AI 做出某决策" → SageMaker Clarify
├── "需要审计所有 LLM 调用记录" → CloudWatch Logs（Bedrock 调用日志）
├── "模型自信地编造了不存在的事实" → 幻觉（Hallucination）→ RAG/降低 Temperature
├── "同样的提示词每次答案都不一样" → 非确定性（Nondeterminism）→ 降低 Temperature/Top-P
├── "多家医院想联合训练模型但数据不能离开本地" → 联邦学习（Federated Learning）
├── "发布统计报告需防止反推出具体个人数据" → 差分隐私（Differential Privacy）
├── "需要持续监控账户中的可疑活动" → Amazon GuardDuty
├── "需要自动发现 S3 中的敏感数据" → [[Amazon Macie]]
├── "公司直接用第三方公开 AI 聊天工具处理业务" → GenAI Security Scoping Matrix Scope 1
├── "公司调用 Bedrock API 构建应用，不做模型定制" → Scope 3
├── "公司用自有数据微调了基础模型" → Scope 4
├── "公司从零训练了专有模型" → Scope 5，承担全部数据治理责任
├── "需要下载 SOC 2/ISO 合规报告给审计方" → [[AWS Artifact]]
├── "需要持续自动化收集合规审计证据" → [[AWS Audit Manager]]
└── "需要持续检测我们自己的资源配置是否符合安全基准" → [[AWS Config]]
```
