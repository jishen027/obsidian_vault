# 负责任的 AI 与安全

> **负责任的 AI (Responsible AI)** 是确保 AI 系统公平、透明、可解释、安全且符合伦理的一套原则与实践。AIF-C01 的 Domain 4（14%）和 Domain 5（14%）均围绕此主题展开，共占约 28% 的考试权重。
>
> 相关文档：[[Amazon Bedrock]] | [[Amazon SageMaker]] | [[AI与ML概念]] | [[AIF-C01 考试概览]]

---

## 负责任 AI 核心原则

| 原则 | 描述 |
|------|------|
| **公平性 (Fairness)** | AI 系统不应对特定群体产生歧视性结果 |
| **可解释性 (Explainability)** | 能够说明 AI 做出某个决策的原因 |
| **透明度 (Transparency)** | 对 AI 系统的工作方式保持开放和透明 |
| **隐私保护 (Privacy)** | 保护个人数据，防止未授权访问和泄露 |
| **安全性 (Security)** | 防范 AI 系统被恶意攻击或滥用 |
| **可靠性 (Reliability)** | 确保 AI 系统在各种条件下稳定运行 |
| **问责制 (Accountability)** | 明确 AI 系统行为的责任归属 |

## AI 偏见 (Bias)

> **AI 偏见** 是指模型因训练数据或算法设计的不平衡，对特定群体产生不公平的预测或决策。

### 偏见来源

| 来源 | 描述 | 示例 |
|------|------|------|
| **数据偏见** | 训练数据不具有代表性 | 人脸识别数据中深色皮肤样本不足 |
| **标注偏见** | 人工标注者的主观偏见影响标签 | 标注者对特定性别/种族有刻板印象 |
| **算法偏见** | 优化目标与公平性目标冲突 | 优化准确率导致忽视少数群体 |
| **部署偏见** | 模型应用于与训练数据分布不同的环境 | 在不同地区部署的模型表现差异大 |

### 检测与缓解偏见

| 方法 | 描述 |
|------|------|
| **数据多样性** | 确保训练数据覆盖各种群体和场景 |
| **公平性指标** | 监控不同群体的模型性能差异 |
| **SageMaker Clarify** | AWS 工具，检测数据和模型中的偏见，提供可解释性报告 |
| **人工审核** | 在敏感决策场景中引入人工复核 |

## 数据隐私与 PII

> **PII（个人身份信息）** 是能够识别特定个人身份的数据，AI 系统必须谨慎处理。

### 常见 PII 类型

| 类型 | 示例 |
|------|------|
| **身份信息** | 姓名、身份证号、护照号 |
| **联系信息** | 电话、邮件、地址 |
| **财务信息** | 银行账号、信用卡号 |
| **健康信息** | 医疗记录、基因数据 |
| **位置信息** | GPS 坐标、家庭地址 |

### AWS 中的 PII 处理

| 服务/功能 | 处理方式 |
|---------|---------|
| **Amazon Comprehend** | 检测文本中的 PII 实体 |
| **Bedrock Guardrails** | 遮蔽或屏蔽输出中的 PII |
| **Amazon Transcribe** | 从转录文字中自动移除 PII |
| **Amazon Rekognition** | 检测图像中的人脸（需合规处理） |

## Amazon Bedrock Guardrails（详细）

> **Guardrails** 是 Bedrock 的内容安全过滤层，可应用于任何基础模型的输入和输出。

### 过滤类型详解

| 过滤类型 | 功能 | 配置说明 |
|---------|------|---------|
| **内容过滤 (Content Filter)** | 检测仇恨言论、暴力、色情、歧视内容 | 设置过滤强度（低/中/高） |
| **禁止话题 (Denied Topics)** | 禁止讨论特定主题 | 最多 30 个话题，每个可提供 5 个示例短语 |
| **词汇过滤 (Word Filter)** | 屏蔽特定词汇 | 可添加自定义词汇黑名单 |
| **PII 过滤** | 处理个人身份信息 | 可选：遮蔽（Mask）或屏蔽（Block） |
| **基础真实性 (Grounding)** | 验证响应是否有参考来源支持 | 需提供参考文档 |
| **相关性 (Relevance)** | 验证响应是否与用户查询相关 | — |

## AI 安全威胁

### 提示注入 (Prompt Injection)

> 攻击者通过构造特殊输入，覆盖或绕过系统提示，使 LLM 执行未授权操作。

| 类型 | 描述 |
|------|------|
| **直接提示注入** | 攻击者直接在用户输入中嵌入恶意指令 |
| **间接提示注入** | 恶意指令嵌入在 LLM 会读取的外部文档/网页中 |

**防御措施：**

```
防御提示注入
├── 使用 Bedrock Guardrails 过滤输入
├── 将用户输入与系统提示明确分离
├── 限制 LLM 可调用的后端系统权限
├── 在敏感操作前加入人工审核
└── 定期监控 LLM 输入/输出日志（CloudWatch）
```

### 其他 AI 安全威胁

| 威胁 | 描述 | 防御 |
|------|------|------|
| **数据投毒 (Data Poisoning)** | 在训练数据中注入恶意样本 | 数据来源验证、数据质量检查 |
| **模型窃取 (Model Stealing)** | 通过大量查询逆向工程模型 | API 访问限制、速率限制 |
| **对抗性攻击 (Adversarial Attack)** | 精心构造输入使模型产生错误预测 | 对抗性训练、输入验证 |
| **幻觉 (Hallucination)** | 模型生成虚假信息 | RAG、降低 Temperature、添加溯源要求 |

## 合规与治理

### AI 系统的安全控制

| 控制层 | 描述 | AWS 服务 |
|--------|------|---------|
| **访问控制** | 限制谁可以使用 AI 服务 | IAM 策略、Bedrock 资源策略 |
| **数据加密** | 保护静态和传输中的数据 | KMS、TLS |
| **日志审计** | 记录所有 AI 调用 | CloudWatch Logs（Bedrock 调用日志） |
| **内容过滤** | 阻止有害输入/输出 | Bedrock Guardrails |
| **网络隔离** | 限制 AI 服务的网络访问 | VPC 端点、私有 API |

### 共享责任模型在 AI 中的应用

| 责任方 | 负责内容 |
|--------|---------|
| **AWS 负责** | 底层基础设施安全、模型安全边界 |
| **客户负责** | 数据安全、应用层访问控制、内容过滤配置、合规使用 |

## 可解释性 (Explainability)

> AI 可解释性是指能够理解和说明 AI 模型做出特定预测或决策的原因。

### 可解释性工具

| 工具 | 描述 |
|------|------|
| **SageMaker Clarify** | 提供特征重要性分析，解释模型预测 |
| **SHAP 值** | 量化每个特征对预测结果的贡献 |
| **LIME** | 局部可解释模型，解释单个预测 |

### 为什么可解释性重要

- **监管合规**：金融、医疗等行业要求解释 AI 决策
- **调试模型**：帮助发现偏见和错误
- **建立信任**：让用户和利益相关者理解 AI 行为
- **问责制**：明确 AI 错误的责任归属

## 考试重点总结

### AIF-C01 高频考点

1. **负责任 AI 原则**：公平性、可解释性、透明度、隐私、安全
2. **AI 偏见**：数据偏见最常见，SageMaker Clarify 可检测
3. **PII 处理**：Comprehend 检测，Guardrails 遮蔽/屏蔽
4. **提示注入**：直接 vs 间接，用 Guardrails 防御
5. **Guardrails**：禁止话题（30个）、词汇过滤、PII、内容过滤
6. **CloudWatch 日志**：监控 Bedrock 调用记录

### 场景题解题思路

```
场景分析 → 选择负责任 AI 措施
├── "AI 对某些群体预测准确率低" → 检查数据偏见，使用 Clarify
├── "防止 LLM 讨论竞争产品" → Guardrails 禁止话题过滤
├── "LLM 输出包含用户个人信息" → Guardrails PII 过滤（遮蔽）
├── "用户输入覆盖了系统指令" → 提示注入 → Guardrails 输入过滤
├── "需要解释为什么 AI 做出某决策" → SageMaker Clarify
└── "需要审计所有 LLM 调用记录" → CloudWatch Logs（Bedrock 调用日志）
```
