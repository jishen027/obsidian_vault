# Amazon Personalize - 个性化推荐服务

> **Amazon Personalize** 是全托管的个性化推荐服务，基于用户与物品的交互数据（浏览、点击、购买等），使用与 **Amazon.com** 相同的推荐技术生成实时个性化推荐，无需自行准备海量数据或掌握机器学习专业知识即可构建生产级推荐系统。
>
> 相关文档：[[Amazon Comprehend]] | [[Amazon SageMaker]] | [[Amazon Bedrock]] | [[Amazon Kendra]] | [[S3]] | [[AWS Lambda]] | [[Amazon Kinesis]] | [[IAM]]

---

## 核心概念

### 为什么需要 Personalize

- **自建推荐系统的门槛**：构建准确的推荐算法需要处理冷启动、稀疏数据、实时更新等复杂问题，且需要专业的机器学习和大规模数据处理能力
- **Personalize 的核心价值**：只需提供**用户-物品交互数据**，Personalize 自动完成特征工程、算法选择、模型训练和调优，直接输出可用于生产环境的推荐结果，并支持根据新增交互数据**自动定期重新训练**
- **在 AWS AI/ML 服务栈中的定位**：与 [[Amazon Rekognition]]/[[Amazon Comprehend]] 类似，Personalize 是**面向特定任务（个性化推荐）**的预训练/预配置托管服务，用预置的推荐领域（Domain）和算法（Recipe）大幅降低构建推荐系统的门槛

### Personalize 在 SAA-C02/AIF-C01 考试中的定位（考试要点）

| 服务 | 核心能力 | 输入数据 | 典型场景 |
|------|---------|---------|---------|
| **Personalize** | 个性化推荐（协同过滤 + 深度学习） | 用户-物品交互数据 | 电商"猜你喜欢"、媒体内容推荐、个性化营销 |
| [[Amazon Kendra]] | 企业语义搜索 | 文档/知识库内容 | 基于问题检索答案，而非基于行为推荐物品 |
| [[Amazon SageMaker]] | 通用机器学习平台 | 任意结构化/非结构化数据 | 需要完全自定义推荐算法或超出标准推荐场景的复杂模型 |

> **考试陷阱**：题目描述**"基于用户历史行为/购买记录生成个性化商品或内容推荐"** → 答案是 **Personalize**；若题目强调**"需要完全自定义推荐算法逻辑，标准推荐场景无法满足"** → 应考虑 [[Amazon SageMaker]] 自建模型，而非受限于 Personalize 预置的 Recipe；判断依据是**是否是标准的"用户-物品"推荐场景**，而非任何"提供个性化体验"的需求都直接选 Personalize。

## 核心数据集

| 数据集 | 是否必填 | 说明 |
|--------|---------|------|
| **用户-物品交互数据（Interactions）** | ✅ 必填 | 用户 ID、物品 ID、时间戳等交互记录，是推荐算法的核心训练数据 |
| **物品元数据（Items）** | 可选 | 物品的属性（类别、价格、标签等），用于缓解冷启动问题、支持基于内容的推荐 |
| **用户元数据（Users）** | 可选 | 用户属性（年龄、地区、偏好等），进一步提升推荐个性化程度 |

> **考试要点**：**只有用户-物品交互数据是必填的**——即使没有物品/用户元数据，Personalize 仍可基于纯行为数据生成推荐；元数据是提升推荐质量和缓解冷启动问题的可选增强项，而非前提条件。

## Domain Dataset Group 与推荐器（考试高频）

### 两种数据集组模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **Domain Dataset Group（领域数据集组）** | 针对 **ECOMMERCE（电商）** 或 **VIDEO_ON_DEMAND（视频点播）** 领域预配置的资源，内置针对该领域优化的推荐器（Recommender） | 标准电商/流媒体推荐场景，希望快速上线、无需自选算法 |
| **自定义数据集组（Custom Dataset Group）** | 手动选择 **Recipe（算法配方）**、自行配置训练方案（Solution）和活动（Campaign） | 需要更灵活地控制算法选择，或使用 Domain 未覆盖的推荐场景 |

### 推荐器（Recommender）vs 活动（Campaign）

- **推荐器（Recommender）**：Domain Dataset Group 下的预配置资源，直接调用 `GetRecommendations` API 获取**实时推荐**，每个区域最多可创建 15 个推荐器
- **活动（Campaign）**：自定义数据集组下、基于训练完成的**方案版本（Solution Version）**部署的推理端点，同样通过 API 获取实时推荐
- **自动重新训练**：Domain Dataset Group 下的推荐器默认**每 7 天自动基于全部数据集重新训练**模型，无需手动触发

> **考试陷阱**：**Domain Dataset Group 下的推荐器只能获取实时推荐，不支持批量推荐**；若需要**批量推荐（Batch Recommendations）**（如离线批量生成邮件营销的推荐列表），必须使用**自定义数据集组**下基于 Solution 训练出的方案，而非 Domain 推荐器。

## 常见推荐类型

| 推荐类型 | 说明 |
|---------|------|
| **用户个性化（User Personalization）** | 为特定用户推荐内容，即经典的"您可能还会喜欢" |
| **相关物品（Related Items）** | 基于某个物品推荐相关的其他物品（如商品详情页的"相似商品"） |
| **热门商品（Trending/Popular）** | 返回当前最受欢迎的物品，常用于冷启动场景的兜底策略 |
| **最近浏览（Recently Viewed）** | 基于用户最近的浏览/交互行为生成推荐 |

---

## 算法配方（Recipe）与 v2 架构

- **Recipe（配方）**：Personalize 内置的推荐算法模板，针对不同推荐目标（个性化排序、相似物品、用户分群等）预先优化
- **v2 Transformer 架构**：新一代基于 Transformer 的推荐算法，相比早期 Recipe 提供更高的推荐准确率、支持更大规模的物品目录、配置更简化，并采用**按请求计费**模式；已有基于早期 Recipe 运行的生产环境应评估迁移到 v2 架构

---

## 与生成式 AI 的集成

- 与 **[[Amazon Bedrock]]** 集成，可利用大语言模型**自动生成物品描述**、补充**合成元数据（Synthetic Metadata）**，缓解物品元数据不完整导致的冷启动问题
- 结合 **[[Amazon Lex]]** 可构建**对话式推荐界面**，让用户通过自然语言对话获取个性化推荐，而非仅依赖传统的列表式展示

---

## 数据摄取与实时更新

| 方式 | 说明 |
|------|------|
| **批量数据导入** | 从 [[S3]] 批量导入历史交互数据，用于初次训练 |
| **实时事件摄取（PutEvents API）** | 应用实时上报用户交互事件（点击、购买等），供 Personalize 结合近期行为动态调整推荐结果 |
| **流式数据集成** | 可结合 [[Amazon Kinesis]] 将实时行为事件流式传输后接入 Personalize |

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以管理数据集组、推荐器/活动，以及调用推荐 API |
| **静态加密** | 数据集和模型产物默认加密存储 |
| **传输加密** | API 调用默认通过 HTTPS/TLS |
| **VPC Endpoint** | 支持通过接口终端节点在 VPC 内私有调用 API |

## 典型应用场景

| 场景 | 推荐配置 |
|------|---------|
| **电商网站的"猜你喜欢"个性化推荐** | Domain Dataset Group（ECOMMERCE）+ 用户个性化推荐器 |
| **视频流媒体的内容推荐** | Domain Dataset Group（VIDEO_ON_DEMAND）+ 相关物品/用户个性化推荐器 |
| **商品详情页的相似商品推荐** | Related Items 推荐类型 |
| **新用户/新商品的冷启动兜底** | Trending/Popular 推荐类型 + 物品元数据补充 |
| **离线批量生成邮件营销推荐列表** | 自定义数据集组 + Batch Recommendations（而非 Domain 推荐器） |
| **对话式推荐体验** | Personalize + Amazon Lex 集成 |
| **物品元数据缺失导致推荐效果差** | 结合 Bedrock 自动生成物品描述/合成元数据 |

## 考试重点总结

### 高频考点

1. **核心定位**：全托管个性化推荐服务，基于用户-物品交互数据，使用与 Amazon.com 相同的推荐技术
2. **唯一必填数据集**：用户-物品交互数据；物品/用户元数据为可选增强项
3. **Domain Dataset Group vs 自定义数据集组**：前者预配置（ECOMMERCE/VIDEO_ON_DEMAND），快速上线；后者手动选择 Recipe，更灵活
4. **推荐器只支持实时推荐**：Domain Dataset Group 下的 Recommender 不支持批量推荐，批量场景需用自定义数据集组
5. **自动重新训练周期**：Domain 推荐器默认每 7 天基于全部数据自动重新训练
6. **每区域最多 15 个推荐器**：容量限制的考试细节
7. **常见推荐类型**：用户个性化、相关物品、热门商品、最近浏览，分别对应不同业务场景
8. **v2 Transformer 架构**：新一代算法，准确率更高、支持更大目录、按请求计费，已有部署应评估迁移
9. **PutEvents 实时事件摄取**：应用可实时上报交互事件，让推荐结果动态反映近期行为
10. **与 Bedrock/Lex 集成**：分别用于缓解元数据缺失的冷启动问题、构建对话式推荐界面

### 场景题解题思路

```
场景分析 → 判断是否用 Personalize
├── "基于用户历史行为生成个性化商品/内容推荐" → Amazon Personalize
├── "标准电商/视频点播推荐场景，希望快速上线" → Domain Dataset Group
├── "需要离线批量生成推荐列表（如营销邮件）" → 自定义数据集组 + Batch Recommendations
├── "新用户/新商品缺乏交互数据（冷启动）" → Trending/Popular 推荐类型 + 补充物品元数据
├── "商品详情页需要展示相似商品" → Related Items 推荐类型
├── "希望推荐结果实时反映用户最新行为" → PutEvents API 实时事件摄取
├── "物品元数据不完整，影响推荐效果" → 结合 Amazon Bedrock 自动生成/补充元数据
└── "需要完全自定义的推荐算法逻辑" → 改用 Amazon SageMaker（而非 Personalize）
```

## 最佳实践

1. **标准电商/流媒体场景优先使用 Domain Dataset Group**：无需自选算法即可快速获得针对性优化的推荐效果
2. **尽可能提供物品/用户元数据**：虽非必填，但能显著缓解冷启动问题、提升推荐质量
3. **批量推荐需求提前规划为自定义数据集组**：避免误用 Domain 推荐器（仅支持实时）导致架构返工
4. **接入 PutEvents 实现实时行为反馈**：让推荐结果动态响应用户最新交互，而非仅依赖历史批量数据
5. **已有早期 Recipe 部署评估迁移到 v2 架构**：获得更高准确率和更简化的配置，同时留意计费模式变化
6. **冷启动场景结合 Trending/Popular 兜底策略**：避免新用户/新商品完全没有可用推荐结果
7. **元数据缺失场景评估 Bedrock 集成**：自动生成物品描述可加速数据准备，降低人工整理成本
8. **推荐结果的调用权限遵循最小权限原则**：通过 IAM 精确控制哪些应用组件可以调用推荐 API
