# Amazon Comprehend - 自然语言处理服务

> **Amazon Comprehend** 是全托管的**自然语言处理（Natural Language Processing, NLP）**服务，使用机器学习从非结构化文本中提取语义洞察——包括情感倾向、命名实体、关键短语、语言种类、敏感信息（PII）等，无需自行训练 NLP 模型。
>
> 相关文档：[[Amazon Comprehend Medical]] | [[Amazon Transcribe]] | [[Amazon Translate]] | [[Amazon Lex]] | [[Amazon SageMaker]] | [[S3]] | [[AWS Lambda]] | [[Aurora]] | [[IAM]] | [[KMS]]

---

## 核心概念

### 为什么需要 Comprehend

- **非结构化文本的价值挖掘难题**：客户评论、客服工单、社交媒体内容、法律合同等大量文本数据蕴含业务洞察，但传统关键词匹配无法理解语义、情感和上下文
- **Comprehend 的核心价值**：提供**预训练的语义分析能力**，通过 API 调用即可从文本中提取结构化信息（情感、实体、关键短语等），并支持 **自定义分类（Custom Classification）** 针对特定业务场景做轻量定制，无需从零训练 NLP 模型
- **在 AWS AI 服务栈中的定位**：与 [[Amazon Rekognition]]（视觉）、[[Amazon Transcribe]]（语音转文本）类似，Comprehend 是**开箱即用、面向"文本语义理解"这一特定任务**的托管 AI 服务，通常作为其他服务（Transcribe 转录结果、S3 中的文档）的**下游语义分析层**

### Comprehend 在 SAA-C02 考试中的定位（考试要点）

| 服务 | 处理对象 | 核心能力 | 典型场景 |
|------|---------|---------|---------|
| **Comprehend** | 文本 | 情感分析、实体识别、关键短语提取、PII 检测 | 客户评论/工单的语义洞察、敏感信息合规检测 |
| [[Amazon Transcribe]] | 音频 | 语音转文本 | 通常是 Comprehend 的**上游**，先转录再分析 |
| [[Amazon Translate]] | 文本（跨语言） | 语言翻译 | 与 Comprehend 是不同维度：一个翻译语言，一个理解语义 |
| [[Amazon Lex]] | 语音/文本对话 | 意图识别、对话管理 | 面向"完成任务型对话"，而非"批量分析已有文本" |

> **考试陷阱**：题目描述**"需要从客服通话记录中提取客户情感倾向、常见投诉主题"** → 标准架构是 **[[Amazon Transcribe]]（转录）+ Amazon Comprehend（语义分析）** 的组合管道，而非单独用其中一个服务就能完成；题目若只问"如何把语音转成文字"，答案是 Transcribe；若问"如何从已有文本中提取情感/实体"，答案才是 Comprehend。

## 核心能力

| 能力 | 说明 |
|------|------|
| **情感分析（Sentiment Analysis）** | 判断文本的情感倾向：正面、负面、中性或混合 |
| **实体识别（Entity Recognition）** | 识别文本中的命名实体，如人名、地点、组织、日期、数量等 |
| **关键短语提取（Key Phrase Extraction）** | 提取文本中最重要的短语，快速概括文本主题 |
| **语言检测（Language Detection）** | 自动识别文本使用的语言 |
| **语法分析（Syntax Analysis）** | 识别词性（名词、动词等）及词与词之间的语法关系 |
| **PII 识别与脱敏（PII Detection & Redaction）** | 检测并可自动遮盖文本中的姓名、地址、电话、邮箱、社保号、信用卡号等个人敏感信息 |

> **考试要点**：处理**医疗/临床文本**（病历、诊断记录）时，应优先使用专为医学语料训练的 **[[Amazon Comprehend Medical]]**，而非通用 Comprehend——通用模型未针对医学术语优化，也不具备 PHI（受保护健康信息）检测和 ICD-10-CM/RxNorm 等医学编码关联能力。

> **考试要点**：**PII Detection & Redaction 是满足 GDPR、HIPAA 等合规要求的关键能力**——题目描述"需要在存储或共享文本数据前自动识别并遮盖其中的个人敏感信息以满足合规要求" → 答案是 Comprehend 的 **PII 识别与脱敏**功能。

---

## 自定义能力

| 功能 | 说明 |
|------|------|
| **自定义分类（Custom Classification）** | 基于用户提供的标注样本，训练能将文本分类到特定业务类别（如工单类型：账单问题/技术故障/退款请求）的轻量模型 |
| **自定义实体识别（Custom Entity Recognition）** | 识别标准预训练模型未覆盖的特定业务实体（如产品型号、内部项目代号） |

- 两者都基于**少量标注数据做迁移学习**，相比从零训练完整的 NLP 模型，大幅降低数据量和机器学习专业知识门槛，与 [[Amazon Rekognition]] Custom Labels 的设计理念一致

---

## 功能可用性变化（考试提示）

> **考试提示**：**Amazon Comprehend 的主题建模（Topic Modeling）、事件检测（Events Detection）、提示安全分类（Prompt Safety Classification）功能自 2026 年 4 月起停止向新客户开放**，情感分析、实体识别、关键短语提取、语言检测、语法分析、PII 检测等核心能力不受影响，仍是标准功能。规划新架构时应关注功能的当前可用范围。

## 处理模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **实时分析（Synchronous）** | 单条文本同步调用 API，立即返回分析结果 | 单条评论/消息的实时情感判断 |
| **批量分析（Asynchronous Batch）** | 提交存储在 [[S3]] 中的大批量文档，异步处理后写回结果 | 海量历史文本（客服工单存档、评论库）的批量语义分析 |

## 架构与集成（考试高频）

| 集成方式 | 说明 |
|---------|------|
| **[[Amazon Transcribe]] + Comprehend** | 语音转文本后进一步做情感/实体分析，构成"语音 → 文本 → 语义洞察"的完整管道，常用于客服通话质检 |
| **S3 触发批量分析** | 文档上传到 [[S3]] 后，通过事件通知触发 [[AWS Lambda]] 调用 Comprehend 批量分析 |
| **[[Aurora]] 机器学习集成** | Aurora 支持直接在 **SQL 语句中调用 Comprehend**（及 [[Amazon SageMaker]]）做预测分析，无需将数据导出到应用层再调用 API |
| **合规数据处理管道** | Comprehend PII 检测作为数据入湖前的预处理步骤，自动脱敏后再落地存储或供下游分析使用 |

## 安全性

| 机制 | 说明 |
|------|------|
| **IAM 策略** | 控制哪些身份可以调用 Comprehend API、访问哪些自定义模型 |
| **静态加密** | 批量分析输出到 S3 的结果可使用客户管理的 [[KMS]] 密钥加密 |
| **传输加密** | API 调用默认通过 HTTPS/TLS |
| **VPC Endpoint** | 支持通过接口终端节点在 VPC 内私有调用 Comprehend API |

## 考试重点总结

### SAA-C02 高频考点

1. **核心定位**：预训练的 NLP 服务，从文本中提取情感、实体、关键短语等语义洞察
2. **判断依据**：处理对象是"已有文本"且需要"理解语义"时选 Comprehend；语音转文字用 Transcribe，跨语言翻译用 Translate
3. **常与 Transcribe 组合**：客服通话质检的标准架构是 Transcribe（转录）+ Comprehend（语义分析）
4. **PII 识别与脱敏满足合规要求**：GDPR/HIPAA 等场景的标准解法，无需自行开发脱敏逻辑
5. **自定义分类 vs 自定义实体识别**：前者给文本打业务类别标签，后者识别预训练模型未覆盖的特定实体
6. **实时 vs 批量分析**：单条文本实时判断用同步 API；海量历史文本用异步批量分析
7. **可与 Aurora 直接集成**：在 SQL 语句中调用 Comprehend 做预测分析，无需应用层额外调用
8. **部分功能已对新客户关闭**：主题建模、事件检测、提示安全分类自 2026-04 起限制新客户接入，核心 NLP 能力不受影响
9. **自定义能力基于少量标注数据迁移学习**：无需海量数据即可训练轻量定制模型，与 Rekognition Custom Labels 理念一致
10. **常作为数据管道的语义分析层**：位于 Transcribe/S3 文档等数据源的下游，而非独立的数据源

### 场景题解题思路

```
场景分析 → 判断是否用 Comprehend
├── "需要从已有文本中提取情感倾向/关键主题/实体" → Amazon Comprehend
├── "需要先把语音转成文字，再做语义分析" → Transcribe（转录）+ Comprehend（分析）组合
├── "文本数据落地前需要自动识别并遮盖敏感信息" → Comprehend PII 识别与脱敏
├── "客服工单需要按问题类型自动分类" → Comprehend 自定义分类
├── "需要识别标准模型未覆盖的特定业务实体" → Comprehend 自定义实体识别
├── "需要在数据库查询中直接调用 NLP 分析" → Aurora 机器学习集成 + Comprehend
├── "海量历史文本需要批量做语义洞察分析" → Comprehend 批量分析（异步）
└── "需要跨语言翻译文本，而非理解语义" → 改用 Amazon Translate（而非 Comprehend）
```

## 最佳实践

1. **明确"理解语义"与"转换格式"的区别**：语音转文字用 Transcribe，跨语言翻译用 Translate，语义分析才用 Comprehend
2. **客服质检场景搭建标准三段式管道**：语音 → Transcribe 转录 → Comprehend 情感/实体分析，避免重复造轮子
3. **合规敏感场景优先启用 PII 脱敏**：作为数据入湖或共享前的标准预处理步骤，而非事后补救
4. **细分业务分类场景评估自定义分类**：用少量标注数据即可获得针对性效果，无需通用机器学习平台级别投入
5. **实时场景用同步 API，海量存量数据用批量分析**：按数据规模和延迟要求选择合适的处理模式
6. **规划依赖主题建模/事件检测的新架构前确认可用性**：这些功能已对新客户关闭，避免设计依赖受限功能的方案
7. **数据库内分析场景评估 Aurora 集成**：减少数据在应用层和 AI 服务之间往返的开销
8. **批量分析结果加密存储**：涉及客户反馈、通话记录等敏感文本的分析结果应在 S3 中启用 KMS 加密
