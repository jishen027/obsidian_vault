# Lifetimes - Making Sure References Never Dangle

> A **lifetime** is the stretch of code in which a reference is valid. C# and JavaScript never make you think about this: the GC keeps an object alive as long as anything still points to it. Rust has no GC, so the compiler has to **prove** that every reference dies before the data it points to.
>
> Related notes: [[01. Introduce Rust]] | [[02. Ownership & Borrowing]] | [[04. Structs & Enums]]

---

## Why Lifetimes Exist

### The problem: dangling references

```rust
fn main() {
    let r;
    {
        let x = 5;
        r = &x;           // ❌ E0597: `x` does not live long enough
    }                     // x dropped here
    println!("{r}");      // r would point to freed memory
}
```

```rust
fn dangle() -> &String {          // ❌ E0106: missing lifetime specifier
    let s = String::from("hi");
    &s                            // s is dropped when the function returns
}

fn no_dangle() -> String {        // ✅ fix: return the owned value (move it out)
    String::from("hi")
}
```

### How C# / JS avoid this (and what it costs)

| | C# / JavaScript | Rust |
|---|----------------|------|
| Returning a reference to a local object | ✅ Fine: the GC keeps it alive | ❌ Compile error, unless you return the owned value |
| Closure capturing a local | GC extends the variable's life | Must `move` the value into the closure, or the closure must not outlive it |
| Cost | GC runtime, unpredictable pauses | Zero runtime cost; the compiler does the bookkeeping |
| Closest C# feature | **`Span<T>` / `ref struct`**: these can't be stored in heap fields or escape the method | All references follow similar rules, enforced everywhere |

> **Key point**: Lifetime annotations **don't change** how long anything lives. They only **describe** relationships between references so the compiler can check them. Think of them as generic type parameters, but for scopes.

## Lifetime Annotations

### Syntax

```rust
&i32          // a reference
&'a i32       // a reference with explicit lifetime 'a
&'a mut i32   // a mutable reference with explicit lifetime 'a
```

Lifetime names start with an apostrophe and are usually short: `'a`, `'b`.

### The classic example: `longest`

```rust
fn longest(x: &str, y: &str) -> &str {     // ❌ E0106: is the result tied to x or y?
    if x.len() > y.len() { x } else { y }
}
```

The compiler can't tell which input the returned reference borrows from. Annotate it:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Read it as: *"The returned reference is valid for as long as **both** `x` and `y` are valid."* In practice that means the shorter of the two.

```rust
fn main() {
    let s1 = String::from("long string");
    let result;
    {
        let s2 = String::from("xyz");
        result = longest(&s1, &s2);
        println!("{result}");          // ✅ s2 still alive here
    }
    // println!("{result}");           // ❌ s2 dropped; result might point to it
}
```

C# comparison: it's like a generic constraint. `T Longest<T>(T x, T y)` ties the return **type** to the inputs; `'a` ties the return **lifetime** to the inputs.

## Lifetime Elision: Why You Rarely Write Them

Most functions need no annotations, because the compiler applies three **elision rules**:

| Rule | What it does | Example |
|------|-------------|---------|
| **1** | Each reference parameter gets its own lifetime | `fn f(x: &str, y: &str)` → `fn f<'a, 'b>(x: &'a str, y: &'b str)` |
| **2** | If there's exactly **one** input lifetime, outputs get it | `fn first(s: &str) -> &str` ✅ no annotation needed |
| **3** | If one parameter is `&self` / `&mut self`, outputs get `self`'s lifetime | `fn name(&self) -> &str` ✅ no annotation needed |

> **Key point**: You only need explicit lifetimes when a function takes **several** reference parameters, returns a reference, and isn't a method. `longest` is the textbook case.

## Lifetimes in Structs

A struct that **holds a reference** must declare a lifetime, so the struct can't outlive the data it borrows:

```rust
struct Excerpt<'a> {
    text: &'a str,
}

impl<'a> Excerpt<'a> {
    fn first_word(&self) -> &str {           // elision rule 3
        self.text.split(' ').next().unwrap_or("")
    }
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let ex = Excerpt { text: &novel };
    println!("{}", ex.first_word());
}   // ex must be dropped before (or with) novel ✅
```

### Beginner advice: prefer owned fields

```rust
// Harder: borrows; lifetimes spread to every user of the struct
struct UserRef<'a> { name: &'a str }

// Easier: owns its data, like a C# class with a string property
struct User { name: String }
```

> **Key point**: When you start out, give your structs **owned** fields (`String`, `Vec<T>`). Use reference fields later, when you have a performance reason (e.g. zero-copy parsers).

## The `'static` Lifetime

`'static` means the data lives for the **entire program**.

```rust
let s: &'static str = "hello";   // string literals are baked into the binary
```

| Where you'll see `'static` | Meaning |
|---------------------------|---------|
| `&'static str` | String literal / compile-time constant |
| `T: 'static` bound (e.g. `thread::spawn`) | `T` holds **no non-static references**; owned data like `String` qualifies |

> **Trap**: If the compiler suggests adding `'static`, it's usually **not** the right fix. The real fix is to own the data (`String` instead of `&str`) or to `move` it.

## Cheat Sheet

```
Compiler says "missing lifetime specifier"?
├── Can I return an owned value (String, Vec)?   → do that (simplest)
├── Returned ref comes from ONE input?            → annotate that input + output with 'a
├── Struct holds a reference?                     → struct Foo<'a> { x: &'a T } (or own the data)
└── Thread / async task complains about lifetime? → `move` owned data in, or use Arc (see [[07. Concurrency]])
```
